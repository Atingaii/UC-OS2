# 第154步：连接原 tick 的 post-hook 运行路径

## 这一步解决什么

上一阶段已连接完整任务链 `while`，但入口已经把局部扫描指针放在链头，也没有把本次时钟递增一起纳入那个端点。本步不再增加一种执行模型，而是直接复用既有 `V293_tick_post_hook_owned_execution`，在同一个实际输出内存 `Mf` 中连接：

1. 进入时钟临界区，实际读取并递增 `OSTime`，退出临界区；
2. 严格检查 `OSRunning == 1`；
3. 实际执行 `ptcb = OSTCBList`，不预设旧 `ptcb` 已经正确；
4. 执行原完整 `while`，包含每次迭代的进入／退出临界区与 idle 终止；
5. 重建同一 `Mf` 的任务记录、ready bitmap、13项优先级表及共享时钟关系。

稳定生产接口是 `certiucos/v293/proofs/V293TimeTickPostHookReady.v` 中的 `V293_tick_post_hook_ready_payload`。抽象端按原有语义先执行 `V293_tick_clock_action`，再执行既有有序 `V293_tick_chain_code`；不是直接假设一个正确的最终状态。原来的 `ready_rel`、`ready_payload` 和原始执行关系均保持，不创建平行生产不变式。

消融没有执行修改后的 C 程序，也不宣称覆盖任意代码故障。它检查的是原执行之后只改动一个关系因素的对照。初始 `ptcb=idle` 是非空正向覆盖，不冒称已经执行“删除初始化语句”的 mutant。

## 准确边界

- 这是原 post-hook **运行分支**的无交错端点连接，不是 `OSTimeTick` 整函数或任意交错 Hoare 定理。
- 执行关系作用于既有手工建模的冻结 AST；本步核对源码身份，但没有新增或证明 C 前端翻译。独立 Coq 内核检查也不等于检查 C 编译器。
- 本接口尚未连接 `cpu_sr=0`、CPU hook、局部声明／分配和返回；已有第34步前缀／返回检查点不会自动拼成一条跨 hook 的连续调用。固定 AST 明确保留 hook，不能拿本步当作 hook 已通过。
- 支持任意有限合法未挂起链，不局限于探针中的三个非idle节点；仍不支持挂起／flags 的全关系连接。
- 本接口的任意初始扫描值指 `Vptr scan`，不包含真实新分配局部对象的 `Vundef`；尚未接到既有第33／34步的原始局部分配／返回检查点。
- 旧任务记录由同一入口原始字段与额外字段推导；没有多要求一份相同可写记录。优先级表作为分离 frame 只拥有一次。
- 非空事件表只是保持的数据，不是已证明 event／TCB 队列一致。tick 超时原代码写独立的 `OS_STAT_PEND_TO`，这里不伪造 ECB 删队列步骤。
- 探针继承的初始 pend 字节7是类型合法的边界值，不声称是生产初始化可达状态；入口可满足不等于系统启动可达。
- 从等待态变为 ready 也可能因为超时，不等于收到消息，更不等于等待操作成功。
- 不是逐物理小步精化模拟；抽象 `clock + chain` 和物理完整后缀共享端点，不能据此宣称全部交错或ISR成立。

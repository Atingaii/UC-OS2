# 第83步：从真实调用入口保留任务记录直到条件返回

## 本步究竟补上什么

上一步从局部对象已经分配、`cpu_sr` 已写入0之后开始。本步将这个入口向前接到真正的 `sfexec OS_TCBInit`：调用者提供实参，语义实际分配7个形参对象与2个局部对象，初始化 `cpu_sr`，再进入原来的初始化／发布链。不是在入口预先放置这9个对象。

新增生产文件：`certiucos/v293/proofs/V293CallRecords.v`。
稳定接口：`V293_OS_TCBInit_call_return_records_under_hooks`。

成功分支的同一条执行链为：

```
调用者内存（没有这9个局部块）
→ sfexec／分配9对象／写入实参／cpu_sr=0
→ 从空闲TCB链表取出新TCB
→ 18次字段初始化，建立新任务记录并保留旧记录
→ 第一个真实Hook（仍需兑现执行／资源契约）
→ 写入优先级表
→ 第二个真实Hook（仍需兑现执行／资源契约）
→ 发布到任务链表、就绪位图和任务计数
→ return 0，恢复调用者，释放9对象共29字节
```

最后是一个 `exists Mf`：同一个末态同时拥有全部任务记录、剩余初始化字段、优先级表／空闲链表／发布结果和哨兵，并具有29字节实际释放事实。没有把不同执行的弱后置条件拼在一起。

## 为何需要可逆的原始单元视图

既有真实调用分配定理接受原始单元所有权，而本步入口还持有已有任务记录。直接丢弃记录的纯条件后再“造回”记录会丢失优先级、等待结果和类型信息。

`V293_task_list_raw_view` 从实际记录提取 `p`、`pend`、边界与每个单元的类型有效性，保留原空间片段；返回一个对任意后续frame都有效的重建蕴含。分配过程中运输的是同一批单元，随后使用原见证重建记录。没有重复写权限，也没有额外预设旧记录的物理副本。反向frame搬运仅交换分离合取的次序。

通用定理不把旧记录限定为ready，布局仍由原status决定；独立字面实例只包含一个ready旧任务。不能把这个实例说成已经分别测试了所有等待／事件状态。

## 独立验证入口

`audit/probes/V293CallRecordsProbe.v` 不导入旧probe：

- 35个类型单元、85字节；新TCB的18个目标字段全部为 `Vundef`。
- 入口完全没有201–209这9个局部块，`CallNoInitialLocals` 对每个块的所有偏移证明读取为 `None`，从而推出真实fresh前提。
- 旧、新任务分别是 `(301,8)` 与 `(301,128)`，共用block、偏移不同；旧任务优先级12，新任务优先级11，原任务链非空。
- 调用者有自己的环境，不能把函数局部环境当作调用者环境；这里只核对其恢复，未证明完整调用者Inv。实例中的栈指针实参为NULL，仅验证本函数的存储／资源行为，不是可安全调度的完整任务实例。
- `CallPrologue` 从真实调用分配对象；`CallPrefix` 无需Hook返回契约即可运行到首个Hook并建立两份记录。
- `CallGoodSameMf` 在两个显式Hook契约下，对同一Mf保留联合资源、语义记录、11项实际读取和全部释放事实。
- `CallFixtureProgram` 真正绑定函数900到当前函数模型，901／902均无实现；`CallMissingHookFixture` 从可满足的字面调用入口实际走到缺失的首Hook，并证明它不能返回。这里不授予任何下游执行信用。
- `CallPrefixExcludesWrong` 对实际prefix末态排除新任务优先级10。另一个前瞻冻结的控制只将完整条件调用后置中的新优先级11改成10，程序、入口、两个Hook契约、frame、释放条件与证明体不变。正例接受、错误后置拒绝；这只是同证明体敏感性，不是所有证明均不可成立的结论。

## 编译故障与对抗性复核

所有失败尝试及对应源快照保留。首个probe编译在展开大量字面单元的分离逻辑重排处长时间消耗CPU，主动中断且不授证明信用；后续保留18字段为一个原始单元列表，只在外部交换空间片段，再展开9个局部单元。最终通过的是相同语义目标，不是减弱后置条件或移除记录。其他故障包括缺少显式导入、列表尾／frame化简及生成字符串的合取符号错误。

复核中保留的限制：

1. 两个Hook仍是开放的真实执行／资源保持契约，尚无具体实现实例，未建立完整成功链的无条件非空性。缺失Hook实例只证明前缀可达与阻塞。固定配置是 `OS_CPU_HOOKS_EN=1`、`OS_APP_HOOKS_EN=0`；当前checkout只有Cfg／Source，CPU Hook函数体未定位，不能因应用hooks关闭就把这两个CPU调用偷偷改为空函数。见 `hook-boundary-observation.json`。
2. 仅接通非空空闲TCB成功分支；没有在本步统一空链表失败分支与成功分支的Hoare接口。
3. 释放条件显式要求幸存任务／单元与局部块分离；没有声称这是最弱的偏移级条件。
4. 任务map是规格参数；真实抽象状态 `O` 未更新。只运输有限的内存资源，不运输任意依赖局部环境的断言。
5. 这是存在的、无交错执行链，不是对所有中断交错的安全证明；不是 `local_hoare`／`WFIFun`／`GOOD_OS`。
6. 初始化记录覆盖的44字节不是56字节完整TCB所有权；尚未完成完整OSInit、启动与全局Inv组合，也未完成同程序K1–K4，uCOS3未开始。

## 为什么先做这个函数

前两步分别执行了真正的 `OS_InitMisc` 和 `OS_InitRdyList`。接下来建立 TCB 空闲链时，固定源码的 `OS_InitTCBList` 先调用 `OS_MemClr` 清除 TCB 数组及优先级指针表。不能跳过这些调用、直接假设数组已初始化。

本步因此先证明实际清零循环。最终验收仍是初始化相连的同一固定程序 `GOOD_OS` 与 K1–K4，之后才做 uCOS3；本步只是该路径上的进展，不是整核完成。

## 生产接口及精确边界

代码：`certiucos/v293/code/V293OSMemClr.v`；证明：`certiucos/v293/proofs/V293MemClr.v`。

1. `V293_OS_MemClr_loop_execution`：对任意旧值列表（可含 `Vundef`），长度不超过65535，偏移非负且最终偏移不超过 `Int.max_unsigned`，给出实际目的指针／计数绑定以及分离可写参数单元和全部目标字节，推导真实循环执行及同一个最终内存的完整结果。指针到范围末端、计数为0、原范围全部置零、任意同环境分离 frame 保留。写入成功来自所有权，不是输入的 store oracle。
2. `V293_OS_MemClr_zero_size`：只需要计数参数为0及其存储，不需要目的指针绑定、指针值或目的存储。它单独检查空范围确实不读目的指针，避免通用非空入口掩盖该边界。

递归证明把刚清零的一个字节移入 frame，对剩余字节应用归纳假设，再恢复原顺序。长度结论覆盖整个16位参数范围，不是仅证明三字节示例。参数及目标的独占分离所有权排除了别名重叠；不声称重叠写入也满足同一结论。偏移限制也明确排除了地址回绕。

**这里仅证明已分配参数单元上的循环体、无交错存在性执行轨迹。** 尚未证明 scall 传参／分配／free／return、`local_hoare`、任意交错下所有执行安全或完整 API 生命周期；函数 AST 包含 `sret` 不等于已执行完整函数返回。

## 新发现：清零字节不能直接当作空指针

`ClrZeroBytesNotNull` 对当前框架实际定义同时证明：

1. 四个8位零值的编码拼接，按指针解码得到 `Vundef`。
2. 指针类型的 `Vnull` 编码可解码为 `Vnull`。
3. 上述两种编码不相等：当前零字节是 `Byte 0`，空指针是四个 `MNull`。
4. 在实际有限零字节堆上执行指针 `load` 得到 `Some Vundef`，不只是展示一个解码等式。

最后一项通过现有 `mapstoval`／`ptomvallist_loadbytes` 连接实际内存读取；没有把 load 返回值设为假设。该实例是**隔离的表示反例**，不是 `OS_InitTCBList` 的完整执行反例，也不表明真实 C 内核存在这一缺陷。它说明当前模型无法直接把 `OS_MemClr` 的字节后置条件当作已建立指针表的 `Vnull` 所有权。

本步不修改既有内存模型、不加公理、不补写额外 C 语句，也不绕开该缺口。下一步应先提出最小、可复现且有兼容性检查的表示处理，再连接 TCB 初始化。仅把断言改成“表已经是空指针”会循环论证；改变解码规则则必须重新检查相关规则和 soundness，不能只重编译这个新文件。

# 第75步：补齐空语句健全性，连接 OS_InitMisc 的 Hoare 证明

## 本步为什么做这个

整核目标要求函数证明进入同一框架，而不是持续增加“存在一条成功路径”的条件定理。`OS_InitMisc` 已有真实十次清零和调用返回的执行证明，本步补足其 `InfRules` 推导与 `RuleSem` 语义连接。

检查发现现有模型包含行政空尾 `sskip None`，框架对应规则却只有历史注释。本步保留现有函数模型及其原执行定理，先独立证明空语句规则的语义健全性，再恢复规则并扩展 `RuleSound`。详见 [ADR-0008](../docs/adr/0008-空语句规则须有语义健全性证明.md)。

## 新增证明接口

文件：[V293InitMiscHoare.v](../certiucos/v293/proofs/V293InitMiscHoare.v)。

- `V293_init_one_hoare`：从可写的旧值／未定义值资源证明一次真正的清零赋值。
- `V293_init_sequence_hoare`：顺序组合任意合法标量清零序列，不删除终端空语句。
- `V293_OS_InitMisc_body_hoare`：完整十字段清零、空尾和 void return 的框架推导；保留 frame，返回值为 `None`。
- `V293_OS_InitMisc_body_semantics`：通过更新后的 `RuleSound` 得到同一函数体的 `RuleSem`，不是另造一套 Hoare 逻辑。

源码重新物化并由 Clang 预处理／提取，全部94个函数身份与冻结清单一致。`OS_InitMisc` 的配置后函数体 SHA256 为 `c46412d3e2adca015c1f5b24cfa1afc39456df56864665a2a2b82c210f7560f8`，确为10条零赋值且顺序、类型逐项检查。C、配置、两类修复及原初始化模型未改变；仍是手工源码映射，不声称已经验证 C 前端。

## 如何理解这一步

1. 原执行定理证明可以沿实际操作语义完成清零；它不是所有交错执行都安全的声明。
2. 新 Hoare 定理从真实所有权推出后置条件，且实际使用框架的赋值、顺序、空语句、返回规则；没有以“请先证明同一函数 Hoare”作为前提。
3. `RuleSound` 把这种推导接到框架方法仿真语义。新空语句规则也必须独立证明这一点，不能只添加构造器。
4. 后续仍需要满足真实函数规格构造器、统一函数环境、全局／局部不变量及顶层连接，才能使用 `verified_os'` 得到具体的 `GOOD_OS`。

## 明确边界

- 新接口要求保留的 `R` 真正蕴含 `CurLINV li tid`。没有假装启动前存在当前任务，也没有从启动状态推出该前提。
- 独立字面 fixture 构造可满足的10个旧单元、当前任务指针、哨兵和抽象资源，排除单纯使用 `Afalse` 的真空前置条件；使用空局部不变量只是测试 fixture。
- 该 fixture **不实例化真实内核运行态全局 `Inv`**，也不证明该全局不变量与初始化所有权可同时满足。不能据此声称实际启动／运行态已经接通。
- 没有补齐 `BuildPreI`／`BuildRetI` 内部规格、完整94函数 `WFIFun`、五个端口边界或同程序 K1–K4。
- 既有第57步已证明七个初始化调用在同一内存中连续执行。旧状态文字把这件事继续列为开放项过时；真正未完成的是完整 `OSInit`、idle/stat 任务、Hook、运行态不变量与顶层统一程序的连接。
- 六门覆盖保持 `94 / 1 / 1 / 1 / 1 / 0`；不把本次未注册的 Hoare 接口自动计入覆盖，不启动 uCOS3。

# 第316步：高优先级当前任务的源码级延时阻塞片段

## 为什么做这一步

第315步证明的是**已经恢复 current 的 pending-return 入口**的返回后缀，不证明旧任务如何重新获得执行权。当前例子中，Ready 的优先级为4，Waiting的优先级为6；数值越小优先级越高。因此即使优先级6真正醒来，只要4仍就绪，6也不能被选中。不能直接赋值 current，更不能把纯标量 continuation 执行结束误当成任务合法阻塞。

本步补上一个必要的源码动作：当前高优先级任务执行 `OSTimeDly` 的临界区更新，从就绪位图撤出，并写入非零延时。它是回切链的一段，**不是完整回切**。

## 实际已证明的内容

生产稳定接口是 `V293_OSTimeDly_blocking_bridge`，导出同一末端堆上的：

1. 原框架 `cstepstar` 执行临界区更新，而不是把执行成功当输入。
2. 从所有权推导实际 store 成功：设置局部 `y`、清当前任务就绪位、必要时清组位、写 `OSTCBDly=ticks`；两个空 trace 展开保持为 SKIP。
3. 精确更新后的单元所有权与任意外部 spatial frame；frame 不是事后另找一块堆。
4. 原 `V293_task_record` 中当前任务为 `wait os_stat_time duration`，优先级与消息保持。
5. 清除后的位图与投影任务表对应、优先级表关系保持，当前任务不再就绪、不能再是最高就绪任务。

函数入口条件包括任务优先级小于13、两个位图字节范围、TCB地址界、环境映射、类型正确的局部单元与相应可写所有权。接口的非零 `duration` 限定正延时片段；**没有反向证明完整函数已通过 guard**。局部 `y` 的探针初值是已类型化的0，不是从完整函数的未初始化局部分配推导出来的前置。

`V293_OSTimeDly_before_delay_execution` 单独给出写延时前的真实前缀以及原延时字段不变，供下述单因素对照复用。前缀拆分只改变 sequence 分组，不增删 C 语句。

`ablation-protocol.json` 在实现消融前冻结。唯一因子：把最后 `OSTCBDly=ticks` 赋值换为 SKIP；同一初始堆、就绪位图更新前缀、continuation、trace SKIP和末端延时=3门均不变。

- 基线：整个片段实际执行，就绪行=64、延时=3，末端门通过。
- 消融：整个变体片段同样实际执行，就绪行仍=64、延时=0，末端门失败。
- 失败上下文同时保留 `Executed : cstepstar`、`ActualDelay` 和 `ClearedRow`，不是名字查找、语法错误或前缀未执行造成的早拒绝。

# 第323步：真实延时调用接通阻塞更新与临界区退出

## 本步要解决什么

第322步已从真正的 `scall OSTimeDly(3)` 构造参数和局部分配、CPU初始化、入口判断、进入临界区，以及未初始化 `y` 的首次实际赋值。本步从该末端继续，不重跑整个 body，不重复 guard、`encrit` 或 `y` 写入。

最小闭环如下：

`实际调用 → 分配/初始化 → 判断/进入临界区 → y首次赋值 → 清除就绪位 → 条件更新组位 → 写入延时 → excrit → OS_Sched调用前`

这里只完成**有限局部执行的正分支**。不是完整 API，不是全局记录不变量，不是全局 ProgSim，也不是 `GOOD_OS`。此前已证明过的其他调度片段不能因名字相同而直接拼接；两边必须具有同一程序、环境、堆和 continuation。

## 源码身份

固定 uC/OS-II V2.93.01、上游提交 `0c4a48e6fbc6e915714e816196619a5481accf0c` 和原配置，仅保留范围文件授权的两类修复。`source.py` 独立重建修复源码并重新预处理，核对 `OSTimeDly`、`OS_Sched`、`OS_SchedNew` 三个函数的源码与配置后哈希；六份函数快照和身份记录位于 `audit/logs/stage323-time-delay-call-block/`。没有修改 C、函数覆盖清单或旧冻结证据。

## 新证明接口

生产文件：`certiucos/v293/proofs/V293TimeDlyTail.v`。

| 接口 | 从什么开始 | 真正证明的结果 |
| --- | --- | --- |
| `V293_dly_after_y_execution` | 已完成首次y赋值的堆及所有权 | 实际清行位、条件清组位；延时仍是旧值 |
| `V293_dly_after_y_updates` | 同一首赋值末端 | 在上述执行后实际写入 `ticks`；不重启更新函数 |
| `V293_dly_after_y_refines` | 同堆物理记录、任务表和共享字段所有权 | 同一末端堆上的全部任务记录、优先级表、位图关系和原框架 `spec_step` |
| `V293_dly_after_y_to_sched_refines` | 实际临界区辅助状态和原 continuation | 接通阻塞更新、实际 `excrit`，恢复进入前 IE，止于调度调用前；供上层消费的稳定接口 |

写入所需内存操作从所有权构造，不把“执行已经成功”或“存在最终写入”作为输入前提。一般证明覆盖条件清组位的两个分支；本步闭合实例走非零行分支，不声称该实例也执行了另一分支。

通用 frame 保留**入口辅助状态快照**：不能把任意依赖辅助状态的 `R` 强行运输到临界区状态。本步在局部执行中使用真实 `(false, si, enabled::ci)`，退出后资源断言与实际恢复状态再次一致。

## 预先登记的单因素消融

`protocol.json` 在新增证明前冻结。唯一因素：在首次y赋值后的**片段边界**，把待执行的延时赋值替为 `sskip`；保留额外 trace-skip、sequence、原输入堆、清行/组位、`excrit`、CPU/参数/canary。

`DYno_delay_write` 分别证明：

1. 原程序真实调用前缀到达 `DCafter / DCcont`，获得堆 `My`；
2. 从同一 `My`、但替换为 `DYno_write_cont` 的 continuation 执行干预片段；
3. 行位已清、IE已恢复且其他资源检查成立，但延时仍为0，不等于要求的3，被**延时值门晚拒绝**。

两条轨迹的 continuation 不同，**不拼成原程序的一条完整调用轨迹**。这是片段级消融，不是完整变异函数执行。负例没有抽象提交，旧任务表与已清位图不匹配，因此不声称它满足全部记录/位图一致性或成功抽象精化。独立正例先证明完整阻塞后置，负例不能替代下游正确性证据。

# 第52步：事件标志组的真实初始化调用

## 本步做什么

固定 V2.93.01 的 `OSInit` 在 Misc、Ready、TCB、Event 之后调用 `OS_FlagInit`。本步先完成这个被调用函数的真实执行接口 `V293_OS_FlagInit_call_return`，**还未把它接到第51步实际返回内存**。不将单函数执行算作完整初始化或整核验证。

来源是配置后的 `os_flag.c:1142–1180`，函数体 SHA256 `5b8594c0edd6c5b4f91eb0e4c6225265da37f9b3c2034032c27102ce3479a62e`。全部94函数身份与冻结源码相同；固定 C、配置和授权修复未改。

## 如何读懂代码

`OS_FLAG_GRP` 不是第50步的 `OS_EVENT`：这里有5组，每组12字节，`OS_FLAGS` 为16位。分析端口的 Clang 静态断言核对总大小60及 Type／WaitList／Flags 偏移0／4／8。Coq 显式表示 padding；这是源码级分析布局，不是 ABI 证明。

| 时点 | 实际动作 | 可观察结果 |
| --- | --- | --- |
| 入口 M | 表中60字节可写，链头有旧值 | 独立实例全255，旧链头121:0，并非预置零 |
| 四次局部分配后 | ix、ix_next、pgrp1、pgrp2 | 各2、2、4、4字节，共12字节 |
| 清零返回 | 真正调用 `OS_MemClr` | 60字节均为零；从实际内存选新鲜清零参数块 |
| 循环四次 | ix依次0、1、2、3，计算下一项并连链 | WaitList依次指向偏移12、24、36、48；Type=0 |
| 尾部 | ix=4，处理第5组 | Type=0、WaitList=NULL、空闲链头指向首组 |
| 返回 Mf | 真实void返回及释放，恢复caller | 12局部字节消失；同名caller变量仍为7 |

原生 `for` 手工归一化为赋值初始化、`swhile` 与循环末尾增量；生产代码没有拿有限写入列表替代循环。独立字面AST定理检查函数声明、清零参数、循环界4、写入和尾部语句。该检查不是已验证 C 前端。

## 证明输出与独立实例

- 同一 `Mf` 保有10项 Type／WaitList 字段、35项其余零字节、1项链头及3项frame：共 **49项可写单元与读回**。
- 35个其余字节包含5个16位 Flags字段及padding；不遗漏清零后未显式重写的部分。
- callee退出前计数器确为4；返回后四个局部对象全部12字节释放。
- caller的41号变量是block110的32位值7，callee同名41号变量是block90的16位计数器；调用返回恢复caller，不偷用空环境。
- 通用接口显式要求四局部块新鲜互异、标识符排序、准确函数／全局绑定、返回资源不落在释放块内；独立实例逐项构造这些前提，没有把执行结果或load成功当入口oracle。
- `FlagProgram` 只有 FlagInit 与 MemClr 两函数；不是完整94函数程序。

## 消融与负控分别证明什么

前瞻消融仅把调用点 `scall FlagInit` 替为 `sskip None`，同一程序、同一入口与frame不变。删除分支是零步no-op：Type字节及Flags低字节仍255，链头仍121:0；原调用返回后对应值为0、0和82:0。frame的123两边相同。证明的是整次调用的必要作用，**不是内部清零／Type写／链接／分配机制各自的独立消融，也不是所有执行safety**。

另有四项前瞻最终接口负控：首链接错误、尾NULL错误、空闲链头错误、frame被篡改。保持生产证明、独立fixture和目标proof body不变，各自在自己对应的读回证明行拒绝；不把它们记作机制消融。

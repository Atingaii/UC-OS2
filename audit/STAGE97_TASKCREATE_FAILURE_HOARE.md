# 第97步：任务创建失败调用与清槽返回的连接

## 这一步解决什么

`OS_TCBInit` 的入口 free-head 为 NULL 时返回 66，但调用者此前预留的优先级槽不会自动消失。本步把第96步的七实参真实调用接到原任务创建后缀：读取 `err`，选择失败分支，进入临界区，将 `OSTCBPrioTbl[prio]` 清为 NULL，退出临界区并返回 66。

稳定接口：`V293_OSTaskCreateExt_empty_call_suffix_hoare`，位于 `certiucos/v293/proofs/V293TaskCreateFailureHoare.v`。完整后缀没有删除成功分支；从真实 `err` 局部字节读取 66，证明成功侧不可达。

## 关键资源边界

- 失败槽必须由调用者实际持有可写 `Amapsto`；不能从错误码推导槽存在，也不能把它凭空加入失败 callee 后置。
- 失败路径的预留值 `reserved` 与完整 callee 规格成功分支中的旧值 `slot` 分开量化。这两个值不必相同，避免为了接通 NULL 分支而偷偷更换同一有限规格表。
- 七个实参、`err : Tint8`、只读 NULL free-head、原 `R` 与额外调用者 frame 均保留。优先级局部和槽各持有一次，不重复分离资源。
- 当前接口限定进入时中断已关闭；临界区压入 false、退出恢复原栈 `cs`。不外推到中断开启的全局不变量。
- 调用仍使用第96步完整 snapshot 规格，包含 NULL／成功两支，而不是另建 empty-only 规格。无新增 guard、load、执行轨迹或本调用 Hoare oracle 前提。

## 如何验证

探针 `audit/probes/V293TaskCreateFailureHoareProbe.v` 明确复用第93／96步字节夹具，增加 block211 offset44 的实际可写预留槽；不是独立 C 翻译。检查同一规格下的调用＋后缀、字面入口、真实局部与槽的读取，以及临界区内实际 store 的操作语义轨迹。

事先登记的单因素消融只把清槽赋值替换成 `sskip None`。保留相同入口字节、GE／LE、优先级11、错误66、NULL free-head、哨兵77与临界区原语。原程序清槽，删除赋值后留下非 NULL token。完整失败后缀的两条轨迹还从实际 err guard 走到 `srete` 边界；尚未执行局部释放／调用返回。两条控制轨迹都由框架既有执行语义检查，不从上游拒绝推断下游有效。token 是预留符号值，不宣称它指向可用 TCB。

第03版有效控制的原程序退出0，删除赋值退出1；负例已通过轨迹证明，最后读取时出现 `Some Vnull` 与 `Some RollbackReserved` 不等。第02版两项控制曾因 Python 字符串把合取写坏而在声明阶段失败，这不是有效消融结果，原记录全部保留；第01版计划未执行。

全内存 `vm_compute` 会展开有限映射的证明字段，三次有界诊断被中断且源码未变；改用既有字节权限／store 存在性和真实 load 引理，未减少读取义务、修改入口或放宽目标。

全部编译失败、源码快照及最终验证记录保留于 `audit/logs/stage97-taskcreate-failure-hoare/`。新增 Python 测试仅是结构回归，不替代 Coq 语义证明。完整测试的既有 423 个失败和 1 个错误、默认审计的旧身份过期、旧空白错误均须如实保留；不是全绿工程。

## 没有完成什么

本步不是整个 `OSTaskCreateExt` 的无条件契约：前置预留／栈初始化／成功调度路径尚未统一，两个 CPU Hook 仍为外部规格，调用分配／局部回收轨迹、全局不变量与 `WFIFun` 仍开放。六门仍为 **94/1/1/1/1/0**，最终源码级 `GOOD_OS` 和同程序 K1–K4 尚未完成，uCOS3 尚未开始。目标保持 active，未提交／推送。

# 第317步：延时阻塞更新连接原抽象一步和同堆全部任务记录

## 这一步解决什么

第316步已执行真实 `OSTimeDly` 临界区片段，得到撤销就绪位、写入延时的末端堆；但任务表变化还只是纯投影，尚未连接原框架 `spec_step`，也没有在同一末端堆恢复全部任务的记录关系。

本步新增稳定接口 `V293_OSTimeDly_updates_refines`。对于固定配置中同一临界片段，从真实内存及共享抽象状态的分离所有权推出：

1. 原 `cstepstar` 实际执行片段，得到一个 `Mf`；不是把执行成功放进前提。
2. 原 `spec_prim_step` 完成对应的抽象一步：读取共享 `curtid`，确认该任务原来 `rdy`，将同一任务改成 `wait os_stat_time duration`。
3. **同一个 `Mf`** 满足全部任务的 `V293_task_records`，并对应更新后的就绪位图／优先级表。
4. 共享任务表槽更新，current、事件表、时间及任意外部 frame 保留。该阶段 current 仍指向刚阻塞的任务；尚未执行后面的 `OS_Sched`，不直接修改 current 伪装成调度。

生产证明：[V293TimeDlyTaskBridge.v](../certiucos/v293/proofs/V293TimeDlyTaskBridge.v)。非空实例：[V293TimeDlyTaskBridgeProbe.v](probes/V293TimeDlyTaskBridgeProbe.v)。机器证据位于 `audit/logs/stage317-time-delay-task-bridge/`。

## 最小机制与消融

`V293_dly_block_step` 是新定义的**局部临界更新契约**，借用原框架的抽象原语规则；不是宣称已有完整 API 规格已连接。抽象任务域和 current 保持性已在原规则的前提中证明，不另造宽松执行规则。

实例从字面非空堆构造入口所有权，包含两份任务记录和独立可写 canary=99。通过相同实际执行得到被阻塞记录、就绪行64及保持为99的canary。

前瞻消融只改变 `DTcommit=true/false`，保持物理代码、入口、末端堆、全部记录、位图和canary不变；false版本省略抽象任务表提交。两个版本先取得实际执行证据；false在最后要求抽象槽等于阻塞后任务表时被拒绝。另有 `DTstale_slot_mismatch` 直接证明旧槽确实不等于新槽，避免只靠语法不可转换来声称语义差异。

**这是抽象提交观察器消融，不是C语句变异，也不证明全局 API 注册的正确性。** 第316步的删延时写入消融保持原样，两个实验隔离不同机制，不能互相替代。

## 对抗性复核与边界

- 入口提供其他任务的所有权，而非直接假定末端全部任务记录；当前任务记录从执行后的字段所有权重组。
- `curtid` 与任务表来自同一个共享抽象状态，实际 C 当前指针和选定任务也由入口单元及同一 `bt/base` 连接。
- 全部任务记录是本片段的条件后置关系，**不是全局记录不变量**，更不是全交错保持证明。
- 原 `spec_step` 的构造已闭合，但新局部契约还没有注册到完整程序 API 规格；不能把该原语步骤称为完整 API 线性化证明。
- 手译 AST 的信任边界、guard／局部初始化／临界调用／return、后续 `OS_Sched`、真实唤醒与物理回切仍未闭合。
- **不是完整回切，不是全局 ProgSim，不是 GOOD_OS。** 初始化、统一 WFInt／TaskSim、所有交错、同程序K1–K4仍开放。uCOS3未开始，须先完成阶段一。

# 第77步：真实启动写入接到框架 CurTid

## 解决的缺口

第76步证明了实际内存中的当前任务指针写入，但参数化的源标识符不自动等于框架保留的 `OSTCBCur = 60`。此外，一个可写指针单元不能在分离合取中既完整保留、又被重复用于当前任务断言。

本步只补这个具体连接：使用真正的保留标识符执行启动调用，将当前指针的完整所有权拆成两个只读半份额，分别建立 `CurTid`；其余单元和 frame 的可写所有权保留。它是完整不变量所需的资源，不是完整不变量本身。

## 生产接口

[V293StartCurrent.v](../certiucos/v293/proofs/V293StartCurrent.v)：

- `V293_start_current_halves`：从任意位置的原始可写指针单元提取所有权，核对真实全局绑定，利用既有 `GV_separate_rw_frm` 拆成两个半份额。不保留同一单元的第三份完整所有权。
- `V293_OSStart_call_establishes_current`：入口不要求 `CurTid` 或 `CurLINV`；调用实际 `OSStart`／`OS_SchedNew`，在同一最终内存中得到两个 `CurTid target` 和其余单元所有权。
- `V293_OSStart_highest_establishes_current`：连接第76步的实际位图／任务映射／优先级表关系，由这些关系推出最高就绪任务，同时建立上述资源。最高任务不是作为结果前提输入。

后两项都停在 `OSStartHighRdy` 的 `sfexec` 入口，保留真实调用者 continuation。没有要求端口成功轨迹，也没有给缺失端口编造实现。

本步没有修改 C、配置、两项授权修复、分析端口或框架语义；使用第76步已经核对的函数模型。没有重新运行 Clang 提取；本步基线逐项核对旧源码和冻结证据不变，不能把旧源码重放记成本步新实验。

## 可满足入口和对照

[V293StartCurrentProbe.v](probes/V293StartCurrentProbe.v) 复用第76步的字面内存构造与输入读取证明，而不是复用一个假定当前任务已存在的入口。

1. 真实保留标识符绑定到块84，入口该指针为 NULL；`CurrentNoInitialTask` 证明入口对任何任务都不满足 `CurTid t ** Atrue`。
2. `CurrentColdCall` 实例化新生产调用；`CurrentHighestCall` 也实际实例化最高就绪任务接口。只有任务12就绪，目标为块90。
3. `CurrentSameMf` 在同一最终内存中同时保留两个半份额、其余单元所有权，并读回当前指针、仍为0的运行字节和仍为123的哨兵。目标 TCB 的实际记录尚未由本实例拥有。
4. 单因素绑定消融使用**两臂完全相同的旧 current=107 程序和同一字面入口内存**：正臂仅增加保留标识符60到块84的别名绑定，负臂不加该绑定。两臂都实际执行到端口；负臂仍写出正确指针，但对任何任务都不能建立 `CurTid`。`CurrentBindingOnlyFactor` 证明其他全局查询不变。这是逻辑连接敏感性实验，不是完整源码全局环境布局。
5. 错误后置负控只将第一个 `CurTid` 的目标改为块91，其他路径、前提及 `exact CurrentColdCall` 证明体相同；预先冻结计划后编译，正控通过，负控在预定类型核对处拒绝。

最初总协议中“同一程序／移除绑定”的文字不足以区分 current=60 生产实例和 current=107 消融实例；在任何 probe 编译前追加 `binding-control-plan.json` 澄清，两版计划均保留，不倒改原协议。

## 结果边界

两次读取半份额合起来仍只是一份实际当前指针，不能据此推出以下开放义务：

- 完整任务记录、就绪位图、事件、时间及资源池的真实全局 `Inv`；
- 抽象当前任务更新或一段抽象执行；当前 fixture 的抽象映射仍只有任务表；
- `OSStartHighRdy` 执行、`OSRunning=1`、完整 `OSInit` 可达性；
- 框架 local Hoare／`BuildPreI`／`BuildRetI`／全程序 `WFIFun`；
- 所有执行或中断交错的 safety、目标程序 `GOOD_OS`、同程序 K1–K4。

模型仍是受审查的手工前端，不是已验证 C 前端。不扩大到汇编、ABI、编译器或硬件验证。uCOS3 尚未开始，最终两阶段目标保持 active；未提交、未推送。

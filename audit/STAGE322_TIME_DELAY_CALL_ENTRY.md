# 第322步：真实调用分配、未初始化局部与第一次实际赋值

## 本步解决什么

第321步的全局延时／调度轨迹从 `cpu_sr` 初始化后开始，并预设局部 `y` 已有类型正确的值。本步从真实 `scall OSTimeDly(3)` 开始，执行参数求值、参数与局部分配、`cpu_sr=0` 初始化、入口判断、进入临界区及 `y = OSTCBCur->OSTCBY`，到达清除就绪位之前。它补上调用入口的一个真实前缀，不把构造好的函数帧冒充调用可达性。

源码准确写着 `INT8U y;`，不是 `INT8U y=0;`。新分配的 `y` 初始读为 `Vundef`；它不满足旧的 typed ownership 契约，不能先假定有效值再证明调用。只有实际读出当前 TCB 的 `OSTCBY` 并存入局部后，才产生类型正确的字节所有权。

## 逐层连接

| 接口 | 输入 | 实际输出 |
| --- | --- | --- |
| `V293_dly_call_allocate` | 精确函数绑定、互异变量／块、fresh 条件及 frame | 原 `scall` 参数求值、真实参数 store 和三块分配；两局部仍为 raw `Vundef` |
| `V293_dly_call_entry`（稳定入口接口） | 同上，没有执行或 store oracle | 构造 CPU 初始化 store，接到原 body；CPU=0，参数有效，y仍未初始化 |
| `V293_dly_raw_y_assignment` | current 指针及TCB字段读条件、raw y 写权限 | 实际字段求值、字节 store 与 `cstepstar`；此后才有 typed y |
| `V293_dly_body_first_y` | 两个零 guard、正 ticks、字段读条件与 raw y | 原 `loststep` 闭包经过 guard、`encrit`、首次赋值，到达真实 clear-row 尾部及精确 continuation |
| `DCcall_first_y` | 只有初始 IE 布尔值；非空堆已由定义固定 | 消费上述入口与首次赋值接口，连接完整局部前缀，并在同一末端堆核对参数／CPU／y／canary及全部任务记录 |

生产证明不导入 `audit`，不改 C 源码或原框架规则。入口接口中的任意 `R` 是在明确给出的将来 callee 环境下检查的资源前提，不是未经证明的 caller-environment Hoare 契约。具体实例的 frame 不依赖局部变量查找，因而可在该环境使用。

## 非空资源与辅助状态

初始 `DCmem` 包含两个完整任务记录、current 指针、就绪行与组、guard、延时字段、canary及共享抽象任务表；参数12、y11和CPU13三个块在所有偏移均不在堆中。它们由原调用规则分配，不是输入中预先放好的局部单元。

当前任务优先级4；另一任务优先级6且已经 ready。这只是输入事实，本步尚未阻塞4，也没有唤醒6。首次赋值读到行号0，末端 y=0、ticks=3、CPU=0、canary=99，两个任务记录及共享任务表保持。`DCboth_IE` 对任意布尔 `enabled` 给出真实轨迹；`DCinitialized_cpu_writable` 给出CPU四字节写权限。

实际执行末端是 `(false, [], [enabled])`，不是原辅助状态。通用 `V293_dly_body_first_y` 的所有权结论刻意保留**入口辅助状态快照**，不能把任意依赖 IE／临界栈的 `R` 搬到真实末端。仅对于此处不依赖辅助状态的具体物理／共享 frame，`DCactual_critical_post` 通过定义转换证明它在实际末端仍成立。这不构成任意 frame 的辅助状态保持定理。

## 前瞻单因素消融

实现前冻结的 `protocol.json` 规定只省略 `cpu_sr=0` 初始化片段。`DCno_initializer` 使用相同初始堆、实参、函数分配、块身份、guard、TCB首次赋值及frame：

1. 真正执行同一个函数的调用分配，停在完整函数体入口；CPU、y都为 `Vundef`。
2. 在明确的片段边界跳过初始化，单独从同一个 body 执行至同一个首次赋值终点。
3. 任务记录、canary、参数、typed y以及CPU写权限仍通过；CPU读取仍为 `Vundef`，严格不等于初始化门要求的 `Some(Vint32 Int.zero)`。

正反例参数 store 的输入与输出式完全相同，框架 `store` 为确定函数，故参数分配后堆一致；变化不是另选一个有利初始堆。这里的晚拒绝由 Coq 证明不等式，不依赖预期编译报错或日志关键词来充当值语义 oracle。

这是**片段级消融，不是另一完整函数**。负例的调用分配轨迹与跳过初始化后的 body 轨迹没有被伪装为可直接拼接的真实完整调用；原函数绑定仍保留初始化。删除初始化不影响 y 首次赋值，却破坏 CPU 初始化值要求，故不能用“早期链接失败”替代此项下游机制检验。

## 必须保留的边界

- 新入口仍是局部 `loststep` 轨迹，不是原 `lpstep` 的完整调用入口可达性。全局规则中 `scall` 早期步骤操作客户端堆，`sfexec` 起进入OS堆；不能把本步单堆轨迹直接整段套用旧全局提升接口。
- 本步实例程序只绑定延时函数1200；尚未需要也未加入调度器112／helper113。它不是第321步整个程序的新可达性定理，更不是全部目标程序的连接证明。
- raw y 首次赋值的终点是 `V293_dly_after_y`，后续 clear-row／group／delay 写入、抽象阻塞及调度切换**尚未与这个真实入口接通**。旧 body 契约要求入口 typed y；不能把新末端当作旧 body 的入口、不重跑整个 body 是下一步的基本约束，否则会重复 guard／encrit／首次赋值。
- 本步是规范化 C 语义与临界区原语边界，不是原始 port 对物理CPU寄存器保存的执行，也不是自动 C 翻译正确性。
- 因此**不是完整 API，不是全局记录不变量，不是全局 ProgSim**。实际恢复／return、优先级缓存同步、统一 WFInt、初始化、源码级 `GOOD_OS` 与同程序K1–K4仍开放；uCOS3未开始，目标保持active。

本步编译调试中保留所有不利结果；例如 typed load 引理不能用于 `Vundef`，改为按原编码／解码证明 raw 读取；canary读取也显式指定地址和类型，避免不受约束的自动实例化选错字段。没有把 `Vundef` 加入类型有效值，也没有增加假的 y 初始化。

新增8项Python回归是接口／溯源／边界回归，不替代 Coq 执行证明或源码级整核证明。最终实测以 `verification.json`、`trust.json`、`full-tests.json` 及清理报告为准；旧冻结证据和旧测试不改写，不提交／推送。

## 对抗性复核与下一条证明接缝

| 质疑 | 本步处置 |
| --- | --- |
| 初始 y 是否被偷偷当作0或typed值？ | 对初始分配后堆证明实际load为 `Vundef`；只有TCB首次赋值后才输出typed所有权；不修改类型有效性定义 |
| 参数／局部是否原本就在输入堆中？ | `DCfresh` 对所有偏移证明三个块不存在；消费原 `sallocp/salloclv`，store是推导结论 |
| 省初始化是否只是更早卡住？ | 反例继续实际执行同一body；保留记录／y／参数／canary及CPU写权限，仅CPU值门失败 |
| 两种IE是否只有资源快照，没有执行？ | `DCboth_IE` 的结论包含任意布尔初始IE的实际完整局部前缀 |
| 入口资源是否被错误搬过encrit？ | 通用接口明确标注入口aux快照，具体frame的真实末端性质另由 `DCactual_critical_post` 证明 |
| 是否已经拼接旧全局切换？ | 没有；raw/typed尾部接缝及客户端堆／OS堆边界均列为未闭合义务 |

下一步应在 `V293_dly_after_y` 暴露清行／组位／delay更新的**后缀接口**，输入是本步真实typed y及同一堆的记录／位图资源。只执行尚未执行的后缀，再连接原抽象阻塞一步及调度切换；不得把新末端重新塞进旧整个body来绕过接口缺口。该后缀连接完成后，仍要单独处理全局调用堆边界，而不是自动宣称第321步整段全局轨迹已从调用者可达。

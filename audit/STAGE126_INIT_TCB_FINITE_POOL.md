# 第126步：真实初始化调用建立增强空闲池

## 本步解决什么

第125步已能从真实空闲链弹出节点并取得固定TCB表成员性，但调用入口仍需要这份增强空闲池。本步把它接到真实 `OS_InitTCBList` 的返回内存：不是先假设池成立，再证明池成立。

稳定接口是 `V293_OS_InitTCBList_call_finite_pool`，位于 `certiucos/v293/proofs/V293InitTCBFinitePool.v`。

1. 入口仍是原调用的程序映射、环境、四个局部块新鲜性、728字节TCB区、52字节优先级区、两个头单元和调用者frame。
2. 原 `V293_OS_InitTCBList_call_return` 提供原 `scall` 到返回的执行及四个局部块释放。
3. 对同一份 `Mf`：把每个节点清零后的20＋32字节折叠成原完整payload；保留中间4字节实际Next，不重复拥有任何字节。
4. 按原13节点链接递归建立增强链；固定表成员性由 `seq 0 13` 的实际索引推出，不作为最终调用接口的独立前提。
5. 另外保留空活动任务头、13个null优先级槽及原frame。局部变量释放结论仍在。

## 源码身份与边界

真实存在的上游文件 `csrc/upstream/v2.93.01/checkout/Source/os_core.c` 第1591–1617行，是本步核对的 `OS_InitTCBList`。文件哈希与冻结程序的对应条目一致；函数切片与既有模型输入哈希见 `audit/logs/stage126-init-tcb-finite-pool/source-identity.json`。本步没有修改C、配置、AST、框架或tactics，也没有声称重新生成／重放不存在的repaired checkout或新完成自动C到AST翻译。

这里的“初始化建立池”仅指这个真实函数调用的局部可达结果；不是整个 `OSInit` 在生产共享Inv下的交错Hoare证明。

## 独立输入和单因素对照

`audit/probes/V293InitTCBFinitePoolProbe.v` 不导入其他audit探针。它用独立编码的非空字节内存：728字节未定义TCB、52字节非零优先级区、原旧头值、边界哨兵和具有同名遮蔽的非空caller，检查完整调用。直接实例化新稳定接口，并从真实返回内存同时检查池、全部Next链接、末节点null与空闲头。

`IPActualThirteenReachable` 用实际内存load遍历：12次到第13节点（偏移672），13次到null。

预先协议只改变一个因素：对同一返回内存，仅把首节点偏移20的Next真实store为null。其余地址（包含另外12节点、所有payload、头、优先级表和frame）逐字节保持；第二节点Next仍指向偏移112，但从头第一步已到null，12步不再到第13节点。

**必须区分**：增强池的fuel是递归上界，不是精确可达节点数量；截断链后可能仍满足带剩余frame的较短池。因此对照只声称完整13节点可达性改变，不声称截断后池必假，也不把提前失败当作下游全部机制得到验证。

### 调试与失败记录

生产稳定版本是 `proof14`，探针稳定版本是 `probe16`。所有之前的失败快照及日志均保留。遍历重写失败的具体原因是 `block` 别名没有被重写器自动归约，以及不透明乘法使显示相似的指针偏移项无法匹配；修正只显式归约类型别名、规范化每个实际地址并应用读取引理。最后一次修正显式指定物理store的指针类型，避免Coq在类型参数未确定时先检查null合法性。

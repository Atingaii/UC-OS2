# 第79步：实际初始化字段写入扩展全任务记录所有权

## 本步解决的问题

第78步把真实启动连接到**所选任务**的记录，但不能由此推断其余任务记录也存在。本步从真实初始化的18次字段写入出发，保留所有既有任务记录，并加入新记录。不是新增完整全局不变量的别名。

生产文件：`certiucos/v293/proofs/V293InitAllRecords.v`。
稳定接口：`V293_OS_TCBInit_fields_extend_records`。

## 输入、执行与输出

1. 输入拥有新TCB原18字段和8个实际调用输入，另有旧任务集合的 `V293_owned_task_records tasks` 及任意frame `R`。新任务ID必须不在旧集合；不预设新记录。
2. 执行原有 `V293_TCBInit_fields` 的18次真实写入，程序、continuation与调用输入都保留。
3. 同一个实际最终 `Mf` 拥有 `set tasks newtid (priority,rdy,Vnull)` 的**全部任务记录**，以及未转为记录的11初始化字段、8输入与原frame。
4. canonical map的 `set'` 按任务ID插入。归纳分别处理前插、相等矛盾和递归插入，不从读取值制造写权限，不丢弃旧记录。

资源重排只消费一次：初始化的18字段44字节，7字段10字节转为新记录，剩余11字段34字节保留。它们仍**不是56字节完整TCB**。旧记录可以与新记录在同一内存块、不同偏移；真正要求的是字节分离，不要求整块隔离。

## 独立非空实例和对照

`audit/probes/V293InitAllRecordsProbe.v` 独立编码34个typed cell、83字节：新字段44、输入25、旧记录10、哨兵4。旧任务 `(301,8)`、新任务 `(301,128)` 共用block301，新任务按ID排序插在旧任务后，覆盖实际递归插入路径。

- `AllLiteralEntry` 从有限字面内存证明入口可满足；旧任务优先级12，新任务输入11，哨兵77。
- `AllGoodCall` 真正实例化新稳定接口；`AllGoodSameMf` 只解构一次执行结果，在同一 `Mf` 给出全记录所有权、物理记录语义、两个任务查询及哨兵读取。
- `AllRawCall` 从同一真实入口执行，不要求任一候选任务集合后置。`AllBadCall` 在该次实际执行的 `Mf` 读回旧优先级12，排除把旧任务写成11的全记录断言。
- `AllMapOnlyFactor` 和 `AllMapLookups` 证明两个**目标规格映射参数**仅在旧任务优先级上不同；新任务、程序、真实入口内存、GE/LE和 `O` 都不变。两臂共享同一实际执行。负例不是输入满足新主定理前提的另一调用，不把旧记录前提拒绝计作下游验证。
- 同证明体负控只将后置中**新任务**优先级11改成10，证明仍为 `exact AllGoodCall`。冻结计划先于控制编译；正例应通过，负例应在后置类型比较被拒绝。实际结果见 `controls.json`。

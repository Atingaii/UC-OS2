# 第344步：初始化优先级表不再允许多余指针

## 这一步解决什么

最终目标仍是固定源码 uC/OS-II V2.93.01 的具体 `GOOD_OS` 和同程序 K1–K4，再按老师要求开展 uCOS3。第343步解决的是带原前提的通用 soundness，不能代替具体内核初始化。

已有优先级表关系只检查「每个任务能找到自己的槽」。它允许没有对应任务优先级的槽重复保存另一个任务指针。本步只在初始化写表阶段增加反向条件：每个非空槽都必须对应同优先级的任务。没有修改原全局就绪不变量，也没有把历史非规范夹具宣称为可达状态。

| 关系 | 原单向要求 | 本步增加的要求 |
| --- | --- | --- |
| 任务 → 表 | 每个任务在其优先级槽中有指针 | 保持不变 |
| 表 → 任务 | 无 | 非空槽中指针对应的任务必须具有该槽的优先级 |
| 空槽 | 可能仍存在相同优先级任务之外的别名 | 等价于没有同优先级任务 |

`V293_init_priority_table` **仅用于初始化阶段**。互斥锁可能合法预留优先级槽；本步不是任意 API 的闭包证明，不能直接用这个关系替换所有运行期不变量。

## 实际证明接口

生产文件：`certiucos/v293/proofs/V293InitPriorityTable.v`。

- `V293_OS_InitTCBList_canonical_clear`：执行实际的两个 `OS_MemClr` 调用前缀，得到全零 TCB 字节和拥有全部13槽的空指针表，以及空任务映射的双向关系。不是整个 `OS_InitTCBList` 的执行证明。
- `V293_OS_TCBInit_canonical_priority_write`：执行 `OSTCBPrioTbl[prio] = ptcb` 的原有语句。由完整可写表所有权构造成功 store，再得到同一个返回堆的表所有权和全部13槽读取结果；任务映射的插入是明确的纯关系，不是假定的抽象执行步骤。
- 指针槽／空槽的双向等价定理供后续初始化连接使用。

写表接口要求：旧表已经满足关系、目标槽为空、任务键尚未存在、参数局部单元有效且与全表分离。它不提供 TCB 字段、就绪位图或链表的完整一致性；没有删除这些后续义务。

配置后函数重新从锁定源码及两类授权修复生成并核对哈希，记录见 `logs/stage344-init-priority-canonical/source-identities.json`。实际赋值位于 `OSTCBInitHook` 和 `OSTaskCreateHook` 之间；Coq 检查它与既有完整成功后缀中的语句相同。C 与 Coq 的对应仍是人工对应，非验证前端和 ADR0005 的信任边界没有消失。

## 非空实例与单因素消融

探针：`audit/probes/V293InitPriorityTableProbe.v`。

1. 独立编码13个空指针槽、两个参数单元和一个 canary，证明真实有限堆所有权。
2. 在优先级12执行原赋值语句，得到具有一个任务的表；同堆全部13槽可读，canary 保持123。
3. 从这个结果仅改槽0：`null` → 已有优先级12任务的指针。两边任务映射相同、表长度相同、其余槽相同；物理内存在槽0的4字节之外完全相同。
4. 两边都具有可读写的合法指针表，且都满足原单向约束；仅新增反向条件拒绝重复指针一边。不是因编码／分配／store 早拒绝而声称下游有效。

消融协议在实现前冻结。修改槽0是受控反例实验，不是源码程序会产生该状态的证据。清零实例明确复用冻结的780字节入口证明；清零与写表实例是两个独立入口，**不是连续的 OSInit 执行轨迹**。

# 第92步：把空闲 TCB 耗尽路径交给标准函数构造器

## 本步解决的问题

上一轮统一了 `OS_TCBInit` 空／非空入口的函数体证明，但入口仍写着已分配的局部地址。调用者不能预先指定被调用函数新分配的地址，返回时也不能丢掉这些资源。

本步先完成**空闲链表为 NULL 的失败路径**与框架 `BuildPreI`／`BuildRetI` 的连接，不把它误记为非空路径或整个函数的全域规格。

稳定接口：`certiucos/v293/proofs/V293TCBEmptyInternal.v` 中的 `V293_OS_TCBInit_empty_internal_contract`。

## 参数、局部与外部资源

| 部分 | 入口 | 返回 |
| --- | --- | --- |
| 七个参数101–107 | 按真实声明及反向实参列表生成，须通过框架类型／长度检查 | 全部重新装入 `buildq` 的存在量化参数资源；没有丢弃 |
| ptcb108、cpu_sr109 | 任意旧值；局部地址从 `LV` 存在量词中取得 | ptcb为NULL、cpu_sr为0；两者完整交回 `buildq` |
| free-head91 | 真实全局绑定与只读NULL指针 | 原样保留 |
| 局部环境 | 恰好七参数、两局部 | 原定义域保留，供框架回收 |
| 中断／临界区状态、抽象操作及R | 入口中断关闭，临界区栈任意；R支持当前线程局部不变量 | 原样保留 |
| 返回值 | 尚未返回 | 仅允许66 |

外部 `fpre`／`fpost` 通过 `GoodFunAsrt` 检查，不含 `Alvarenv`、局部地址、局部定义域或“不遮蔽全局”的额外oracle。全局91不被局部变量遮蔽，是从框架产生的准确九项定义域推导的。

证明复用真实完整函数体的空链表 Hoare；两个CPU Hook仍在原语法中，但这条路径不会到达它们。因此此接口对任意 `Spec` 成立，包括所有查询均为None的表。并未为Hook编造实现或把调用改成skip。

## 怎么阅读

1. 对照 `V293_TCBInit_parameters` 看七个参数的类型与顺序。
2. 看 `V293_tcb_internal_buildp/buildq`：与框架构造结果是定义相等，不是另造入口。
3. 看 `V293_tcb_internal_no_shadow`：准确局部定义域如何排除91。
4. 看 `internal_unpack/entry`：拆出局部旧值和地址，接到已有body证明。
5. 看 `internal_parameter_return/local_return/exit`：保留原资源，逐项装回返回构造器。
6. 最后看稳定接口：前提直接使用两个标准构造器等式，没有额外body正确性假设。

## 验证与边界

独立探针 `audit/probes/V293TCBEmptyInternalProbe.v` 自行构造九个局部／参数内存块以及free-head、当前线程、哨兵资源；检查真正可满足的完整builder入口，而不仅仅检查构造器能返回Some。

前瞻单因素控制仅把准确局部定义域条件改成True，保持导入、全局标识、量词、结论和证明体不变。正控通过后才运行负控。其信用只限“不遮蔽”推导，不能外推到分配／释放执行或整核正确性。

一次直接展开全部参数地址再自动重装返回资源的尝试导致搜索过慢；在源文件未改动时显式中断并保留记录，改成逐参数／局部装回的证明。没有新增公理或弱化目标。`write-probe.py` 只记录最初草稿生成过程；后续人工修订以各次编译快照和最终探针源码为准，不能用草稿生成器覆盖最终文件。所有编译尝试和最终验证结果保留在 `audit/logs/stage92-tcb-empty-internal/`，以最终报告为准。

本步没有新增具体alloc/free轨迹；它验证的是框架标准资源交接，分配／回收语义仍来自既有框架。失败规格只覆盖真实NULL入口，不是整个 `OS_TCBInit` 的 `WFIFun`，也没有完成非空路径的标准构造器连接、统一全局Hook规格、全局不变量或可达性。

# 第90步：真实 CPU Hook 调用现场接入框架规则

## 本步解决什么

第89步的完整非空 `OS_TCBInit` 函数体已经接通字段初始化、优先级表写入、任务发布和返回，但仍以两个 Hook 调用的 `InfRules` 为前提。本步直接应用框架 `call_rule`，证明两个实际调用现场，改为显式的两项外部规格表查找；没有改写 C 或将 Hook 替换成 `skip`。

稳定入口：

- `V293_tcb_hook_argument`：从真实局部绑定和内存 `load` 推导 `[evar 108]` 的单参数求值及 `OS_TCB *` 类型，不接受求值轨迹作为前提。
- `V293_tcb_hook_view`：双向分离调用者资源与被调用者资源。
- `V293_tcb_hook_call`：应用真实 `call_rule`，保留调用者 frame。
- `V293_OS_TCBInit_hook_calls_body_hoare`：完整既有非空函数体；无 Hook `InfRules` 前提，仍需两个真实 CPU Hook 的规格查找。
- `V293_OS_TCBInit_hook_calls_body_semantics`：通过既有 `RuleSound` 得到对应 `RuleSem`。

## 资源和契约

Hook 接收初始化后的18字段、free-list 相关单元、优先级表槽和发布段所需单元，以及控制状态和 `R`。NULL／非NULL旧 ready-head 分别为26／27个 owned cell。调用者的9个局部／参数 cell（含 `cpu_sr`、`ptcb` 和7个参数）及所有局部／全局绑定留在 frame；规格没有借用调用者局部变量名或局部地址。

外部规格明确检查：参数必须是新 TCB 指针、当前任务身份匹配、void 返回为 `None`，并保留转交的资源。新增 `GoodFunAsrt R` 限制保证合法的函数断言，**不是无条件加强第89步对任意 `R` 的定理**。规格是当前调用现场的资源特化，并非已经链接到真实 CPU port 的统一全局 Hook 规格。

## 验证与反例检查

独立探针不导入旧探针。字面内存覆盖两次调用位置（优先级槽为 `Vundef`／已写新指针）、旧 ready-head 的 NULL／非NULL分支及任意临界区栈。新 TCB、旧 ready-head 和 free-next 同 block、不同 offset，依次为128、256、384，避免将两个不同指针混为一谈。

实际参数读取之外，另外检查错误参数被排除、外部 pre 拒绝 free-next 指针、post 拒绝有值返回。两个不同 Hook ID 的有限规格表证明查找条件可以同时满足；这个表只有规格，没有 Hook 实现。

前瞻单因素控制仅把实际参数接口中的期望指针从新 TCB 改为 free-next；导入、调用现场前提、表达式、类型和证明体不变。它只为参数接口提供消融证据，不证明 Hook 实现或下游发布机制。

完整编译、假设检查、内核复核、回归和清理结果以 `audit/logs/stage90-tcb-hook-call/final-report.json` 为准。所有失败尝试保留；一次构造中途追加探针源码的编译不计为稳定证据，必须使用固定最终源码重编译。

## 仍未完成

选定源码树只有两个 CPU Hook 的声明，未提供其具体实现。本步没有补造实现，没有证明 Hook `WFIFun`；局部变量分配／释放、启中断入口、全局不变量及整函数链接仍开放。规格表中的声明不能代替被调用函数的实现证明，也不能推出实际程序的无条件整核正确性或终止性。

六门保持94／1／1／1／1／0；`GOOD_OS` 和同程序 K1–K4 尚未完成，uCOS3 尚未开始。原 C、配置、两个授权修复、旧源码和冻结证据不变，未提交／推送。下一步应优先连接已有空闲链表为空分支与非空分支的统一返回接口，并继续暴露真实 port／链接义务，而非把规格声明当作实现闭合。

探针中的计数254只用于逼近8位上界的局部算术检查；在配置仅13个优先级的情况下，不把这个独立入口声称为已由全局不变量证明可达的内核状态。

初始控制对因共同缺少 `ListNotations` 导入，在目标类型检查之前同时失败，不计为有效负控。保留这两个失败及原计划，补齐双方相同导入并另存前瞻计划后重跑，才得到正控通过、仅改指针的负控被目标类型拒绝的有效控制对。

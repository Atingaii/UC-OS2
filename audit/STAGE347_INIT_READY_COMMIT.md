# 第347步：TCB返回资源连接真正的抽象任务创建

## 一句话理解

上一步得到“内存里的任务和就绪位图”；本步补上“抽象系统也新增该任务”，使两者在同一个返回内存 `Mf` 上一致。没有把纯映射 `set` 当成执行。

稳定接口：`certiucos/v293/proofs/V293InitReadyCommit.v` 中的 `V293_OS_TCBInit_shared_return_under_hooks`。

## 输入、执行和输出

| 层次 | 本步实际做了什么 |
| --- | --- |
| 固定对象 | uC/OS-II V2.93.01，上游提交 `0c4a48e6fbc6e915714e816196619a5481accf0c`，配置和两类授权修复不变 |
| 真实源码路径 | 复用第346步的TCB初始化前缀、发布及返回／释放证明；不修改已有源码、旧证明或冻结证据 |
| 物理输入 | 原来的任务记录、原始可写单元、完整优先级表、位图关系；frame中另外保留 `OSTCBCur` 的当前指针 |
| 抽象输入 | 当前任务、旧任务表、事件表、时钟四个原抽象槽；待创建任务新鲜；当前线程位于原 `spec_crt` |
| 客户端创建 | 复用原 `hpcrt_step`；为一个指针参数、没有局部变量、函数体任意的客户函数构造真实三步参数分配执行及成功store/readback |

| 抽象输出 | 新线程控制、客户局部环境、参数内存和抽象任务表按原创建规则共同更新；当前／事件／时钟不改变 |

抽象客户内存 `clientM` 与内核返回内存 `Mf` 是框架中的不同状态分量，不能把两者当成同一个内存。新分配并写入参数发生在前者，强就绪资源保留在后者。

## 为什么不使用普通抽象原子步骤

框架普通 `spec_prim_step` 要求 `eqdomO`，其中任务表定义域保持不变。新增一个原先不存在的任务恰好改变定义域，因此不能靠普通原子步骤完成。

`V293_init_insert_not_ordinary_primitive` 机器证明这个障碍；实现采用框架已有、允许创建线程与客户环境的 `hpcrt_step`，而不是修改规则或放宽定义域检查。

`CurTid` 需要只读半权限，不是完整可写权限。这里先使用原 `GV_separate_rw` 拆出两个半权限，一份建立当前指针，另一份仍留在frame中；没有把两种权限直接等同。

## 单因素对照及其边界

事前方案见 `audit/logs/stage347-init-ready-commit/protocol.json`。

- 唯一切换因素：抽象任务表插入新任务，或者保留旧任务表。
- 保持不变：整个物理内存、当前任务、事件、时钟、新任务、优先级以及待认证的原共享就绪资源。
- 正向：在原物理／hook等前提下，构造原创建步骤，并认证更新后的固定任务表见证。
- 负向：旧抽象表缺少新任务，因此不能认证这个**固定更新任务表见证**。该否定对任意物理内存成立，不依赖更早的物理入口检查失败。

不声称负向排除了所有可能的存在量化 `ready_core` 见证，也不声称坏状态可从OSInit到达。探针独立构造了客户分配及创建步骤的闭合实例，但没有构造满足两个hook契约的完整启动实例；不能据此宣称整个源码入口已无条件可达。

## 尚未完成的目标

本接口要求已有当前线程及其 `spec_crt` 控制点，不能直接用于尚未设置 `OSTCBCur` 的冷启动；OSInit仍需要独立的bootstrap连接。

本步定理同时给出低层局部执行和高层创建步骤，再连接它们的任务资源；**不是**逐步交错同步或整个创建API的 `TaskSim`／`ProgSim`。

仍缺少两处CPU hook实现、完整创建调用者模拟、完整初始化链／链表不变量、真实ISR的未过滤 `WFInt` 和具体 `GOOD_OS` 实例。入口仍在分配和CPU_SR初始化之后。ADR0005、函数标识符映射以及非验证前端边界不改变。原共享就绪谓词也不额外保证当前任务属于任务表或处于ready；不能把它当作完整内核不变量。

K1–K4同程序回归证明及uCOS3阶段均未完成，不登记 `full_target_linked`，不以新增文件数或编译通过代替整核完成。

# 第337步：完整时间API的源码对应与同一组件连接

## 为什么这一步不继续堆tick片段

复核现有材料后确认：两个CPU hook仍缺实现，不能补造空函数来闭合初始化/程序环境；同时完整 `OSTimeGet`、`OSTimeSet` 的函数、资源证明及API构造器契约已经存在，再写一套并无价值。本步补其固定配置后C函数到已有完整证明的可执行对应检查，并把两个生成函数放入**同一个**API组件，复用相同的时间不变量和名字局部不变量。

固定版本、配置、两类授权C修复、全部旧证明/测试/冻结证据保持不变。旧覆盖清单不改写；本步组件证据单列，不能将两个函数局部连接偷记为全内核覆盖或最终完成。

## 从哪些实际源码来

`scripts/check-v293-time-source.py` 在一次性目录重新生成两个授权修复后的完整C程序，逐字节核对 `FROZEN_SOURCE.json`、整个配置后预处理身份、函数位置和函数体身份。不是直接相信历史快照。

- `OSTimeGet`：原 `os_time.c:237–250`，局部ticks、cpu_sr=0、进入临界区、ticks=OSTime、退出、返回ticks。
- `OSTimeSet`：原 `os_time.c:267–278`（完整身份另见本步 `replay-*/report.json`）；ticks参数、cpu_sr=0、进入临界区、OSTime=ticks、退出、隐式void返回。
- Clang和GCC分别预处理，再用Clang AST检查相同的函数签名、unsigned int宽度、volatile全局读写、参数/局部声明顺序、初始化、两次同一保存对象地址、复制及返回。未知AST字段、额外语句、错误地址/标记、类型和声明次序均拒绝。
- `scripts/v293-time-source.py` 只接受这两种完整结构；在该结构内复制源可以是OSTime或ticks，以便真正让单因素负控走过解析阶段。

生成文件：`certiucos/v293/code/V293TimeSource.v`。C声明进入函数的参数/局部声明表；局部初始化保留为赋值；setter末尾的隐式void返回显式映射为sret。两种32位类型使用框架现有Tint32表示；这两段不涉及有符号算术差异。

**这是受信任的受限Python AST解码/生成器，不是经验证C前端。** 临界宏仍采用既有ADR0005归一化；同一cpu_sr地址和顺序被检查，但不证明真实端口读写、CPU_SR与保存栈相等、编译器/ABI/硬件正确性。volatile访问次数与位置被结构检查，不扩展为硬件可观察行为的仿真。

## 复用而非重做证明

生产证明：`certiucos/v293/proofs/V293TimeSourceAPI.v`。

| 稳定接口 | 实际结论 |
| --- | --- |
| `V293_source_time_get_exact`、`V293_source_time_set_exact` | 生成的完整函数与原已证明函数定义相等，不只是函数名/正文片段相似 |
| `V293_source_time_entries` | 两个不同函数ID分别对应实际getter/setter及其规格，排除只剩空程序/一个条目的信用 |
| `V293_source_time_domains` | 同一代码/规格映射的域及函数签名一致 |
| `V293_source_time_api_rule` | 同一双函数映射中，真实BuildPreA'/BuildRetA'给出的两个API义务均由已有完整函数契约消除；不假设执行或正文正确性 |
| `V293_source_time_coherent` | 同一个时间IRQ不变量、调度规格和名字局部不变量同时满足GoodI与上述APIRule |

只要求实际不同的参数/局部/全局名字、良构局部不变量及全局名字绑定；没有预设具体时钟值、成功执行前提或抽象更新oracle。getter在临界区内线性化时钟读取，setter在临界区内提交抽象时钟修改；这些语义来自旧契约，不由生成脚本重新定义。

`audit/probes/V293TimeSourceAPIProbe.v` 独立内联两个函数正文/签名及API条目，检查组件接口类型；另对getter无参、setter任意32位参数证明两个实际构造器结果存在。**构造器有结果不等于初始化状态可达或所有前置断言可满足**，本步不冒充全局初始状态存在性证明。

## 事前单因素消融

协议在实现之前保存于 `audit/logs/stage337-time-source-connection/protocol.json`，不回写。

| 候选 | 唯一改变 | AST解码 | 原完整函数等式 |
| --- | --- | --- | --- |
| 原getter/setter | 无 | 通过 | 通过 |
| getter负控 | `ticks = OSTime` → `ticks = ticks` | 通过，实际生成不同模型 | 在原getter等式的reflexivity处拒绝 |
| setter负控 | `OSTime = ticks` → `OSTime = OSTime` | 通过，实际生成不同模型 | getter等式仍通过，在原setter等式处拒绝 |

两种突变从真实配置后完整程序中只替换唯一复制语句，再由Clang重新解析；声明、初始化、临界标记、返回及另一函数全部不变。负控生成器与正控共用代码；完整函数等式的文字在三次检查中不变。脚本要求失败恰在预期等式证明行且为不能统一，缺依赖/语法错/更早失败不计通过。

这是对应关系门的消融，**不是运行时反例**，不证明任何突变可在良构C状态中执行，也不能替代原模型的资源/执行证明。首次开发负控暴露未使用形参无法推断类型，已通过统一显式var参数类型修复；该次早失败及快照保留，不计入成功消融。

## 反方审查与边界

- 对应检查是否只是找字符串？不是：源程序身份重放、完整AST结构/类型/声明身份检查、完整模型逐字比较及Coq函数定义相等分开验证；文本测试仅用于证据约束。
- 是否把源模型重新生成后也同步改了答案？没有：等式右侧是保持原样的已有完整函数，两个旧API契约也保持原样；历史输入哈希另检。
- 是否由早拒绝宣称下游正确？没有：两种受控复制突变必须通过同一个AST解码器并生成模型，随后在原Coq等式处晚拒绝。
- 是否只是两个不兼容的不变量？不是：稳定接口在同一函数映射上同时给出GoodI/APIRule，独立探针展开两条代码和规格。
- 是否等于统一内核程序？不是：这里只有两个时间函数。没有全API表、WFInt/WFIFun、非空全局初始化或最终GOOD_OS。
- CPU hook缺失是否解决？没有。真实hook/合法ISR及同一全局创建—中断路径仍开放，不能借本组件回填。
- 旧审计失败是否被覆盖？没有。旧覆盖与旧证据保持原样，旧身份过期仍须作为失败报告。

最终GOOD_OS、同程序K1–K4与uCOS3尚未完成，**总目标保持active**。本步不提交/推送。

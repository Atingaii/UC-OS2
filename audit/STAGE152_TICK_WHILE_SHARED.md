# 第152步：完整 tick while 与共享任务表的有序抽象执行

## 本步解决什么

上一检查点已构造原完整 `while` 的实际执行，并在同一个输出内存里重建任务记录。本步补上抽象任务表这一侧：等待任务按链表顺序执行原抽象原语，ready 节点跳过，idle 作为终点不遍历；得到的任务表与实际内存重新联合封闭。

固定目标仍为 uC/OS-II V2.93.01，提交 `0c4a48e6fbc6e915714e816196619a5481accf0c`。本步不修改 C、配置、冻结 AST、framework、tactics、旧证明或旧测试。`source-identity.json` 继承原函数精确源码定位及哈希，不声称重新运行 C 前端。

## 从一个例子理解

四个任务记录放在同一个物理 block 的不同、不重叠偏移上。开始时共享表不是空表，当前任务为 ready 节点，另有非空信号量事件表、时钟37，以及独立 canary99。

| 对象 | 执行前 | 只执行第一个等待任务的抽象步 | 完整 while 对应的抽象结果 |
| --- | --- | --- | --- |
| 头任务，优先级10 | 等信号量，delay=1 | ready | ready |
| 第二任务，优先级2 | 时间等待，delay=3 | 仍等待，delay=3 | 仍等待，delay=2 |
| ready 任务，优先级4 | ready | 不变 | 不变 |
| idle，优先级12 | ready，链终点 | 不变 | 不变 |
| 当前任务／事件表／时钟37 | 已存在 | 不变 | 不变 |
| canary99 | 已存在 | 不涉及物理写入 | 实际执行后仍为99 |

不要把“倒计时归零”理解成“收到消息”：这个例子中头任务因超时变为 ready，不意味着信号量消息已经送达。`while` 内也没有推进全局时钟；时钟递增属于第148步的另一个片段，尚需整函数组合。

## 生产接口与证明链

新增 `certiucos/v293/proofs/V293TimeTickWhileShared.v`，稳定接口为 `V293_tick_while_shared_records`。

1. `V293_tick_bindings_run` 从旧表计算新表；不是由调用方提供任意正确答案。`V293_tick_chain_code` 使用现有 `spec_seq` 和 `V293_tick_wait_step`，没有新建执行关系。
2. `V293_tick_chain_transition` 对合法、键不重复的有限链归纳，用原 `spec_stepstar` 逐个执行等待节点。读到的尾部旧记录由不重复键保证不被前面的写入破坏。
3. `V293_tick_bindings_run_map` 证明结果恰为规范 after-map。虽然不相交表更新可交换，探针仍检查代码顺序和第一个真实中间抽象状态，不能只用最终表相等冒充顺序正确。
4. `V293_tick_chain_records_before` 从同一组 raw 链、额外字段及 idle 资源推导旧规范读记录；入口不额外假设第二份可写规范记录，也不把不一致的旧物理／抽象表当作合法入口。
5. 复用第151步原完整 while 执行，输出只有一个 `Mf`。在该 `Mf`，用 `V293_shared_replace_slot` 只更新任务表槽位，联合拥有任务记录、最终局部指针、bitmap、其他共享槽位和调用方 frame。

## 单因素消融：只漏第二项更新

`ChainEntry` 先构造非空入口；`ChainLiteral` 同时得到实际完整 while 和完整抽象执行。`ChainFirstStep` 又真实执行仅含头任务的原抽象原语，得到第一中间表。`ChainFirstIsSingleOmission` 证明这张表与正确最终表相比只把第二任务恢复为旧 delay3，其他记录完全相同。

`ChainOmitSecondControl` 在同一个完整物理执行输出 `Mf` 上检查两条抽象执行：正确表能连接联合后置条件，而遗漏表要求第二任务 delay3，与实际读数2矛盾。它不删除堆、不修改 C、不依赖负例入口提前拒绝，不把尚未执行的下游机制算成通过。

`ChainSlotsReadyIdleFrame` 另查非空事件槽位、当前任务、时钟、ready、idle 和 canary。事件表“保持原值”不等于证明其等待队列关系在超时后仍有效。固定源码的这个超时分支写 `OS_STAT_PEND_TO`、清 pend 状态并置 ready 位，没有在这里修改 ECB 等待表（定位见 `tick-event-boundary.log`）；下一步必须结合超时结果及后续清理建关系，不能为获得定理而强制抽象删除等待队列。

## 不能越界的结论

这是无交错的片段端点连接：存在实际完整 while，并存在对应的有序原抽象执行，端点共享同一个内存／任务表关系。尚不是每个物理小步都匹配抽象步的模拟定理，也不是完整 tick 的 Hoare/API/ISR 证明。

生产定理要求合法、有限、键不重复的 ready／未挂起等待链，可覆盖 time、sem、mbox、q、mutex 与 uint32 倒计时；不含挂起、flags。键不重复不是优先级不重复；联合 byte ownership 也不是生产 ready bitmap／优先级表／事件队列一致性。完整记录只指现有规范 layout，不等于整个 TCB。

入口资源可满足的探针不是生产初始化可达性。完整 tick 的 running 分支入口、局部指针初始化、临界退出、时钟步组合、生产 Inv、初始化、WFIFun、ISR、源码级 `GOOD_OS` 与同程序 K1–K4 仍开放。本步不增加函数覆盖信用：六门仍为94/1/1/1/1/0。旧423失败／1错误、审计源码身份失败和旧 framework 空白问题如实保留。uCOS3 尚未开始，总目标保持 active；本步不提交、不推送。

## 下一步如何做

先补任务表、ready bitmap、优先级与事件等待关系的共同不变量及保持性，先单独对照漏置 ready 位；事件关系的对照需先按实际超时／清理语义确定协议，不能假定 tick 必须修改事件槽位；再组合时钟、running 判定、指针初始化、完整 while 与临界出口。只有这些连接到生产 Inv／规格及原函数入口后，才讨论整函数和 ISR 覆盖，不能把本步端点连接直接计为 `GOOD_OS`。

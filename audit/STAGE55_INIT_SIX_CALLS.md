# 第55步：把内存分区初始化接入实际五次调用之后

## 本步解决什么

第54步已经证明独立的 `OS_MemInit` 完整调用，但其入口要求两个新鲜局部块。单函数通过，不代表它能接到启动主线上。

本步稳定接口 `V293_OSInit_six_calls` 执行：

```text
OS_InitMisc → OS_InitRdyList → OS_InitTCBList
           → OS_InitEventList → OS_FlagInit → OS_MemInit
```

同一个程序 `P`、同一个全局环境、同一个调用者，从入口 `M` 连续执行到 `Mf`；中间 `Mflag` 来自前五次真实调用，绝不是入口假设。两个 Mem 局部块根据这个实际 `Mflag` 的内存上界和全部返回资源构造，互异、新鲜且不覆盖资源。

## 源码身份与入口

- 固定 uC/OS-II V2.93.01、固定配置及原有两类授权修复，没有修改 C。
- `source/result.json` 重新物化、预处理并比较全部94个函数身份。
- `source-connection.json` 比较六个已有函数的准确身份、哈希和 OSInit 中的顺序：零基位置1–6。
- 这段在尚未实现的 `OSInitHookBegin` 后；`OSInitHookBegin/End` 仍仅有声明。
- 手工 AST 语句分组，不是已验证的 C 前端。

## 如何连接

1. 将100字节旧分区表、旧空闲链头当作 frame，穿过前五次调用。
2. 从实际 `Mflag` 的所有权重排得到 Mem 入口，不预置清零结果。
3. 构造两个 fresh 局部块，调用第54步完整函数接口。
4. 执行真实100字节清零、四次循环、尾 NULL、空闲链头赋值及返回释放。
5. 在同一个 `Mf` 保留 Mem／Flag／Event／TCB／Ready／Misc／frame 的可写所有权。

最新两个局部对象共6字节已释放；调用者环境恢复。早先 Flag、Event、TCB、Ready 的局部块可能被后续分配复用，**不声称它们在最终 Mf 仍全部缺失**。

# 第十六阶段：当前 TCB 与真实空间切换目标

## 验证对象与准确边界

本轮延续同一冻结 V2.93.01 的 `OS_Sched`，不改 C、配置或通用框架。源码身份仍为 `74390755cddc42a391055da46b744bbf32e77ba3dc025c2ae55b9441ba6170da`；配置后函数体 SHA-256 仍为 `4bbf6819f5a458dfdadb30dbc8aeaad5156553b98f1b6466d4b89054cbd965e9`，定位 `Source/os_core.c:1702–1732`。沿用原受限 AST 对应工具，不宣称验证了 C 编译器。

目标是消除上一检查点“当前优先级只是任意字节、没有对应当前 TCB”的局部缺口，不是另建调度模型。新增 `V293_current_task tasks tid nc`：当前任务存在于同一抽象任务表，优先级为 `nc` 且小于 13；状态可以是就绪或等待。不把调用调度器前已经阻塞的当前任务排除。

| 稳定根 | 提供的结果 |
| --- | --- |
| `V293_OSSched_current_target` | 最高就绪目标与当前任务指针相同，当且仅当选中优先级等于当前优先级 |
| `V293_OSSched_current_tail_entails` | 从原递增后空间状态推出当前成员、不同目标、实际 `AHprio` 和可写全局目标指针 |
| `V293_OSSched_guarded_current_prefix` | 同一两层 guard、内部调用、指针赋值、优先级比较及计数器前缀；给真实切换 continuation 交付加强前置 |
| `V293_OSSched_current_precondition_witness` | 任意合法 guard 字节、任意计数器下，当前关系与整个前置共同可满足；同时覆盖相同与不同目标 |

优先级表在每个合法优先级只含一个指针。先由两边最高性证明优先级相等，再用同一表槽证明任务指针唯一；不能仅从整数相等跳到指针相等。`AHprio` 消耗原状态 `Aabsdata` 中的抽象任务表，可写全局目标指针来自原绑定与实际赋值输出；不添加“它就是切换前置”的 oracle。

加强后置使用逻辑合取：一侧保留原完整资源，另一侧展示可供切换使用的资源视图。不是把 `AHprio` 与原 `Aabsdata` 用分离合取同时拥有，不复制抽象任务表所有权。当前成员关系仍是待真实共享不变量兑现的接口前提，没有凭空证明整个合法内核运行态。

## 非空洞见证

- 相同目标：沿用原单就绪任务，当前指针为块 7，优先级 12。
- 不同目标：当前指针仍为块 7，优先级 4、状态为时间等待；块 15 的任务优先级 12、就绪。表第 4 槽指向当前任务，第 12 槽指向目标；位图仍只有 12 就绪。
- 两种情况都保持原物理当前指针、只读表／位图、两个 guard、当前优先级字节和可写计数器共存于同一状态。只有任务表与指针表按场景改变，不换掉内部前置。

这证明本轮局部前置可满足，不是证明实际 API 已将任务置为等待，也不是完整初始化／共享不变量见证。

## 未完成的真实 switch 义务

本轮只提供 `SWPRE_NDEAD` 的部分关系与资源，尚未建立它的整个断言：

1. `isrclr`、中断栈／临界区状态与 `SWINVt`。
2. `OSTCBCur` 的完整写权限；现有 `CurTid` 仅提供半权限读取。同值两个半权限可以合并，但不能把一个半权限直接当可写。
3. 当前任务成员与真实 TCB 字段、优先级字节、共享不变量的联系。
4. 调度抽象动作与 `switch_rule` 的前后动作连接。

尤其不能将中断标志作为普通 `GoodFrm` frame 穿过现有内部调用：框架对这些标志不满足 `GoodFrm`。后续必须处理实际调用契约／标志保持，而不是添加不可能满足的 `GoodFrm` 前提。

### 对抗审查：合法自删除不是本轮的“仍存活当前任务”场景

上游 `OSTaskDel` 在移除 TCB、清除优先级表项后仍可能调用 `OS_Sched`。已授权补丁只拒绝调度锁定下的自删除，不禁止解锁状态的合法自删除。因此本轮 `V293_current_task` 前提不能提升成所有调度入口都必须满足的全局要求，也不能通过重新插回已删除 TCB 来制造证明通过。

框架另有 `SWPRE_DEAD`／`switchdead_rule`（后置为 `Afalse`，表示已删除任务不再返回）。后续完整 `OS_Sched` 必须明确区分仍存活与已删除的当前任务路径。本轮证明仅覆盖前者，包括仍存活但已等待的当前任务；后者保持开放。此处只读核对实际上游 `os_task.c` 和通用规则，不修改冻结证据或源码。

`OS_Sched` 完整内部组件、初始化、最终 `GOOD_OS` 和同程序 K1–K4 均未完成；六门覆盖不因新增辅助根而提高。uC/OS-III 尚未开始。

# 第326步：延时调用在调度入口重新建立联合就绪资源

## 本步解决的问题

第325步已连接真实客户端延时调用到原全局切换，但该轨迹的末端记录、位图等观察还不是一个联合拥有的就绪断言。本步先闭合更小的必要边界：**从同一原始客户端调用，到 `OS_Sched` 调用前，重新建立 `V293_ready_full`，并保留完整局部／frame 资源。** 不把已有切换可达性误写成跨切换所有权保持。

目标仍固定为 uC/OS-II V2.93.01，提交 `0c4a48e6fbc6e915714e816196619a5481accf0c`，只保留既有两类授权修复。三个相关函数的准确源码定位、哈希和预处理重放见证据目录，不新增 C 修改。

## 用双任务实例理解

| 项目 | 调用前 | 阻塞后、调度调用前 |
| --- | --- | --- |
| 当前任务 | 优先级4，ready | 优先级4，等待时间3 |
| 另一任务 | 优先级6，ready | 不变，仍ready |
| 就绪低／高行 | 80／0，即位4、位6为1 | 64／0，只保留位6 |
| 当前物理指针 | 仍指向原任务 | 尚未切换，仍指向原任务 |
| 抽象任务表 | 原表 | 同一原抽象阻塞一步提交后的表 |
| 优先级指针表 | 13项，包含两任务 | 不变，仍与阻塞后任务表对应 |
| 局部资源 | 三块在 OS 入口堆 fresh | 参数3、y=0、CPU值0及写权限 |
| frame | canary99、调度控制字段及查找表 | 完整保留，不丢入任意垃圾断言 |

这里的 `V293_ready_full` 表示就绪数据结构、TCB记录、共享抽象字段及当前指针共同一致，**不表示当前任务仍然 ready**。当前任务已经阻塞，另一个 ready 任务保证就绪集合非空。通用定理显式要求存在不同优先级的另一 ready 位；没有偷偷假设阻塞最后一个 ready 任务后就绪表还能非空，也未证明 idle 初始化。

## 生产接口及资源连接

生产文件：`certiucos/v293/proofs/V293TimeDlyReadyClosure.v`。

- `V293_dly_ready_rel_after`：从原任务表／位图对应关系与另一 ready 位，推出清位后位图与阻塞后任务表的对应关系、范围和非空性。
- `V293_dly_ready_resources`：消费更新后的实际字段、其他任务记录、共享字段和物理优先级表，重建规范枚举的完整任务记录。直接复用既有 `V293_owned_task_records_reassemble`，不另造任务表插入机制。联合组成 `V293_ready_full ** (locals ** R)`，并给出同一堆的精确 `V293_ready_loads`。
- `V293_dly_global_call_ready`：稳定接口，输入只有函数绑定、环境、freshness、初始拆分资源和任务对应关系；没有把执行、store、最终不变量作为前提。调用已有真实全局入口／阻塞定理，在**同一个输出堆**同时给出原全局执行、原抽象阻塞一步、任务记录、位图、精确物理读取和联合所有权。

`V293_dly_local_frame` 只是参数、y、CPU和guard资源的简短组合。入口附带的优先级表从 frame 移入就绪结构；并未复制其所有权。`R` 保留在联合分离合取中，而不是从分别满足弱断言推断共同所有权。通用执行仍使用入口 aux 快照，不声称任意 aux 敏感 frame 在动态临界状态下保持。

实例文件：`audit/probes/V293TimeDlyReadyClosureProbe.v`，复用现有非空、分离且可写的两任务堆。`DRglobal_ready` 没有执行前提，调用上述稳定接口；`DRboth_IE` 覆盖初始 IE 两种值；`DRcanary_cpu` 从联合末端资源提取 canary、CPU初值及写权限。客户端环境／堆沿用第325步的独立实例，整条轨迹的 `DXclient` 固定不变；不是把同编号的客户端块和 OS 块拼成一个堆。

## 事前冻结的单因素消融

协议 `protocol.json` 在实现前冻结，SHA256：`60556d7cd8ea64e38bea8c5e0dadac093e4cdd5689cf5be97068204f5f3733b7`。

`DRlate_ablation` 先给出同一个实际执行结果、精确低／高行64／0、任务记录、联合所有权、canary及CPU写权限。对这同一个末端状态：

- 选择旧表时，`DRstale_bitmap` 证明关系不成立：旧表声称优先级4仍ready，实际位4已清。

这是晚期抽象／物理对应关系门的反例，不是只靠早期拒绝。也**不是修改程序后的完整执行**，不声称所有权断言在负例中整体不可满足、整核模拟失败或所有交错都已检查。负例保留的是正例实际物理执行，不伪造一次不提交抽象步骤的全局运行。

## 精确边界与下一步

这**不是完整 API，不是全局记录不变量，不是全局 ProgSim，也不是 GOOD_OS**。本步止于调度调用前；第325步切换可达性仍然保留，但本步尚未把联合就绪所有权运输过实际调度／helper／切换。`V293_ready_full` 不能直接冒充带中断标志条件的 `SWINVt`，两种 IE 下也不能无条件关闭该不变量。

下一步应消费这里的真实末端资源，穿过实际调度调用和 helper 分配／释放，再闭合切换后的所有权。优先级缓存同步、旧任务恢复／return、全交错保持、统一 WFInt、初始化、最终源码级 GOOD_OS 和同程序 K1–K4 仍开放。三函数六阶段登记保持只有 located=true，局部可达／资源结果不自动提升完整函数覆盖。uCOS3 尚未开始，总目标 active。

没有提交或推送 Git。临时 Trust 驱动／对象、缓存备份及本轮一次性生成脚本须逐项复核后清理；保留全部失败快照、旧306份 pyc、用户材料及可复用生产／实例编译产物，实际清理结果见 `cleanup.json`。

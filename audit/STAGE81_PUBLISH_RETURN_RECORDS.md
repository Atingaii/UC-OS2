# 第81步：任务记录穿过真实发布、返回及局部内存释放

## 这一步解决什么

第80步已经证明：发布新任务时，链表、就绪位图、任务计数会实际更新，所有任务记录仍在。但它停在 `return 0` 的表达式前，不能据此说调用者拿到了这些资源。

本步向前接通真实返回：执行返回表达式、释放局部对象、恢复调用者环境。**结论属于真实函数后缀的实质进展，不是整个内核验证完成。**

## 新的上层接口

文件：`certiucos/v293/proofs/V293PublishReturnRecords.v`

稳定接口：`V293_OS_TCBInit_publication_return_preserves_records`

| 项目 | 输入或结论 |
| --- | --- |
| 执行起点 | 第二个真实 Hook 已返回的 continuation 锚点；不假装已经实现或执行 Hook |
| 输入资源 | 包含新任务的全部记录、发布链接/全局字段、9个局部对象和有限幸存单元 |
| 发布 | 调用第80步真实执行接口，借用记录内三个读取字段后归还，不重复权限 |
| 返回 | 调用真实返回/释放执行证明，而不是直接替换成调用者状态 |
| 同一末态 | 返回值0、恢复 caller、全部记录与发布结果及指定 frame 联合拥有 |
| 释放 | 9个局部对象共29字节变为 `None`；后置不再拥有局部 `ptcb` |
| 抽象状态 | `O` 不变；任务 map 是规格参数，不是实际抽象更新 |

主接口没有要求任务记录一定是 ready：新记录是 ready，旧记录可以是既有定义支持的任意状态。允许新旧任务在同一个 block 的不同 offset。

## 为什么不能直接套旧返回接口

旧接口只保留 raw cell 列表，不能单独证明所有任务记录的分离所有权。也不能分别证明“每条记录还在”，然后未经依据拼成联合所有权。

新增辅助 `V293_records_raw_return_many` 先提取一个**原本就联合分离的记录+幸存单元片段**。证明它在释放块上没有字节，在其他块上原样保留，因此还是末态的子内存；随后重建原分离关系。不会靠读取值重新制造写权限。

幸存资源的 block 必须避开局部释放块。这是显式且偏强的适用限制。没有声称任何依赖局部环境/返回值的任意断言 `R` 都可以跨 caller 恢复保持成立；本步只运输任务记录和有限 raw cells 这类 memory-only 资源。

## 独立实例与反例检查

`audit/probes/V293PublishReturnRecordsProbe.v` 从字面构造31个类型单元、72字节的入口，不依赖生产证明中的前置可满足性假设：

- 旧任务 `(301,8)` 优先级12，新任务 `(301,128)` 优先级11，非空旧 head；
- 9个局部块为201–209；其中208保存局部 `ptcb`；
- caller 使用不同的局部环境；哨兵 `(601,0)` 为77；
- 同一个实际返回 `Mf` 给出全记录、两个 map 查询、8项真实内存读取以及全部局部释放事实。

`RetInitialLocal` 证明入口确实拥有可读取的新任务指针；`RetFreedLocalCannotSurvive` 证明实际释放后不可能再拥有局部 `ptcb` 的写权限；`RetActualNoLocal` 把该反例与真实执行、正确记录及8项读取放在**同一个末态**，不是入口早拒绝。

另有编译前冻结的单因素控制：程序、初始内存、证明体、释放后置都不变，只把新记录的后置优先级11改为10。正例通过，负例按预期因类型不匹配拒绝。该控制只说明此证明体对错误目标敏感，不是“所有证明都不可能”的定理。初次控制依赖probe04，最终控制重新对最终probe06产物编译；两组原始日志都保留。

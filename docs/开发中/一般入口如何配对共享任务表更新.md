# 一般入口如何配对共享任务表更新

## 先看这一步解决什么

上一轮已把一个固定例子（优先级8改成6）的具体执行与抽象任务表更新配对。本轮去掉“只能使用这组固定地址和数值”的限制：在原有成功路径的物理前提下，对任意合法入口内存、地址、参数和调用者继续证明。

稳定接口是 `V293_critical_ready_null_owned_execution`，位于 `certiucos/v293/proofs/V293CriticalReturn.v`。它只处理**目标任务已经 ready，且其事件指针为 NULL**的成功路径。

## 从入口到出口，一步步读

| 步骤 | 已知或推导 | 为什么不能省略 |
| --- | --- | --- |
| 1. 固定入口 | 同一原始内存 `M` 中有参数、TCB、任务指针表、ready字节和局部变量写权限 | 不能分别在不同内存里证明“看起来能运行” |
| 2. 连接抽象表 | `V293_priority_table entries tasks`、`V293_bitmap_tasks lo hi tasks`，且目标指针在 `tasks` 中为 ready | 把物理槽位、位图与同一个任务表联系起来 |
| 3. 持有该表 | 原始 `M` 满足 `V293_shared_fields ... tasks ... ** R`，并有外部抽象帧 `join Os Of OO` | 不是另取一个仅有相同数据的假想表 |
| 4. 推导新优先级空闲 | 实际新槽读取为 NULL；表读取关系推出 `nth new entries = Vnull`；任务到槽位关系排除新优先级成员 | 不新增“抽象更新已经可执行”的前提 |
| 5. 实际执行两边 | 复用完整具体路径，同时构造 ready 局部原语的 `spec_step` | 执行完成、store成功、free成功都不是入口 oracle |
| 6. 查看同一出口 | 返回0、恢复caller、释放locals；同一 `Mf` 中有更新后的TCB、表、ready字节和抽象字段所有权 | 出口观察不能来自不同轨迹 |
| 7. 选最高就绪任务 | 更新后的位图与任务表推出最高就绪任务，并在同一 `Mf` 的表槽实际读到其指针 | 这只是出口选择性质，不是正常调度切换已经执行 |

## 怎样理解 `R` 和 `Atrue`

入口可以有任意物理剩余资源 `R`。但函数会写内存并释放局部变量，因此**没有证明这个任意 `R` 在出口仍然成立**。

`V293_shared_fields_owned_transport` 先证明四个抽象字段本身不占具体堆，再把它们放到最终 `Mf`，出口只给 `shared_fields ** Atrue`。`Atrue` 不约束其余堆。抽象外部帧另有 `join Os' Of OO'` 保持；明确列出的具体非写入、非局部字节另有 frame 等式。三者不能混称为“所有资源保持”。此外，抽象当前任务字段尚未与物理 `OSTCBCur` 指针绑定；四字段所有权不是完整共享状态一致性。

## 怎么排除前提彼此冲突

固定探针 `audit/probes/V293ReadyGeneralEntryProbe.v` 中的 `expected_general_owned_nonvacuity`：

1. 在同一个原始具体内存构造全部地址、load、可写权限和局部分离条件。
2. 构造真实抽象字段所有权与空外部帧。
3. **实际调用一般接口** `expected_general_owned_contract`，不是拿旧固定执行见证代替。
4. 得到实际抽象步骤和同一最终内存上的返回轨迹、释放、位图／任务表及最高任务指针读取。

该见证仍是人为构造的合法局部入口，不是从 `OSInit` 可达的状态。其运行标志为1、中断嵌套为1、锁为0，所以真实调度调用走中断受阻分支。

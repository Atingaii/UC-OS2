# 把等待分支接到同一次优先级迁移

## 这一步解决什么

先前已经分别证明：前半段修改优先级表、读取TCB旧坐标并执行ready条件；后半段读取事件指针、判断非空并修改事件等待位图。但两段分别正确，不代表第一段留下的内存满足第二段的要求。

现在稳定接口 `V293_task_prio_prefix_event_nonnull_execution` 在同一个入口内存上把它们连接起来，覆盖固定配置 `OSTaskChangePrio` 源码119–143行。代码和证明仍在原有 `V293OSTaskChangePrio.v`／`V293TaskPrioRekey.v`，没有另造简化操作系统。

## 按实际顺序理解

| 内存 | 刚完成的工作 | 必须确认的事情 |
| --- | --- | --- |
| M | 入口 | 表、TCB、ready与事件都在同一个内存中 |
| M1 | 旧优先级槽清空 | 其余槽及TCB等资源保留 |
| M2 | 新槽放入同一TCB指针 | 两次表写真的先后发生 |
| Mr | 读取TCB的旧Y、BitY、BitX | 不是直接假设三个旧局部正确 |
| Mf | 执行ready判断及可能的迁移 | 事件字节、目的权限仍有效 |
| Me | 从TCB读事件指针并赋给pevent | 旧pevent故意是错误指针，必须真正覆盖 |
| Mg | 非空事件条件成立，迁移等待位 | 在这里同时检查最终表、两张位图、pevent与局部 |

证明中称为 `frame` 的性质，就是“这段代码只写这些位置，因此其他位置保持原值”。连接的关键不是再写一份后缀证明，而是把资源沿真实内存变化运输过去。

## 等待任务不会因此变ready

以下都将优先级从8改成6。每行都包含真实小步执行，而不只是计算结果。

| 程序入口ready旧位 | 入口ready低/高行 | 入口事件低/高行 | 最终ready低/高行 | 最终事件低/高行 | 最终事件组 |
| --- | --- | --- | --- | --- | --- |
| false | 16 / 0 | 0 / 1 | 16 / 0 | 64 / 0 | 1 |
| true | 16 / 1 | 0 / 1 | 80 / 0 | 64 / 0 | 1 |
| false | 16 / 0 | 16 / 3 | 16 / 0 | 80 / 2 | 3 |
| false | 16 / 0 | 0 / 129 | 16 / 0 | 64 / 128 | 3 |

`16=2^4`表示另一个优先级4的任务ready，`64=2^6`表示优先级6对应的位。第一行仅把“等待队列里的旧优先级8”换成6；ready低行没有增加64，所以没有唤醒。第三行原等待行还有其他任务，不能把整行或组误清空。第四行验证不操作的高位保持。

这些是程序内存边界用例，不是完整API状态可达性。第二行只检验两段条件都真的执行，不据此声称合法等待任务同时ready；true/false入口还改变组摘要，不把两行对比叫单因素实验。

## 仍缺哪一步

现在停在143行。固定配置关闭Multi-Pend，下一段实际是162–166行：

```c
ptcb->OSTCBPrio = newprio;
ptcb->OSTCBY    = y_new;
ptcb->OSTCBX    = x_new;
ptcb->OSTCBBitY = bity_new;
ptcb->OSTCBBitX = bitx_new;
```

这五个物理字段目前**还未更新**，所以不能宣布完整函数结束或共享不变量已经恢复。接下来应定位并建模它们，证明实际字段写入，再接到本轮Mg；随后处理入口guard、临界区、调度以及全程序规格／初始化／GOOD_OS。同程序K1–K4闭合后，才进入uC/OS-III阶段。

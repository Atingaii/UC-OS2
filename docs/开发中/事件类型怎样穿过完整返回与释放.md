# 事件类型怎样穿过完整返回与释放

## 1. 这一步解决什么

上一检查点只证明了“读取事件指针并改事件位图”这个子语句不改事件类型。本轮把它连接到前缀、坐标计算、TCB 更新、受阻调度、返回和局部变量释放，并连接原来的实际 ECB 查询及等待列表。

关键不是分别找到两次执行，而是：**同一个入口 M，构造同一个出口 Mf；返回值、任务状态、事件类型等结论都说这个 Mf。**

## 2. 具体例子，表格已补齐

固定例子的事件块是72，事件起点是5；任务指针始终是 `(41,8)`，优先级从8改成6。

| 观察项 | 执行前 | 同一完整执行后 | 为什么 |
| --- | --- | --- | --- |
| 事件类型，绝对偏移5 | 3，信号量 | 3，信号量 | 不在事件写集合内，释放也不删除事件块 |
| 事件组字节，偏移15 | 2 | 1 | 原第二行清空，第一行变成非空 |
| 事件第一行，偏移16 | 0 | 64 | 第6位被置位 |
| 事件第二行，偏移17 | 1 | 0 | 原第8优先级对应位被清除 |
| ready两行 | 16 / 0 | 16 / 0 | 该任务仍在等待，没有变成ready |
| 任务表第8槽 | 指向该TCB | NULL | 删除旧优先级入口 |
| 任务表第6槽 | NULL | 指向同一个TCB | 建立新优先级入口 |
| TCB优先级 | 8 | 6 | 更新优先级及相关坐标 |
| 等待原因、超时、消息 | 等待同一个信号量、1、非空消息指针 | 保持 | TCB细粒度frame仍保留 |
| ECB抽象数据与等待列表 | 信号量数据、包含同一个任务指针 | 保持同一数据和列表 | 修改的是等待任务优先级，不是事件身份 |
| 返回及局部变量 | 函数仍在运行、locals存在 | 返回0、locals释放、caller恢复 | 真实return/free步骤完成 |

信号量的事件类型码是3，TCB的信号量等待状态位是1；它们不是同一种编码。

## 3. 跟着读证明

打开 `certiucos/v293/proofs/V293CriticalReturn.v`，按名称查找：

1. `V293_event_rekey_byte_frame`：事件只可能写相对偏移10、11、12，其余字节不变。
2. `V293_task_prio_prefix_event_update_preserves_writable_event_frame`：使用真实的两次任务表store及事件指针store，串起同一个中间内存；不另行猜测最终状态。
3. `V293_task_prio_coordinates_update_execution_writable_event_frame`：把上述结论接过坐标计算。
4. `V293_critical_event_update_execution_writable_event_frame`：接过SELF解析及入口查询，保留全部原结果。
5. `V293_critical_event_return_tcb_frame_event_frame`：执行真实尾部、返回和free；利用事件块不是local块这一已有条件，将事件frame传到最终Mf。
6. `V293_critical_wait_payload_execution_event_frame`、`V293_critical_event_queue_execution_event_frame`：沿同一次执行继续保留抽象步骤、等待payload、同一实际ECB查询和列表关系。

第6步的类型结论是：**如果入口物理类型匹配同一ECB查询的数据种类，出口也匹配。** 它没有声称入口类型一致性已经由初始化或全局不变量保证。

原来的六个接口名及其完整命题逐字保留，作为增强执行核心的投影；不是两套独立执行证明。旧Coq调用者继续使用原接口，新调用者可以取得更强的frame。

## 4. 怎样验证不是空话

新固定probe：`audit/probes/V293EventReturnFrameProbe.v`。

- 在同一个原始内存中安装信号量类型字节3，重建全部物理前提，实际调用新的完整队列执行接口。
- 同一个Mf中，类型仍为3，等待位图完成8→6迁移，任务仍等待，返回及释放完成。
- 独立语义定理排除入口同时是邮箱类型1。
- 另一个语义定理从**同一次完整执行**得到偏移17由1变0、原始内存单元与最终单元不同。这比上一轮只检查纯写表达式更强。
- 两个负控分别只改最终frame范围或最终类型，保留完整目标Proof；拒绝只说明固定Proof对后置条件敏感，不能代替上面两个语义控制。

# 第一步连接：物理就绪位图与共享任务表

## 先记住三件事

1. `M` 是具体内存：C 程序读写的任务表指针、TCB 字节、ready 位图都在这里。
2. `tasks` 是抽象任务表：每个任务对应 `(priority, status, message)`。
3. `O` 是框架的抽象状态。`Aabsdata abstcblsid (abstcblist tasks)` 表示**持有 O 中这份任务表的资源**，不是另外随便找一个数学集合。

此前已经有从同一具体入口一直执行到 `return 0`、释放全部局部变量的见证。本轮把一个 NULL 事件、ready 任务的成功见证，接到真正持有的抽象任务表更新。仍然没有完成整个内核验证。

## 用一个例子看懂更新

数字越小，优先级越高。两个任务的标识保持不变：

| 观察对象 | 修改前 | 修改后 |
| --- | --- | --- |
| 任务 `(41,8)` 的抽象优先级 | 8，`rdy` | 6，仍为 `rdy` |
| 另一个任务 `(60,0)` | 4，`rdy` | 4，仍为 `rdy` |
| 具体任务表第 8 槽 | 指向 `(41,8)` | NULL |
| 具体任务表第 6 槽 | NULL | 指向同一个 `(41,8)` |
| ready 低行 / 高行 | 16 / 1，即优先级 4、8 | 80 / 0，即优先级 4、6 |
| TCB 优先级 / Y / X / BitY / BitX | 8 / 1 / 0 / 2 / 1 | 6 / 0 / 6 / 1 / 64 |
| 最高优先级就绪任务 | `(60,0)`，优先级 4 | **还是 `(60,0)`，不是刚修改的任务** |

`(41,8)` 中的 `8` 是地址偏移，不会因为任务优先级改成 6 而改变。不要把任务标识与任务优先级混为一谈。

## 本轮新增的连接是什么？

主文件：`certiucos/v293/proofs/V293CriticalReturn.v`，从原 4586 行之后阅读。

### 1. 抽象操作 `V293_ready_prio_step`

这是一个**只针对 ready 情形、已解析任务和优先级的局部抽象原语**，不是完整 `OSTaskChangePrio` 规格：

- 从 `O` 读取实际任务表；目标任务原来确实在表内，状态是 `rdy`。
- 旧优先级小于 13，新优先级小于 12；新优先级尚未被任何任务占用。
- 只把该任务的优先级改为新值，保留状态和消息，并返回零。
- 参数列表为空，因为任务与已解析优先级直接作为原语参数；**不能将其当成处理 SELF、参数错误等全部 API 输入的规格**。

### 2. 所有权步骤 `V293_ready_prio_owned_step`

它不是要求调用者先给一个“抽象执行成功”的前提，而是实际应用框架的 `spec_prim_step`：

- 从 `V293_shared_fields ... ** R` 中取得真正持有的任务表。
- 用 `V293_shared_replace_slot` 更新该抽象槽，保持当前任务、事件表、时钟和 `R`。
- 证明任务域没有增加或删除，抽象当前任务未改变。
- 保持抽象外部帧 `Of`：入口 `join O Of OO`，出口 `join O' Of OO'`。

这一步解决“改的是不是共享状态里那份表”，但它本身不执行 C。

### 3. 分支关系 `V293_ready_prio_branch_relations`

因为入口位图与入口抽象任务表相符，并且目标任务是 `rdy`，可以推导实际 ready 测试为真；**没有额外假定测试结果或出口位图已经正确**。

随后由入口关系推导：

- 更新后的位图对应 `set tasks next (new,rdy,message)`；
- 更新后的物理任务表条目，也对应**同一个** `set tasks next ...`。

### 4. 完整见证连接 `V293_critical_ready_owned_success`

该根实际调用既有完整 NULL 成功执行见证，同时调用上述抽象步骤和关系保持引理。一个最终 `Mf` 同时包含：

- 完整具体执行轨迹与 `return 0`，恢复空 caller 和 `kstop`；
- TCB 五字段、ready 位图、物理任务表与 NULL 事件指针的出口观察；
- 11 个局部块共 17 字节全部释放；
- `(shared_fields ... ** Atrue)` 的出口所有权；
- 同一更新后抽象任务表与位图、物理任务表的关系；
- 优先级 4 任务仍是最高就绪任务。

其中所有权断言自身占空具体堆，再与真正的 `Mf` 分离组合。`Atrue` **不约束剩余堆**，所以这不等于已经恢复完整共享不变量。

固定 probe 还实际构造抽象入口状态，消掉所有权与空外部帧前提，避免仅有一个前提无法满足的条件定理。

## 两个已经证明的反例

- `V293_ready_prio_stale_bitmap_rejected`：出口物理 ready 为 80 / 0，却保留入口抽象任务表，关系不成立。入口表仍宣称优先级 8 的任务就绪。
- `V293_ready_prio_moving_not_highest`：出口直接选择刚改成优先级 6 的任务，不满足最高就绪优先级性质，因为优先级 4 的任务仍在。

它们是 Coq 内核检查的否定命题，不只是修改某个脚本后编译失败。另有三个保留目标完整 Proof 的单因素负控，仅记录各自首次拒绝，不给后续未执行机制授予信用。

## 如何自己阅读，不需要先回答问题

按名称定位，比记行号更稳：

```bash
grep -n 'V293_ready_prio_owned_step\|V293_ready_prio_branch_relations\|V293_critical_ready_owned_success' \
  certiucos/v293/proofs/V293CriticalReturn.v
```

先看上面的表，再看三个定理的 `Proof.` 之前：分清哪些是入口前提，哪些是出口结论。最后只追四个调用：

1. `V293_critical_null_success_return_witness`：具体执行来自哪里；
2. `V293_ready_prio_owned_step`：抽象状态怎样真正更新；
3. `V293_ready_prio_branch_relations`：两种物理表示怎样对应同一任务表；
4. `V293_ready_selection_task`：为什么最高就绪任务仍是优先级 4。

## 下一步，以及还没完成的部分

下一步应把**一般入口**的具体资源、同一抽象任务表和断言组合起来，替代当前固定 NULL 成功见证；继续处理非 ready / 事件情形及真实共享关系，接正常无锁调度。

当前没有证明：完整 API 规格、前向模拟、完整 `V293_ready_inv`、全部 TCB/事件语义、初始化可达、API 入口局部分配、正常无锁选择和切换、ISR/API 全部保持、完整函数环境、`GOOD_OS` 或同程序 K1–K4。具体见证仍是运行 1 / ISR 1 / 锁 0，真实调度调用走中断受阻分支；得到“最高就绪任务”性质，不等于实际执行了一次无锁切换。

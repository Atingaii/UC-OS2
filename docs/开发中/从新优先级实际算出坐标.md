# 从新优先级实际算出坐标

## 这一步解决什么问题

前一步已把“写优先级表 → 读取旧TCB坐标 → ready判断 → 非空事件迁移 → 写回TCB五字段”接成连续执行，但入口还要求新坐标已经算好。本步去掉这个局部便利条件：增加冻结配置后源码110、111、116、117行的实际四次赋值，再接同一后缀。

```c
y_new    = (INT8U)(newprio >> 3u);
x_new    = (INT8U)(newprio & 0x07u);
bity_new = (OS_PRIO)(1uL << y_new);
bitx_new = (OS_PRIO)(1uL << x_new);
```

只改变Coq模型和证明，没有修改固定C、配置、分析端口、框架或正式覆盖。

## 第一遍：把数字看明白

优先级位图每行有8位。以新优先级6为例：

| 局部变量 | 运算 | 结果 | 意义 |
|---|---|---:|---|
| `y_new` | `6 >> 3` | 0 | 第0行 |
| `x_new` | `6 & 7` | 6 | 行内第6位，**索引** |
| `bity_new` | `1 << 0` | 1 | 行选择掩码 |
| `bitx_new` | `1 << 6` | 64 | 行内位掩码，**不是索引** |

因此TCB的Prio／Y／X／BitY／BitX最终分别是6／0／6／1／64。

源码中byte会先提升再参与运算，最终再缩窄。冻结Clang AST确认右移结果类型为`int`，按位与为`unsigned int`，两个左移为`unsigned long`。框架整数语言没有完整C有符号类型区分，本步明确验证0..12范围内算术右移与逻辑右移相等；不推广到负数，`unsigned long`按固定32位分析端口处理。

## 第二遍：知道证明到底检查什么

`V293_task_prio_coordinates_execution` 的入口只给：

1. 真正存于内存的`newprio`；
2. 四个目的局部变量的绑定和写权限；
3. 目的之间及源／目的之间的充分分离；
4. 当前固定13槽的算术容量范围。

它不假定四个目的旧值正确，也不把“store成功”“中间程序已执行”“最终读回正确”当作前提。证明实际计算表达式、构造四次byte store和顺序小步执行，再导出四结果、源保持及四地址以外的byte／permission保持。

**13槽容量不等于完整API合法新优先级范围。** 完整`OSTaskChangePrio`还要检查`newprio < 12`，不能用本局部范围替代。

## 第三遍：为什么把四个初值都设成255

新的物理入口只覆盖原入口的四个局部字节，全部置为255。`V293_coordinate_fixture_delta`证明其他地址不变；四赋值执行后，通过逐地址内存外延性证明中间内存恰好恢复旧后缀的真实入口。

随后调用已经证明的同一后缀，得到：

```text
四局部均为255的实际入口
  → 计算0／6／1／64
  → 写表、读旧TCB、ready判断、非空事件迁移
  → TCB五字段写回
  → 在同一个最终内存检查全部观察
```

`V293_coordinate_update_witness`同时观察13槽、ready位图、事件位图、五字段、局部指针、TCB内部EventPtr及TCB未写字节。这里的连续见证是固定8→6、非空事件路径，不是任意优先级的完整整函数定理；通用接口目前仅覆盖四赋值。

## 四组例子怎么读

| 入口条件 | 出口ready低／高行 | 出口事件低／高行 | 事件组 |
|---|---|---|---:|
| 等待，事件0／1 | 16／0 | 64／0 | 1 |
| ready真支，事件0／1 | 80／0 | 64／0 | 1 |
| 等待，旧事件行仍有其他位16／3 | 16／0 | 80／2 | 3 |
| 等待，保留事件高位0／129 | 16／0 | 64／128 | 3 |

这些是实际内存资源可满足性／程序执行见证，不是完整等待／ready共享关系合法性或初始化可达性。ready真／假还改变行和组，并非单因素实验。

**改优先级没有收到消息。** 等待例子的ready一直是16／0，并不会因为坐标从旧值变成新值就自动唤醒任务。

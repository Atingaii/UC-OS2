# 从列表更新走到两次真实内存写入

后续：已从入口关系推导 ready 改优先级后的值级对应，见[就绪位图对应](改优先级后的就绪位图对应.md)。尚未连接物理位图／TCB 写入；以下保留本步历史范围。

## 这一步在解决什么

之前已经证明了：如果同一优先级表中的旧槽为空，最高就绪优先级就不可能是这个旧优先级。但“把数学列表的旧项改为空”还不等于程序实际执行过写入。

本步处理冻结 `OSTaskChangePrio` 的两条语句：

```c
OSTCBPrioTbl[oldprio] = (OS_TCB *)0;
OSTCBPrioTbl[newprio] = ptcb;
```

对象是两项授权修复后的 `Source/os_task.c` 第 119–120 行；固定源码身份为 `74390755cddc42a391055da46b744bbf32e77ba3dc025c2ae55b9441ba6170da`。源码定位和临时重建核对记录在 `audit/logs/stage26-task-prio-rekey/located-source.json`、`table-write-source.txt`。不是借用另一发行版的代码。

**只处理这两句，不是完整 API，不是完整 C→Coq 翻译器的正确性证明。** 数组按既定分析配置使用 13 项、每指针 4 字节；C 的带指针类型空值使用语言中的 `enull` 表示。片段的索引范围不替代完整函数较早的合法参数检查。

## 可以怎样理解证明

例如任务从优先级 8 改为 6：

| 时刻 | 槽 8 | 槽 6 |
| --- | --- | --- |
| 具体实例入口 | 指向该任务 | 空 |
| 第一条赋值后 | 空 | 空 |
| 第二条赋值后 | 空 | 指向该任务 |

程序不是直接更新一个 Coq 列表。它先从实际局部变量单元读取索引和 `ptcb`，计算数组元素地址，再按字节写入内存。

`V293_OSTaskChangePrio_table_execution` 是上层后续连接用的稳定入口：

1. 接收真实全局数组绑定、局部参数绑定和初始 `load` 观察。
2. 要求两个目标槽各有 4 字节写权限；操作数所在内存块不能是数组块，避免第一条写入悄悄改掉第二条要读的参数。
3. **构造**两次成功的 `store`，而不是把“写入必成功”作为接口前提。
4. 交付真实 `cstepstar`，从这两条赋值执行到 `skip`。
5. 证明最终旧槽读回 `Vnull`，新槽读回目标指针；两写入区间以外的每个字节保持原值。

第二条赋值从第一条写入后的内存重新读取参数；没有把第一次读取结果无条件沿用。

## 怎样接回之前的列表和调度关系

`V293_task_prio_rekey_table_model` 把同一物理数组中 13 项的实际 `load`，传递到“两次列表更新”的抽象视图。它不假装只有数学列表发生了变化。

`V293_task_prio_rekey_ready_choice` 随后证明旧槽最终为空，并在**显式给定更新后位图／任务表／优先级表对应**时，推出最高就绪优先级不是旧优先级。

这里的条件不是已证明的完整 API 效果：位图、事件等待表、TCB 字段更新尚未接到这段执行上。不能反过来把这条条件定理当作它们都已正确的证据。完整 ready 不变量、临界区、初始化可达性和源码切换调用边界也没有因此闭合。

## 为什么保留“新旧优先级不同”

做单因素语义对照：保持同一初始内存、同一目标指针和两次写入顺序，只让两个索引相同。第一次写空，第二次立即写回指针，最终就不为空。

`V293_task_prio_rekey_alias_control` 直接构造两次实际 `store` 并读回结果，证明这个差异；它不是仅靠“删掉一个假设后证明报错”。完整 API 较早会拒绝相等优先级，因此该对照**不是完整 API 合法路径反例**，也不给尚未建模的参数 guard 验证信用。

`V293_task_prio_rekey_fixture_execution` 则无条件给出具体 `8 → 6` 内存实例和实际执行。实例仅分配两个触及的槽和三个操作数；不分配其余 11 槽、不构造物理 TCB，不冒充完整数组／ready 入口或初始化状态。

# 下一步：把成功入口的全部条件放到同一内存

## 1. 上一步为什么还不够？

上一步证明了两个条件定理：**只要入口资源都满足，就能连续执行成功片段、返回 0、释放局部变量并恢复调用者。**

但很多条件分别看起来合理，不代表它们能同时成立。例如，同一地址既被当成必须保留的任务表，又被当成返回时必须释放的局部变量，就会冲突。

这一步不是再假设一次条件成立，而是构造具体内存，实际满足所有条件并应用上述定理。NULL 和非 NULL 事件分支各有自己的一个入口内存；不是声称同一个事件指针同时为空和非空。

## 2. 本次入口和执行结果

两个见证均选择 SELF 参数 255，当前任务优先级 8，新优先级 6，原任务处于 ready 位图中。入口的 `ptcb` 局部指针为空，四个坐标目标字节故意为 255，不能偷用已经计算好的中间状态。

| 对象 | 入口 | 同一执行的最终状态 |
| --- | --- | --- |
| 旧优先级参数 | 255，须读取当前任务解析为 8 | 参数局部存储已释放 |
| 新优先级参数 | 6 | 参数局部存储已释放 |
| 优先级表槽 8 | 指向原 TCB | NULL |
| 优先级表槽 6 | NULL | 指向同一 TCB |
| TCB 优先级 | 8 | 6，坐标和掩码也已更新 |
| ready 两行 | 16 / 1 | 80 / 0，组字节为 1 |
| 非 NULL 分支的事件两行 | 0 / 1 | 64 / 0，组字节为 1 |
| TCB 的事件指针 | NULL 或事件地址 | 对应指针保留 |
| 当前函数的局部存储 | 11 个互异块，共 17 字节，全部可写 | 全部字节查询为 `None` |
| `OSRunning` / 中断嵌套 / 调度锁 | 1 / 1 / 0 | 三个全局块逐字节保持 |
| 返回控制 | 当前函数及调用栈 | 返回 0、恢复空 caller 和 `kstop` |

ready 的数字可以手算：清除优先级 8 对应的第二行第 0 位，再将优先级 6 对应的第一行第 6 位置位。于是 `16 / 1 → (16 + 64) / 0`。事件表同理得到 `0 / 1 → 64 / 0`。

这里刻意检查多个写分支，是程序执行的物理夹具，不代表已证明一个合法整核状态：尤其不能从“非空事件指针加 ready 位”推出等待任务已经收到消息。真正等待消息、旧 ready 位未设置的任务，改优先级并不会自动变为 ready；仍需由实际唤醒操作改变等待／就绪状态。后续共享不变量必须把这些关系约束起来。

17 字节只计算此见证中当前函数的 9 个字节局部变量及 2 个四字节指针局部变量；不是完整内核的内存用量。调度被调函数自己新分配和释放的保存变量属于另一层调用。

## 3. 证明入口在哪里？

文件：`certiucos/v293/proofs/V293CriticalReturn.v`。

按此顺序阅读新增部分即可：

1. `V293_complete_fixture_ge`：把三个运行／调度 guard 的全局绑定加进环境。
2. `V293_complete_fixture_mem`：在原物理入口上写入三个 guard 字节。
3. `V293_complete_fixture_get_frame` / `V293_complete_fixture_load_frame`：证明这三个新地址不改变其他块的字节和 load。
4. `V293_critical_null_success_return_witness`：在 NULL 分支的一份原始内存上，证明全部资源、局部权限和分离条件，再真正应用完整返回根。
5. `V293_critical_event_success_return_witness`：在非 NULL 分支的一份原始内存上完成同样连接，额外保留最终事件位图观察。

见证只对 `ir`、原中断开关和相关栈参数化，没有“请先提供资源正确／执行完成”的前提。最终任务表、位图、TCB、局部释放和 guard frame 都属于同一个 `Mf`，不能分别挑不同的最终内存。

## 4. 为什么不直接计算整份内存？

分离逻辑的内存表示包含有限映射及其证明。直接展开大型具体内存的 `vm_compute` 曾消耗大量内存并被中止，不能当成验证成功。

这里改为逐块证明：先用 frame 排除无关写入，再复用已检查的具体 load 和写权限事实。新增生产证明不再使用 `vm_compute`。这不是放宽条件；仍然证明同一组入口条件和同一个完整执行结果。

## 5. 本次没有证明什么？

- 不是完整 API 的调用入口分配证明：当前函数的 callee locals 已给定。
- caller 固定为空、后续 continuation 固定为 `kstop`；原一般返回根仍允许更多参数，具体见证没有覆盖全部情况。
- `OSRunning=1`，所以真实执行调度调用；但中断嵌套为 1，因此走受阻分支，**没有执行正常无锁选择或任务切换**。
- 没有证明这些具体状态由初始化可达，也没有建立整核共享不变量。
- 仍沿用明确的临界区宏抽象，不是原始端口或机器码证明。
- 最终 `GOOD_OS`、同程序 K1–K4 和 uC/OS-III 阶段均未完成。

## 6. 再下一步怎么做？

先保持上述成功片段及其真实数据更新不变，把其输出的物理 ready／TCB／事件关系接到调度入口的**同一个共享不变量**，而不是直接拼接两个资源归属不同的定理。然后处理中断嵌套和锁都为 0 的分支、准确当前优先级缓存及源码级切换对应。

具体阅读／实现顺序如下，不需要先回答练习：

1. 打开 `certiucos/v293/model/V293SchedulerTasks.v`，读 `V293_bitmap_tasks`：某优先级的 ready 位，必须对应抽象任务表中的 ready 任务；再读 `V293_priority_table`，把这个任务身份接到物理表指针。
2. 在 `V293TaskPrioRekey.v` 中复用 `V293_rekey_ready_tasks_preserved` 和 `V293_rekey_task_table_preserved`。它们已经从旧关系推导出同一次任务表更新后的新关系，不必再写一套模型，也不能直接假设新关系成立。
3. 将这些新关系绑定到本次真实执行的那个最终内存 `Mf`，并证明它们使用共享状态中实际拥有的同一个抽象任务表。单独写“存在一个任务表”还没有完成这一步。
4. 再接调度选择。当前例子 `80 = 16 + 64`，ready 优先级是 4 和 6，数值较小的 **4** 应先被选择，表项指向 `(60, 0)`，不是刚迁移到 6 的 `(41, 8)`。这是下一步检查的预期值，**本轮受阻调度没有实际执行这个选择**。

这些连接完成后，才继续完整函数环境、入口分配、ISR／其他 API 保持性和初始化，最终实例化 `GOOD_OS` 并关闭同程序 K1–K4。uC/OS-III 按老师要求在第一阶段完成后启动。

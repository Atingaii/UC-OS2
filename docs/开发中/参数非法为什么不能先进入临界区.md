# 参数非法为什么不能先进入临界区

## 1．这一步在解决什么

上一步接通了 `OSTaskChangePrio` 的40／41／67错误出口，但它们都在进入临界区之后。错误码42不一样：参数不合法时，应当直接返回，不能先读取任务表、执行SELF解析或修改中断状态。

这里仍只证明固定V2.93.01的一个局部有限执行，不代表整函数或整核已经验证完成。

## 2．补全执行表

`255` 是SELF标记；本固定配置允许的新优先级是0–11。

| oldprio | newprio | 本次控制流 | 结果 |
| --- | --- | --- | --- |
| 12–254 | 任意字节 | 第一个参数检查直接返回 | 42 |
| 0–11 | 12–255 | 第一个检查通过，第二个检查返回 | 42 |
| 255（SELF） | 12–255 | 识别SELF合法，第二个检查返回；不读取当前TCB | 42 |
| 0–11或255 | 0–11 | 参数检查通过，继续进入临界区 | 后续40／41／67或成功路径 |

前三行的构造执行均不执行 `encrit`／`excrit`，不访问共享任务表，也不要求端口函数有实现；原IE、保存栈、ISR状态保持不变。这里说的是已构造的局部执行，不是所有并发交错的性质。

## 3．“算出42”还不等于“函数已经返回”

此前 `V293_task_prio_argument_execution` 停在如下位置：

```text
return表达式已求值得到42
  → 仍带着 kret，调用者环境尚未恢复
```

现在补上的链条是：

```text
同一个临界前缀的原始入口
  → 实际检查参数，求值return42
  → sretv，把返回值交给释放过程
  → 按真实局部环境getaddr逐块free
  → sfreeend，恢复调用者局部环境和continuation
```

新增接口仍在 `certiucos/v293/proofs/V293CriticalReturn.v`，没有增加活动证明文件或修改执行规则：

- `V293_evaluated_return_execution`：从“值已求好”的状态构造真实释放／返回，避免重新执行一次return表达式。
- `V293_invalid_critical_return`：上层稳定接口，连接参数判断至调用者恢复。最终返回42，所有局部字节被删除，非局部块保持；后面的任意语句不执行。
- `V293_invalid_critical_witness`：空全局环境下的物理实例，只有参数、保存变量和共享哨兵。实际释放old／new各1字节和保存变量4字节，哨兵23保留。

接口仍要求局部块不重复且每个局部字节可释放；也要求两个参数均有原始字节读取。这些是充分条件，未声称最小，更没有证明真实API入口自动分配出这些资源。

## 4．怎么核查，而不是只相信说明

独立探针 `audit/probes/V293CriticalInvalidProbe.v` 手写预期接口，并实例化三条不同路线 `(12,6)`、`(8,12)`、`(255,12)`。程序相同，初始中断状态任意，后缀故意包含没有定义要求的 `scall 999`，验证它确实被返回跳过。

运行命令：

```bash
COQBIN=/data/home/lucentzhou/.opam/default/bin/ \
  python3 scripts/check-v293-critical-invalid.py \
  --output-dir /tmp/critical-invalid-review
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s tests -p 'test_critical*local.py' -v
```

门禁同时检查生产／探针编译、`coqchk`、实际根假设、完整／隔离正控与四项单因素负控：返回值42改43、错误接纳合法old、终态IE取反、撤掉可写权限。负控保留原Proof后缀，只检查指定证明拒绝；不把早拒绝解释为后续机制都已验证，也不证明变更后的命题绝对不可证。正式日志在 `audit/logs/stage26-critical-invalid/`。

## 5．接下来做什么

下一条主线是**成功路径**，不是再增加错误码文件：

1. 从同一个参数入口经过encrit、空新槽、SELF、实际lookup及非NULL／非保留判断。
2. 连接已有真正的优先级表、ready位图、TCB和事件迁移后端，运输入口资源；不能假设后端已经执行。
3. 接excrit及真实 `OS_Sched` 调用、成功返回；不能把调度调用替换成“已经返回”的前提。
4. 再补真实局部分配、物理共享关系与整函数Hoare接口，汇入完整环境与初始化。

本轮没有原始端口调用／CPU_SR字节token仿真信用，也没有新的全量source-only干净重编信用。旧完整回归与默认审计失败继续保留，最新实际数字见 `VERIFICATION_STATUS.md`。正式覆盖仍未晋级；源码级 `GOOD_OS` 与同程序K1–K4完成后，才转入老师要求的uC/OS-III。

后续检查点已接通上述成功入口、数据更新及excrit，仍未连接调度调用／成功返回。继续阅读[成功路径如何更新数据并退出临界区](成功路径如何更新数据并退出临界区.md)；本页其余内容保留为1132行历史检查点说明。

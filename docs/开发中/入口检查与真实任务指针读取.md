# 入口检查与真实任务指针读取

## 1. 这一步在解决什么

我们仍在验证固定的 uC/OS-II V2.93.01，不是在重新实现一个操作系统。

前一步已经证明“给定正确的任务指针和真实资源，后面的优先级迁移怎样执行”。现在向函数入口推进：**正确的任务指针必须由原程序自己查出来，不能事先假设局部变量已经装好了答案。**

对应文件：

- 程序：`certiucos/v293/code/V293OSTaskChangePrio.v`
- 证明：`certiucos/v293/proofs/V293TaskPrioRekey.v`
- 本步记录：`audit/logs/stage26-task-prio-entry/`

## 3. 参数检查表，直接看结果

固定配置中 `OS_LOWEST_PRIO=12`，`OS_PRIO_SELF=255`。

| oldprio输入 | newprio输入 | 参数检查结果 |
| --- | --- | --- |
| 0..11 | 0..11 | 继续；不改内存 |
| 255，即SELF | 0..11 | 继续；稍后才读取当前任务优先级 |
| 12..254 | 任意字节 | 返回错误42，不继续后续参数检查／查表 |
| 0..11或255 | 12..255 | 返回错误42 |

`V293_task_prio_argument_execution` 对0..255输入全称量化。非法路径当前证明到“返回表达式已求值、处于kret continuation”的位置，不等于已经释放局部变量并回到调用方。成功接口是 `V293_task_prio_argument_accepts`。

**13个表槽不是newprio可以取12的理由。** 输入限制和数组容量是两件事。SELF解析后的任务优先级使用 `<13` 的实际查表边界；不能把输入oldprio的检查机械复制到解析结果上。

## 4. 两个例子走完全相同的代码

固定新优先级为6，旧任务实际优先级为8：

| 观察项 | 指定任务 | SELF |
| --- | --- | --- |
| oldprio输入 | 8 | 255 |
| 当前任务字段 | 8 | 8 |
| 入口ptcb局部 | NULL | NULL |
| 表的8号槽 | 指向目标TCB | 同左 |
| 表的6号槽 | NULL | 同左 |
| SELF语句 | 条件假，跳过读取 | 条件真，读当前TCB字段，写oldprio=8 |
| 实际查表后ptcb | 目标TCB指针 | 同左 |
| 出口oldprio/newprio | 8/6 | 8/6 |

两份物理入口只差oldprio的一个选择字节，其他地址和权限保持。`V293_entry_fixture_delta` 证明这个差异边界，`V293_task_prio_entry_witness` 实例化实际通用接口，避免前置条件互相矛盾而“空洞成立”。

这只是资源可满足性，不是完整系统状态合法性或初始化可达性证明。参数检查和93–104片段各有真实执行判断，**没有用一个人为组合程序跳过92行临界区调用来冒称连续整函数。**

## 5. 看新接口时抓住三个要点

稳定接口：`V293_task_prio_entry_lookup_execution`。

1. 入口没有“ptcb已经等于正确指针”的load前提，只有四字节写权限；成功store由证明构造。
2. 当前任务指针和字段资源只在 `old=255` 条件下需要。非SELF分支不会偷偷要求一次未执行的读取。
3. “新槽为空、旧槽为非空指针”本身推出两个槽号不同，不另外把这个结论当作oracle。

出口在同一个Mf中检查oldprio、newprio、ptcb和两个表槽，另给出写权限和未写块的byte／permission frame。这里使用充分的块隔离，不声称最弱分离条件。

## 7. 下一步为什么不是直接宣布完成

`OS_TCB_RESERVED` 使用非零整数转指针。目前框架对该表达式的 `evaltype` 返回None；补充边界探针检查了这个事实。这不是证明源程序有错，也不能把条件删掉或用NULL冒充保留值。下一步需要先确定忠实的保留指针表示与语义连接，再补临界区、错误路径、后缀和返回。

更上层还要连接等待／ready共享关系、其他API保持性、函数环境和初始化，最终建立源码级GOOD_OS和同程序K1–K4。修改等待任务的优先级仍然不会收到消息，不会自动变成ready。完成阶段一后才按老师安排推进uC/OS-III。

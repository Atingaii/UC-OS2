# 等待任务改优先级为什么不会被唤醒

## 从你的理解继续

你之前说“不会立即变成 ready，因为等待的消息还未收到”，这个判断是对的。优先级回答的是**有资格运行时谁先运行**；等待状态回答的是**现在有没有资格运行**。修改前者不能代替事件发生。

本轮把这个区别接到同一条具体程序轨迹和实际持有的抽象任务表中，不只演算两组位图数值。

## 一张表看懂入口与出口

本轮同状态见证选用信号量事件，任务8改成6，另一个优先级4任务保持ready：

| 观察项 | 入口 | 出口 | 含义 |
| --- | --- | --- | --- |
| 目标任务优先级 | 8 | 6 | 仅改变其优先级及对应坐标 |
| 抽象状态 | `wait reason Int.one` | 原样保留 | 没有收到等待事件，仍不可运行 |
| 等待原因／超时／消息 | 原值 | 原值 | 不借改优先级完成事件或超时 |
| ready两行 | `16 / 0` | `16 / 0` | 目标任务不加入ready位图；优先级4仍就绪 |
| 当前事件等待两行 | `0 / 1` | `64 / 0` | 事件等待位由8移到6，不是加入ready |
| 任务指针表 | 旧8槽有目标，新6槽NULL | 旧8槽NULL，新6槽有目标 | 指向同一个TCB |
| 目标TCB事件指针 | 指向同一事件 | 不变 | 没有解除等待关联 |
| 函数结尾 | 未执行 | 返回0、释放locals、恢复caller | 这些观察来自同一个最终内存 |

`64`是第6位的掩码，不是任务状态“ready=true”。两种位图不能混用。

## 证明怎样连接起来

稳定接口为 `V293_critical_wait_event_owned_execution`，位于 `certiucos/v293/proofs/V293CriticalReturn.v`：

1. 保留已有一般事件成功路径的全部物理入口条件，不假定程序已经执行完成。
2. 要求同一入口的任务指针表、ready位图、事件等待位图与同一个抽象任务表对应，并实际持有 `shared_fields ** R`。
3. 从新物理表槽读取NULL推导抽象新优先级空闲，不要求调用者提供抽象步骤完成的结论。
4. 利用任务到槽位关系排除同优先级另有ready任务，推出本次ready测试为false；这一步不能只从“目标不ready”直接猜测位图为空。
5. 构造真实框架 `spec_step`，只改任务优先级，保留完整 `wait reason delay` 和消息。
6. 实际调用已有一般事件完整返回根，得到同一最终内存中的TCB、表、ready、事件字节、释放与返回。
7. 同时导出：ready关系不变，事件位图对应更新后的任务表，以及目标成员仍为wait、不是任何ready成员。

`V293_event_wait_tasks` 是“一个事件等待原因的优先级位图 ↔ 同一任务表的等待成员”关系。一般接口把原因限制为同一物理事件地址上的信号量、队列、邮箱或互斥信号量等待。

## 为什么还要做入口见证与负控

固定探针 `audit/probes/V293WaitEventOwnedProbe.v` 的 `expected_wait_event_nonvacuity` 在一个原始内存中构造全部入口条件，实际调用上述一般接口，不用历史固定执行结果代替。

两个预先指定的单因素负控保留完整目标Proof：一个只把出口目标成员改为ready，另一个只让最终事件位图关系使用旧任务表。它们只检验固定证明是否依赖这些结论；拒绝不等于改动后的所有命题都不可证，也不授任何下游机制信用。

另有独立的语义否定定理 `expected_wait_stale_event_rejected`：事件位图已从8迁移到6时，不可能仍对应原入口任务表。它与负控信用分开记录。

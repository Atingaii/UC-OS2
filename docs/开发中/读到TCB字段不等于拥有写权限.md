# 下一步入门：读到 TCB 字段，不等于拥有写权限

## 1. 我们到底在证明什么

最终目标没有变：先把固定 uC/OS-II V2.93.01 的真实代码、规格、共享不变量、初始化和已知反例排除连接到源码级 `GOOD_OS`；完成后再做 uC/OS-III。

上一节已经证明：给等待任务修改优先级后，同一次返回中的抽象任务表，与每个成员的选定物理字段一致。但“字段值一致”还不等于“证明拥有修改这些字段的权限”。这就是本节补的缺口。

本节新增的是**资源断言及其读取解释**，不是又完成了一个 API，也不是整个内核不变量已经闭合。

## 2. 先看一个最小反例

假设地址 `(41,58)` 存着字节6：

| 内存状态 | 读取字节6 | 直接写入7 | 满足完整写权限断言 |
| --- | --- | --- | --- |
| 一个 `false` 权限片段 | 可以 | 不可以 | 不满足 |
| 一个 `true` 权限片段 | 可以 | 可建立 store 的存在性 | 满足所需物理片段，另需值与类型匹配 |

这里 `false` 是框架的半权限，`true` 是完整权限；不是 C 的布尔变量，也不是“这个任务 ready 与否”。两个合法半权限片段的合并规则是另外一回事，不能凭一个可读取的片段推断已经拥有完整权限。

`OwnershipReadableNotWritable` 由 Coq 同时检查三件事：确实读到6；该内存不满足完整字段所有权；向同一内存写7不存在成功结果。这不是用字符串检查替代内存语义。

## 3. 从单个字段逐步组合

本轮生产文件：`certiucos/v293/proofs/V293TaskRecordOwnership.v`。

| 层次 | 已补好的定义／定理 | 它解决的问题 |
| --- | --- | --- |
| 一个字段 | `V293_owned_record_cell` | 同时要求类型匹配和实际完整 `Amapsto` 片段 |
| 一组字段 | `V293_owned_record_cells` | 用分离合取 `**` 组合，不能随意把重叠完整字节当成两个独立资源 |
| 一个任务 | `V293_owned_task_record` | 根据任务优先级和 ready／timewait／IPC 状态选择物理布局 |
| 全部任务 | `V293_owned_task_records` | 遍历实际有限任务表的规范列表 `TcbMod.lst`，不是只检查例子的两个任务 |
| 读数解释 | `V293_owned_task_records_sound` | 从空间资源推出上一节的全称字段对应 |
| 共享状态连接 | `V293_shared_task_records` | 将当前指针、四个抽象共享字段和全部任务字段放在一个空间组合中 |
| 同状态结论 | `V293_shared_task_records_sound` | 得到同一抽象任务表槽位，以及同一个物理内存上的字段对应 |

`**` 不是普通的 `/\`。它要求提供真实的内存片段、抽象状态片段及其 `join`。只把“有一个好内存”与“另一个共享状态”并排写成纯命题，不能替代这个要求。

## 4. 不同任务状态拥有哪些字段

偏移相对于任务指针中的 TCB 基址；任务指针不是只有 block，也包括 offset。

| 字段 | 偏移 | ready | timewait | IPC 等待 |
| --- | --- | --- | --- | --- |
| 优先级 | 50 | 拥有 | 拥有 | 拥有 |
| 位图行／列 | 52／51 | 拥有 | 拥有 | 拥有 |
| 行／列掩码 | 54／53 | 拥有 | 拥有 | 拥有 |
| 消息指针 | 32 | 拥有 | 拥有 | 拥有 |
| 状态字节 | 48 | 0 | 0 | SEM=1、Q=4、MBOX=2、MUTEX=16 |
| 延时 | 44 | 本断言不要求 | 拥有 | 拥有 |
| 等待结果字节 | 49 | 本断言不要求 | 本断言不要求 | 拥有，范围小于256 |
| 事件指针 | 28 | 本断言不要求 | 本断言不要求 | 拥有，指向同一等待事件 |

这是**选定字段**，不是整个 TCB：链表指针、栈、分配器、全局优先级表、ready／事件位图等没有自动包含进来。局部布局是比上一节读数关系更强的入口条件，不意味着真实初始化已经建立它。

## 5. 双任务实例：同一份内存，而不是两份互不相干的例子

测试文件：`audit/probes/V293TaskRecordOwnershipProbe.v`。

| 项目 | 当前 ready 任务 | 另一个等待任务 |
| --- | --- | --- |
| TCB 指针 | `(60,0)` | `(41,8)` |
| 优先级 | 4 | 6 |
| 抽象状态 | `rdy` | 等待信号量 `(72,5)` |
| 状态字节地址／值 | `(60,48)`／0 | `(41,56)`／1 |
| 优先级地址／值 | `(60,50)`／4 | `(41,58)`／6 |
| 消息 | NULL | 指针 `(120,7)` |
| 延时 | 本断言不要求 | 1 |
| 等待结果字节 | 本断言不要求 | 0 |
| 事件指针地址／值 | 本断言不要求 | `(41,36)`／`(72,5)` |

当前指针单独使用半权限编码，指向 `(60,0)`。它和两个任务的完整字段片段确实能够 `join`，再与四个实际抽象槽位组合。`OwnershipSharedLiteralSpatial` 是这个空间断言的具体见证；`OwnershipSharedLiteralRecords` 从该见证得到同状态结论。

**这个实例没有执行 `OSTaskChangePrio`。** 它证明新增资源条件可满足，不是把上一轮的完整执行证明升级成了“所有权在整个 API 中保持”。等待任务仍是等待任务；优先级为6不意味着收到消息或变成 ready。

## 7. 接下来做什么

下一步应在**同一次真实 API 执行**上证明资源更新：改优先级时只更新该任务的相关字节，并把其他字段和任务的资源归还；再把 ready／事件位图、优先级表等关系组合到同一个共享不变量。之后还需要初始化建立及各 API／ISR 保持性。

本轮不以新增文件数、一个可满足例子或一项负控早拒绝替代上述义务。不跳过 uC/OS-II，提前宣称进入 uC/OS-III。

### 本节还不能推出的事实

- 一般共享组合尚未要求 `current` 在任务表中且为 ready，也未要求每个等待事件在 ECB 表中存在。
- 没有证明所有抽象任务表都能实现；具体双任务见证只排除本例入口空洞，不能代替初始化可达性或任意状态的可满足性。
- `V293_owned_record_cell_store` 只证明一个已拥有字段能发生 store；不包含完整 API 的后置资源、任意替换值的类型合法性或全部资源的保持。
- 偏移读取关系在当前内存模型中成立，不额外授予 C 指针边界、结构体布局前端、编译器或 ABI 正确性信用。
- 特别留意：本例实际使用空的抽象 ECB 表，却仍有任务记为等待某个 SEM。这正说明新增组合只约束任务字段和选定共享槽位，尚不是事件／任务相容的完整合法内核状态。

# 成功尾部：真正调用调度，再返回调用者

## 1. 我们正在补哪一段

固定对象仍是 **uC/OS-II V2.93.01** 的配置后源码。最终要求不是演示几个例子，而是闭合源码级 `GOOD_OS` 和同程序 K1–K4，再开展 uC/OS-III。

上一检查点的成功路径已经执行参数检查、临界区入口、SELF 解析、查表、优先级/就绪位图/事件位图/TCB 更新及临界区退出，但停在下列代码之前：

```c
if (OSRunning == 1u) {
    OS_Sched();
}
return (0u);
```

所以“已退出临界区”不等于“整个 API 已返回”。本轮继续补这个缺口。

## 2. 先读懂两个判断

`OSRunning` 必须等于 **1** 才调用调度；不是任意非零都调用。

`OS_Sched` 内部还有两层条件：

```c
V293_EnterCritical(&cpu_sr);
if (OSIntNesting == 0u) {
    if (OSLockNesting == 0u) {
        /* 选择最高就绪任务，更新目标，必要时切换 */
    }
}
V293_ExitCritical(&cpu_sr);
```

| 入口情况 | 实际执行 | 本轮证明边界 |
| --- | --- | --- |
| `OSRunning != 1` | 不调用 `OS_Sched` | 不要求函数环境定义调度器，也不读取调度器的嵌套/锁字节 |
| `OSRunning == 1`，中断嵌套非零 | 真正调用调度器，但跳过内部调度体 | 中断分支连锁变量的绑定也不需要 |
| `OSRunning == 1`，中断嵌套为零、锁非零 | 真正调用调度器，检查锁后跳过内部调度体 | 保留临界区入口/出口及真实返回 |
| 三个条件允许正常调度 | 执行最高优先级选择及可能的切换 | 尚未接入本轮有限执行根 |

“跳过内部调度体”不是“跳过整个函数”：局部变量分配、初始化、临界区入口/出口、返回与释放仍须实际执行。源码 AST 中的未执行分支也保留，不能删掉后声称证明了完整调度。

## 3. 怎样证明调用确实发生

关键根 `V293_success_sched_call_execution` 逐步使用框架的真实规则：

1. `snpcall_step` / `sfexec_step`：查函数环境，进入被调函数；
2. 从当前内存的有界表示推出一个 fresh block；不是让外界提供分配结果；
3. `salloclv_step`：分配 `cpu_sr` 的四字节局部对象；
4. 实际赋值 `cpu_sr = 0`，从写权限构造 store 的结果；
5. 执行 `encrit`、真实字节 guard、`excrit`；
6. `sret_step` / `sfree_step` / `sfreeend_step`：释放局部对象，恢复 caller。

其后置恢复**完全相同的入口内存、调用者局部环境、中断标志与两类栈**。新局部块没有遗留。这是当前框架中显式临界宏抽象的有限执行，不是原始端口调用对 `CPU_SR` 字节的模拟，也不是所有并发交错的证明。

## 4. 现有根分别交付什么

| 根定理 | 起点 | 终点 |
| --- | --- | --- |
| `V293_success_schedule_execution` | 成功更新之后的内存与运行标志 | 条件调用完成，内存/调用环境不变 |
| `V293_critical_null_schedule_execution` | 无事件分支的原始更新前资源 | 更新、退出临界区、真实条件调度调用完成 |
| `V293_critical_event_schedule_execution` | 有事件分支的原始更新前资源 | 同上，并保留实际事件位图更新 |
| `V293_success_tail_return_execution` | 更新与临界区退出之后，且持有待释放 locals 的写权限 | 返回整数 0、释放 task-callee locals、恢复其 caller |

两条“原始资源 → 调度调用完成”根从原内存读运行/嵌套/锁信息，再用实际更新结果的 frame 证明它们未被改坏；没有假设调度已执行或给定中间 store 结果。

它们目前仍停在 `sskip None`。后一个尾根才到 `sskip (Some (Vint32 Int.zero))`，且起点不同。**不能把这两个分开成立的结论直接宣传成整个 API 的单一入口到返回定理。** 还须从原始入口权限证明更新后的全部 locals 可释放，再真正连接。两条更新根另有显式全局读块不别名条件；本轮尾部物理见证不代表这些完整更新根的所有新前提已有统一入口见证。

## 5. 为什么还要物理见证与负控

`V293_success_tail_return_witness` 在同一份物理内存中放入运行标志、中断嵌套、锁字节和两个待释放 locals，构造实际调用/返回轨迹，并检查 locals 消失、全局字节保留。运行值和两个嵌套值可取任意合法字节，只在运行值为 1 时要求调度受阻；中断标志与栈任意。

独立接口探针再实例化非运行、中断受阻、锁受阻三种场景，还专门检查“非运行时函数环境完全为空”和“中断受阻时无锁变量绑定”。这些是可满足性/有限执行见证，不是初始化或可达性证明。

消融一次只改变一个因素：运行比较常量、调用目标、函数定义前提、临界区出口、返回值、恢复环境。保持原证明正文不变，实际运行 Coq，记录第一处拒绝；早期拒绝不能给尚未执行的后续义务授信，也不表示修改后的规格绝对不可证明。

## 6. 下一步怎么做

下一项具体缺口是：**从原始入口写权限推出全部更新后的 task-callee locals 仍可释放**，再把两条更新根与成功尾根连成同一个返回轨迹。不能直接新增“中间内存可释放”前提来冒充这个结果。

随后仍需连接正常调度/切换、真实共享不变量、完整函数环境、初始化、所有剩余 API 和最终 `GOOD_OS`。正式六门覆盖不因这些辅助执行根自动增加。

本轮源码身份、实际门禁、消融首拒绝及完整回归结果见 `audit/logs/stage26-success-sched-return/`；冻结源码与框架不修改，历史失败不覆盖。

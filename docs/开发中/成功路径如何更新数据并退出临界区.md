# 成功路径如何更新数据并退出临界区

## 1．先看全局位置

项目最终要证明：**固定配置的 uC/OS-II V2.93.01 程序符合规格，建立源码级 `GOOD_OS`，并以同程序定理排除 K1–K4 反例。** 完成后再进入老师要求的 uC/OS-III。当前还没有完成这两个阶段。

现在推进的是 `OSTaskChangePrio`：修改任务优先级。此前已连接42／40／41／67错误返回，本次接通成功路径的数据更新和退出临界区，终点仍在实际调度调用之前。

本页中的“执行”，指显式临界宏表示下，现有 Coq 小步规则的局部有限执行；不是已经验证过C前端、原始端口函数或所有并发运行。

## 2．补完整张路线表

| 检查或操作 | 条件／结果 | 当前连接范围 |
| --- | --- | --- |
| 参数检查 | old不是0–11或SELF255，或new不是0–11 | 42：实际释放局部并恢复调用者 |
| 新优先级槽检查 | 新槽已占用 | 40：实际退出临界区、释放并返回 |
| SELF解析与旧槽查询 | 找不到任务 | 41：实际退出临界区、释放并返回 |
| 保留标记判断 | 旧槽是保留指针 | 67：实际退出临界区、释放并返回 |
| 成功，无事件关联 | 旧任务有效、新槽空、事件指针NULL | 实际更新表／ready／TCB，退出临界区 |
| 成功，有事件关联 | 同上，事件指针非NULL且资源满足接口 | 实际更新表／ready／事件／TCB，退出临界区 |
| 成功尾部 | 接下来调用`OS_Sched`，再返回0 | **尚未从本条成功链连接** |

SELF不是一种新任务：它要求从当前TCB读取旧优先级，并写回局部参数，然后继续按同一程序查表。

## 3．用8→6看懂数据怎么变化

物理见证初始 `ptcb=NULL`，四个新坐标局部变量均为255，不预先给出正确结果。

| 数据 | 原值／计算 | 更新后 |
| --- | --- | --- |
| old参数 | 普通入口8；SELF入口255 | 解析后8 |
| ptcb | NULL | 查表得到同一个任务指针 |
| 新行号 `y_new` | `6 / 8` | 0 |
| 新位号 `x_new` | `6 % 8` | 6 |
| 新行掩码 `bity_new` | `1 << 0` | 1 |
| 新位掩码 `bitx_new` | `1 << 6` | 64 |
| 优先级表旧槽8 | 原任务指针 | NULL |
| 优先级表新槽6 | NULL | 原任务指针 |
| TCB | 原优先级／坐标 | 优先级6、Y=0、X=6、BitY=1、BitX=64 |

ready位图不是无条件修改：如果任务原先ready，清旧位再置新位；如果原先不ready，保持ready位图。见证的低行原值16：ready时更新到 `16 | 64 = 80`，不ready时仍是16；高行最后均为0。

事件表与ready表不是同一个对象。事件指针NULL时跳过事件更新，物理事件块72保持；非NULL时实际更新事件自己的行和group，且保留TCB中的原事件指针。事件字节可参数化，这里不把物理布置可满足说成符合完整内核不变量或初始化可达。

## 4．为什么这次不是“假设后端已经运行”

两条稳定接口在 `certiucos/v293/proofs/V293CriticalReturn.v`：

- `V293_critical_null_update_execution`
- `V293_critical_event_update_execution`

入口只提供原内存中的load、可写权限、地址分离、类型／变量绑定等条件。证明先实际执行SELF／lookup到中间内存，再用frame运输原资源，调用当前版本的坐标、表、位图及五字段TCB更新证明，最后执行真实框架`excrit_step`。接口不要求调用者提供中间执行、store或调度已经完成的结论。

内部 `V293_success_segment_execution` 是普通顺序组合引理，当然带有两段执行前提；上面两个公共根从原资源证明并消去了这些前提，不能把内部helper单独当作无条件整函数证明。

中断状态的构造链是：

```text
原IE与原保存栈ci
  → 参数检查通过
  → encrit：把原IE压入ci，关闭中断
  → 原始入口判断、SELF与lookup、实际数据更新
  → excrit：弹出刚才保存的IE，恢复原ci
```

对原IE=true和false、任意原栈及ISR状态使用同一个程序。这里擦除了CPU_SR字节操作，不是字节token与保存栈的仿真。

门禁检查生产／固定字面probe的 `coqc`、`coqchk`、实际假设，以及不导入候选模块的五个正控。probe在本检查点转录成独立固定文件，显式写出预期程序；门禁不会从待测源码重新生成它，也不把它说成独立第二份证明。

七个单因素控制检查SELF、lookup、进入／退出原语、恢复IE、TCB后置和事件后置。退出原语控制同步修改同一tail的continuation表示，避免先在无关continuation匹配处拒绝。所有控制保留完整Proof，只信用实际到达目标义务后的脚本敏感性，不宣称变更命题不可证，也不把早拒绝算作下游正确性。

实际结果与旧回归失败见 `VERIFICATION_STATUS.md` 和 `audit/logs/stage26-critical-success/`。正式覆盖不会因为新文件或新局部定理自动增加。

## 6．下一步直接做什么

下一次继续沿**同一成功链**推进，不另开无关功能：

1. 对齐固定C里成功尾部的真实 `OS_Sched` 调用及函数环境、continuation。
2. 用调度器已证明的资源接口实际接通调用；处理中断／共享资源借还，不假设它已经返回。
3. 对能返回的路径，实际执行return0、局部释放和caller恢复；若涉及不返回的控制流，按相应规则说明，不能强行归入返回结论。
4. 再补真实局部分配、物理／抽象共享关系、整函数Hoare与初始化，汇入最终`GOOD_OS`。

眼下终态是同一局部环境中的 `sskip None`：局部变量仍在，没有释放，没有返回值0，也没有恢复调用者。理解这个停止位置，比把“成功更新”误认为“整函数验证完成”更重要。

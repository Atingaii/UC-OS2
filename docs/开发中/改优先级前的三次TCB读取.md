# 改优先级：先从 TCB 读出旧位图坐标

## 一、这一步在整个目标里的位置

最终目标仍是固定 uC/OS-II V2.93.01 的源码级 `GOOD_OS` 与同程序 K1–K4，再开展 uC/OS-III。这里继续连接 `OSTaskChangePrio`，不是重新做一个独立调度小模型。

当前已经分别有两次优先级表写入和 ready THEN 中位图写入的局部证明。二者之间还有代码，不能把它跳过就宣称整段程序已经连续执行。本步接上其中的三次 TCB 字段读取：

```c
y_old    = ptcb->OSTCBY;
bity_old = ptcb->OSTCBBitY;
bitx_old = ptcb->OSTCBBitX;
```

注意顺序是 `Y → BitY → BitX`，不是字段在结构体中排列的顺序。

## 二、先区分三个量

| C 字段／变量 | 意义 | 旧优先级为 10 时的例子 |
|---|---|---:|
| `OSTCBY` / `y_old` | 所在位图行号 | 1 |
| `OSTCBBitY` / `bity_old` | 组位图中这一行的掩码 | 2 |
| `OSTCBBitX` / `bitx_old` | 行内的位掩码，不是位编号 | 4 |

10 除以 8 的商是 1、余数是 2，所以行号为 1、行内掩码为 `1 << 2 = 4`，组掩码为 `1 << 1 = 2`。

本步的通用执行定理实际上允许三个任意合法字节：它证明程序忠实地搬运内存数据，**不提前假定这些数据一定来自正确的抽象任务不变量**。例子 `1、2、4` 与优先级 10 的位图坐标一致，但稀疏见证没有同时初始化 `OSTCBPrio` 等所有字段，不能算完整任务初始化。

## 三、为什么不能忽略两字节填充

从冻结源码的实际配置后 AST 核对到完整的 21 个 TCB 字段。这里 `OS_FLAGS` 是 16 位，`OSTCBFlagsRdy` 后到 `OSTCBDly` 前有两字节填充：

| 字段 | 配置后类型 | 固定分析布局中的偏移 |
|---|---|---:|
| `OSTCBFlagsRdy` | `OS_FLAGS`，16 位 | 40 |
| 填充，不是 C 字段 | 两字节 | 42–43 |
| `OSTCBDly` | `INT32U` | 44 |
| `OSTCBPrio` | `INT8U` | 50 |
| `OSTCBX` | `INT8U` | 51 |
| `OSTCBY` | `INT8U` | 52 |
| `OSTCBBitX` | `OS_PRIO`，8 位 | 53 |
| `OSTCBBitY` | `OS_PRIO`，8 位 | 54 |
| `OSTCBDelReq` | `INT8U` | 55 |

框架的结构体长度算法直接相加，不自动补齐。模型因此保留全部字段，并在准确位置放置一个仅供布局使用的两字节数组，字段标识为 `-1`，它没有对应 C 左值。否则后面的地址会错两字节；也不能把 `OS_FLAGS` 错写成 32 位来凑长度。

这只是固定源码／配置／分析类型表示的对应，不是对编译器、全部 ABI 或硬件的正确性证明。原 C、配置、分析端口和框架均未因此修改。

## 四、形式化证明究竟做了什么

代码在 `certiucos/v293/code/V293OSTaskChangePrio.v`，证明在已有的 `certiucos/v293/proofs/V293TaskPrioRekey.v`，没有另起一套内核证明树。

1. `V293_tcb_old_field_layout` 检查完整结构大小 56 和这三个字段的类型／偏移。
2. `V293_tcb_byte_field_eval` 从局部 `ptcb` 的实际指针读取，计算 `base + field_offset`，得到实际字段字节；基址可以不是零。
3. `V293_tcb_field_assignment` 从目的字节的写权限构造成功存储和小步执行，不要求调用方直接提供成功的 `store`。
4. `V293_task_prio_read_old_execution` 按源码顺序组合三次读取与赋值。第二、三次读取使用真实中间内存，重新读取 `ptcb`，而不是偷偷复用旧表达式结果。
5. 出口推导三个局部字节的实际 `load`，以及 TCB 三字段、指针和其他内存的保持性。

### 入口为什么要求不混叠

三个局部目的字节需要不同的存储块，而且都不能覆盖 `ptcb` 的指针存储块或 TCB 块。否则第一次写局部变量就可能破坏后面还要读取的数据。

这不是靠口头解释：`V293_tcb_pointer_alias_control` 在同一个实际内存中，把 `ptcb` 的第一个指针字节改为普通字节；随后真实指针读取返回 `Vundef`。这是模型层面的混叠语义控制，不冒称正常 C API 的合法调用反例。

### 为什么还要同状态见证

只有“如果入口满足 A，那么可以执行”的定理还不够；若 A 自相矛盾，定理可能空洞成立。

`V293_tcb_read_entry_witness` 在同一份稀疏内存中同时放入：四字节 `ptcb` 指针、三个 TCB 字段、三个有写权限的目的字节以及四项局部绑定。TCB 基址故意取 8，所以字段实际地址为 60、62、61，而不是机械假定基址为零。

`V293_tcb_read_execution_witness` 消去这些物理入口条件，得到任意合法三字节的实际执行；具体控制把三个局部初值 255 改成 `1、2、4`，可以发现把 BitY 错读成 BitX 等错误。它不包含完整 TCB 分配、初始化可达性或完整 ready 不变量。

## 五、怎样阅读和复现

在项目根目录执行：

```bash
export COQBIN=/data/home/lucentzhou/.opam/default/bin/
export PYTHONDONTWRITEBYTECODE=1
python3 scripts/check-v293-task-prio-rekey.py --tcb
python3 -m unittest discover -s tests -p 'test_task_prio_tcb_local.py' -v
```

Python 测试只是结构性同伴检查，不代替 Coq。子门禁实际重编两源和独立字面探针、打印七根接口的真实假设、执行三次 `coqchk`、同环境正向副本重编，并保留全部原证明执行四项单头部负控：

- 删除目的字节写权限；
- 删除局部目的块与指针块的隔离；
- 把 Y 的偏移 52 谎称为 50；
- 把具体 BitY 出口 2 谎称为 BitX 值 4。

某个前提被去掉后原证明拒绝，并不自动说明所有下游机制都经过独立检查；因此另外保留真实内存混叠控制。七根接口的假设检查也不替代整核信任审计。

## 六、下一步，不跳步

紧接源码的条件是：

```c
if ((OSRdyTbl[y_old] & bitx_old) != 0u) {
    /* 前一检查点已经证明的 ready THEN */
}
```

要用刚刚从 TCB 读出的局部值真实求值此条件，再决定是否进入 THEN。`bity_old` 用于组位图更新，不是这里行内判断的掩码。随后还需把前面的两次表写和这段程序在同一份内存中连续组合，并接 waiting／事件、TCB 五字段更新、临界区和调度。

**当前没有这条完整连续链、完整 `OSTaskChangePrio`、初始化或 `GOOD_OS`。** 验收记录见 `VERIFICATION_STATUS.md`；TCB 子门禁通过也不表示包含外层分支的较大前瞻协议全部完成。

## 七、一个证明脚本层面的性能教训

错误结论也可能“拒绝得很慢”。本步最初用 `apply` 从结果反推通用见证的参数，正确控制快速通过，但错误出口会触发数分钟的转换比较。原完整门禁最终正常拒绝并通过，不应把观察很慢误报成已超时。

单独将 `set` 设为 opaque 的消融没有改善最小复现，所以没有保留它。显式固定见证的 `P、ks、1、2、4` 后，最小复现中正确版本约 0.87 秒通过，错误版本约 0.90 秒在同一定理内拒绝；定理、写内存算法和错误出口都没变。修正后仍重跑完整规范门禁，不以最小测试替代验收。

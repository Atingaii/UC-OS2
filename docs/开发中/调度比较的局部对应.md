# 调度比较的局部对应：为什么不能直接删掉优先级缓存

## 这一步解决什么

前一个检查点发现：框架普通切换更新当前任务指针和抽象当前任务，但不写独立的 `OSPrioCur` 字节。不能未经证明就加强不变量，要求这个字节始终准确。

本次没有修改切换规则或冻结 C，而是先证明更小的一件事：**在同一状态中，若优先级缓存准确、任务表与就绪位图／优先级表一致，那么比较优先级与比较任务指针得到相同结果。** 这给后续源码归一化提供一个局部依据，不是已经批准或完成了整个程序替换。

## 两种判断分别读什么

| 判断 | 实际读取 | 意义 |
| --- | --- | --- |
| 源码片段的优先级判断 | 最高就绪优先级字节、当前优先级缓存字节；提升为 `Tint32` 后比较 | 两个优先级是否不同 |
| 候选归一化片段的指针判断 | 目标任务指针、当前任务指针 | 是否需要换到另一个任务 |

两个表达式都经框架真实 `evalval`／`evaltype` 计算。定理从变量环境绑定、无局部遮蔽和实际 `load` 等式推导表达式求值；没有直接假设复合判断已经算出正确答案。

这不是通用 C 指针比较定理。这里使用已有 CoqImp 的指针值相等语义；完整 C 到该模型的对应仍是独立义务。

## 为什么需要这些前提

- 同一任务表联系就绪位图和优先级表，保证选择值对应最高就绪任务。
- 优先级表的同槽指针关系排除不同任务共享同一优先级的歧义。
- 当前任务存在于这张表中，缓存字节准确记录其优先级。
- 最高就绪字节、目标指针和当前指针的真实读取，分别对应上述选择和任务。

当前任务**不要求就绪**。它可能刚刚进入等待，此时仍须运行调度器，把处理器交给其他就绪任务。

主要接口是 `V293_OSSched_comparison_refinement`，位于 `certiucos/v293/proofs/V293OSSchedPointerCompare.v`。其余引理分别隔离字节读取、指针读取和任务／优先级判定关系。

## 单字节消融：确实不能省略缓存准确性

独立探针构造四块真实内存：高优先级字节、当前缓存字节、目标指针、当前指针。任务关系沿用原见证：当前任务 `(7, 0)` 的优先级为 4、正在等待；目标 `(15, 0)` 的优先级为 12、最高就绪。

| 观察 | 正向实例 | 只改缓存字节 |
| --- | --- | --- |
| 最高就绪优先级 | 12 | 12 |
| 当前缓存 | 4 | **12** |
| 目标指针 | `(15, 0)` | `(15, 0)` |
| 当前指针 | `(7, 0)` | `(7, 0)` |
| 优先级不同 | 真 | **假** |
| 指针不同 | 真 | 真 |

探针 `checked_single_byte_ablation` 证明上述两次真实读取／表达式求值；`checked_instance_relations` 检查同一任务表的关系可满足。它们不是完整物理 TCB、初始化或可达性证明。代理变量编号 200–203 和内存块 1–4 仅用于这项局部检查，不声称已经对应完整 C 全局布局。

这个反例说明两种表达式**不能无条件互换**，不表示真实 C 会把缓存写错，也不是第三项 C 漏洞。

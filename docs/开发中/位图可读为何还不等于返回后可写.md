# 下一步：位图可读，为何还不等于返回后可写？

## 先抓住一个区别

`load` 成功只说明能读到值，不能推出完整写权限。框架中半份额也能读，但不能 `store`。因此，之前已经证明返回后的 ready/event 位图数值正确，仍不足以把它们接入共享空间不变量。

本轮连接的是：**入口的真实完整权限 → 实际更新过程中保持权限 → 返回释放 locals 后保留非 local 字节 → 同一终态中的联合位图资源**。不是再跑一次程序，也不是从正确的读数凭空制造权限。

## 这次程序具体做了什么？

仍是固定 uC/OS-II V2.93.01 的选定成功路径：任务 `(41,8)` 的优先级由 8 改成 6，但仍等待信号量 `(72,5)`，delay 为 1，非空 message 不表示它已经 ready。另一个任务 `(60,0)` 保持 ready／优先级 4；调度因 ISR 嵌套而受阻，不发生正常无锁切换。

你之前的理解仍然正确：**等待条件未满足，不会因为改了优先级或消息指针非空就立即变成 ready=true。**

## 已填好的字节表

`be` 是 event 对象，base 为 5；其位图在同一个对象内，不是三个独立对象。

| 对象／字节地址 | 入口值 | 返回值 | 返回时的事实 |
| --- | ---: | ---: | --- |
| ready 低行 `(30,0)` | 16 | 16 | 完整写权限；属于六字节联合资源 |
| ready 高行 `(30,1)` | 0 | 0 | 完整写权限；属于同一联合资源 |
| ready group `(31,0)` | 1 | 1 | 完整写权限；属于同一联合资源 |
| event 低行 `(72,16)` | 0 | 64 | 等待优先级移到第 6 位；完整写权限 |
| event 高行 `(72,17)` | 1 | 0 | 清除原优先级 8；完整写权限 |
| event group `(72,15)` | 2 | 1 | 高行变空，低行非空；完整写权限 |
| priority table 新槽 `(50,24..27)` | NULL | `(41,8)` | 四字节完整权限，实际 pointer store 存在 |
| priority table 旧槽 `(50,32..35)` | `(41,8)` | NULL | 四字节完整权限，实际 pointer store 存在 |
| oldprio local `(51,0)` | 8 | 已释放／None | 不可再写；不能套用非 local 权限保持结论 |

表里的 pointer store 是从同一返回内存分别存在的后续写操作；不声称任意修改仍保持内核 Inv，也不声称两个存在量词描述顺序执行。

## 读证明的顺序

在 `certiucos/v293/proofs/V293TaskRecordOwnership.v` 原 1528 行之后看：

1. `V293_full_byte_load_encoding`：在已有完整权限的前提下，用实际 typed read 确认该字节的编码。读操作本身不增加权限。
2. `V293_full_byte_cell_owned`：从真实完整字节构造一个空间单元；半份额不能满足前提。
3. `V293_full_byte_cells_owned`：要求地址 `NoDup`，逐个分离出完整字节，构造一份联合资源。不能把六个独立的 `cell ** Atrue` 直接当成六个可分离的 cell。
4. `V293_bitmap_layout`：只枚举 ready 三字节和一个 event 的三字节，复用已有 `V293_owned_record_cells`，不另建状态模型。
5. `V293_critical_event_return_bitmap_owned`：一次真实更新连接一次真实尾部返回；同一个 `Mf` 同时满足执行、原有 loads/frame/free 结论、非 local 完整权限保持和六字节联合所有权。原来的入口前提全部保留，没有把执行或最终权限作为入口 oracle。

然后读 `audit/probes/V293BitmapOwnershipProbe.v`：`BitmapOwnedFullReturn` 重新构造字面入口；后续定理消费同一终态的资源，证明六字节可逐个更新、两个 priority 槽分别可实际 store、旧 event 位图被排除、半份额不能写、已释放 local 不能写。

## 做到哪里，还缺什么？

本轮补上的是位图资源与返回释放之间的连接。**尚未把这份位图资源与上一轮的 CurTid／全部任务字段，在一个顶层契约里联合归还。** 两个局部定理分别给出存在的终态，不能未经证明就把它们认作同一个终态来拼接。

下一步应沿现有一次执行接口继续联合这些资源及 priority table 的空间所有权，再处理正常调度、其他 API／ISR、初始化，最后闭合源码级 `GOOD_OS` 与同程序 K1–K4。之前的正式审计失败仍保留；不是整核验证完成，uCOS3 尚未开始。

实际检查结果与边界见 [本轮审计](../../audit/STAGE26_BITMAP_PERMISSIONS.md)。

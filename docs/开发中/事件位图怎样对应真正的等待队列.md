# 事件位图怎样对应真正的等待队列

## 与上一步的区别

上一步已把任务的等待状态、超时和消息对应到真实TCB字段。但还有一个问题：任务表里说“等待事件E”，不代表抽象ECB里真的列出了这个任务。仅证明位图对应某种wait状态，会漏掉ECB登记不一致的情况。

这一轮增加的连接是：

```text
同一抽象events表的ECB项
       ↕ 双向任务成员关系
同一tasks表中的wait任务
       ↕ 已证明的优先级/事件位图关系
同一实际返回内存Mf中的事件位图
```

## 新关系到底要求什么

`V293_event_wait_queue events tasks eid reason data waiters` 要求：

1. 在实际持有的`events`中，`eid`确实映射到`(data,waiters)`。
2. 等待原因、事件地址和抽象事件数据种类一致，例如信号量等待对应`abssem`，不是邮箱`absmbox`。
3. 对每个任务指针，**在waiters中，当且仅当**它在同一tasks表中等待这个reason。

双向很重要：只从队列指向任务，会漏掉“任务等待却未登记”；只从任务指向队列，会漏掉“幽灵等待者”。这里保留同一列表，因而不会重新排序、去重或删除任务；但没有给任意入口列表额外证明`NoDup`。当前性质不需要该条件，不把它作为无用前提加入。

## 改优先级为什么不改等待者身份

`V293_event_wait_queue_rekey` 分两类证明：

- 被修改任务：优先级从old变成new，但指针、等待原因、超时、消息不变；仍是同一队列成员。
- 其他任务：任务表查询不变，因此成员关系不变。

`events`映射保持原值，所以事件数据与等待者列表保持原值。这不是“事件没有改变”的额外执行前提：实际抽象原语本来只更新任务表；新证明把其更新后的任务表重新连接到这个ECB项。

## 接入真实执行

稳定接口为`V293_critical_event_queue_execution`。它保留上一轮全部原始入口条件，再要求上述入口关系；实际调用既有一般执行根，不以已经执行完成或最终关系作为前提。

在同一个`Mf`上保留实际返回0、局部释放、TCB/任务表/事件位图迁移、等待payload保持等结论，并得到：

- 同一实际抽象出口中的ECB仍含同一waiters列表；
- 最终位图在`p < 13`的有效优先级域内，对应这个列表里的真实任务；同一域内反向也成立。此处并未另行证明任意入口列表中所有任务的优先级都在该域内。

固定探针使用信号量ECB与单元素列表，任务8改成6，另一个ready任务4不在等待队列中。它从原始物理内存构造全部条件并实际调用新接口；不是拿旧固定执行结果充作前提。

阅读顺序：先看`V293_event_wait_queue`三条条件，再看`V293_event_wait_queue_rekey`如何保留指针身份，最后看`V293_critical_event_queue_execution`怎样把关系放回同一次真实返回。无需手算整段Coq证明，也不需要修改固定C。

## 如何检查错误说法

预先固定的两个单因素负控仅改变出口声明，完整Proof保持：把出口列表改成空列表、把出口事件数据改成邮箱。首次拒绝需要在目标Proof内部，且必须核对具体原因，不能把早期拒绝算成所有下游机制都有效。

另有独立语义定理：固定非空ECB不能同时是空列表；信号量等待不能被此关系绑定到邮箱数据。这些与固定Proof敏感性不同，不等于修改C程序后的验证。

此外，单独的`Membership.v`补充检查先显式证明两种输入的ECB查询及信号量类型／地址都正确，再分别删去真实等待者、加入ready任务，验证成员关系的两个方向确实排除这两种错误。它的精确源码和检查记录保存在本轮审计日志，不能用前述“查询先失败”替代这一步。

## 仍没有证明什么

这里的事件种类是**抽象edata种类**，不是物理`OSEventType`字节。锁定源码中事件类型码为MBOX=1、Q=2、SEM=3、MUTEX=4，与TCB等待状态位SEM=1、MBOX=2、Q=4、MUTEX=16不同，不能混用。

真实`OSEventType`、`OSEventCnt`、`OSEventPtr`与抽象数据的完整绑定、物理/抽象当前任务一致性、无重复队列不变量、初始化可达性和正常无锁调度仍待完成。此次实际调度依然受ISR阻塞，出口也不保任意物理frame。

最终仍必须把同一程序、规格、初始化以及K1–K4接到`GOOD_OS`；之后才开始uC/OS-III。

## 下一步怎样做

下一步先补物理事件头，不能只把新的入口前提写出来就宣布完成：

1. 从固定源码和当前结构布局核对`OSEventType`的类型、相对偏移以及四个事件码；不要使用TCB状态位代替。
2. 从实际写操作证明：改优先级只改事件等待位图的相应字节，事件头字节穿过调度尾、返回和释放仍保持；目前已有的大范围frame排除了整个事件块，不能直接拿来证明块内字节。
3. 用同一原始内存构造新增入口绑定，实际调用增强后的一般执行根；不预给最终load。
4. 保持其余条件，单独把事件类型改错，检查精确拒绝位置，再检查物理／抽象当前任务一致性。

这几项完成以后，还要证明API／ISR保持共享不变量及初始化建立它，才能把这些局部结果接向`GOOD_OS`。

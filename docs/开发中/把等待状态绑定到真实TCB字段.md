# 把“仍在等待”绑定到真实 TCB 字段

## 这一步解决什么问题

上一步已经证明：任务优先级从8改为6时，抽象任务仍是wait，ready位图不变，事件等待位迁移。但是，抽象表里写着“等待”，并不自动说明真实内存的状态、超时和消息字段也与它对应。

本轮补这条连接：**在同一入口内存绑定字段，沿实际程序执行保持，在同一返回内存重新读出它们。** 不能分别找到两个不同的出口内存，拼成一个看似成立的结论。

## 一张字段表

以下偏移以固定配置的TCB起点为零；不是其他版本或任意ABI的通用布局。

| 字段 | 模型类型 | 相对偏移 | 改优先级后 |
| --- | --- | --- | --- |
| `OSTCBMsg` | `Tptr Tvoid` | 32 | 原消息指针 |
| `OSTCBDly` | `Tint32` | 44 | 原超时值 |
| `OSTCBStat` | `Tint8` | 48 | 原等待状态 |
| `OSTCBStatPend` | `Tint8` | 49 | 原结果字节 |
| `OSTCBPrio`及四个坐标 | 5个`Tint8` | 50～54 | 按新优先级更新 |

`V293_wait_payload_field_layout` 用Coq核对前四项的类型和偏移。原生状态位来自锁定版本 `ucos_ii.h`：信号量1、邮箱2、队列4、互斥锁16。

`V293_wait_payload` 目前只绑定**未叠加挂起位的单事件等待**。它把真实32位超时、消息指针与抽象wait的相同参数对应起来，并保留显式的pend字节。pend参数并不证明超时或abort生命周期已经处理完毕；组合挂起状态也不在这条局部关系中。

## 为什么原来的frame还不够

原完整返回接口主要说明“没有写入的其他块保持”。但状态、超时、消息与优先级字段都在同一个TCB块里：整个块显然改变了，不能直接用其他块保持来证明它们不变。

新增 `V293_critical_event_return_tcb_frame` 从已有真实更新轨迹取出更细的字节范围：目标TCB中50～54之外的字节保持。随后把这一事实穿过实际受阻调度、退出、return和局部变量释放。释放局部变量不能破坏TCB，因此仍需要明确的堆块分离前提。

最后，`V293_wait_payload_frame` 按各字段的实际读取长度运输load：消息读32～35，超时读44～47，状态读48，结果读49，都不与50～54相交。

## 一般接口与具体例子

新的稳定接口是：

```text
V293_critical_wait_payload_execution
```

它保留上一轮一般等待路径的入口条件、实际持有的抽象任务表、同一表的ready／事件关系，并额外要求入口字段绑定。出口在同一个`Mf`中同时得到：

- 实际返回0、恢复调用者并释放局部变量；
- 优先级、指针表和事件等待位正确迁移；ready位图不变；
- 抽象任务仍等待同一事件，超时、消息不变；
- 真实TCB的等待状态、超时、消息和pend字节仍对应这些原值。

固定探针选用非空消息指针 `Vptr (120,7)`，不是全零消息，以免“保持消息”与“错误清空消息”无法区分。先在原始内存安装字段，再构造全部一般接口条件，实际调用新接口；没有拿旧的执行结果当作入口前提。

## 如何理解反向检查

两个前瞻单因素负控只改出口字段要求，完整Proof不变：

1. 声称出口超时变成原值加1。
2. 声称出口消息被清成NULL。

固定Proof拒绝这些改动，只说明它确实依赖相应后置条件；不等于对修改后的C程序完成验证，也不等于所有类似命题都不可证。另有独立语义定理，证明这个非空消息输入不能同时绑定成NULL。

复核命令（输出目录须不存在）：

```bash

PYTHONDONTWRITEBYTECODE=1 python3 -B scripts/check-v293-wait-payload.py \
  --output-dir /tmp/v293-wait-payload-recheck
```

## 还没有解决的事

这只是局部关系加强，不是完整TCB或共享内核不变量。`OSEventType`、ECB抽象等待队列、物理与抽象当前任务的一致性、挂起组合等待仍未连接。具体见证不是初始化可达状态；调度调用仍受ISR阻塞，不能算正常无锁切换。

出口仍只给共享字段所有权与`Atrue`，不声称任意物理frame跨写和释放成立。完整API Hoare、前向模拟、函数环境、ISR/API保持和初始化仍待完成。必须最终把同一程序、规格、初始化和K1–K4连接到源码级`GOOD_OS`，才进入老师要求的uC/OS-III。

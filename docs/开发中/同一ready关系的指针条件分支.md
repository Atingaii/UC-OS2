## 当前推进：空缓存槽分支与同指针计数轨迹

### 为什么不能直接沿用“缓存准确”

冻结 C 的自改优先级试验已表明：`OSTCBCur` 和目标可以指向同一个 TCB，但该任务的优先级已由 8 改为 6，`OSPrioCur` 仍为 8。原 C 比较的是 `6 != 8`，不是两个指针是否相等。因此它仍递增 `OSCtxSwCtr` 并走向切换调用；把条件换成指针比较，会漏掉这次计数与调用。这里不是修复 C，而是让证明忠实于固定源码。

本次不再假定该分支缓存准确，而从**同一任务优先级表的缓存槽为空**出发：最高就绪任务必须在表内对应一个 TCB 指针，因此不可能选中空槽，原字节条件必为真。该前提只覆盖空槽这一支，不声称任意陈旧缓存都满足它。

| 接口 | 本次连接 | 严格边界 |
| --- | --- | --- |
| `V293_rekey_vacates_cache` | 清空旧槽、填入不同新槽后的列表效应 | 对应冻结 `os_task.c:119–120`；不是这两条 C 写入的小步执行或完整 API 证明 |
| `V293_vacated_cache_selection` | 同一位图／任务表／优先级表中，选中优先级不等于空缓存槽 | 不要求当前／目标指针不同，也不要求缓存准确 |
| `V293_ready_OSSched_vacated_cache` | 沿原字节条件连接两层 guard、真实内部调用／目标赋值、UINT32 增量和普通框架切换 | 关中断后条件接口；没有实际 `encrit/excrit`、完整调用者来源或 `OSCtxSw` 源码对应 |
| `V293_assign_counter_execution`、`V293_OSSched_changed_execution` | 真实表达式、赋值和内存 store 小步，直到指定后缀入口 | 通用 UINT32 模增量，成功写入是显式前提；不越过后缀／调用边界 |

| `V293_cache_lag_pointer_rewrite_execution` | 同一内存、相同计数语句和调用后缀，仅换成候选指针条件：跳过分支、counter 仍为 17 | 对错误替换的局部语义消融；不采用该候选作为冻结程序 |

启用调度时，新 ready 接口消费抽象 `sched` 并恢复同一共享关系；任一 guard 禁止时，归还该关系并保留 `sched;;aop`。普通框架切换本来允许同一任务作为目标，不额外插入缓存同步写入，也不把这种允许当成已经证明真实 `OSCtxSw` 的缓存契约。

## 前一检查点：两份内存之间的源码缓存观察对应

上一检查点已证明，不能把当前 ready 不变量直接加强成“缓存总是准确”并期望框架普通切换自动保持。本次向源码对应推进，而不是再把准确性当前提包装一次：在现有 `V293OSSchedPointerCompare.v` 中证明**两份内存之间**的局部对应，并在现有边界文件中实际实例化。

### 对应保留什么

源码内存 `source` 与框架表示内存 `normalized` 只允许缓存的**一个地址 `(cache, 0)`**不同；其他每个地址的存在性、权限和内容全部相同，同一块的其他偏移也没有删除。该缓存地址本身的权限不由 `same_except` 约束；要执行源码缓存写入，必须另行给出该地址的全写权限。`V293_cache_correspondence` 还要求源码中该地址的实际 `load Tint8` 为参数指定的优先级，不能只给纯快照或把缓存读取从观察中移除；比较定理再用同一抽象任务表将该优先级联系到表示端的当前任务。

| 已证明接口 | 内容 | 不包含什么 |
| --- | --- | --- |
| `V293_cache_related_load` | 任意类型、任意偏移的非缓存块读取在两份内存中相同 | 不声称缓存块内的任意宽度读取都相同 |
| `V293_cache_related_storebytes` | 框架侧非缓存块写入成功时，从逐地址对应构造源码侧同一写入成功及新对应 | 不假设第二份写入成功；但不是完整任务执行模拟 |
| `V293_cache_synchronized_store_refinement` | 框架只写任务指针；源码写同一指针，再显式写准确缓存，构造两个实际成功 `store` 后的新对应 | 不认定真实 `OSCtxSw` 已执行该写入，也不认定这就是实际端口指令顺序 |
| `V293_OSSched_cross_memory_comparison` | 从同一任务表、位图和真实读取证明源码优先级条件与另一内存中的候选指针条件相同；同时交付源码真实缓存变量读取及两种表达式类型 | 不把源码准确性前提从 ready 不变量中凭空推出；不是整个 C 程序的归一化 |

非缓存块限制保证多字节 `load`／`store` 不跨入被映射的字节。两份状态共用全局／局部环境，局部变量无遮蔽和 `high` 不与缓存块混叠都是显式前提。比较所用当前任务关系、最高就绪目标和优先级唯一性来自**同一任务表**，没有复制一个与真实读取无关的决策 oracle。

通用比较接口只观察源码端的 `high/cached` 与表示端的 `target/current`；它本身不交付源码端两指针的读取结论，也没有建立完整物理 TCB 对应。整状态映射仍须证明相关全局块不混叠，再使用非缓存读取定理运输这些指针观察。下面的具体夹具使用不同块，但不能把该实例的块分离自动推广到任意实参。

### 可观察的正向与反向检查

在已有小型边界夹具上增加独立的最高优先级字节与目标指针。两份内存当前／目标指针都指向优先级 12 的最高就绪任务；源码缓存为 12，框架表示中保留旧缓存 4。夹具实际证明了指针存储、显式缓存存储和只差一个地址的关系，并调用通用跨内存定理，不只是把两个算出的常数拼在一起。

| 后续真实观察 | 源码内存 | 框架表示内存 |
| --- | --- | --- |
| 当前缓存变量读取 | 12 | 4 |
| 原优先级条件 `high != cached` | 0（不切换） | 1（会进入分支） |
| 候选指针条件 `target != current` | 本次比较对应的源码端仍用优先级条件 | 0（不切换） |

这同时说明两点：准确源码缓存能支持局部指针比较对应；**仅仅隐藏缓存地址、却保留原优先级条件，并不是观察保持的翻译**。`V293_cache_observation_decisions` 正面证明了真实表达式的不同结果，负控编译拒绝不是这个语义反例的替代物。

该实例是已有小型原始内存夹具的扩展，不是上轮完整 ready 夹具的新执行轨迹，不证明 `OS_SchedNew` 前缀、初始化可达性、调度计数器或端口实现。当前 `csrc/analysis-port/os_cpu.h` 仍只有声明，`OSCtxSw` 真实源码边界契约仍开放。这里证明的是**如果源码边界交付所列存储效果，就能构造何种表示对应**，没有把这个条件当成已经满足，也没有增加公理或修改 C／框架语义。

### 对最终目标还缺什么

本次没有选择或完成整程序缓存消去方案。要用于最终 `GOOD_OS`，必须把对应提升到实际任务／中断边界与执行轨迹，明确同步效果的允许来源及顺序无关条件，并覆盖所有受影响的真实缓存读取／写入、相关 ISR／API、初始化与函数环境。不能仅凭这一条比较等价就把整程序换成指针比较版本。源码与框架仍为原固定对象，六阶段覆盖不变；uC/OS-III 继续排在 uC/OS-II 最终证明之后。

### 新发现的真实 API 边界：同指针仍可能进入切换分支

进一步审查冻结的 `OSTaskChangePrio`：它先更新任务表／位图及 `ptcb->OSTCBPrio`，不直接写 `OSPrioCur`，然后调用 `OS_Sched`。因此，“每次进入调度器前缓存已等于当前 TCB 优先级”不能仅凭切换完成后的同步保证推广到所有调用者。

本轮用**未修改的冻结内核**和既有受控 C 切换夹具实际执行该 API，在 `OSCtxSw` 入口、夹具同步缓存前观察。两支启动状态相同：当前就绪任务优先级 8，另一就绪任务优先级 10，缓存 8、计数器 17；新优先级都为 6。唯一的内核输入变化是 `oldprio`：自任务或另一个任务。

| 切换调用前的真实观察 | 改自任务优先级 | 改另一任务优先级 |
| --- | --- | --- |
| `OSPrioHighRdy / OSPrioCur` | `6 / 8` | `6 / 8` |
| 当前 TCB 的实际优先级 | 6 | 8 |
| 原优先级条件 | 1 | 1 |
| 候选指针条件 | **0** | 1 |
| 原源码计数器 | **18** | 18 |

**结论限于受控边界下的真实 C 执行，不是实际端口、初始化可达性或任务栈切换的 Coq 证明，也不是新增 C 缺陷。** 观察发生在端口同步之前，说明合法重排优先级路径本身就需要处理缓存暂时滞后及同指针切换／计数行为。它不反驳本次有明确准确性前提的局部 Coq 定理，却排除了直接把该前提推广到所有调度入口的方案。下一步应先建立这条真实 API 路径的形式化见证及调度分支对应，再连接允许的源码切换边界；不能只补一个“端口同步后准确”的前提就宣布整程序归一化成立。

## 最新推进：实际 ready 不变量的缓存反例

先前 `V293_priority_boundary_GoodI_obstruction` 要求调用者提供某个不变量接受旧小型夹具的前提；它没有证明实际 ready 不变量接受那个夹具。本次不改该定理，而在同一边界文件末尾构造**完整就绪位图、查表数组、优先级指针表、共享字段、独立缓存及计数器共同存在的具体状态**，直接证明实际 ready 不变量的入口和切换后状态，不留下入口接受假设。

- `V293_ready_boundary_entry`：当前任务在等待，优先级为 4；共享缓存实际读取为 4，准确性成立，完整 `SWINVt` 成立。

# 开发中：同一共享布局的两层调度判断

这是[真实条件分支](同一共享布局的调度条件分支.md)之后的局部推进，不是完整 `OS_Sched` 或最终 `GOOD_OS`。冻结 C、固定配置、两类授权修复、框架及旧正式函数 JSON 均不变。

## 先理解实际执行顺序

`os_core.c` 中 `OS_Sched` 第 1702–1732 行，进入临界区以后，先后判断：

| 条件 | 具体动作 | 本次组合证明交付 |
| --- | --- | --- |
| `OSIntNesting != 0` | 不执行调度主体，也不读取内层锁条件 | 完整入口不变，`sched;;aop` 保留 |
| `OSIntNesting == 0` 且 `OSLockNesting != 0` | 不执行调度主体 | 完整入口不变，`sched;;aop` 保留 |
| 两个字节均为 0，且最高就绪优先级不同 | 调用计算、目标赋值、UINT32 模加一、框架普通切换 | 消耗 `sched`，恢复同一共享不变量 |
| 两个字节均为 0，且优先级相同 | 调用计算、目标赋值，不执行具体递增／切换 | 从同一任务表完成抽象自调度，交付相同恢复后置 |

“调度被禁止”不是“已经调度完成”。所以禁用路径的抽象操作仍然是 `sched;;aop`，不能错误地写成 `aop`。之后怎样在完整调用者规格中表达延期，仍是上层义务。

本页证明的 AST 只有临界区内部的上述判断和主体，**尚不含临界区的进入／退出，也不是完整 C 函数翻译证明**。准确源码定位及 SHA-256 记录在 `audit/logs/stage26-guards/source-location.json`。

## 为什么不能把两个 guard 当成私有局部值

调度锁和中断嵌套计数是共享全局量。其他任务／中断执行之后，不应从切换前的值推断它们仍为 0。本次在原共享单元列表后接入：

```text
prefix arrays / high / priority table
  ++ counter : Tint32
  :: current_priority : Tint8
  :: interrupt_nesting : Tint8
  :: lock_nesting : Tint8
  :: rest
```

- `guardbindings` 只保存变量名到地址／类型的环境绑定，不含物理字节。
- 完整字节权限属于同一 `V293_storage_inv` 的共享存储；不是私有 `px`。
- 入口额外用普通合取 `//\\` 给出两个 guard 的准确只读观察。两个合取项解释同一状态，不复制独占权限。
- enabled 路径沿用统一恢复后置，仅恢复有类型共享存储，不承诺旧 guard、计数器或当前优先级值保持不变。
- disabled 路径未执行主体，完整入口原样返回。

稳定组合接口是 `V293_OSSched_storage_guarded`，接在原 `V293_OSSched_storage_conditional` 上；两层真实 `if` 使用已有的 `V293_OSSched_guards_rule`，没有新增后半段 oracle。

## 入口真的能同时满足吗

`V293_storage_guarded_entry_witness` 构造**一个**状态，包含数组、两个指针、四个独立标量块、唯一抽象槽位以及真实 `sched;;aop`：

| 块 | 变量标识 | 物理内容 |
| --- | --- | --- |
| `12` | `108` | 当前优先级 UINT8 |
| `13` | `109` | 任意 UINT32 计数器 |
| `14` | `110` | 任意合法 UINT8 中断嵌套字节 |
| `15` | `111` | 任意合法 UINT8 调度锁字节 |

Coq 定理对两个 guard 分别量化 `0 <= n < 256`，不是只测试均为 0。沿用两种任务模式：当前任务就绪／最高优先级相等，以及当前任务时间等待／最高优先级不同。它们与任意计数器、任意事件表／时间／continuation 同时存在。

新旧见证复用 `V293_conditional_fixture_physical`，仅提取此前重复的数组、指针及标量构造；旧入口签名不变。新见证先构造完整物理 guard 字节，再分别导出准确只读观察与有类型共享存储。这不是把分别存在的几个状态断言合在一起。

这是入口可满足夹具，不是完整初始化可达性证明，也不覆盖所有物理 TCB 形态。组合接口即使走外层禁用路径，入口仍要求两个 guard 的资源；不应把它推广为“没有锁字节也能满足这个完整入口”。已有独立 `V293_OSSched_interrupt_skip` 才是无需锁资源的短路接口。

不能仅把 `enter/exit` 两条语句包在本定理外就声称完成函数。当前共享不变量主要保证有类型存储及抽象共享核心；位图、优先级表与抽象任务表的关系仍由临界区内入口提供。外部状态进入临界区前后可能受中断影响，不能把这些准确快照跨干扰当作私有 `GoodFrm` 保存。后续必须建立进入后能够重新取得的物理／抽象关系，或如实保留更窄的入口边界；不得把这个缺口改名为调用者假设来报告整函数完成。

## 后续推进：进入临界区后取得新鲜的就绪关系

旧 guard 检查点的上述限制仍成立。本次在既有 `V293OSSchedStoragePrefix.v` 内增加一个更强的关系不变量，尚未把旧 guard 定理替换为使用它的完整函数证明。

### 先抓住这个区别

| 项目 | 旧的有类型存储不变量 | 新的就绪关系不变量 |
| --- | --- | --- |
| 物理资源 | 完整数组、指针和有类型单元 | 复用同一资源布局，不复制内存 |
| 抽象任务表 | 唯一共享任务槽 | 同一任务槽，其 `tasks` 也用于下面两项关系 |
| 就绪关系 | 调用者在临界区内提供准确观察 | 不变量内部存在量化 `lo/hi`，约束物理位图对应 `tasks` |
| 优先级表 | 有类型的指针数组 | 实际 13 槽数组对应同一个 `tasks`，并另外要求指针类型正确 |
| 当前优先级同步 | 入口观察／开放的端口义务 | 仍未解决，不能从任意 UINT8 推断当前任务优先级 |

`V293_ready_invariant_good` 检查真正的 `GoodI`，包括实际 `OSTCBCur` 指针写入和抽象 `curtid` 槽更新后的保持性。位图、任务表和优先级数组不随这两项更新改变，因此它们之间的关系得以保留；不是通过放弃这些关系来证明保持性。精确性复用同一足迹到旧有类型存储的擦除证明。

没有把 `OSPrioCur` 对应关系硬塞进该不变量：框架普通切换只更新 `OSTCBCur` 和抽象 `curtid`。未同步更新的优先级字节无法在该边界下无条件维持此关系，这一缺口必须后续正面解决。

### 真正执行了哪一步

`V293_ready_enter_critical` 使用实际 `encrit1_rule`，程序是 `sprim encrit`：

```text
中断开启、空中断栈、ATopis INUM、私有 frame P
    ↓ 实际 encrit
中断关闭、临界区栈压入 true、就绪关系快照、同一私有 frame P
```

前置没有固定的 `lo/hi/tasks/entries`。后置从刚打开的共享不变量重新取得它们，并把纯对应关系与实际完整数组／指针放在同一个状态断言中。这里的“新鲜”表示不沿用进入前的旧快照，不是分配新的数组。

审查草稿时发现过一个真正的空洞入口风险：空中断栈满足 `gettopis nil = INUM`，不是 0。草稿中的 `ATopis 0` 已在验收前改正，独立探针固定为 `ATopis INUM`，并增加显式中断开启前置的可满足见证。原草稿不算通过证据。

`V293_ready_invariant_witness` 复用此前实际构造的物理状态，证明新不变量和另一半当前指针可以同时持有，并在同一状态观察对应任务表和完整数组。它覆盖当前任务就绪／等待两种模式，以及任意事件表、时间和 continuation；没有重新拼一个脱离物理资源的小模型。另一个开启中断的见证只证明局部规则前置可满足。两者都不是完整系统初始化可达性证明。

前瞻协议及补充位于 `audit/logs/stage26-ready-invariant/PROTOCOL*.txt`。独立探针字面固定不变量资源、真实入口程序、后置及具体／抽象写入接口，不从候选定理生成预期类型。保留旧 6 根，新增 7 根，局部总数为 13。

## 后续纵向连接：同一个关系不变量贯穿真实临界区前缀

这一轮不再只证明“入口能打开关系”。`V293_ready_OSSched_critical_prefix` 已建立下列同一 `V293_ready_inv` 下的规则推导：

```text

  → 实际 excrit，恢复中断开启和原临界区栈，仅交付私有 frame
```

这个程序是**临界区内调用／赋值前缀的局部片段**，不是从原函数抽出来就自动等同于完整 `OS_Sched`。准确地说，它为验证资源归还而把真实 `excrit` 原语接到前缀后，构成一个局部闭合测试程序；原 C 在退出临界区前还会执行 guard 内余下的比较／计数／切换逻辑。这里没有证明移动原 C 的退出位置合法，也没有把这个测试程序当作原函数的完整翻译。其相对函数环境仍要求实际 callee 的既定规格条目，尚未给出完整函数环境连接。guard、优先级比较、计数器与普通切换仍在旧有类型不变量的另一组定理中，未接入上述新关系链。

### 为什么这次可以接通，而不是伪造跨中断快照

- 开启中断的前置只拥有私有 `CurTid` 半份及名字／类型绑定，不带 `lo/hi/tasks/entries`。它们全部在实际 `encrit` 后从共享关系中取得。
- 执行期间由同一个任务槽中的 `tasks` 解释物理位图和实际 13 槽表。借出数组的读取半份后，另一半留给调用方；执行结束把两半真实归还，恢复完整数组和同一关系。不是只保留一个有类型的旧 `SWINV`。
- 中断关闭时，开放执行后置还同时观察最高就绪任务、实际目标单元与共享任务槽，为下一步调度分支准备接口。`excrit` 重新开启中断后**不再保留这份共享值观察**，不能把此前快照当作其他任务运行后不变。

- 同样提取原真实执行的“返回实际物理资源”接口，使旧类型不变量和新关系不变量共用同一份执行证明，不复制两套程序执行推导，也不把新不变量擦除成旧不变量来结束证明。

## 同一关系继续接入真实递增与框架切换

`V293_ready_OSSched_prefix_increment_switch` 把以下程序接到**同一个** `V293_ready_inv`，不再在归还阶段降成旧类型存储不变量：

这是**无条件调用／赋值／递增／切换的局部组合**，不是原 C 的条件控制流，也还没有与上一节的 `encrit`／`excrit` 组合。准确的两个 guard、优先级比较、相等分支和完整临界区仍须纵向连接。入口中的 `tasks/lo/hi/entries` 是关中断后同一状态的准确观察，不能拿它们充当中断开启前的旧快照。普通 `switch_rule` 仍不等于 `OSCtxSw` 的实现或源码／port 对应证明。

### 如何避免再造一套物理布局

复用原 `V293_storage_connected_payload`／`tail`，它们本身不含旧不变量，只描述真实资源。原计数器赋值证明仅提取为任意 ambient `RI : Inv` 下的 `V293_storage_connected_increment_under`；原接口保留为头部不变的 wrapper，没有复制执行证明。精确后置仍是 `Int.add c Int.one`，包括 UINT32 回绕。

新的 `V293_ready_connected_return` 先把完整计数器归入共享存储，再用同一份位图／表／任务关系恢复 ready 不变量。新的 `V293_ready_connected_switch` 直接使用实际 `switch_rule`，切换条件来自同一份共享任务槽、目标指针和保留的当前指针半份，不增加调度 oracle。恢复后置不固定旧 `tasks/lo/hi/entries/c/next`；它表示本线程恢复，不表示切换后目标线程的立即执行状态。

## 后续推进：同一 ready 关系的真实优先级条件双分支

本节是上一节之后的新检查点，不能用上一节的 19 根／17 项历史结果给本次改动背书。新稳定局部接口为 `V293_ready_OSSched_conditional`：

```text
关闭中断后的同状态入口
  ＋ 明确的 V293_current_task tasks tid nc 前提
```

### 准确当前优先级为何必须写成前提

当前 `V293_ready_inv` 联系位图、实际优先级表和唯一共享任务表，但没有保证 `OSPrioCur` 等于抽象当前任务的优先级。框架的普通切换更新具体当前指针和抽象当前任务，不同步这个字节；因此，不能直接把准确关系塞进不变量，再声称已有 `GoodI` 自然保持它。

本次没有改冻结 C、端口或框架，也没有添加隐式赋值。`V293_current_task tasks tid nc` 是**关闭中断后这个入口状态的显式局部前提**。其中 `tasks` 来自同一物理入口的共享任务槽，`nc` 来自同一布局的准确当前字节，允许当前任务就绪或等待。这既不是中断开启前快照，也不是已经由实际 `encrit` 自动取得的事实。完整函数仍须解决该关系的来源及切换保持性。

### 两条路径实际复用了什么

- `V293_ready_conditional_comparison` 从归还前仍打开的同一物理状态取得两个字节、全局绑定与类型，证明真实 `evalval`／`evaltype`，不接受比较结果 oracle。
- 不同分支复用原 `_under` 精确模递增证明与 `V293_ready_connected_switch`。实际递增证明体与本轮开始时逐字相同。
- 相同分支利用准确当前优先级前提和最高就绪选择结果确定 `next = tid`，再消费 `sched`。抽象执行机制只保留一份 `V293_self_schedule_consume`，旧 typed finisher 与新 ready finisher共同复用，而不是复制两套调度执行证明。
- 两支归还的是同一个 `V293_ready_inv`，不是降为旧 `V293_storage_inv`。恢复后置仍是本线程最终恢复，不是目标线程的立即状态，也不冻结旧位图、表、任务、当前优先级、目标或计数器。
- `V293_ready_conditional_entry_witness` 复用旧条件入口的**同一个 `s`**，恢复新关系并保留精确计数器观察。覆盖当前就绪／等待两种模式及任意 UINT32、事件表、时间、continuation；不声称初始化可达性。

原 30 个组合／见证引理和定理头部机械比较不变。新增 6 根独立接口，预先固定总数为 25；探针单独写出完整物理资源、任意 `val` 旧目标、真实调用／赋值／条件／递增／切换 AST、明确的当前任务前提与非冻结恢复后置，不从候选声明生成预期类型。

### 消融如何解释，哪些结论不能给信用

前瞻协议为 `audit/logs/stage26-ready-conditional/PROTOCOL.txt`。新增四项分别只省略新条件分支递增、只省略切换、只擦除归还前实际当前字节的准确观察、只取消相等分支准确当前任务关系前提。原“取消抽象自调度消耗”的唯一执行变异不变，指定拒绝声明随单份机制提取移至 `V293_self_schedule_consume`；不是让控制在无关 wrapper 提前失败。

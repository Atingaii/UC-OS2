# 一次返回如何归还全部任务字段

## 先理解这一步解决什么

上一检查点已经证明：等待中的目标任务修改优先级后，成功更新和返回确实执行，而且目标任务的选定字段仍有完整写权限。

但任务表中还有别的任务。只把目标任务的资源交回来，不能说明整个任务表仍满足空间断言。本次把入口和出口加强为：**对实际抽象任务表的规范枚举，所有任务的选定字段一起拥有、一起更新、一起归还**。

例如任务表有两项：

| 对象 | 入口 | 同一次成功返回后 | 这意味着什么 |
| --- | --- | --- | --- |
| 等待任务 `(41,8)` | 优先级8，SEM等待，delay1，非空消息，完整字段资源 | 优先级6，等待原因／延时／消息不变，仍拥有字段资源 | 修改确实发生，且没有把写权限弄丢 |
| ready任务 `(60,0)` | 优先级4，ready，NULL消息，完整字段资源 | 仍是优先级4、ready、NULL，仍拥有字段资源 | 不仅数值不变，字段资源也一起保留 |
| 抽象任务表 | 实际旧表 | 对同一目标执行 `set` 后的表 | 资源不能绑定一张另外构造的表 |
| 局部变量 | 实际调用环境 | 返回时释放，恢复caller | 不承诺任意物理frame跨释放保持 |

## 证明为什么不能简单“逐个任务拼起来”

`record1 ** Atrue` 与 `record2 ** Atrue` 分别成立，不自动推出 `record1 ** record2`。前两句话可能重复使用同一份资源。

本次从入口取得的是完整分离列表，不是若干条独立的可读断言。目标字段更新使用框架真实store的frame性质，其他记录始终留在同一个分离列表里。返回时再把**整个列表的原空间片段**搬到同一个最终内存；不会从load重建所有权。

关键连接：

1. 用 `TcbMod.lst` 枚举实际任务表；排序保证更新目标时的枚举正确。
2. 更新目标记录五个优先级相关字段，同时保留列表其他部分的资源。
3. 旧成功返回根只调用一次，得到实际最终内存 `Mf` 与实际抽象资源 `Os'`／`OO'`。
4. 目标块用精确字节和权限frame，其他任务块用实际写集合与局部变量释放集合之外的frame。
5. 将全部任务字段与同一张更新后的 `shared_fields` 联合归还。

没有额外要求“每个任务必须分配在不同内存块”。同块的其他记录由整块精确frame及真实store的分离frame处理；本次字面API执行实例仍只测试两个不同块，不冒充同块执行实例。

## 本步边界

这里只拥有选定字段，不是完整TCB布局、链表或分配器不变量。也尚未把 `CurTid` 指针资源、所有事件和ready位图资源与它们统一为完整共享不变量。

实际执行仍是run／ISR／lock为1／1／0的受阻调度成功更新与返回，不是完整外部调用、所有入口分支、正常无锁切换、初始化或全部ISR。整核 `GOOD_OS`、同程序K1–K4及uC/OS-III仍未完成。

## 接下来怎么做

下一步先把当前任务指针资源和全任务记录联合保持，再逐步统一位图、event及调度条件。只有资源与全局关系都接到同一次实际执行，才能继续覆盖正常调度和其他API，最后连接初始化与顶层定理。

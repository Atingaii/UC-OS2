# 为什么两个优先级槽可写，还不等于整表可写

## 先把前后关系串起来

老师要求先用 uC/OS-II 熟悉验证复杂系统软件的流程，再做 uC/OS-III。本仓库固定的是 uC/OS-II V2.93.01 及两类获准修复，不能拿其他版本的证明替代。

上一检查点已在**同一次实际 API 返回**中联合归还当前任务指针、所有任务的选定字段、ready/event 六个位图字节及抽象共享字段。但是，优先级表当时只有读结果，以及两个被修改槽的写权限，尚未取得整表的分离逻辑所有权。

本检查点补的是这块必要基础：**完整表的入口所有权，以及两次真实 store 对整表资源的保持**。尚未把它接进上一检查点的 API 联合返回；二者不能直接当作一个已经完成的定理。

## 第一步：明确要保住什么

固定配置下表有 13 个槽，每槽是四字节指针，共 52 字节：

| 对象 | 这次需要的证据 | 已实现的边界 |
|---|---|---|
| 全部 13 个槽 | 每槽都包含实际的四字节内存片段 | `V293_priority_cells` 描述全部槽 |
| 全部 52 字节 | 每个字节均持有完整写权限 | 入口明确要求 `V293_bytes_writable ... 52` |
| 每个指针值 | 能读出对应值，且值满足指针类型 | 读结果和 `Forall` 类型条件分别列出 |
| 修改旧、新槽 | 前后是实际 `store` 得到的 M1、M2 | 保留整表及原有 frame `R` |
| 其他 11 个槽 | 没有被两个 store 丢失或抹掉 | 返回的空间资源仍包含所有槽 |
| API 的同次终态 | 与当前指针、任务、位图合成同一份资源 | **尚未连接，不计完成** |

`load` 只说明可以读，不能凭空提供写权限。纯数学关系 `V293_priority_table` 也不能独自证明所有槽的值都满足指针类型，因此这里保留显式的类型前提。

## 第二步：看一个已经填好的例子

新探针构造了一份完整的字面内存，不用已经完成的执行轨迹作入口 oracle：

| 槽号 | 入口值 | 两次 store 后 |
|---|---|---|
| 4 | 指向任务 60 | 仍指向任务 60 |
| 6 | `Vnull` | 指向任务 41，指针偏移为 8 |
| 8 | 指向任务 41，指针偏移为 8 | `Vnull` |
| 其他 10 槽 | `Vnull` | 仍为 `Vnull` |

实际顺序是：

1. 清空旧优先级 8 的槽，即字节偏移 `4*8=32`。
2. 把同一任务指针写入新优先级 6 的槽，即字节偏移 `4*6=24`。
3. 在第二次 store 的**同一个 M2**中归还更新后的整表，并从整表资源读出所有槽。
4. 验证任意一个合法槽仍可进行一次类型正确的 store，且该次 store 后整表仍保留。

第 4 项是从同一终态分别验证各槽可以写，不是声称已连续执行 13 次写操作，更不是声称任意写都保持完整共享不变量。

**优先级表不是 ready 队列。** 修改表中 8→6 的映射，并不能推出任务已经 ready。上一检查点的等待分支仍保留 SEM 等待状态；要等待的消息／事件尚未到达，改优先级不会自动解除等待。本次独立表探针本身不建立任务状态或初始化可达性。

## 第三步：看反例，避免证明错目标

| 控制或反例 | 实际改变 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 半份额字面表 | 全表字节只有只读半份额 | 13 槽可读，但第一个槽的 store 失败 | 不能据可读推断可写 |
| 两槽稀疏字面内存 | 只给旧、新两个槽的完整字节 | 两槽可写，而整表 52 字节条件不成立 | 不能推广到未分配的 11 槽 |
| `ReadOnlyTableBytes` 负控 | 仅将构造器的完整字节权限换成半份额 | 检查完整权限是否是必要前提 | 不给下游整核机制记功 |
| `StaleFullTable` 负控 | 仅将两次 store 后的更新表改回旧表 | 检查后置条件是否真正反映更新 | 不证明 API 的所有分支 |

构造证明中的 `freeb` 只是用来分离数学上的内存片段，不代表本次 API 又执行了一次释放。

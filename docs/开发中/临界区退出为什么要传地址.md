# 临界区退出为什么要传地址

## 先分清这轮在修什么

这次发现的不是 uC/OS-II 上游 C 的错误，而是我们手写 Coq 程序模型的对应错误。固定 C、配置、CPU 分析端口和通用证明框架没有改变，也没有增加第三类内核补丁。

本项目分析端口里是：

```c
typedef unsigned int OS_CPU_SR;
void V293_ExitCritical(OS_CPU_SR *saved);
#define OS_EXIT_CRITICAL() V293_ExitCritical(&cpu_sr)
```

- `cpu_sr`：局部变量中保存的整数值。
- `&cpu_sr`：这个局部变量的地址。
- 被调用函数声明要的是后者。Coq 的表达式必须写成 `eaddrof (evar cpu_sr)`，而不是 `evar cpu_sr`。

原模型在三个错误分支上写成了传值：新优先级已占用（40）、旧任务不存在（41）、表项是保留标记（67）。先前成功路径跳过这些分支，因此成功路径证明通过不能替这些调用作证。

## 第一步：先使错误可重复出现

运行：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check-v293-critical-args.py
```

命令重新从冻结源码物化配置、运行 Clang 预处理并读取实际 AST，不以 Coq 模型生成 C 端期望。它检查函数实际的一个进入和四个退出调用，参数都必须是对 `unsigned int` 局部 `cpu_sr` 的取地址，表达式类型为 `OS_CPU_SR *`；再检查目前已建模的三个错误退出。

最初的提取正则只捕获了两个分支，已保留该开发失败；修正提取器后，`red-02.log` 才是三个分支全部捕获的修复前红灯证据。只改模型三处参数及说明注释后，同一命令变绿。还有逐一把三个参数改回值的回归测试，不能靠另外两个正确调用掩盖一个错误调用。

这是一个窄范围手工映射检查，不是已经验证的通用 C 前端。

## 第二步：让模型真正走到调用边界

新接口 `V293_task_prio_error_exit_arguments` 从真实入口语句结构中确定两个错误分支，再和保留分支一起执行。不是只检查源文件中出现了 `eaddrof`。

它只要求局部环境里有 `cpu_sr : Tint32` 的绑定，不预给它的 load 结果，也不假设被调用函数的实现或执行结果。实际执行依次是：

1. 展开 `sseq`，把对应 `return 40/41/67` 留在 continuation。
2. 开始 `scall`，确认参数类型 `Tptr Tint32`。
3. 执行取地址，得到 `Vptr (bs, 0)`。
4. 到达 `sfexec`，带着实际指针值和指针类型，内存仍是原来的同一个内存。

`V293_cpu_sr_unreadable_witness` 还给出一个闭合区分实例：局部名字有绑定，但内存为空。读 `cpu_sr` 得到 `None`；取 `&cpu_sr` 仍能得到地址。这是对两种表达式不同的语义证据，不是合法初始化状态或完整内核可达状态的证明。

## 第三步：不要把边界误当作完成

这里停在 **准备执行被调用函数** 的 `sfexec`，还没有：

- 从函数最初参数入口执行全部错误 guard；
- 执行 CPU 端口函数体；
- 建立保存 token 与框架中断状态的关系；
- 证明实际中断状态已经恢复；
- 执行错误返回、释放局部或回到调用方。

普遍量化的 `P` 可以没有这个函数的定义，这也说明新结论不能推出调用已经完成。下一步应把真实 guard 连接到这些调用，再在明确的 CPU 抽象边界上连接进入／退出，而不是把它们改成 `skip`。

## 历史记录怎么处理

旧探针和部分测试也手写了同一个错误的传值期望。它们不能因为曾经通过就成为源码真相；本轮保留它们和历史日志，实际重放、公开失败，不用改旧期望来伪造持续绿色。原有成功根的证明代码保留并需重新编译；编译通过和旧字面接口匹配是不同检查。

本轮实际结果见 `audit/logs/stage26-task-prio-critical-args/`，当前状态见根目录 `VERIFICATION_STATUS.md`。整核 GOOD_OS、同程序 K1–K4 和后续 uC/OS-III 都不能由本页的局部结论替代。

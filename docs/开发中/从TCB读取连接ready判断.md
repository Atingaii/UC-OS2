# 从 TCB 读取连接到 ready 判断

后续步骤见[从两次表写串起 ready 更新](从两次表写串起ready更新.md)；下文保留本检查点当时的范围。

## 这一步解决什么

前一步证明三个字段能够被正确读取；再前一步证明 ready 分支的位图写入。单独成立不代表它们能够连续执行：前段赋值可能破坏后段使用的局部变量或位图。

本步在**同一份真实中间内存**中接起这两段，不再由调用方额外提供“读取完成后的六个局部值”。稳定接口是 `V293_task_prio_read_ready_execution`，位于 `certiucos/v293/proofs/V293TaskPrioRekey.v`。

## 先读懂实际代码

固定配置下的关键顺序是：

```c
y_old    = ptcb->OSTCBY;
bity_old = ptcb->OSTCBBitY;
bitx_old = ptcb->OSTCBBitX;
if ((OSRdyTbl[y_old] & bitx_old) != 0u) {
    /* 清除旧 ready 位，必要时清除旧组位，再设置新组位和新 ready 位 */
}
/* 这里不是 else；后续事件处理是独立的判断。 */
pevent = ptcb->OSTCBEventPtr;
if (pevent != (OS_EVENT *)0) {
    /* 更新事件等待表 */
}
```

`y_old` 选择 ready 表的一行，`bitx_old` 选择该行的一位。例如旧优先级 2 对应行 0、掩码 4。

条件只回答：“该 ready 位当前是否为 1？”它不回答任务为何不 ready，也不意味着条件为假时函数已经结束。任务可能还在事件等待表中，后面必须继续处理。

## 一张执行表

两次实例都把旧优先级 2 改为新优先级 6，高行是 0，组字节的摘要为 1。三个旧局部目的字节起初均为 255，必须真正读取后才能使用。

| 项目 | ready 位存在 | 只清掉旧 ready 位 |
|---|---:|---:|
| 入口低行 | 20（位 2、4） | 16（仅位 4） |
| 三次读取后 `y_old / bity_old / bitx_old` | 0 / 1 / 4 | 0 / 1 / 4 |
| `低行 & bitx_old` | 4 | 0 |
| ready 条件 | 真 | 假 |
| 该片段的出口低行 | 80（位 4、6） | 16（不修改） |
| 出口高行 / 组值 | 0 / 1 | 0 / 1 |

两入口只相差位 2，即 `20 ^ 16 = 4`。`V293_read_ready_physical_controls` 不仅计算这个表，还包含实际语句执行、条件求值和最终内存读回。

## 证明怎样接起来

1. **入口 `M`**：真实指针、三个 TCB 字段、旧局部写权限、三项新局部值，以及位图读取和写权限。
2. **执行读取得到 `Mr`**：三个旧局部值从 TCB 读出；证明这些赋值没有破坏位图和新局部值。新局部目的块不能与旧目的块混叠。
3. **在 `Mr` 求条件**：C 将两个字节提升后按位与，再与零比较。框架没有 `!=`，故使用 `!(a == 0)`；这只用于零相等判断，不推广为有符号／无符号大小比较的等价性。
4. **执行分支得到 `Mf`**：真支执行已有顺序位图存储；假支仅跳过 ready 更新，保持 `Mr`。后者仍已经完成前三次局部赋值，所以一般不是保持入口 `M`。
5. **推导出口**：实际小步执行、条件值、两行／组字节读回、权限及局部值保持、未涉及块的逐字节 frame。

2048 个合法“行字节 × 比特位置”组合由 Coq 内核计算检查；独立探针另写条件及程序 AST，不把候选 AST 别名作为预期答案。

# 从真实入口走到三个错误退出调用

## 这一步解决什么

`OSTaskChangePrio(oldprio,newprio)` 不是一进函数就改任务的优先级。它必须先检查新位置是否被占用，再找到旧任务，最后排除保留表项。

上一检查点纠正了 `OS_EXIT_CRITICAL()` 的实参：固定分析端口实际调用 `V293_ExitCritical(&cpu_sr)`，不能误建模成读取并传入 `cpu_sr`。但“某条错误语句可以调用退出函数”不等于“原程序会走到这条错误语句”。本次补上后者。

## 按实际判断顺序补齐表格

| 新优先级表项 | 解析后的旧优先级表项 | 实际走向 | 到调用前发生的写入 |
| --- | --- | --- | --- |
| 非NULL | 无需读取 | 退出临界区调用，之后待返回40 | 无，内存保持原样 |
| NULL | NULL | 退出临界区调用，之后待返回41 | SELF时更新局部oldprio；查表实际写ptcb=NULL |
| NULL | RESERVED | 退出临界区调用，之后待返回67 | SELF时更新局部oldprio；查表实际写ptcb=保留指针 |
| NULL | 非NULL且非RESERVED | 通过入口检查，接成功迁移 | 旧检查点负责后续表／TCB／ready／事件迁移 |

这里的“之后待返回”不是已经返回：当前证明停在端口函数开始执行之前。

`oldprio=255` 表示SELF，需要读取当前任务的真实优先级。普通oldprio不读取当前任务。这些判断也不会把等待任务立即变成ready；入口拒绝与唤醒是不同操作。

## 真正执行了哪些步骤

三个稳定接口都从同一真实 `V293_task_prio_entry_reserved` 语句开始，而不是从人为选好的错误分支开始：

- `V293_task_prio_occupied_entry_execution`：读新参数、算数组地址、读新表项、执行非NULL判断，然后准备错误40的退出调用。无需旧参数、ptcb或RESERVED符号的读取资源。
- `V293_task_prio_absent_entry_execution`：通过新槽为空检查，实际执行SELF解析，读取旧表项，利用局部写权限构造真实store，写入ptcb=NULL，执行NULL判断，准备错误41的退出调用。没有把中间store或执行结果作为前提。
- `V293_task_prio_reserved_entry_error_execution`：复用已证明的非空查表执行，再从实际读出的ptcb执行RESERVED比较，准备错误67的退出调用。没有预先假设ptcb已经是保留指针。

SELF／查表写入产生的同一中间内存贯穿后续判断。后置观察的是同一个最终内存，不是给每一项结果另外选一个内存。

## 一个容易错误加强的前提

成功迁移时，新槽为空而旧槽非空，可以推出旧、新优先级不相等。**不能把这一结论复制到旧任务不存在的错误路径。**

若oldprio=newprio=8，而且第8槽为空，函数仍然可以正确报告旧任务不存在。`V293_task_prio_absent_same_slot_witness` 具体证明这个入口可执行；同时覆盖普通8和SELF解析到8。

见证把局部ptcb初值设成另一个真实编码的指针 `(70,0)`，查表后变成NULL，防止“最初就给好正确ptcb”掩盖赋值未执行。保留路径也从该不同指针实际写到保留指针 `(90,0)`。占用路径则逐步证明整个内存不变。

这些是物理内存可满足性见证，不是完整OS共享不变量、合法局部分配或初始化可达证明。不同错误种类的夹具改变不止一个输入，不把它们冒充单因素消融。

## 尚未跨越的边界

当前终点是：

```text
sfexec exit_id [Vptr(bs,0)] [Tptr Tint32]
```

含义仅是“已经求出 &cpu_sr，下一步将执行端口函数”。它不代表：

1. 真实进入／退出临界区函数已执行，保存token或中断状态已恢复；
2. saved局部已分配可读，或与所有写入块分离；当前接口不要求读取saved值；
3. 错误码已经返回调用者，局部存储已释放；
4. 已接好参数检查之前的入口、OSRunning、调度、完整API；
5. 符号RESERVED已获得统一全局绑定／与真实TCB不冲突／数值地址1的前端证明；
6. 全API／ISR保持性、初始化、源码级GOOD_OS与同程序K1–K4已完成。

下一步应把这些调用前边界接入真实临界区保存／恢复协议，再连接实际return；不能仅增加更多孤立错误分支定理来代替这一步。阶段一仍开放，随后才开展uC/OS-III。

# 整张优先级表如何与任务、位图同次归还

## 1. 先分清项目目标和本步目标

最终要证明的是固定 uC/OS-II V2.93.01 的真实配置后程序满足源码级 `GOOD_OS`，并排除同一程序上的 K1–K4。之后才开始老师要求的 uC/OS-III 阶段。**当前仍在第一阶段，局部定理不是整核完成证明。**

上一步已经证明：13 个优先级槽的真实 52 字节能构造成整表所有权，而且先清旧槽、再写新槽的两次真实写入保持整表和它旁边的资源。本步连接这张表与一次实际 API 执行后的其他资源。

## 2. 为什么“分别证明”还不够

下面两句话不等于联合归还：

- 存在一个最终内存，里面有任务字段和位图。
- 存在另一个最终内存，里面有整张优先级表。

需要的是：**同一次执行得到同一个 `Mf`；在 `Mf` 中，这些资源满足分离逻辑的 `**`，能一起使用，而不是拿两份独立存在量词拼在一起。** `**` 描述资源片段的兼容分离，并不是要求程序额外执行一次释放。

新接口是 `V293_critical_wait_table_joint_owned_execution`，位于 `certiucos/v293/proofs/V293TaskRecordOwnership.v`。

## 3. 本步已填写的状态表

本例修改一个仍等待信号量的任务优先级，从 8 改成 6。另一个就绪任务的优先级是 4。

| 对象 | 入口 | 返回时 | 原因 |
|---|---|---|---|
| 目标任务优先级 | 8 | 6 | 修改了任务的优先级字段 |
| 目标任务状态 | 等待信号量 | 仍等待信号量 | 没有收到等待的消息／唤醒事件 |
| 优先级表槽 8 | 指向目标任务 | `Vnull` | 清除旧映射 |
| 优先级表槽 6 | `Vnull` | 指向目标任务 | 安装新映射 |
| 优先级表槽 4 | 指向另一个任务 | 保持不变 | 与本次修改无关 |
| 就绪位图两行 | 16／0 | 16／0 | 等待任务没有进入 ready 集合 |
| 事件等待位图两行 | 0／1 | 64／0 | 等待集合中的优先级位置从 8 移至 6 |
| 当前任务指针 | 指向另一个任务 | 保持不变 | 本例使用中断嵌套路径，不发生正常无锁任务切换 |
| 运行／中断／调度锁计数 | 1／1／0 | 该路径对应的返回状态 | 不据此推广正常调度路径 |

“数字优先级变了”和“等待条件已满足”是两件事。你之前的理解是对的：**不会立刻变成 `ready=true`。** Coq 中的状态构造子是 `wait ...` 与 `rdy`，不直接使用这个布尔字段。

## 4. 联合所有权来自哪里

1. **入口给真实权限**：52 字节完整写权限、13 个指针值的类型合法性。读得到数值不等于拥有完整写权限。
2. **只执行一次**：调用既有的真实位图返回执行根，取同一个 `Mf` 和执行轨迹。
3. **证明资源不重叠**：当前指针、选定任务字段、位图字节的实际片段不占用表所在块。
4. **从剩余片段取表**：把 `Mf` 中保持下来的表权限与更新后的 loads 搬到原联合资源的剩余片段，构造整表，而不是另造一份内存。
5. **接回抽象共享字段**：物理资源的抽象片段为空；共享字段使用其自己的抽象片段。组合后仍是原来的 `Mf`。

返回资源可简写为：

```text
((((CurTid ** task_fields) ** bitmap_bytes) ** updated_priority_table)
  ** shared_fields) ** Atrue
```

`CurTid` 仍是可读半份额，不宣称当前任务指针可任意改写。入口的任意 `R` 不承诺跨局部变量释放保持；上一轮的 `R` 保持仅针对两次表写入。

## 5. 怎么检查本证明实际使用了哪些条件

- **允许表与当前指针重叠**：只删一个分离前提，不改后面的证明。应当拒绝；这只检验片段支持辅助根，不自动给后续 API 根信用，也不证明所有共享同一块但偏移不重叠的布局都不合法。
- **返回旧表**：只把最终联合资源中的更新表换回旧表，不改证明。应当拒绝；不把失败归因于所有下游机制。
- **消费返回资源**：验证 13 个槽逐个可写；写一个表槽时其他联合资源可作为 frame 保持。
- **检查旧值不能冒充新值**：槽 8 已空、槽 6 已指向目标任务、槽 4 不变，旧表所有权被排除。

这两个负控固定整个证明后缀，只定位既有证明对条件／结论的依赖；不是一个初始化可达的混叠反例，也不独立证明所有下游机制。

任意改写表槽不保证语义不变量成立。上面的写权限检查只证明资源可用及 frame 保持，不证明任意写后的调度器仍正确。

## 6. 不用答题，直接读下一步

现在沿以下顺序读代码：

1. 在新根中找到 `as (Mf & Surviving & BitmapOwned & Result)`：这是同一次真实执行的结果。
2. 找到 `TableWritableFinal`：入口的完整权限怎样到达 `Mf`。
3. 找到 `PointerTableApart`、`TasksTableApart`、`CellsTableApart`：三个不重叠条件分别保护什么。
4. 找到 `FinalFullJoint`：整表怎样加入同一个资源分割。
5. 打开 `audit/probes/V293TableJointReturnProbe.v`，对照上表读实际入口和返回资源的消费者。

**接下来的证明工作**：先清点完整共享不变量中仍缺少哪些物理资源／关系，再让这些资源在 API 入口、真实执行与返回之间闭合；随后扩展正常无锁调度、其他 API／ISR 和初始化。只有这些覆盖连接到顶层，才有资格说 `GOOD_OS` 与 K1–K4 完成。当前测试和默认审计的既有失败也要保留、定位，不能靠放宽断言制造“全绿”。

## 7. 下一步先核对完整不变量的缺项

不要被 `shared_fields` 这个名字误导：在 `V293SharedState.v` 中，它只是当前任务、任务表、事件表、时间这四类**抽象状态字段**的资源，并不是整个物理内核状态。

| 已连接部分 | 本步准确范围 | 还不能据此声称的内容 |
|---|---|---|
| `CurTid` | 当前指针读半份额 | 切换时的完整写权限 |
| `owned_task_records` | 任务表中每个任务的选定字段，由 `V293_record_layout` 定义 | 完整 TCB、链表、栈和所有调度资源 |
| `owned_record_cells` | ready 位图及本例一个事件位图，共六字节 | 所有事件、队列和全局对象资源 |
| `owned_priority_table` | 本配置的 13 个槽，52 字节 | 所有内核配置或任意修改后仍满足调度关系 |
| `shared_fields` | 四类抽象字段 | 完整物理不变量、初始化与全程序保持 |
| 本例执行 | 等待任务变更优先级，经中断嵌套分支返回 | 所有 API、所有 ISR、正常无锁切换 |

因此下一项不是再起一个“全局正确”名字，而是把缺项按真实函数的读写集合列出：哪些只读、哪些需完整写权限、哪些会释放、哪些在切换或中断边界必须交回。随后逐项连接现有接口，并用实际入口检查它们能同时成立。这个过程不能用不可满足的入口或 `init := False` 省略。

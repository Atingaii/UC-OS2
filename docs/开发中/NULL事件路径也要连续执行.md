# NULL 事件路径也要连续执行

## 这一步为什么必要

上一步把真实任务表读取、SELF 解析、坐标计算、优先级迁移接成了连续执行，但接口要求任务的 `EventPtr` 非空。这只覆盖一个分支。现在对同一程序补上 `EventPtr=NULL` 的成功路径；不是把 `if` 删掉再证明。

## 从程序顺序理解

| 顺序 | 程序实际做什么 | 本步证明了什么 |
| --- | --- | --- |
| 1 | 查新优先级槽，解析 SELF，读旧槽 | 原始局部 ptcb 不必正确，实际读取后才成为真实 TCB 指针；空新槽和非空旧槽推出新旧优先级不同。 |
| 2 | 检查保留标记 | 使用现有局部符号表示；上层统一绑定等义务仍保留。 |
| 3 | 计算新 Y、X、BitY、BitX | 四个目的原来可以都是255，由真实赋值算出新坐标。 |
| 4 | 迁移任务表和 ready 位图 | 任务原来 ready 才迁移 ready 位；原来不是 ready 不会被此操作唤醒。 |
| 5 | 读取内部 EventPtr，再判断是否非空 | 实际读到 NULL，因此跳过事件位图更新；局部 pevent 的读回也是 NULL。 |
| 6 | 写回 TCB 五个优先级相关字段 | 与前面是同一次执行，最终字段、表、位图及未写区域一起检查。 |

不要把 `EventPtr=NULL` 翻译成“任务一定 ready”。事件指针只反映一个字段，任务还可能因延时、挂起等原因不可运行；合法共享关系仍要另外建立。

## 两个容易混淆的结论

1. **连续执行**：不是各片段分别存在某个出口，而是前一个片段实际产生的内存，确实满足后一个片段的入口条件。本步通过未写区域的 byte／permission frame 运输资源，最终结果回到最原始内存比较。
2. **没有写事件对象**：NULL 分支不要求虚构一个事件对象。见证旁边保留一个哨兵块，证明其全部地址不变；它不是这个分支的必需资源。

## 物理例子

同一 `8 → 6` 入口，原 ptcb=NULL，四个新坐标局部为255。SELF／非SELF 和 ready 两个状态分别实例化同一个通用定理。

| 入口 ready 位 | 最终 ready 位图两行 | 意义 |
| --- | --- | --- |
| false | 16／0 | 目标任务仍不 ready，没有因修改优先级被唤醒。 |
| true | 80／0 | 把原优先级对应的 ready 位迁到新优先级，保留其他任务位。 |

新 NULL 夹具相对旧非空夹具只替换内部事件指针的四字节；逐地址差异引理检查其余字节相同。ready 的 true／false 两个入口不作为单因素消融。所有夹具只证明物理前提可满足，不是完整共享不变量或初始化可达性。

# 从临界入口连续执行到占用错误返回

## 1．这一轮究竟接上了什么

最终目标仍是同一固定 uC/OS-II V2.93.01 程序的顶层 `GOOD_OS` 与 K1–K4 回归，然后再进入 uC/OS-III。当前不把局部结果算作这两个阶段完成。

上一检查点分别证明了保存值保持、框架退出原语和端口返回后的实际 `return`，但原始端口调用没有函数体，几段不能自动拼接。这次在**项目已接受的源码级中断抽象**内，接成一条归一化程序的连续路径：

```text
参数满足范围要求
  → 原参数 guard 实际求值并放行
  → encrit：把进入前 IE 压入框架保存栈，并关中断
  → 读取 OSTCBPrioTbl[newprio]，发现非 NULL
  → excrit：恢复同一次进入保存的 IE，弹出栈顶
  → 求值 return 40
  → 释放局部存储
  → 恢复调用者环境，调用者收到 40
```

这是已有 `loststep` 的有限步闭包中的一条实际执行，不是另加了“端口执行成功”的规则，也不是面向所有并发调度的 Hoare／整核 safety 定理。成功迁移、返回41／67等分支仍未获得这条连续执行信用。

## 2．先分清两份源码表示

| 表示 | 进入／退出 | 已证明到哪儿 |
| --- | --- | --- |
| 原始手工调用模型 | `scall enter [&cpu_sr]`／`scall exit [&cpu_sr]` | 保留原证明；无函数体的 `sfexec` 仍无下一步 |
| 显式宏归一化结果 | 框架已有 `sprim encrit`／`sprim excrit` | 新槽已占用路径可从参数检查连续走到实际返回 |

`V293_port_normalize` 只接受不同的进入／退出标识，以及同一保存变量的单个取地址参数。传值、错变量、两个标识相同均拒绝；运行时分配／释放／函数执行节点不作为可归一化输入。普通条件、SELF、查表、返回码和语句顺序保持。

`V293_critical_prefix_normalization` 是一次明确的语法映射证明，**不是原始调用到框架执行的语义保持证明，也不是已验证 C 前端**。它把 CPU_SR 的字节存取擦除，改由框架保存栈承载中断状态。

新鲜配置后 C 的检查发现：`cpu_sr` 为 unsigned int，初始化0；函数内全部五次引用恰为一次进入、四次退出的 `&cpu_sr`，没有其他读取。这只为本函数手工映射提供回归证据，不能证明通用别名安全或真实端口行为。决策见 [ADR-0005](../adr/0005-显式临界宏映射不等于端口执行.md)。

## 3．开中断与恢复中断不是一回事

| 进入前 IE | encrit 后 IE／栈 | excrit 后 IE／栈 |
| --- | --- | --- |
| true | false／true::ci | true／ci |
| false | false／false::ci | false／ci |

`V293_occupied_critical_return` 对任意 `enabled`、原保存栈 `ci` 和 ISR 状态成立，程序没有随 `enabled` 改变。返回时仍是原 `enabled`，不是无条件 true。

定理要求实际局部绑定、参数和表项的读取，以及局部块不重复、每个待释放字节可写。它没有预给中间执行、`store`、`free` 或退出后的状态。证明实际执行参数 guard、进入、占用判断、退出和构造性释放过程。

## 4．为什么构造一个保存字节为23的见证

`V293_occupied_critical_witness` 为 SELF／普通旧优先级及两种初始 IE 提供非空物理实例。`cpu_sr` 四字节始终编码23，而不是0／1：这是刻意揭示**字节已被擦除**，绝不能将该实例当作原始保存值与栈相等的证据。

执行后保存变量四字节、oldprio／newprio各一字节都实际释放；共享表的占用指针保持。后面放着没有任何函数定义要求的 `scall 999 []`，但错误返回将它连同剩余语句全部跳过。这个状态不是实际函数入口分配或初始化可达性证明。

# 退出临界区与真正返回是两回事

> 本文记录前一398行检查点；后续显式宏抽象的连续路径见[新教程](从临界入口连续执行到占用错误返回.md)。后续结果不是本文原始端口调用桥已闭合。

## 第一步：看清三个不同的终点

我们仍在验证固定 uC/OS-II V2.93.01 的 `OSTaskChangePrio`。上一轮已从真实入口连续执行三个错误路径：新槽占用返回 40、原任务不存在返回 41、保留表项返回 67。终点都只是 `sfexec exit_id [&cpu_sr]`，后续保存着相应的 `return`。

`sfexec` 表示准备执行函数，不是函数已经执行完。本轮补了以下局部事实：

```text
真实保留错误入口
  │ 实际 SELF 解析／查表／ptcb 写入，saved 内存值保持（本轮）
  ▼
sfexec exit_id [&cpu_sr]，后续 return 67
  │ 尚缺：同一调用的端口解释、进入时的保存动作及栈对应
  ▼
框架 excrit 原语：恢复栈顶保存的中断状态（本轮独立证明）
  │ 尚缺：端口调用执行并返回到调用者的连接
  ▼
sskip None，后续 return error（端口已经返回）
  │ 实际求值／释放局部存储／恢复调用者环境（本轮）
  ▼
调用者收到 error
```

图中的缺口是未完成义务，不能把上下几段直接当成一条已证明的整函数执行。

## 第二步：把“有地址”与“保存值正确”分开

分析端口的真实声明是：

```c
void V293_ExitCritical(OS_CPU_SR *saved);
#define OS_EXIT_CRITICAL() V293_ExitCritical(&cpu_sr)
```

需要分别证明：地址能求值 → 地址中的保存值可读 → 中间写入不破坏它 → 退出时恢复同一次进入保存的状态。

第一项不会自动推出后三项。上一轮的物理入口见证没有分配保存值字节；本轮另构造实际存有四字节值的见证。

新模块 `certiucos/v293/proofs/V293CriticalReturn.v` 中，`V293_saved_ie M bs saved` 表示从保存块读取 `Tint32`，得到布尔状态的 0／1 编码。这只是中断使能位的**局部观察编码**，不是说真实完整 `OS_CPU_SR` 只有两个值，也不是最终硬件端口规范。

## 第三步：理解为什么不能无条件开中断

| 进入前 | 临界区内 | 正确退出后 |
| --- | --- | --- |
| 开中断 `true` | 关中断 | 开中断 `true` |
| 关中断 `false` | 关中断 | 关中断 `false` |

`V293_excrit_restores_saved` 检查真实 `loststep`，从栈 `saved :: ci` 恢复中断状态 `saved` 和栈 `ci`，内存不变。

这里**显式要求栈顶与保存值对应**。框架 `excrit` 使用栈顶，不读取 `cpu_sr` 内存；尚未证明真实进入操作建立了两者的对应关系。不能把该前提算成完成的端口连接。

单因素负控只把退出结果改成 `true`，其余输入和原证明不变，Coq 在目标 `Proof.` 后拒绝。手写探针还对 `saved=false` 单独实例化，避免只检查原来开中断的情况。

## 第四步：确认写入没有破坏保存值

保留错误入口可能写两个块：SELF 解析写 `oldprio`，查表后写 `ptcb`。`V293_reserved_entry_preserves_saved` 从原始资源实际执行入口，在保存块与这两个写块不同的条件下，证明同一出口内存仍有原保存值。

入口不预给正确 `ptcb`，也不预给中间执行结果。物理见证覆盖 SELF／普通参数、保存状态真／假。**本轮只为返回 67 的保留入口接了保存值保持接口**，另外两个错误入口不能自动继承这项信用。

还有一个单因素反例：初始四字节表示 1，只把保存块首字节改成 8，其余每个地址不变，原保存值便不再成立。它说明别名写可能破坏保存值，但不声称该状态从真实 C 初始化可达。

去掉保存块与 `ptcb` 块分离的负控也在目标 `Proof.` 后拒绝。这只说明原证明敏感，不证明修改后的命题一定不可证，更不授予后续恢复步骤信用。

## 第五步：理解真正的 return

`V293_error_after_port_return` 从“端口已经返回”开始，实际执行：

1. 选择后续 `return error` 并求值。
2. 从局部环境取得需要释放的存储。
3. 根据各字节可写资源构造真实释放过程，不预给释放结果。
4. 释放后恢复调用者环境，交付返回值。

条件是局部块不重复、各局部所占字节可写。这些是充分资源条件，尚不是完整 API 入口已经分配好局部变量的证明。

具体见证有一个四字节保存变量、一个单字节局部变量，以及非局部共享哨兵。返回后五个局部字节都不存在，哨兵仍为 23，调用者环境恢复。continuation 中故意放了尚未执行的 `scall 999`：`return` 会跳过它；见证对任意程序环境 `P` 成立，无须假设函数 999 有定义。

局部保存变量在返回时释放是正常行为：它只需在退出临界区需要它时有效。

## 第六步：辨认还缺哪座桥

当前分析端口只有声明，没有函数体。框架调用规则要求程序环境中有定义，不能自动执行外部声明。

`V293_missing_port_has_no_step` 明确证明：如果 `P exit_id = None`，该 `sfexec` 没有下一步 `loststep`。不能静默换成 `sprim excrit`，也不能假设“端口已经执行”绕过缺口。

下一步沿已接受的框架中断抽象边界，建立**同一次调用的临界进入保存、保存值与栈的对应、退出调用到原语及调用者恢复**，再连接已有定理。不要求转去证明硬件／ABI，但必须明确手工源码模型如何解释端口边界。

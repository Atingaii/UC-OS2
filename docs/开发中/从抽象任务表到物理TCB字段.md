# 从抽象任务表到物理 TCB 字段

## 先分清这三个对象

| 对象 | 它说明什么 | 不能据此推出什么 |
| --- | --- | --- |
| 抽象任务表 `tasks` | 某个任务的优先级、ready/wait 状态、消息 | 内存中已分配并正确初始化了完整 TCB |
| `CurTid` | 标准 `OSTCBCur` 指针存储的实际读取权限 | 指针所指的整个任务结构、链表和资源都合法 |
| 本轮 `V293_task_records` | **每个**抽象任务都有对应的选定物理字段 | 完整 TCB 所有权、链表分离、内存分配器不变量、初始化可达性 |

上一轮的例子有抽象 current `(60,0)`，但并未构造它的物理 TCB。不能把“抽象任务 ready”直接说成“真实任务结构合法”。本轮为该任务明确安装选定字段，再从新的入口内存重新构造所有执行前提。

## 第一步：列出真正需要保持的字段

任务指针是 `(block, offset)`，字段偏移相对于该指针，而不是绝对地址。

| 字段 | 相对偏移 | 对应关系 |
| --- | --- | --- |
| 优先级 | 50 | 抽象优先级，限定在当前配置的 13 个槽内 |
| 行、列 | 52、51 | 优先级除以 8、模 8 |
| 行、列掩码 | 54、53 | 对应行、列的单个位 |
| 状态 | 48 | ready 与仅时间等待为 0；IPC 等待与其原因一致 |
| 延时 | 44 | 时间等待或 IPC 等待的抽象延时；ready 不约束此字段 |
| 消息 | 32 | 抽象任务消息，不把非空消息悄悄清空 |
| 等待结果 | 49 | IPC 路径保留原有字节；本关系不把它加入抽象任务表 |
| 事件指针 | 28 | IPC 等待原因中的同一个事件 |

`V293_task_record` 检查单个任务；`V293_task_records` 对抽象表的全部成员量化。不是只检查此次被改优先级的任务。

## 第二步：区分“被改任务”与“其他任务”

- 被改任务 `(41,8)`：优先级从 8 变成 6。必须使用这次真实执行写出的五个坐标字段，并保留等待状态、延时、消息、等待结果、事件指针。
- 当前任务 `(60,0)`：优先级 4，ready、NULL 消息。没有被此函数写入或作为局部变量释放。
- 一般定理显式要求其他任务所在 block 不在写集合、也不在释放 locals 的集合。该条件比逐地址不重叠更强；本轮**没有覆盖多个 TCB 共用一个 block 的数组布局**。

`V293_task_record_frame` 用逐字节块相等运输 typed load；`V293_task_records_update_frame` 按 map 的单点更新分出这两类任务。改任务不是靠 frame 蒙混过关，其他任务也不是靠检查一个代表样本代替全称证明。

## 第三步：接回同一次完整返回

`V293_critical_event_task_records_execution` 只调用一次已有的完整执行根。它保留原来的所有入口前提与输出，另外增加全称物理对应和明确的其他任务块分离条件。

最终物理字段、ready 位图、优先级表、事件位图、事件数据、当前指针读取权限和抽象任务更新，都指向同一个 `Mf`、`Os'`、`OO'`。不是分别找几个可满足的终态，再拼成“执行成功”。

新的字面例子从 `RecordProbeMemory` 出发。它在旧入口上为 block 60 安装五个坐标字节、ready 状态字节、完整 NULL 消息编码。旧输入和旧证明不改；新输入的指针权限、表读取、可写性、局部变量、事件和调度前提全部重新建立，然后调用新根，不能拿旧输入已经完成的 trace 代替。

## 第四步：读反例，不只看成功

| 检查 | 固定什么 | 单独改变什么 | 能支持的结论 |
| --- | --- | --- | --- |
| `DroppedOtherFrame` | helper 的完整 Proof 后缀 | 其他任务的块相等前提改为 True | 固定证明依赖该前提；不自动证明下游全部有效 |
| `StaleTaskRecord` | 完整执行根的整个 Proof | 最终对应的任务表改回旧表 | 固定证明拒绝过期任务表 |
| 同次返回的独立语义反例 | 实际新输入和执行终态 | 尝试用旧优先级 8 解释已写成 6 的字段 | 同一 `Mf` 不满足旧任务表对应 |
| 旧输入缺失 current 记录 | 原有旧内存和抽象表 | 不补建物理 current 字段 | 旧例子不能被升级成满足新入口；这是额外反例，不追认为前瞻实验 |

本轮没有修改 C，也没有把负控的早期拒绝算作后续执行机制的通过。

## 接下来做什么

这还是 `OSTaskChangePrio` 的等待任务成功路径，真实调度调用受 ISR 条件阻挡。下一步应将这些物理对应放入上层可保持的共享不变量，处理正常无锁调度、其他分支/API、ISR 和初始化，而非继续凭空增加字段名称。

最终阶段一仍是：固定 V2.93.01 和两项授权修复，闭合源码级 `GOOD_OS` 及同程序 K1–K4。当前没有完成整核，也没有开始 uC/OS-III。

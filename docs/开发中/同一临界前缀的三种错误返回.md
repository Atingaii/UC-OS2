# 同一临界前缀的三种错误返回

这是980行历史检查点的讲解。参数非法42的后续连接已见[下一步教程](参数非法为什么不能先进入临界区.md)。

## 1．接着上一步看实际控制流

这里的目标仍是固定 uC/OS-II V2.93.01 的源码级 `GOOD_OS` 与同程序 K1–K4 回归，完成后再做 uC/OS-III。下面只讲 `OSTaskChangePrio` 的一个纵向片段，不表示整函数或整核完成。

上一步已经把“新优先级被占用”接到真实返回40。本轮在**同一个** `V293_primitive_critical_prefix` 中，继续两条较长路径：

```text
检查原始 oldprio/newprio 参数
  → encrit，压入原 IE 并关中断
  → 新优先级槽为空，允许继续
  → oldprio=255（SELF）时从当前 TCB 读取实际优先级，并写回 oldprio
  → 读取 OSTCBPrioTbl[解析后的 oldprio]，把结果写入局部 ptcb
  → 根据写入的结果判定：
       NULL：excrit → return41 → free → 恢复调用者
       保留指针：excrit → return67 → free → 恢复调用者
       其他任务指针：进入成功迁移分支，尚待连接
```

`NULL` 表示这个优先级没有任务；保留指针不是可操作的正常任务，也不能因为“非 NULL”就进入成功分支。它们不是同一种错误。

## 2．补全这张执行表

| 新槽 | 解析后的旧槽 | 是否写 oldprio | 是否写 ptcb | 返回 |
| --- | --- | --- | --- | --- |
| 非 NULL | 不读取 | 否 | 否 | 40 |
| NULL | NULL | SELF 时写 | 是，写 NULL | 41 |
| NULL | 保留指针 | SELF 时写 | 是，写保留指针 | 67 |
| NULL | 其他任务指针 | SELF 时写 | 是，写任务指针 | 成功分支待接 |

所有三条已接通错误路径均恢复**进入之前的 IE**。进入前关闭，返回后仍关闭；不是一律打开中断。原先的框架保存栈和 ISR 状态也恢复，不执行后面的成功语句。

一个容易漏掉的情况是 `oldprio=newprio=8` 且该槽为空：新槽检查通过，旧槽查询仍为空，应返回41。新接口没有加 `resolved <> new` 排除它。保留路径中旧槽非空、新槽为空，自然不能是同一槽，无需额外假设。

## 3．三个新接口各自承担什么

文件仍是 `certiucos/v293/proofs/V293CriticalReturn.v`，没有新增活动证明文件或修改框架执行规则。

- `V293_resolve_lookup_resources`：实际执行 SELF 和查表赋值，证明 `ptcb` 读取到本次查表结果，并运输所有原有可写权限。可以查询 NULL 或任意指针，不要求初始 `ptcb` 已经正确。
- `V293_lookup_error_critical_return`：上层统一使用的41／67接口。`absent` 只选择入口数据与预期结果，不改变待执行程序。从原始参数及入口内存资源出发，连续执行到返回调用者，实际释放全部局部字节、保持非局部块。
- `V293_lookup_error_critical_witness`：给上述接口一个具体、非空的物理实例，覆盖 SELF／普通入口、41／67和任意初始 IE。

为什么还要运输可写权限？返回会调用真实 `free`。SELF 写一个字节、查表写四个字节之后，不能直接假设中间内存仍可释放。本轮证明覆盖写入的字节仍是可写权限，未覆盖的字节保持，再从入口资源推出返回时的释放条件。没有新增“中间执行成功”“store成功”或“free成功”的外部假设。

局部块无重复、待释放字节可写仍是明确的**充分条件**；实际 API 局部分配建立这些条件还未连接。地址区分也是该接口的显式条件，不能说已经证明所有合法 C 调用必然满足。

## 4．物理见证怎样防止看似正确但没做事

| 数据 | absent=true | absent=false |
| --- | --- | --- |
| 原始 oldprio | SELF=255 或普通8 | SELF=255 或普通8 |
| SELF 解析结果 | 8 | 8 |
| newprio | 8 | 6 |
| 旧槽 | NULL | 保留指针90 |
| 初始 ptcb | 指针70 | 指针70 |
| 局部保存变量字节 | Tint32 编码23 | Tint32 编码23 |
| 真实最终返回 | 41 | 67 |

初始 `ptcb=70` 刻意与查询结果不同，因而不能靠预填好结果来假装执行了赋值。返回会实际释放 ptcb 四字节、保存变量四字节、oldprio/newprio各一字节，共10字节；共享表的旧槽保持。待执行的 `scall 999 []` 被错误返回跳过，对程序环境不要求提供函数999。

保存字节23与初始 IE 无关。原因不是端口可以随意保存，而是这份显式抽象擦除了 CPU_SR 字节操作，改用框架保存栈。它**不证明原始 sfexec 端口调用，也不证明字节 token 与框架栈的一致性仿真**。原始表示和抽象表示不能混用结论；参见 [ADR-0005](../adr/0005-显式临界宏映射不等于端口执行.md)。

## 6．下一步，不再把错误路径当成功路径

接下来分两步，不重新发明已有后端：

1. 先把参数非法的42返回接到实际free／caller恢复。这条分支发生在encrit之前，不能错误地调用excrit；现有 `V293_task_prio_argument_execution` 只作参数分支选择基础，不自动等于整函数真实返回。
2. 在新槽为空、旧槽为正常任务指针且不是保留标记时，连接真实就绪表／TCB／事件等待表更新，再接最终退出、真实调度调用与成功返回。已有 `V293_task_prio_entry_update_execution`（事件指针非NULL）和 `V293_task_prio_entry_null_update_execution`（事件指针为NULL）可作后端依据，但它们使用原始error-call表示，不能直接冒充本轮归一化完整程序的证明。需要明确连接并运输前后资源，不能假设后端或调度“已经成功”。

随后才是整函数规格、局部分配、共享关系、调用环境及初始化，把这些连到固定程序的 `GOOD_OS`。

本轮只是标准 `loststep` 有限步闭包中的构造性路径存在；不是所有并发交错安全、不是整函数 Hoare 定理。正式函数覆盖未晋级，最终两阶段目标继续保持未完成。

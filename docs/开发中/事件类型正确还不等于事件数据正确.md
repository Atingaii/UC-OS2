# 事件类型正确，还不等于事件数据正确

## 1. 这一轮为什么继续往下做

上一轮把同一个事件的类型字节保持到完整return/free。但“这是信号量”不能推出“内存中的计数与抽象信号量计数相等”；“这是邮箱”也不能推出“消息指针相等”。所以本轮补的是这两个数据对应关系，不更换程序或跳到uC/OS-III。

先固定范围：仍是V2.93.01、原固定配置与两授权修复。源码级GOOD_OS和K1–K4全部闭合才算阶段一完成；随后才按老师附件推进uC/OS-III。

## 2. ECB里到底有什么

锁定源码的`os_event`字段按顺序为Type、Ptr、Cnt、Grp、Tbl。在现有分析布局里：

| 字段 | 类型 | 相对起点偏移 | 本次数据关系 |
| --- | --- | --- | --- |
| OSEventType | Tint8 | 0 | SEM=3、MBOX=1 |
| OSEventPtr | Tptr Tvoid | 4～7 | SEM为NULL，MBOX为同一抽象消息 |
| OSEventCnt | Tint16 | 8～9 | SEM为同一抽象计数，MBOX为0 |
| OSEventGrp | Tint8 | 10 | 修改优先级时可能变化 |
| OSEventTbl | 两个Tint8 | 11～12 | 旧优先级位清除、新优先级位置位 |

这些是已有手工模型及其字段计算，不是另行证明C编译器或真实ABI正确。实际源码预处理、函数定位与hash在本轮configured-source记录中重新核对。信号量和邮箱创建函数的字段赋值也已定位；没有因此宣称创建API已经完成Hoare证明。

## 3. 新关系读什么

`V293_event_sem_mbox_data`除了检查类型，还检查：

- `abssem count`：count不超过65535，完整Tint16读取等于count，完整指针读取等于NULL。
- `absmbox message`：完整Tint16读取为0，完整指针读取等于message。
- 队列与互斥锁：本关系不覆盖，结果为False，不能只凭它声称队列存储或锁所有者正确。

只看计数低字节是不够的。例如0和256低字节都是0，但两个完整计数不同。指针同样要读完整四字节，而不是把类型字节相同当作消息相同。

## 4. 怎样接到同一次返回

`V293_event_header_load_frame`逐字节使用上一轮的细粒度frame。计数字段8～9、指针字段4～7均在写集合10～12之外，所以完整load保持。

`V293_critical_event_queue_execution_event_frame_data`只调用一次原完整队列执行根，取得它的同一个Mf、Os'、OO'。保留全部旧结果，包括实际ECB查询和等待列表，再把数据对应传到这个Mf；不是再找另一段执行，也没有把同类但不同的ECB拼进来。

新结论仍是条件式：**入口数据关系成立，则同一次完整返回后的数据关系成立。** 它不替代入口合法性、共享不变量或初始化证明。原有6851行不改，本轮在同一个活动文件末尾追加接口适配证明，不复制底层实际执行实现。

## 5. 固定例子，表格已补齐

事件块72、起点5，因此消息指针绝对偏移9～12、计数绝对偏移13～14。新probe在完整执行之前安装完整NULL指针和完整0计数，然后重建入口资源。

| 项目 | 入口 | 同一完整返回后 |
| --- | --- | --- |
| 抽象ECB | 同一信号量，计数0，同一等待列表 | 保持 |
| 类型 | 3 | 3 |
| 完整计数 | 0 | 0 |
| 完整事件指针 | NULL | NULL |
| 位图两行／group | 0/1，2 | 64/0，1 |
| TCB优先级／等待原因 | 8，等待同一信号量 | 6，仍等待同一信号量 |
| 返回／locals | 尚未返回、locals存在 | 返回0、locals释放、caller恢复 |

独立语义控制分别检查：同一次完整返回不可能把计数0当作1；同类型、同低字节的256不能当作0；非空邮箱消息指针不能当作NULL。邮箱控制只验证具体头数据，不声称完成邮箱等待路径或整API执行。

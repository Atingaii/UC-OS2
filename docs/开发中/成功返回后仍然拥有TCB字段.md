# 下一步：成功返回后，仍然拥有目标任务的字段

## 1. 前因后果

这个仓库的阶段一目标是固定配置、固定源码身份的 uC/OS-II V2.93.01 源码级 `GOOD_OS`，并在同一个程序中排除 K1–K4 已知反例。局部模型、单个例子和编译成功都不能替代这个目标。阶段一完成后才进入老师要求的 uC/OS-III；当前尚未开始阶段二。

我们正在纵向连接 `OSTaskChangePrio` 的成功路径。上一小步证明了真实五次赋值后的中间内存具有新字段所有权；缺口是：函数还要退出临界区、调用调度器、返回、释放局部变量。中间内存 `M'` 的事实，不能自动当作最终内存 `Mf` 的事实。

本轮把**同一次成功更新与返回**的实际执行、目标字段写权限和抽象任务表更新接到一起。入口仍有明确的资源、布局、分离和受阻调度条件；不是完整函数调用入口、参数分配、全部保护分支或整核定理。

## 2. 先看补好的表格

固定实例：目标任务 `(41,8)`，优先级 8 改为 6；信号量事件 `(72,5)`。优先级数值越小，优先级越高。

| 观察项 | 入口 | 同一次返回后 | 为什么 |
|---|---|---|---|
| 目标任务标识 | `(41,8)` | 不变 | 修改优先级，不新建任务 |
| 优先级 | 8 | 6 | 本次请求 |
| 就绪 `ready` | false | false | 等待的信号量还没有到来 |
| 等待原因 | SEM `(72,5)` | 不变 | 改优先级不是唤醒 |
| 超时计数 | 1 | 1 | 此路径不是 tick |
| 消息字段 | 非 NULL `(120,7)` | 不变 | 不清空消息 |
| 等待结果字段 | 0 | 0 | 不伪造等待完成 |
| ready 行位图 | 16 / 0 | 16 / 0 | 目标不是 ready 成员 |
| event 等待行位图 | 0 / 1 | 64 / 0 | 将第 8 位搬到第 6 位 |
| 优先级表槽 8 | 目标指针 | NULL | 清理旧索引 |
| 优先级表槽 6 | NULL | 目标指针 | 安装新索引 |
| 目标字段资源 | 旧值 8，完整写权限 | 新值 6，完整写权限 | 不仅仅能读到 6 |
| 抽象任务表 | 目标优先级 8 | 同一目标优先级 6 | 与上述物理终态配对 |
| 局部变量 | 已分配 | 释放 | caller 环境恢复，返回值为 0 |

入口还安装了另一个 ready 任务 `(60,0)`、优先级 4。不能因此声称新出口已经拥有所有任务记录或完整 `CurTid` 共享组合：本轮空间出口只明确组合**目标选定字段**和抽象 `shared_fields`。

实际写入的五个字段（实例基址 8）为：优先级地址偏移 58→6、行号 60→0、列号 59→6、行掩码 62→1、列掩码 61→64。保持的字段包括 event 指针偏移 36、消息 40、delay 52、状态 56=1、pend 57=0。这里是当前模型的布局，不是新增 ABI 验证结论。

## 3. 按顺序读一条证明链

1. **入口资源**：`shared_fields ** (owned_task_record ** R)`。`**` 表示真实的可分离资源组合；不是把两个读数事实写在一起。
2. **抽象更新**：只调用一次 `V293_wait_prio_owned_step`，更新实际持有的抽象任务表，得到 `Os'`、`OO'` 和 `spec_step`。新槽为空与优先级表对应关系共同推出抽象新优先级未被占用。
3. **实际写权限**：从入口所有权推出五个字段可写，再证明实际五次赋值所得模型内存具有新值所有权，不额外假设目标可写。
4. **真实返回**：`V293_critical_event_return_tcb_owned_block` 运行真实成功更新语句和尾部返回，各执行根只调用一次，产生 `Mf`。它保留既有输出，并证明整个目标块（字节及权限）等于五赋值内存中的目标块。
5. **搬运资源**：`V293_owned_task_record_block_frame` 利用块相等，把真实资源片段搬到返回后的 `Mf`。只比较 typed load 不够，因为读相同的值不代表保留写权限。
6. **同一终态组合**：`V293_owned_task_fields_reconstruct` 在同一 `Mf / OO'` 重建 `(owned_task_record 新值 ** shared_fields 新任务表) ** Atrue`。

供后续调用的稳定接口是 `V293_critical_wait_record_owned_execution`，位于 `certiucos/v293/proofs/V293TaskRecordOwnership.v`。

出口的 `Atrue` 不表示任意入口 `R` 跨返回仍保持。局部变量已释放，不能把包含这些变量的任意 frame 原样交还。本轮没有通过把完整共享不变量弱化成 `Atrue` 来宣称整核通过；它只新增一个边界明确的局部接口。

## 4. 为什么要做反例和负控

- 字面 probe 重新构造入口资源，直接调用上述一般接口，不用另一条已完成执行来冒充入口。
- 在同一次终态上证明旧优先级 8 的所有权不成立，并从新所有权推出实际写入字节 7 可以成功；这是对权限的验证，不是业务上要求再改一次优先级。
- 单独的半权限字节可以读到 6，却不能写入 7，也不具有完整字段所有权。
- 两个预先登记的单因素控制分别只将块级字节／权限相等改成 typed-load 相等，或只把最终所有权的 new 改成 old。整个目标 `Proof` 后缀不变，检查固定证明是否拒绝。
- 负控拒绝只支持对应敏感性，不自动证明所有下游机制有效；实际执行与上述独立语义反例另行提供证据。

实际检查结果见 [本轮审计](../../audit/STAGE26_API_TASK_OWNERSHIP.md)；保留了所有开发失败、超时中断和最终成功快照。

## 5. 接下来怎么做（不需要先答题）

先将现有的目标字段空间资源、全称任务字段对应、当前任务资源、ready／优先级表／event 对应统一到**同一个可保持的共享不变量**，而不是为每个事实再造一个互不相连的小模型。每增加一个资源组合，先检查物理／抽象资源是否重叠，不能重复拥有同一字节或任务表。

然后扩大调度路径：本例 `run / ISR / lock = 1 / 1 / 0`，调度确实受 ISR 阻挡；不能记成正常无锁切换已证。接下来还要覆盖正常调度、完整 API 入口及其他分支、ISR 和初始化，最后实例化源码级 `GOOD_OS` 与同程序 K1–K4。

你现在需要掌握的阅读顺序就是：**入口拥有什么 → 实际执行改变什么 → 返回释放什么 → 出口仍拥有什么 → 哪些边界尚未证明**。先沿这条链阅读本例，不必从全部 Coq 战术开始背起。

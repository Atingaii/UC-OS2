# 下一步：局部 pevent 正确，不代表 TCB 内部没被写坏

现在同一个优先级迁移片段的NULL／非空路径都能完成TCB五字段写回。继续向完整函数推进前，还要补一个会影响上层共享关系的事实：**未被源码赋值的TCB字段保持原值**。

## 1. 为什么还需要这一步？

```c
pevent = ptcb->OSTCBEventPtr;
/* 可能修改事件等待位图 */
/* 修改TCB的Prio、Y、X、BitY、BitX */
```

只证明最后局部变量`pevent`正确是不够的。假设后面意外破坏了`ptcb->OSTCBEventPtr`，局部变量仍可能保存之前的正确副本。以后其他API再次读取TCB时就会出错。因此需要分别观察：

| 检查对象 | 非空路径最终结果 |
| --- | --- |
| 局部 `pevent` | 仍是原事件指针 |
| TCB内部 `OSTCBEventPtr` | 仍是原事件指针 |
| TCB五个被写字段 | 与新优先级一致 |
| TCB其余字节 | 与入口完全相同 |
| 事件等待位图 | 执行真实优先级迁移 |
| ready位图 | 按独立ready条件处理，不因事件迁移自动唤醒 |

不能把第一行当成第二行的证明。

## 2. 地址范围怎样判断？

在当前固定分析布局中：

- EventPtr占偏移28..31。
- Prio／Y／X／BitY／BitX实际依次写50／52／51／54／53。
- 因此写区是50..54，其他字节必须保持。
- 实际DelReq字段在偏移55，也属于保持范围，不是填充字节。

新接口的后置为：对所有偏移`i`，若`i < base+50`或`base+54 < i`，最终TCB字节等于入口字节。它包含数据及权限，不只是把几个字段重新读一遍。当前物理夹具没有另加已初始化DelReq哨兵；这里对该字段的信用来自泛用保持定理，不冒称另做了带值实例。

这里只讨论源码级分析布局，不声称编译器或硬件ABI已被证明。

## 3. 新证明如何接已有执行？

强化接口：`V293_task_prio_prefix_event_update_preserves`。

入口资源和此前非空连续接口逐字相同，没有额外要求“最终内存已正确”。证明过程是：

1. 实际执行表写、旧TCB字段读取、ready判断和事件迁移，取得中间Mg。
2. 用前缀的真实frame证明Mg中TCB整块与入口相同。
3. 从Mg执行真实五字段写入，得到Mh。
4. 用五写的细粒度frame证明50..54以外与Mg相同。
5. 合并两段，得到这些字节与原始入口相同；由四字节读取外延性得到内部EventPtr原指针。

在同一个Mh中同时交付13槽、ready、事件位图、五字段、pevent、ptcb、内部EventPtr和未写字节。不是分别找两个不同的“正确出口”。旧接口保留，本次强化接口向后续调用方明确提供更强结果。

`V293_tcb_update_frame_witness`复用原先物理入口，四组控制覆盖ready假／真、事件旧行仍非空以及事件未操作高位。8→6时五字段仍为6／0／6／1／64；X索引6不能写成BitX掩码64。等待用例ready仍16／0，没有收到消息或解除等待。

这些入口只证明物理资源可满足，不证明初始化可达或完整等待／ready共享状态合法；ready真／假还改变行和组，不是单因素消融。

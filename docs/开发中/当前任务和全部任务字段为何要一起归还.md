# 当前任务和全部任务字段为何要一起归还

## 先把前因后果讲清楚

老师要求先用固定版本 uC/OS-II 学会复杂系统软件的机器验证流程，再推进 uC/OS-III。第一阶段终点不是“某个脚本通过”，而是同一个配置后 C 程序的源码级 `GOOD_OS` 和 K1–K4 回归证明。现在仍在连接局部函数与共享状态，没有达到整核终点，尚未启动 uC/OS-III。

上一节证明了：一次真实成功更新并返回之后，抽象任务表枚举的全部选定 TCB 字段资源仍然存在，且目标记录已变成新优先级。本节继续解决一个具体缺口：这些任务字段，能不能和全局 `OSTCBCur` 指向谁的资源**同时**归还？

## 第一步：看懂需要保持什么

| 记号／问题 | 本节填好的解释 |
| --- | --- |
| `CurTid current` | 全局 `OSTCBCur` 保存当前任务指针；框架定义只要求只读半份额，不是完整写权限。 |
| `V293_owned_task_records tasks` | 按规范任务表枚举，拥有全部选定任务记录字段的空间资源。不是全部 TCB 字节，也不是整个内核堆。 |
| `P ** Q` | P、Q 的实际内存／抽象资源能够按分离逻辑的 join 规则同时组合。只读份额按框架规则组合，不能简单理解成所有地址都不同。 |
| 分别有 `P ** Atrue`、`Q ** Atrue` 为什么不够？ | 两次独立的存在性结论可能选中了重叠或不兼容的资源，不能据此拼成 `P ** Q`。 |
| 本节怎么解决？ | 从入口提取整个 `CurTid ** all_records` 联合片段，保持内部 join，并把同一个片段搬到同一个终态。 |
| 为什么检查字节与权限，而不只检查 load？ | 读到同样的值，不代表仍拥有可写权限；不能由 load 成功反推空间所有权。 |
| 任意剩余资源 R 呢？ | 入口允许 R，但返回过程释放局部变量，因此不宣称任意 R 都跨 free 保持。 |

## 第二步：沿着一个定理读，不必从头通读仓库

打开 `certiucos/v293/proofs/V293TaskRecordOwnership.v`，从原1235行之后阅读：

1. `V293_current_fragment_local`：找到 current 指针片段实际依赖的全局块，保留真实指针编码和只读权限。
2. `V293_current_task_records_block_frame`：把 current 与全部任务记录的**联合**片段搬到最终内存。其前提是 current 块及每个实际任务块的字节／权限精确保持。
3. `V293_current_tasks_fields_reconstruct`：将联合物理片段与更新后的抽象 `shared_fields` 组合。这里后者物理内存为空、前者抽象域为空，不是在复制物理资源。
4. `V293_critical_wait_current_all_owned_execution`：只调用一次已有成功执行根，把程序执行、抽象更新、位图／表／事件关系和联合资源绑定到同一个 `Mf / Os' / OO'`。

五次赋值的内存模型并非第二次执行：它只用于描述目标 TCB 的最终字节／权限。实际执行来自唯一一次旧执行根调用。

## 第三步：把条件和结论分开

| 条件／结论 | 具体含义 |
| --- | --- |
| 原有成功等待分支条件 | 版本、配置、优先级范围、指针、任务／事件关系、locals 和控制状态仍按原接口要求。未删掉不利前提。 |
| 非目标任务块的 frame 条件 | 必须避开此次实际写集合和局部 free 集合。条件显式暴露，没有声称对所有任意入口成立。 |
| current 指针块的 frame 条件 | 仅当其块不等于目标 TCB 块时，要求避开实际写／free 集合；相等时用已证的目标整块精确关系处理。没有强加块不相等。 |
| 联合终态 | `((CurTid current ** all_records updated_tasks) ** shared_fields updated_tasks) ** Atrue`。 |
| 未获得的结论 | 全共享 Inv、所有 API 分支、ISR、正常无锁切换、初始化可达性、整核 GOOD_OS、同程序 K1–K4。 |

## 第四步：看一个确实能消费联合资源的例子

新例子位于 `audit/probes/V293CurrentAllOwnershipProbe.v`，从入口真实组合三个片段，不把旧“执行完成”定理当作入口证明：

- 全局块80存放只读半份额的 `OSTCBCur`，指向 ready 任务 `(60,0)`。
- 目标任务 `(41,8)` 优先级8→6，仍等待同一 SEM 事件 `(72,5)`，delay=1，消息为非 NULL `(120,7)`。
- 另一个任务 `(60,0)` 仍 ready、优先级4。
- 一次返回后，从**同一个联合终态**读回 current=60，并分别证明两个任务字段仍可实际 store。
- 另从终态实际 load 排除“current 错改成目标任务41”，从实际更新值排除“还拥有旧规范任务表”。

“优先级变了”不等于“等待结束”。本例没有执行满足等待条件的事件操作，目标仍在等待；消息指针字段非NULL也不被当作ready条件。这与之前入门时的状态判断一致。这里是满足本节局部前提的字面入口，尚未证明它能从内核初始化到达。

# 改优先级的目标任务，不等于当前任务

## 1. 先把三种信息分清

`OSTaskChangePrio(oldprio,newprio)`修改的是指定任务，不一定是调用者。

- **目标任务**：本例是等待信号量的`(41,8)`，优先级从8改成6。
- **物理当前任务**：全局`OSTCBCur`的内存指针。本例改为就绪任务`(60,0)`。
- **抽象当前任务**：证明状态中`curtid`项记录的任务。本例一直是`(60,0)`。

括号里的第二个数是地址偏移，不是优先级。任务身份是TCB指针；改优先级不能换掉身份。

## 2. 上一轮为什么还不够

上一轮完整执行例子用`OS_PRIO_SELF=255`解析到物理任务`(41,8)`，抽象current却是`(60,0)`。局部位图、事件头、返回值等结论可以成立，但不能据此认定入口满足全局不变量。

本轮保留旧例子和证据，并明确证明它的物理指针与抽象current不匹配。没有把旧编号改掉后重新宣布旧结果通过。

新例子是另外构造的**同一份入口内存**：普通选择器8指定等待任务41，当前任务指针指向已经存在的就绪任务60。抽象任务表、抽象current及两任务原有状态不改。模型的标准`OSTCBCur`标识符显式绑定到指针块80。这只是具体例子的标识符映射，不是已经验证的C前端。

## 3. 填好的状态表

| 项目 | 新入口 | 同一次完整返回后 |
| --- | --- | --- |
| 选择器 | 普通优先级8，不是SELF | 目标已查找，局部变量释放 |
| 修改目标TCB | `(41,8)` | 仍为`(41,8)` |
| 目标优先级 | 8 | 6 |
| 目标状态 | 等待同一信号量 | 仍等待；不会自动变ready |
| 物理`OSTCBCur` | `(60,0)` | `(60,0)` |
| 实际抽象`curtid`查询 | `(60,0)` | `(60,0)` |
| 当前任务表成员 | 优先级4，ready，消息NULL | 相同 |
| ready两行 | 16/0 | 16/0 |
| 信号量等待两行 | 0/1 | 64/0 |
| 信号量类型／计数／指针 | 3／0／NULL | 保持 |
| 调度环境 | run=1、ISR=1、lock=0 | 调用调度，但受ISR条件阻止切换 |
| 返回 | 尚未返回 | 返回0，释放locals，恢复caller |

注意：“当前任务是ready”与“被修改任务是ready”是两回事。本例修改等待任务，并没有收到它等待的消息，因此它仍等待。

## 4. 一般证明怎么做

`V293_critical_event_current_execution`从原始入口条件开始，只调用一次上一轮完整执行根，保留其全部前提、输出以及同一`Mf/Os'/OO'`。

新增结论是条件式：若入口`OSTCBCur`的完整指针读取等于抽象current、该current是实际任务表中的就绪成员，且指针块不在写集合和待释放locals中，则同一次返回后：

1. 完整指针读取仍指向同一current；
2. 实际最终抽象状态`OO'`的`curtid`查询也等于该current；
3. current仍是任务表中的同一就绪成员。

指针保持来自执行产生的逐内存单元frame，不是把出口load放进前提。抽象查询来自真正持有的共享字段。就绪成员保持来自“被修改任务在wait、current在ready，所以两者不同”，再使用任务表单点更新性质。

## 5. 怎样检查不是自说自话

独立语义定理在**同一次完整执行**的`Mf/OO'`上排除：把最终物理指针或抽象current说成等待任务41。另一个定理保留并指出旧入口的41/60错配。

正式门禁实际执行两个单因素负控：只将最终物理指针或最终抽象current换成等待任务，完整目标Proof不变。两者均在最终tauto被拒绝，只授固定Proof的结论敏感性；不把它说成C突变已验证、一般不可证明性或所有下游机制都正确。18项实际门禁检查符合预期，包含三次coqchk内核复核；这不代表整仓测试或最终验收全绿。

## 6. 这一步还没有证明什么

完整指针load相等，不等于已经重新构造拥有内存权限的`CurTid`分离断言。新接口本轮只保持**纯对应事实**，不声称完整共享不变量成立。还要接入`CurTid`所有权、真实API／ISR保持、初始化、正常无锁调度、同程序K1–K4与源码级`GOOD_OS`。

固定目标仍为uC/OS-II V2.93.01及原两类授权修复。阶段一未完成；之后才按老师附件推进uC/OS-III。

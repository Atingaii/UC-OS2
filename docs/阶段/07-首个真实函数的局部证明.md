# 第七步：让真实 C 函数进入证明链

## 1. 这一轮究竟推进了什么

过去的三个内核小模型可以说明设计意图，但没有把真实函数体交给框架证明。这一轮选取冻结程序里的 `OSVersion()`，完成下面的连接：

```text
锁定上游 + 两项既定补丁 + 固定配置
  → 实际预处理的 OSVersion AST
  → 含返回类型转换的 CoqImp 函数
  → 独立返回值规格
  → 任意 frame 下的局部 Hoare 定理
  → 真实操作语义中的返回执行
```

这是第一个函数的前四道门，不是整核完成。组件连接、初始化和最终 `GOOD_OS` 仍开放。

## 2. 先读实际 C，而不是根据名字猜测

冻结清单记录：`Source/os_core.c` 第 1025–1028 行：

```c
INT16U OSVersion(void)
{
    return (OS_VERSION);
}
```

**注意：这个发行版的 `Source/ucos_ii.h` 定义 `OS_VERSION` 为 `29300u`，不是 29301。** 发行版身份仍为 V2.93.01，不为迎合名称修改源码或规格。

预处理后，Clang 实际得到：

```text
FunctionDecl INT16U (void)
  CompoundStmt
    ReturnStmt
      ImplicitCastExpr IntegralCast → unsigned short
        ParenExpr unsigned int
          IntegerLiteral unsigned int 29300
```

`INT16U` 的返回类型会将 32 位无符号常量转换为 16 位无符号值。虽然 29300 本身不发生截断，也不能把这个转换从翻译中随便删掉。

## 3. 对应的 CoqImp 程序

文件：`certiucos/v293/code/V293OSVersion.v`。

```coq
Definition V293_OSVersion_expr : expr :=
  ecast (econst32 (Int.repr 29300)) Tint16.

Definition V293_OSVersion_body : stmts := srete V293_OSVersion_expr.

Definition V293_OSVersion_function : function :=
  (Tint16, dnil, dnil, V293_OSVersion_body).
```

- `Int.repr`：框架的 32 位整数表示。
- `ecast ... Tint16`：无符号窄化；框架具体以模 65536 实现。
- `srete`：有返回值的 `return`。
- 两个 `dnil`：没有参数、没有局部变量。

检查器只接受上面这个受限 AST 形状，重新生成文件并逐字比较。它不会遇到不支持的语句就跳过；多一个调用、参数、属性、语句或者改变有符号性都会拒绝。

**信任边界：** Clang、配置后 AST 到 CoqImp 的这个小型生成器仍是受信任的源码对应工具；没有证明 Clang 或一个完整 C 编译器正确。GCC 独立预处理得到相同结果只是交叉检查，不会自动变成编译器正确性定理。

## 4. 如何阅读局部 Hoare 定理

规格文件：`certiucos/v293/spec/V293OSVersionSpec.v`。

```text
前置：frame
执行：V293_OSVersion_body
返回：Some (Vint32 (Int.repr 29300))，并保留 frame
```

`frame` 是调用者已有的资源／状态断言，可以包含内存和抽象状态。定理对它任意量化，而不是要求一个永远无法满足的前置条件。

框架用 `InfRules` 表达这个判断。`V293_OSVersion_local_hoare` 利用 `rete_rule`，证明返回表达式确实计算出指定值，并把调用者原有断言原样交回。尾部的 `Afalse` 表示 `return` 后没有正常直落的后继，不是把前置条件设成 `False`。

还要注意本框架的 `[| P |]` 携带空资源要求。后置条件采用 `[| result = ... |] ** frame`，使用分离合取保留原有资源，而不是错误地要求整个调用者内存为空。

证明文件：`certiucos/v293/proofs/V293OSVersionProof.v`。

| 定理 | 证明内容 |
| --- | --- |
| `V293_OSVersion_local_hoare` | 面向上层的稳定局部接口；返回指定版本值，保留任意 frame |
| `V293_OSVersion_post_exact` | 从后置断言提取精确返回值及原 frame |
| `V293_OSVersion_execution` | 从空的被调用者局部环境实际执行到返回；内存不变，恢复调用者环境 |

最后一条对任意内存成立，给出有限步执行，而不是通过“初态不可满足”或“函数永远不能启动”绕过证明。

## 5. 检查器怎样避免假进度

在仓库根目录执行：

```sh
make check-functions COQBIN=/data/home/lucentzhou/.opam/default/bin/
make audit
```

`check-functions` 会：

1. 重放既定 C 修复、预处理并核对全部冻结身份。
2. 分别读取 Clang／GCC 预处理结果中的实际函数 AST，核对受限翻译。
3. 在一次性目录仅复制活动源码，干净构建全部 112 个 Coq 文件；不复制旧 `.vo`，不读取参考资料。
4. 用另一个写死正确接口类型的 Coq 探针接收导出的定理，避免只检查定理名字。
5. 打印三个根的真实假设，并执行 `coqchk` 检查其对象和依赖闭包。
6. 运行下面两项单因素反向实验。

| 只改变什么 | 保持什么不变 | 必须在哪里失败 |
| --- | --- | --- |
| AST 返回常量 29300 → 29301，并重新生成模型 | 原规格、证明及工具环境 | 表达式结果定理 `V293_OSVersion_eval` |
| 局部定理前置条件改成 `Afalse`，保留其名字并给出可通过的空洞证明 | 模型、规格、接口探针及其它证明 | 空洞定理本身编译成功，但独立 `checked_local_hoare` 类型检查失败 |

AST 的各类拒绝条件另外逐项单因素测试。报告还绑定活动 Coq 源码、构建入口和检查器的哈希；改过源码却拿旧报告申报覆盖会被拒绝。

`make audit` 只验证已保存证据的身份和覆盖规则；不会隐式执行完整 Coq／C 检查。实时重放要运行 `check-functions`。以后新增函数或修改活动证明，会使当前函数报告过期，需要生成新的验收版本，不能悄悄沿用旧结果。

## 6. 为什么后两道门还是 0

`local_hoare` 只说明这个函数体满足局部接口。现在还没有把它接到整核 API 表、抽象操作推进、函数规格表及共享不变量中，所以 `component_linked=false`。

具体程序、规格、初始化和总连接仍未实例化，所以 `full_target_linked=false`。不能用只有 `OSVersion` 的程序、永假初始化或抽象规格允许任意行为的办法宣称 `GOOD_OS`。

下一步沿两个真实依赖推进：先接入 API 组件接口，再对固定配置的就绪位图与真实 `OS_SchedNew` 建立内存表示和最小优先级规格，随后连接任务、等待、同步对象与初始化。K1–K4 必须最终落到同一个真实程序上；已有 C 回归和小模型仍不能替代它们。

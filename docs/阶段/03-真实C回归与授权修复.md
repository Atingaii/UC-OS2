# 第三阶段：让真实 C 反例先失败，再接入两项修复

这一阶段对应“真实 C 回归与两项授权补丁”的提交。它承接 [第二阶段](02-源码配置与函数清单.md)，不要求你预先了解嵌入式系统，也不需要先学习汇编。

## 1. 先知道这次在解决什么

前两阶段解决的是“工具能否工作”和“我们究竟拿到了哪份源码”。现在开始改变内核行为，但只能改变已经授权的两类：

1. 一个任务持有多个互斥锁时，释放锁不能把它恢复到已经失效的中间优先级。
2. 当前任务已经锁定调度时，不能再成功删除自身并继续使用已回收的任务记录。

这次的产物不是一堆新的 Coq 引理，而是：

- 能真正调用当前版本 C 函数的回归夹具；
- 两份能应用到锁定源码上的补丁；
- 同一批测试在修复前、修复后、各移除一个补丁时的结果；
- 针对各个辅助机制的单因素消融。

**C 测试通过不等于 Coq 证明完成。** 六阶段函数证明覆盖仍为 0。后续仍要冻结修复后源码、建立不变量、翻译和证明函数、连接初始化及整体程序。

## 2. 内核最基本的几件事

### 2.1 任务与 TCB

可以先把任务想象成一段需要被安排执行的程序。内核用一个结构体记住它的状态，这个结构体叫任务控制块，即 `OS_TCB`。

这次最常见的字段和全局量是：

| 名称 | 用直白的话解释 |
| --- | --- |
| `OSTCBPrio` | 这个任务目前使用的优先级 |
| `OSTCBStat` | 等待、挂起等状态位 |
| `OSTCBStatPend` | 一次等待的结果：成功、超时、中止 |
| `OSTCBDly` | 还要等待多少次时钟滴答 |
| `OSTCBCur` | 当前执行任务的 TCB 指针 |
| `OSTCBPrioTbl[p]` | 优先级 p 对应的 TCB，或空／互斥锁预留标记 |
| `OSRdyTbl`、`OSRdyGrp` | 哪些优先级有就绪任务的位图 |
| `OSTCBFreeList` | 可分配 TCB 的空闲链表 |

优先级表并不保证“一个 TCB 只出现一次”。优先级继承期间，基础优先级槽和某个互斥锁槽可以同时指向同一任务。需要防止的是两个不同的活动任务拥有相同的有效优先级，以及就绪位解析到空／预留／不匹配的 TCB。

### 2.2 数值越小，优先级越高

本项目中，优先级 3 比 5 高，5 又比 10 高。后文说“提高优先级”时，数字通常变小。

任务“就绪”只表示有资格执行，不表示它就是当前执行任务。挂起任务没有执行资格；等待任务要等事件或超时；这两种状态可以叠加。

### 2.3 互斥锁、所有者与优先级继承

互斥锁保护一份同一时刻只能由一个任务使用的资源。拿到锁的任务叫所有者。

假设低优先级任务 A 拿着锁，高优先级任务 B 来等待这把锁。为了让 A 尽快完成并释放资源，内核可以临时提高 A 的优先级。这就是本次讨论的优先级继承。

本版本用互斥锁的 `OSEventPtr` 指向所有者 TCB；`OSEventCnt` 的高 8 位存锁的 PCP，低 8 位存恢复所需的优先级。PCP 是这把锁预留的优先级，不是一个新任务。低 8 位为 `0xff` 则表示锁可用。

## 3. K3：为什么不能简单恢复“上次保存的数字”

### 3.1 先看出错的过程

任务 A 的基础优先级是 10。两把锁的 PCP 分别是 5 和 3。

| 步骤 | A 当前优先级 | 关键变化 |
| --- | --- | --- |
| A 拿到第一把锁 | 10 | 第一把锁记录 10 |
| 优先级 7 的任务等待第一把锁 | 5 | A 临时继承 PCP 5 |
| A 再拿第二把锁 | 5 | 原上游把临时数字 5 存入第二把锁 |
| 优先级 4 的任务等待第二把锁 | 3 | A 再继承 PCP 3 |
| 先删除第一把锁 | 3 | 5 号槽被释放，但第二把锁仍保存旧的 5 |
| 在 5 号槽创建新任务 C | 3 | 5 号槽现在属于 C |
| 再删除第二把锁 | 原上游恢复为 5 | A 与 C 优先级冲突，槽位还可能被 A 覆盖 |

回归还包含不创建 C 的版本：即使没有覆盖其他任务，最后恢复到 5 而不是基础优先级 10 仍是错误。不能只检查“有没有崩溃”。

测试中的等待者使用真实 Pend 与 Tick 产生超时，再显式挂起／恢复相关任务。超时并不立即撤销已经发生的 PCP 继承；锁的释放才触发恢复路径。

### 3.2 修复分成三个必要环节

第一，获取锁时保存基础优先级，而不是当下临时继承的优先级。

`OSMutex_BasePrio` 检查任务当前优先级与其仍拥有的锁中保存的值。在目标不变量成立时，它们的最大值是基础优先级，因为较大的数字表示较低的基础优先级。

第二，释放锁时，不能每次都直接恢复基础优先级。任务可能还持有另一把有继承贡献的锁。

`OSMutex_EffectivePrio` 排除本次正在释放的锁，从基础优先级开始，保留其他仍拥有且已激活的 PCP 贡献。优先级表的 PCP 槽仍指向该所有者，是这里判断贡献已激活的依据。

因此：

```text
恢复值 = 基础优先级与其他仍生效 PCP 中，数值最小的一个
```

第三，实际改变优先级时，同时移动相关位图，不能顺手改变任务是否就绪。

- 原来就绪的任务，移动就绪位。
- 原来挂起的任务，不能因恢复优先级而被偷偷唤醒。
- 正在等待另一个互斥锁的任务，需要移动等待表中的对应位。
- 被移动的不是当前任务时，不能改当前任务的 `OSPrioCur`。

这三件事都由不同的测试或消融检查。不是因为“最后恢复成 10”就宣称所有辅助机制都正确。

### 3.3 哪些路径接入了同一规则

- `OSMutexAccept`：无需阻塞地获取可用锁。
- `OSMutexPend`：获取可用锁时保存基础优先级。
- `OSMutexPost`：原所有者恢复；将锁交给等待者时，也保存新所有者的基础优先级。
- `OSMutexDel`：ALWAYS 与 NO_PEND 的成功删除分支都进行所有者恢复。

NO_PEND 表示“有等待者就不允许删除”，不是“没有等待者就无需处理所有者”。有等待者时原来的拒绝行为未被改掉。

上述行为都在原有临界区内完成，没有新增公共 API 或 TCB 字段。内部新增两个静态辅助函数；最终配置后函数总数要由下一阶段清单确认，不能直接继承原上游的 92。

## 4. K4：为什么删除自身前要检查调度锁

### 4.1 调度锁不是“所有事情都停止”

`OSSchedLock` 增加 `OSLockNesting`，暂时阻止内核切换到其他任务。它不意味着之后的 API 自动禁止创建／删除任务，也不等于中断一直关闭。

原上游允许以下过程：

```text
当前任务锁定调度
  → 删除自身成功
  → 当前 TCB 被放回空闲链表
  → 创建新任务，复用同一个 TCB
  → 原来的执行上下文却还没有安全切走
```

回归不是只断言一个错误码；在上游分支里，它还实际调用创建函数，并观察到了新任务复用当前 TCB。

### 4.2 补丁为什么放在这里

`OSTaskDel` 原来的顺序包括参数检查、解析 `OS_PRIO_SELF`、取得目标 TCB、检查空指针与互斥锁预留槽，然后才修改就绪位、等待链、任务链和空闲链。

补丁插入在“TCB 已验证”与“第一次破坏性修改”之间：

```c
if ((ptcb == OSTCBCur) && (OSLockNesting > 0u)) {
    OS_EXIT_CRITICAL();
    return (OS_ERR_SCHED_LOCKED);
}
```

用 TCB 指针判断“是不是自己”，不是只比较传入的优先级数字。返回值 50 是上游已有的错误码，没有造一个新错误码。

放得太早，会改变 ISR、非法优先级、空／预留表项等错误的优先顺序。放得太晚，即使返回 50，也可能已经损坏就绪状态。

### 4.3 我们检查了什么

- `OS_PRIO_SELF` 与显式当前优先级两种调用方式。
- 调度锁嵌套次数为 1 和 255。
- 拒绝前后，TCB 表、优先级表、就绪图、事件／标志表、相关链头、计数及删除 hook 调用数的快照相同。
- 可以逐层解锁，然后重新删除自身成功。
- 锁定调度时删除其他任务仍允许。
- 没锁定时删除自身仍允许。
- 原来的参数与上下文错误优先顺序不变。

快照覆盖的是本测试明确列出的内核状态，不是“扫描并证明了所有机器内存不变”。后者需要正式的 frame 条件与源码级证明。

## 5. 为什么要四种补丁组合

如果只跑“原始版本失败、两个补丁一起通过”，不能知道两个补丁是否都真正起作用。

本次固定源码、配置、测试与运行方式，仅改变启用的补丁：

| 版本 | K1、K2 与原有控制场景 | K3 的十个失败场景 | K4 的四个失败场景 |
| --- | --- | --- | --- |
| 原上游 | 通过 | 按指定断言失败 | 实际回收／复用当前 TCB，然后按指定断言失败 |
| 只接互斥锁补丁 | 通过 | 通过 | 仍失败 |
| 只接自删除保护 | 通过 | 仍失败 | 通过 |
| 两项都接入 | 通过 | 通过 | 通过 |

反序释放本来就能成功的场景也保留为控制组，不把它们算成新的修复收益。

每个可执行程序跑 23 个场景。四种补丁组合，分别用 GCC／Clang 和 `-O0`／`-O2`：共 `23 × 4 × 2 × 2 = 368` 次场景执行。

矩阵报告 PASS 表示“观察符合预先约定的前后对照”，**不表示原上游的失败被算成正常内核行为**。原上游和单补丁版本的失败输出仍完整保留在 JSON 中。崩溃、超时或不匹配的断言不算复现成功。

## 6. 为什么还要逐机制消融

测试文件 `tests/test_c_regressions.py` 另外构造十一种一次只改变一个机制／状态写入的变体：

| 被撤销／改变的机制 | 必须命中的观察点 |
| --- | --- |
| Accept 保存基础优先级 | Accept 嵌套场景最终不再恢复到 10 |
| Pend 保存基础优先级 | Pend 嵌套场景最终不再恢复到 10 |
| Post 交接时保存新所有者基础优先级 | 新所有者保存的值不是 10 |
| 保留其他锁贡献 | 第一把锁刚释放，仍持第二把锁时就错误降到基础优先级 |
| 保持挂起状态 | 原本挂起的所有者出现就绪位 |
| 移动等待位 | 新优先级对应的等待位缺失 |
| 只更新当前任务的当前优先级变量 | 其他删除者的 `OSPrioCur` 被改坏 |
| 恢复到正确基础优先级后，再故意覆盖已复用槽位 | 基础优先级检查通过后，独立的槽位所有权检查仍能报错 |
| 仅拒绝当前任务 | 删除其他任务被误拒绝 |
| 仅在调度已锁时拒绝 | 未锁定自删除被误拒绝 |
| 在状态修改前拒绝 | 返回 50，但拒绝前后的快照不同 |

每个变体必须到达自己预定的断言，不能用更早的崩溃代替下游机制的检验。还有两个边界测试：配置漂移应被拒绝且不被重写；补丁不能修改第三个源码文件。

## 7. 这些 C 测试究竟在哪里运行

测试直接 `#include "ucos_ii.c"`，因此调用的是锁定版本的实际配置后 C 定义，而不是在 Python 里另写一个类似内核。

但当前仓库没有可执行的真实 CPU 汇编端口。测试沿用 32 位分析头文件，并在夹具里实现模拟边界：

- 临界区保存／恢复一个模拟的中断状态，检查进出是否平衡。
- 上下文切换根据真实 `OS_SchedNew` 的结果选择最高就绪 TCB。
- 指定回调在切换边界执行另外一个任务的 API 片段。
- 任务栈初始化和 CPU hooks 只满足测试边界，不运行实际任务函数。

驱动器在 API 边界接着当前选中的任务执行下一段；它没有为每个任务建立独立 C 栈，也没有模拟异步中断。因此，这属于**真实 C API 的受控边界回归**，不是整段任务程序在真实 CPU 上的运行证明。

采用 Linux 32 位无 libc 可执行程序，是为了保留分析头文件中的指针与整数位宽。不能为了让测试能跑，就把活动分析端口改成 64 位或空临界区。

最初夹具曾因未选定当前任务就调用 Suspend 而崩溃；优化编译也暴露了输出系统调用没有声明 EAX 返回值的问题。这两项都修在夹具中，不作为内核缺陷或补丁收益。原始失败与优化反汇编留在本地日志，见阶段报告。

## 8. 你可以怎样重跑和阅读

在仓库根目录：

```sh
make source-audit
make check-c
make check-c-evidence
make test
make audit
```

`make check-c` 首先以只读方式核验第二阶段源码清单，包括原始源码、配置、端口边界和工具身份；不会调用配置生成器把本地漂移悄悄改回去。

测试仅在自动创建的一次性目录里复制锁定源码并应用补丁，结束后删除源码副本与可执行程序。不会覆盖 `csrc/upstream/v2.93.01/checkout/`，也不会在仓库里安装依赖。

如果你的编译器版本不同，已提交报告的逐字比较可能失败。先看工具版本与内容差异；不要为了绿色输出而删除失败结果或直接改测试预期。Linux 不支持 i386 程序时，也应报告环境不满足，不能改成未标明的 64 位测试。

推荐阅读顺序：

1. 本文第 2–4 节，理解两个问题为什么会发生。
2. `tests/c/kernel-regressions.c` 中的 `nested_mutex` 和 `locked_delete`，看真实调用顺序。
3. 两份 `.patch`，先看自删除保护，再看互斥锁的三个环节。
4. `scripts/check-v293-c-regressions.py` 的 CASES 与四种组合，理解什么结果才算符合预期。
5. `tests/test_c_regressions.py`，看逐机制消融为何能拦住不完整的修复。
6. [第三阶段报告](../../audit/STAGE03_C_REPAIRS.md) 与 [JSON 执行证据](../../audit/c-regressions.json)。

## 9. 下一步仍然是什么

下一阶段要把这组补丁接入修复后源码生成／冻结流程，重新产生完整函数清单，并逐个记录真实函数身份。随后从纵向函数切片和共享不变量进入 CoqImp 证明。

尚未证明的关键条件包括：持锁任务的基础优先级始终可恢复、优先级表别名与有效贡献一致、位图和任务链一致、初始化建立这些条件，以及全部 API 如何保持它们。

上游注释要求不能在持有互斥锁时随意改变／删除所有者任务；本次不把这种用法静默改写成一个新功能。嵌套锁场景本身按项目授权扩展处理。后续若发现其他真实反例，要按范围规则记录并取得决定，不能直接扩大修复清单，也不能通过缩弱规格把反例排除掉。

最终目标仍然是连接真实程序、规格和初始化的源码级 `GOOD_OS`，不是本章的 C 回归报告。

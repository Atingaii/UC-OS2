# 第二十一课：把共享任务表借给调度前缀，再归还

## 一、这次解决什么问题

上一课建立的共享核心，已经拥有：

| 资源 | 作用 |
| --- | --- |
| `OSTCBCur` 半权限 | 读取真实当前 TCB 指针，并与抽象当前任务对应 |
| 抽象 `curtid` | 抽象当前任务身份 |
| 抽象任务表 | 哪些任务存在、优先级和等待状态是什么 |
| 抽象事件表 | 事件对象状态 |
| 抽象时间 | 当前 tick 值 |

但此前的调度前缀也要求在不变量**外面**持有抽象任务表。如果把那个旧前缀直接用在新的非空不变量上，就会要求同一个独占槽位同时属于两块不相交资源。这不是多写一个参数能解决的：这种入口根本无法满足。

本轮的正确顺序是：**打开共享核心 → 借出唯一的任务表 → 执行原来的真实调用与赋值 → 归还任务表 → 关闭同一个共享核心**。

## 二、先分清两种连接符

- `P ** Q`：把资源分成两个不相交部分，分别满足 `P`、`Q`。
- `P //\\ Q`：在**同一个状态**上同时检查 `P`、`Q`，并不分配第二份资源。

新定义 `V293_shared_snapshot` 使用第二种连接符：一边是实际 `SWINV V293_shared_inv`，另一边观察其中的当前任务、任务表、事件表和时间。这样能记住开关前后的值，没有在外面另外分配任务表。

`V293_shared_snapshot_open` 从这个观察中确定共享核心内隐藏的四个值；`V293_shared_snapshot_close` 把同一组资源重新封装，保留观察。

## 三、为什么内部调用需要区分两个不变量参数

此前的契约把两个不同用途的参数写成了同一个 `I`：

| 参数 | 实际含义 |
| --- | --- |
| 资源参数 `I` | 内部契约里实际打包、传递并返回什么资源 |
| 规则参数 `RI` | `InfRules`／`WFFunEnv` 正在使用哪个逻辑不变量 |

打开共享核心后，内部计算不需要再次拥有整个共享核心；它只需要原中断／临界区协议。`V293_opened_inv` 的每个槽位都是 `Aemp`，用于打包这个协议，但**实际规则参数始终仍是非空的 `V293_shared_inv`**。

这不是把真实不变量换成空不变量，也没有修改框架规则。已有证明现在允许 `I` 与 `RI` 分开，旧接口仍作为 `RI = I` 的特例保留。实际函数体、构造器和调用规则都继续复用。

## 四、真实执行的代码没有变

稳定入口是 `V293_OSSched_shared_prefix`，证明的仍是：

```c
OS_SchedNew();
OSTCBHighRdy = OSTCBPrioTbl[OSPrioHighRdy];
```

| 时刻 | 任务表在哪里 | 其余共享字段在哪里 |
| --- | --- | --- |
| 入口 | 共享核心内 | 共享核心内 |
| 内部调用／目标赋值期间 | 原前缀的唯一任务表资源 | 作为合法 `GoodFrm` 资源保持；中断／临界区协议放在内部契约里 |
| 出口 | 归还共享核心 | 原值归还共享核心 |

出口给出最高就绪任务及真实目标指针；事件表、时间、当前任务和动态栈不变。这里尚未执行真正任务切换，所以不能把“目标指针已写好”理解成“当前任务已经切换”。

## 五、如何排除一个永远进不去的入口

`V293_OSSched_shared_precondition_witness` 在同一个状态中构造整个入口，而不是分别证明各块看起来合理：

1. 实际位图、优先级数组和输出单元；
2. 同一个当前指针分出的两半权限；
3. 一份抽象任务表和另外三个抽象槽位；
4. 两种场景：当前任务就是选中任务，以及当前任务已经时间等待、将选中另一个任务；
5. 任意事件表和任意时间值。

因此这不是通过重复持有独占任务表制造的空前置。见证的栈仍为空，只证明可满足，不证明真实启动后可达。

## 六、本课的验证和下一步

验证不只看 `Qed`。独立接口固定写出资源形状和前后值，并预先规定四种单因素控制：返回错误时间、让内部契约重新占有共享核心、移除见证的时间槽位、给稳定接口偷偷增加 `False` 前提。每项必须在指定证明／探针处拒绝，不能把更早的类型或导入错误计作成功。

正式结果见[第二十阶段审计](../../audit/STAGE20_SCHEDULER_SHARED.md)。本课不要求你回答问题；阅读顺序是先看新模块中的 `V293_shared_prefix_pre`，再看 `V293_shared_prefix_post`，最后对照稳定入口定理。

下一步将这一资源借还方式接回两层 guard、优先级比较和计数器后续，继续关联实际物理共享结构并处理真正切换。完整物理 TCB／ECB 关系、`OSCtxSw` 与 `OSPrioCur` 的同步边界、临界区、初始化、最终 `GOOD_OS` 及同程序 K1–K4 都仍未闭合；完成阶段一后才推进 uC/OS-III。

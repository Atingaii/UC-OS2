# 第八步：从局部函数证明连接 API 组件

第七步证明了实际 `OSVersion` 函数体返回 29300，且不破坏调用者给出的资源。现在要解决的是：**调用这个 API 时，框架是否真的找到了这个函数，并使用了相同的参数和返回规格？**

## 1. 先区分函数体和调用入口

`V293_OSVersion_local_hoare` 的输入只是函数体和一个资源断言。调用方还需要知道：

- 函数标识符查到的确实是这个函数，而不是空映射。
- 函数无参数、无局部变量，返回类型是 `Tint16`。
- 抽象规格只返回指定常量，而不是允许任意结果。
- 框架生成的调用前置和返回后置确实可以由这条局部证明连接起来。

这些不是另一个算术性质，而是上层使用已有证明所必需的接口。

## 2. 本次只建立一个真实的 API 单元

新文件：`certiucos/v293/proofs/V293OSVersionAPI.v`。

`V293_OSVersion_api_unit version_id` 只在 `version_id` 处保存已检查翻译的真实函数；`V293_OSVersion_api_spec version_id` 在相同位置保存无参数、返回 29300 的规格。

这里的 `version_id` 由未来链接器选择，定理对任意选择成立。**这不是最终整个内核的程序表，也没有提前决定全部函数／全局变量的标识符分配。** 其余 93 个定义没有因为这个单元而得到证明。

## 3. 定义域对应是什么意思

`V293_OSVersion_api_domains` 证明框架的 `EqDomAPI`：

1. 程序存在函数的地方，规格也存在；反之亦然。
2. 双方参数类型列表一致。
3. 双方返回类型一致。

只证明“两个空表定义域相同”没有价值。因此独立验收探针把两张表、唯一函数体和返回常量直接写进预期类型，不能通过把导出定义改为空表来替代当前目标。

## 4. 框架如何生成调用前置和返回后置

框架提供 `BuildPreA'` 和 `BuildRetA'`。它们根据函数声明生成：

- 抽象 API 执行位置；
- 调用者局部不变量和当前任务信息；
- 参数／局部变量资源；
- 中断、临界区状态和局部环境定义域。

本函数没有参数、局部变量。`V293_OSVersion_api_builders` 证明传入空参数列表时两者确实返回 `Some`，不允许靠构建器总是返回 `None` 让证明的前提永远无法满足。

这条构建器引理证明的是断言确实被生成，不是整个内核初始化可满足性。具体共享状态和初始化仍是后续独立义务。

## 5. 稳定连接接口

`V293_OSVersion_api_contract` 可以放进任意包含这个准确函数的 API 表，并连接框架生成的前后置。

证明复用第七步的局部定理：它保留整个前置资源，并额外给出精确返回值。把返回值替换为 29300 后，前置中的抽象执行位置正好就是框架返回后置要求的 `spec_done`。

最后 `V293_OSVersion_api_rule` 使用框架的 `api_rule`，得到这个单函数单元的 `APIRule`。

注意量词的含义：它并没有假定其他 93 个函数已经正确，也没有据此导出整核 `GOOD_OS`。整体链接还需要其他函数、中断、调度、共享不变量和真实初始化。

## 6. 怎样确认门禁真的检查了新环节

两个新的单因素控制保持底层模型、规格和局部证明不变：

| 只改变的因素 | 指定拒绝位置 | 检查什么 |
| --- | --- | --- |
| API 规格返回 29301 | `V293_OSVersion_api_contract` | 组件不能借用与自身规格不一致的局部证明 |
| 从程序 API 表删除唯一入口 | `V293_OSVersion_api_domains` | 有规格但没有函数体不能算连接成功 |

原来的两个局部控制也保留。`False` 前置变异只编译局部证明与独立局部探针，主动排除下游组件的提前拒绝，防止把“下游先报错”错记为“局部接口检查有效”。

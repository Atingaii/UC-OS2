# 第二阶段：从真实 C 源码确定我们到底要证明什么

## 1. 先回顾前因后果

这个仓库不是一个让你直接编译烧录的嵌入式应用。它的最终交付是：用 Coq 证明**指定版本、指定配置、两项授权修复之后**的 uC/OS-II 内核满足规格，并把逐函数证明接到整体 `GOOD_OS` 定理。

第一阶段 `66a5cda` 让 Coq 8.18.0 基础工程和审计可以被可靠检查；没有因此证明真实 C 内核。第二阶段要解决的是一个更具体的问题：

> 这份内核源码经过固定配置选择之后，究竟留下哪些函数？每个函数的准确来源在哪里？哪些操作由 CPU 端口提供？

如果不先回答，就可能证明了一个没被启用的 API，或者漏掉一个已经进入程序的内部辅助函数。历史材料中的函数数不能代替实际清点。

你不需要先会写这个生成器。本阶段按下面顺序理解输入、输出、检查边界即可，不需要先回答练习题。

## 2. 源码、配置和翻译单元分别是什么

### 源码：零件全集

真实源码位于：

```text
csrc/upstream/v2.93.01/checkout/Source/
```

其中 `os_task.c` 是任务管理，`os_mutex.c` 是互斥锁，`os_time.c` 是时间服务。`ucos_ii.h` 定义结构体、常量和函数原型。

这个目录被 Git 忽略，但它不是随便找来的副本：`csrc/UPSTREAM.lock.json` 记录准确提交和每个文件的 SHA-256。文件内容变了，校验就应失败，不能拿改过的文件冒充原上游。

### 配置：选择哪些零件

例如：

```c
#if OS_TMR_EN > 0u
/* timer manager 的函数 */
#endif
```

固定配置令 `OS_TMR_EN=0u`，这一段就不会进入当前程序。关闭 timer manager 不等于关闭 `OSTimeTick` 或 `OSTimeDly`：普通时间服务仍在范围内。

`csrc/config/v29301-profile.json` 记录对上游模板的覆盖值，生成 `checkout/os_cfg.h`。配置头也有预期哈希；不允许为了让证明简单而临时关闭某个功能。

### 翻译单元：本次实际交给 C 前端的内容

上游 `Source/ucos_ii.c` 依次包含各模块 `.c` 文件：

```text
ucos_ii.c
  → ucos_ii.h / os_cfg.h / os_cpu.h
  → os_core.c / os_flag.c / os_mbox.c / ... / os_tmr.c
```

预处理器处理 `#include`、宏和 `#if` 后，才得到当前配置的实际 C 内容。不是“源码目录里的所有函数都活动”，也不是“只数应用直接调用的函数”。

## 3. CPU 头缺失为什么不能随便补空宏

可移植内核不自己实现如何关闭中断、保存 CPU 上下文或切换任务。这些通常由移植到具体处理器的端口实现。当前源码 checkout 没有选择硬件端口。

为了让编译器解析，我们新增 `csrc/analysis-port/` 两个薄头文件。它们**不是可运行 CPU 端口**：

- 指针、`INT32U`、栈元素按 32 位分析，`INT16U` 为 16 位，`INT8U` 为 8 位。
- `OS_STK_GROWTH=1u` 选择栈向低地址增长的源码分支。
- `OS_CRITICAL_METHOD=3u` 选择保存／恢复 CPU 状态的源码分支。
- 使用静态断言确认解析环境中的类型宽度。

临界区不是空宏：

```c
#define OS_ENTER_CRITICAL() V293_EnterCritical(&cpu_sr)
#define OS_EXIT_CRITICAL()  V293_ExitCritical(&cpu_sr)
```

切换同样保留：

```c
#define OS_TASK_SW() OSCtxSw()
```

这些函数只声明，没有实现。以后必须把它们对应到 Coq 框架的中断／切换语义，不能当成已经证明正确、也不能假设没有副作用。此阶段只是让“这里有一个不能丢掉的边界操作”可见。

“应用 hooks 关闭”也不等于“CPU hooks 关闭”。固定模板仍启用 CPU hooks，所以清单不能删掉栈初始化、任务创建／删除 hook 等端口入口。

具体取舍见 [ADR-0001](../adr/0001-源码清单与端口边界.md)。

## 4. 生成器实际上做了什么

入口：`scripts/inventory-v293-source.py`。

```text
校验上游文件集合、哈希、模板与固定配置
  → Clang 预处理 + C AST
  → GCC 独立预处理 + C 语法检查
  → 比较两条预处理路径的函数信息
  → ctags 对照活动定义起止行，并索引未配置源码
  → 检查最终配置宏与显式边界仍保留
  → 输出可审查 JSON
```

**AST** 可以先理解成编译器识别出的程序树。它能区分“只有声明的函数”和“真正有函数体的定义”，不是靠搜某个名字出现了几次。

不使用优化后的可执行文件做清点，因此“当前没被调用”不会自动被删掉。也没有链接或执行内核，更没有产生硬件正确性结论。

两条预处理路径都用 Clang 解析成 AST；因此这里有独立的预处理／GCC 语法检查，但不是两个完全独立的 AST 解析器或形式化翻译证明。Ctags 只是辅助源码索引，不能取代活动集合的编译器依据。

## 5. 本次得到的表格

### 活动 C 定义：92 个

| 分类 | 数量 | 读法 |
| --- | ---: | --- |
| public | 65 | 内核对外 API，例如 `OSTaskDel`、`OSMutexPost` |
| internal | 27 | 内核内部辅助函数，例如 `OS_Sched`、`OS_InitRdyList` |
| 合计 | 92 | 固定配置上游实际进入翻译单元的 C 函数体 |

这里 `internal` 是内核接口分类，不完全等同于 C 的 `static`。27 个 internal 中有 10 个 `static`；其他辅助函数仍可能拥有 external linkage，但不表示应用应调用它们。

### 声明级边界：16 个

| 类别 | 数量 | 例子 |
| --- | ---: | --- |
| CPU hook／栈初始化 | 11 | `OSTaskStkInit`、`OSTaskDelHook` |
| 上下文切换入口 | 3 | `OSCtxSw`、`OSIntCtxSw`、`OSStartHighRdy` |
| 临界区适配入口 | 2 | `V293_EnterCritical`、`V293_ExitCritical` |

它们不冒充第 93～108 个已经存在 C 函数体的函数。清单单独列出，并标记契约未完成。`OSTaskSwHook` 在当前可移植 C 中只有声明，没有调用；端口是否以及怎样调用它是后续边界义务。

### 未进入配置翻译单元：34 个目录索引项

例如 Multi-Pend、timer manager、命名和任务寄存器相关函数。`OSDebugInit` 的源文件没有进入当前主翻译单元，也列在这个集合。

该集合来自 ctags 对锁定源文件的全分支索引，不代表所有配置组合都被编译或验证过。活动集合的准确性和未配置目录索引的完备性是两件事，不能相互替代。

一个容易误删的项是 `OS_StrLen`：虽然名称功能和 timer manager 都不在验证范围，它仍因模板中的 `OS_TMR_CFG_NAME_EN=1u` 条件进入当前编译结果。因此它算在 92 个里；本阶段不通过修改配置或优化删掉它。

## 6. 怎样读一个函数的清单记录

打开 `audit/source-inventory.json`，搜索 `"name": "OSVersion"`。它对应 `Source/os_core.c` 第 1025～1028 行：

```c
INT16U OSVersion(void)
{
    return (OS_VERSION);
}
```

上游 `OS_VERSION` 宏值是 `29300u`。版本注释为 V2.93.01，但这个上游常量确实是 29300；不要“修正”它来伪造一致。

清单字段可以这样读：

| 字段 | 用途 |
| --- | --- |
| `name`、`type` | 确认函数名、参数和返回类型 |
| `source`、`first_line`、`last_line` | 找到锁定源码中的准确范围 |
| `source_file_sha256` | 判断整份原文件是否还是同一份 |
| `source_lines_sha256` | 判断原始函数行片段是否改变 |
| `preprocessed_*_byte` | 定位预处理结果中的半开字节区间 |
| `preprocessed_definition_sha256` | 标识展开后的整个函数定义 |
| `preprocessed_body_sha256` | 标识展开后的函数体 |
| `direct_calls` | 直接调用了哪些函数，包括显式边界 |
| `indirect_call_sites` | 通过函数指针调用的站点数，不是被调用目标列表 |

原始片段可能包含 `#if` 分支；预处理后的片段才对应固定配置。本阶段记录两者，避免把“行号没变”误当成“配置后的行为没变”。哈希只确定身份，不证明行为正确。

另几个可直接定位的上游例子：

| 函数 | 文件与行 | 之后要理解的重点 |
| --- | --- | --- |
| `OSTaskDel` | os_task.c:450–560 | 删除 TCB 的破坏性修改发生在哪里 |
| `OSTaskResume` | os_task.c:846–892 | 清除挂起后，是否仍有等待位 |
| `OSTimeTick` | os_core.c:937–1008 | 超时与等待结果如何更新 |
| `OSMutexPost` | os_mutex.c:642–705 | 所有者与优先级恢复 |

这些行号都属于修复前上游；补丁插入代码后行号会变化，必须生成新身份，而不是沿用旧定位。

## 7. 本机怎么复现

需要 Git、Python 3、Make、Clang、GCC 和支持 JSON 的 **Universal Ctags**；普通 Emacs etags 或其他同名工具不一定支持这些参数。Coq 检查继续要求 8.18.0。

已有正确 checkout 时：

```sh
make source-audit
make config-audit
make source-inventory-check
make test
make audit
```

首次克隆、checkout 还不存在时，先执行：

```sh
make fetch-source
```

已有源码修改时**不要重复获取**，因为现有获取器会重建 checkout。先保留和审查现场；本阶段只在原先不存在 checkout 的条件下获取过一次。

`make source-inventory-check` 不写文件。它重新运行编译器并与已提交的 JSON 逐字比较，内容、工具版本或定位漂移都会失败。出现失败要读差异原因，不是直接覆盖旧证据。

只有确认是预期且经过审查的变更，才使用：

```sh
make source-inventory
git diff -- audit/source-inventory.json
```

第二阶段开始，`make test` 包括真实源码集成测试，因此先要求 checkout 通过上游审计，不会为缺少源码静默跳过。这与第一阶段提交时的 14 个纯基础测试不同；现在一共 26 项。

## 8. 为什么测试里故意制造错误

新增 12 项测试，复制锁定源码到各自临时目录，不修改工作目录的真实 checkout：

- 正确配置生成 92 个函数，重复 `--check` 内容一致。
- 改一个上游函数、增加隐藏源文件、改有效配置，都拒绝。
- 适配头悄悄关闭互斥锁功能，拒绝。
- 临界区或任务切换被改成空操作，拒绝。
- 新增没分类的外部声明，拒绝。
- 偷改清单，检查失败而且不回写。
- 改错 32 位类型，编译器静态断言失败。
- 伪造 GCC 输出使名称不一致，拒绝。
- 删除 ctags 的一个活动函数项，拒绝。

这里故意替换的工具仅存在于测试自己的临时 `PATH`；不会替换本机 Clang／GCC／ctags。所有临时目录由退出清理管理。

在边界门禁加入前，临界区空操作和后加载配置改写两项确实失败。它们揭示了“两个编译器都通过”也可能是共享错误的结果，不是可以省略的防御。

## 9. 现在离最终目标还有什么

本阶段清单顶层明确记录：

```text
source_layer = PINNED_UPSTREAM_BEFORE_AUTHORIZED_REPAIRS
proof_coverage_credit = false
```

意思是“知道原上游有什么”，不是“已经证明修复后的内核”。因此覆盖清单仍为 0 行，六阶段均未提升；还不能计算整核证明完成百分比。

后续顺序不变：

1. 集成嵌套互斥锁恢复、锁定自删除这两类授权修复；给出真实 C 的原始／修复对照回归，不新增未经授权修复。
2. 冻结修复后源码与清单。辅助函数可能增加，所以不能把 92 当最终不可变总数。
3. 建立 TCB／事件／就绪表等共享状态和不变量。
4. 逐函数接通源码定位、CoqImp 表示、规格、Hoare 证明、组件连接与整体连接。
5. 建立初始化和最终 `GOOD_OS`，对同一程序完成 K1–K4 回归、假设审计和 Coq 内核检查。

每个阶段都要形成有代码、有检查结果、有中文教学的完整提交，而不是以新增文档数量冒充证明推进。实际结果与限制见 [第二阶段检查记录](../../audit/STAGE02_SOURCE_INVENTORY.md)。

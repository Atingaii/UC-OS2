## 2. 为什么还要调整目标指针的归属

`OSTCBHighRdy` 保存即将选中的 TCB 指针。切换规则需要从共享部分读到这个真实单元，而且要持有完整权限。

上一课的共享核心拥有任务表和当前指针半权限，却没有拥有这个目标单元。直接使用它会发生两难：

- 把目标单元放在局部 frame：规则的 `SWPRE` 看不到局部 frame，不能据此完成切换。
- 在切换后把目标单元丢掉：本项目的分离逻辑不允许任意丢弃占有的资源。

因此本轮只增加必要的一项：共享核心同时拥有一个**类型正确的目标指针单元**。它可以保存空指针或真实指针；需要执行切换时，再用同状态 snapshot 确定它是最高就绪目标。

`V293DispatchState.v` 证明新核心精确、在 ISR 变化下稳定，并证明实际当前指针写入和抽象 `curtid` 更新后仍满足它，最终得到框架的 `GoodI`。这仍不是完整物理 TCB／ECB 不变量。

## 3. 切换会消耗什么

入口抽象动作是 `sched;;aop`：先调度，再继续后面的抽象程序。新定理直接应用框架 `switch_rule`，出口动作是 `aop`，不是仍然等待调度的 `sched;;aop`。

最容易误解的是出口线程身份：

> 从调用线程的 Hoare 视角看，出口描述的是这个原线程后来恢复执行的状态，不是选中的另一个线程刚开始执行的状态。

因此出口仍以原来的 `tid` 表示当前线程。中间可能执行过其他线程，事件表、时间、任务表和目标指针都可能变化；出口只能重新取得共享不变量，不能保留入口 snapshot 中这些共享值。

局部 frame 则必须满足规则的 `GoodFrm` 和 `LINV` 条件，才可以在恢复后取回。这个条件不是整段切换正确性的 oracle，而是局部资源归属的显式要求。

## 4. 怎样排除“入口根本不存在”

`V293OSSchedSwitchWitness.v` 实际构造同一个状态，里面同时有：

- 真实当前指针完整单元分出的两个半权限；
- 共享目标指针的完整单元；
- 唯一的四个抽象槽位；
- 所需的中断标志、空动态栈；
- 真实待执行的抽象动作 `sched;;aop`。

见证覆盖两种情况：当前任务就是最高就绪目标；当前任务已经时间等待，最高就绪目标是另一个任务。事件表、时间和后续 `aop` 均可任意选择。

相同目标的见证只说明资源前置可以存在，不表示 C 在相同优先级时也执行切换。

这是**可满足性**，不是“真实内核初始化可以到达这个状态”，也不是合法自删除后的切换见证。

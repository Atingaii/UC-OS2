# 第五阶段：先检查证明的地基，再使用框架证明内核

第四阶段已固定 C 源码，接下来准备真正使用 CoqImp 框架。此时发现一个必须先处理的问题：框架现有的一条内存公理与它允许的内存类型相冲突。

本阶段完成了可重现审计与正确的有界分配接口，**没有完成整个框架修复，也没有新增真实 C 函数证明覆盖**。

## 1. 公理、定理、False 分别是什么

- 定义：说明某个对象是什么。
- 定理：在给定定义与前提下，由证明推出的结论。
- 公理：没有在本工程中证明、直接允许使用的前提。
- `False`：表示不可能成立的命题。

Coq 会检查“在所给前提下，证明步骤是否合法”。它不会自动保证用户写下的所有公理互相兼容。若一个前提组能推出 `False`，就能进一步推出任意命题；这样的前提组不适合支撑内核正确性声明。

本阶段的 `False` 仅存在于隔离诊断模块，用于证实问题；它不加入活动 Coq 工程，也不被内核证明导入。

## 2. 先读实际类型，不猜设计意图

`framework/model/memory.v` 中的内存类型最终是：

```coq
addr -> option (bool * memval)
```

可以把它理解成一张查找表：输入地址，得到没有分配的 `None`，或带权限和值的 `Some ...`。

地址由两部分组成：

```text
(block, offset)
```

`block` 是抽象块标识，使用正整数；`offset` 是块内偏移，使用整数。这些是源码级模型，不是硬件地址位宽证明。

关键点：这个类型允许**任意函数**，没有“只能占用有限个块”的限制。

## 3. 什么叫内存已满

框架定义：

```coq
Definition FullMemory m := forall b, exists i, indom m (b, i).
```

读法：对每个块标识 `b`，总能找到一个偏移 `i`，其地址已占用。因此没有一个完全空闲的新块可选。

随后原框架声明：

```coq
Axiom MemoryNotFull : forall m, ~ FullMemory m.
```

它不是说“从空内存经历有限次分配得到的内存未满”，而是说“该类型中的任意内存都未满”。范围扩大到了任意函数。

注释里写“无限内存，因此分配总能成功”，并不能自动约束函数空间。无限地址空间也允许数学上的全满函数；必须限制允许出现的状态，或使用更合适的内存类型。

## 4. 反例只需要一个常量函数

构造：

```coq
Definition occupied_everywhere : mem :=
  fun _ => Some (true, Undef).
```

不管问哪个地址，都回答已占用。

对于任意块 `b`，选择偏移 0，就能证明它已占用，所以这个内存满足 `FullMemory`。原公理又说它不满足，两者合起来得到矛盾。

诊断中实际编译的核心结论是：

```coq
Theorem memory_inconsistent : False.
Proof.
  exact (@MemoryNotFull occupied_everywhere occupied_everywhere_full).
Qed.
```

这里的 `@` 是显式传入隐式参数，不是绕过检查。第一版探针忘记了它，出现参数类型错误；那次没有证明成功。修正参数应用后，Coq 才真正接受矛盾证明。

## 5. 如何确认问题确实来自这条公理

检查器做了一个单因素消融：

| 版本 | 原内存定义 | 满内存见证 | 同一矛盾证明 |
| --- | --- | --- | --- |
| 原框架副本 | 不改 | 编译通过 | 编译通过，假设列表含 MemoryNotFull |
| 只移除该公理的副本 | 其他内容不改 | 仍编译通过 | 在 MemoryNotFull 引用处明确失败 |

两个副本使用不同临时模块名以分别编译，但实现内容仅移除这一条声明。

不能把“同一矛盾证明无法重放”夸大成“剩余所有公理已经证明一致”。这个实验只定位了具体矛盾路径。也没有把编译崩溃或其他错误当作成功的消融。

## 6. 正确的最小前提是什么

为了选一个新块，真正需要的是：当前已占用的块标识都有一个上界。

新增 `framework/proof/memory_bound.v`：

```coq
Definition blocks_below (m : mem) (upper : positive) : Prop :=
  forall b i v,
    get m (b, i) = Some v -> (b < upper)%positive.
```

读法：只要某个地址已占用，它所属的块标识就严格小于 `upper`。

于是 `upper` 这个块本身必然空闲：否则就会推出 `upper < upper`，这是不可能的。

稳定接口为：

```coq
Theorem blocks_below_fresh : forall m upper,
  blocks_below m upper -> fresh m upper.
```

以及存在形式：有一个满足边界条件的上界，就有一个新块。它们是带正确前提的定理，不是替换成另一条全局公理。

## 7. 上界不是固定容量，也不是最大任务数

这个 `upper` 可以随分配增长，不表示“本工程最多分配 N 个块”。它与任务数量、优先级上限、物理 RAM 容量不是同一个概念。

空内存可以选择任意正上界。若要写入块 `b`，可将新上界取为：

```text
max(old_upper, successor(b))
```

对每个有限执行前缀，边界仍是一个具体正整数；因此可以继续选择新的抽象块标识，不需要“所有任意函数都未满”的错误假设。

这里仅约束已占用的**块标识**，尚不要求每个块的偏移域都具有有限支持；这是新鲜块论证所需的最小约束，而不是完整真实内存模型。

## 8. 新模块实际证明了什么

11 个接口均由 Coq 8.18.0 编译检查：

| 接口组 | 意义 |
| --- | --- |
| 边界单调、空内存 | 边界可扩大，前提并非不可满足 |
| 边界推出 fresh、存在 fresh | 用正确前提得到可分配的新块 |
| set／set_grow | 修改界内地址保持边界，写入新块可扩大边界 |
| del | 删除地址不会凭空占用新块 |
| allocb／allocb_grow | 原有块分配操作保持或扩大边界 |
| storebytes | 成功写入已有字节不新增越界块 |
| freeb | 成功释放不会新增越界块 |

注意 set 更新不等于内核任务创建；这些是通用内存操作引理，不能据此为 `OSTaskCreate` 计分。

还构造了同一个全满函数，直接证明它不满足任何 `blocks_below`，且此结论不依赖 `MemoryNotFull`。这验证边界前提不能无条件删掉。

## 9. 为什么还不能说地基已经修好

旧框架仍保留原公理，`memory_prop.v` 和 `rulesoundlib.v` 中的两份无条件 `fresh_exist` 仍直接调用它。新增正确引理，不会自动改变旧证明链。

下一步必须把边界传入真实的共享状态与操作语义，处理全局内存与分离逻辑碎片、分配、释放、客户端执行、调用和中断边界，并迁移相应 soundness 证明，最后移除原公理。

初始化也必须确实存在，不能设成 `False`，否则任何“从初始化出发都正确”的定理都可能只是没有合法起点。

因此当前专门信任门禁明确失败。它不能被“新增文件能构建”或“已有小模型无公理”替代。

## 10. Print Assumptions 和 coqchk 各有什么用

- `Print Assumptions`：列出某个根定理实际依赖的全局假设。
- `coqchk`：重新检查编译后的 Coq 对象及其依赖是否合法。

两者都需要，但都不会自动证明接受的公理本身一致。

新增 11 个根定理的实际列表不含 `MemoryNotFull`；仍列出依赖函数外延性与经典排中律。这里如实保留这些依赖，不声称“完全没有公理”。

原有三个小模型根定理仍可独立检查为无全局假设，但这并不消除整套框架的上述问题。

## 11. 运行方法与退出码

正向检查：

```sh
make check-memory-bound COQBIN=/data/home/lucentzhou/.opam/default/bin/
```

它在独占临时目录重编新模块、检查 11 个根假设与全满函数的边界反例，并对新对象执行 coqchk。通过返回 0，但不宣称整框架已安全。

专门信任门禁：

```sh
make check-framework-trust COQBIN=/data/home/lucentzhou/.opam/default/bin/
```

当前会打印：

```text
FRAMEWORK TRUST: BLOCKED_GLOBAL_MEMORY_AXIOM_DERIVES_FALSE
```

这是已确认的失败，不应改成通过。Python 检查器在复现不安全时返回 1，工具、版本、证明或指定对照异常返回 2；GNU Make 通常将非零子命令转成自身退出码 2，因此要结合具体输出判断。

可把一次新的完整诊断写入一个不存在的 JSON 文件：

```sh
COQBIN=/data/home/lucentzhou/.opam/default/bin/ \
  python3 scripts/check-memory-trust.py --report /tmp/new-memory-trust-report.json
```

已有报告不会覆盖。报告仍会如实写入“不安全”状态并返回 1，不通过拒绝保存失败来隐藏结果。

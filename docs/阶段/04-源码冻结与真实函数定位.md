# 第四阶段：固定证明对象，给每个真实函数建立位置证据

这一阶段承接第三阶段的实际 C 修复。先记住一句话：**证明之前，必须固定究竟证明哪一份程序；找到了函数，不等于已经证明函数。**

你不需要回答练习题。下面直接给出背景、操作、结果和阅读方法。

## 1. 为什么不能直接开始写一堆 Coq 定理

假设我们证明了“删除任务之前检查调度锁”，但 Coq 中用的是改过的函数，最终交付却用了未改的 `os_task.c`。两者不是同一份程序，证明就不能支持这份交付。

又如，同一个 `OSMutexPend`，不同配置会保留或删除不同的 `#if` 分支。文件名与函数名相同，不保证执行的代码相同。

因此需要固定三件事：

1. 上游版本和全部源文件。
2. 两份补丁应用后得到的准确内容。
3. 配置及分析端口选择的类型、宏和 CPU 边界。

这一阶段的“冻结”是给这些内容建立可重放的身份记录。它不是宣称代码已无 bug，也不是禁止以后修复；若以后确有新证据需要改变对象，应明确创建新修订并重新建立对应证据，不能悄悄改旧清单。

## 2. 三个阶段的清单为什么都要保留

| 材料 | 它回答什么 | 它不能回答什么 |
| --- | --- | --- |
| 第二阶段 `audit/source-inventory.json` | 原上游在固定配置下有哪些函数 | 修复后函数有哪些、是否正确 |
| 第三阶段 `audit/c-regressions.json` | 哪份 C 在具体场景下得到什么结果 | 任意状态、任意交错都正确吗 |
| 第四阶段 `audit/repaired-source-inventory.json` | 当前修复后程序的全部函数在哪里 | 是否已完成翻译和证明 |
| `csrc/repairs/FROZEN_SOURCE.json` | 这些源码、配置、补丁与清单如何绑定 | 最终 `GOOD_OS` 是否成立 |
| `audit/coverage.json` | 每个函数目前真正完成到哪一步 | 不能仅凭文件数推断完成率 |

没有把第二阶段的 92 改成 94；它作为历史上游证据仍保持原样。第三阶段的执行报告、补丁与运行器也没有为了新增清单而改写。

## 3. SHA-256：把内容变成可比较的身份

SHA-256 把一段字节内容计算成一个固定长度的值。文件中一个字符变化，通常就会得到不同值。

这里的哈希用于**发现内容漂移**，不是数学正确性的证明，也不是文件作者身份认证。

我们分别记录：

- 全部 15 个源码／头文件的哈希；
- 生效的 `os_cfg.h` 和两个分析端口头的哈希；
- 补丁、生成工具、配置描述和既有 C 执行证据的哈希；
- 每个函数原源码行范围、预处理后定义和函数体的哈希。

程序身份由源码、配置、分析端口内容及目标版本的规范化 JSON 计算，不把测试输出当作内核程序本身。工具、清单和 C 报告另外在冻结记录中绑定。

当前身份为：

```text
74390755cddc42a391055da46b744bbf32e77ba3dc025c2ae55b9441ba6170da
```

## 4. 如何得到修复后的程序

入口是 `scripts/freeze-v293-source.py`，常用命令是：

```sh
make source-freeze-check
```

它执行以下步骤：

1. 重新核验锁定上游，重新生成内存中的上游清单，与第二阶段已提交清单比较；不调用配置生成器，不覆盖本地配置漂移。
2. 验证第三阶段 C 报告的全部输入哈希仍与当前文件匹配。
3. 在本任务独占的临时根中复制锁定源码与配置，重放两份补丁。
4. 逐文件比较输出与第三阶段 `both` 组合实际测试的源码哈希。
5. 对修复后主翻译单元进行 Clang 预处理与 AST 解析；GCC 独立预处理、语法检查，并比较实际定义。
6. 用 Ctags 再交叉检查每个函数的起止行。
7. 核对变化仅为原有六个函数内容及两个静态 helper；已有函数接口、生效配置与 16 个声明级边界不变。
8. 将重新得到的冻结记录、修复后清单与已提交文件逐字比较；不一致就失败，不自动更新证据。
9. 删除独占临时根，保留原始 checkout、已提交证据和用户资料。

注意：这条命令核对 C 报告的身份关联，但**不会重新执行 C 场景**；实际执行另用 `make check-c-evidence`。

首次建立记录使用过 `python3 scripts/freeze-v293-source.py --record`。它只允许创建原先不存在的记录，已有任意一份时拒绝覆盖。日常重跑不要使用它。后续源码修订必须审查差异与新证据，不把此选项当“修好所有漂移”的按钮。

## 5. 为什么清单路径在本地找不到

修复后清单中的路径形如：

```text
csrc/repaired/v2.93.01/checkout/Source/os_task.c
```

这是**独占临时根内的稳定逻辑路径**，不是声称项目根常驻一份这样的文件。每次重跑都会重新构造，结束自动删除。这样既保留稳定的预处理路径，也避免维护两份容易不同步的完整源码。

原始上游实际保留在：

```text
csrc/upstream/v2.93.01/checkout/
```

需要阅读精确改动时，结合上游与 `csrc/repairs/` 的两份补丁；需要验证清单时，让上述命令自动构造，不要手动修改上游再假装它仍是原始版本。

## 6. 清点结果：94，不是 92 或历史记录中的其他数字

| 类型 | 数量 | 含义 |
| --- | ---: | --- |
| public 定义 | 65 | 清点规则中的公共功能入口，不等于 65 个已证明 API |
| internal 定义 | 29 | 内部函数及静态 helper |
| 配置后 C 定义合计 | 94 | 上面两项之和，是本阶段位置清单的全集 |
| 声明级边界 | 16 | 临界区、上下文切换和 CPU hooks；契约仍开放 |
| 未进入当前配置的目录索引定义 | 34 | 不计入本次活动函数全集，也不表示其他配置已验证 |

原上游 92 个定义，加上两个静态 helper，得到 94。没有删除原函数，也没有新增公共 API。

原有内容发生改变的函数是：

```text
OSMutexAccept  OSMutexDel  OSMutexPend  OSMutexPost
OSMutex_RdyAtPrio         OSTaskDel
```

新增静态函数是：

```text
OSMutex_BasePrio          OSMutex_EffectivePrio
```

这不是用补丁行数猜出来的，而是对实际修复后翻译单元清点并交叉检查的结果。

## 7. 用一个最简单的真实函数认识“位置”

先看 `OSVersion`。修复后清单给出：

```text
source:     .../Source/os_core.c
first_line: 1025
last_line:  1028
```

其 C 内容为：

```c
INT16U  OSVersion (void)
{
    return (OS_VERSION);
}
```

`OS_VERSION` 是宏。原始源码写宏名，预处理后的函数体使用实际展开值。清单同时记录两层证据，因此以后不能只拿同名函数或另一配置的内容代替。

再看 `OSTaskDel`：修复后位置是 `os_task.c` 的 450–566 行；位置记录绑定的是包含保护分支的修复后文件哈希，而不是仅凭函数名绑定。

## 8. 六阶段到底分别意味着什么

| 阶段 | 当前含义 | 本阶段数量 |
| --- | --- | ---: |
| `located` | 准确修复后函数已定位，文件、行号和函数体哈希可重放 | 94 |
| `modeled` | 已有与该函数对应的 CoqImp 程序表示及对应证据 | 0 |
| `specified` | 该函数已有适当的前置／后置条件和共享状态约束 | 0 |
| `local_hoare` | 该函数的局部正确性证明闭合 | 0 |
| `component_linked` | 局部证明已连接到同一组件与共享不变量 | 0 |
| `full_target_linked` | 已连接到最终完整程序和顶层证明 | 0 |

因此 `94 / 94 located` 不是“内核证明已完成 100%”，也不能把六个阶段机械平均成完成百分比。现有三个小模型仍不自动算作真实函数的 `modeled`。

## 9. 审计为什么比原来严格

运行：

```sh
make audit
```

位置审计会核对版本、程序身份、冻结输入和清单哈希；要求覆盖恰好包含全部 94 个函数，逐行匹配函数位置与函数体哈希；阶段值必须是真正的 JSON 布尔值，不能把字符串 `"true"` 当成证明结果。

它还会拒绝：缺函数、重复函数、错发行版、旧源码身份、错误函数体、修改阶段列表、跳过前置阶段等。

更后阶段尚没有独立的证据检查器。因此此时手动把 `modeled` 改成 `true`，即使写上文件名或定理名，也会被拒绝。以后真正实现翻译和证明时，必须同时实现对应检查器，不能先放开布尔值再补证据。

两条命令的边界不同：

- `make audit`：检查已记录材料的身份与位置一致性，不重新运行 C 编译器。
- `make source-freeze-check`：从实际锁定源码重放、编译清点，再比较记录。

“静态材料一致”与“实际重放成功”都需要，但都不是 Coq 正确性证明。

## 10. 这次如何检查检查器没有形同虚设

第四阶段新增 22 项测试，包括真实重放、实际差异检查、完整位置审计三项正向检查及 19 项单因素反向检查。

反向检查分别改变一个输入或声明，其余材料保持不变，例如：

- 在补丁末尾改一处字节：必须触发 C 执行输入身份漂移。
- 把 C 报告记载的修复后文件哈希改错：必须触发“重放源码与测试源码不同”。
- 在配置清单中删除一个函数、把 helper 改成外部函数、抹掉一个 CPU 边界：对应范围检查必须拒绝。
- 将某行函数体哈希改错、少放一个函数、重复一行：覆盖审计必须拒绝。
- 仅把 `modeled` 设为真：不能借已有小模型冒领真实源码翻译覆盖。

每项要求命中指定失败原因，不把任意异常算成检查有效。新增测试可单独运行：

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_source_freeze.py -v
```

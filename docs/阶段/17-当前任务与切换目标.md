# 第十七课：把“数字不同”接到“任务不同”

上一课已经证明：最高就绪优先级不等于当前优先级时，计数器加一。本课继续回答：这为什么意味着要切换到另一个任务？

## 1. 先补齐数字的含义

`OSPrioCur` 不应只是任意字节。我们需要知道：当前指针对应的任务确实在任务表中，而且优先级就是这个数字。新关系 `V293_current_task` 表达的正是这件事。

不能额外要求当前任务就绪。任务调用等待 API 后，可能先变为等待态，再调用调度器。此时它仍是 CPU 上正在执行的当前任务，但已经不在就绪集合。

## 2. 为什么可以比较任务指针

同一优先级表的每个槽存放一个任务指针：

1. 位图选出最高就绪优先级。
2. 任务表与位图关系保证对应任务存在且就绪。
3. 优先级表关系保证该槽确实指向该任务。
4. 当前任务也由同一张表定位。

因此“选中优先级 = 当前优先级”等价于“选中指针 = 当前指针”。缺少任务／表关系时，单独比较两个数字得不出这条结论。

## 3. 本轮见证表（已填写）

| 场景 | 当前任务 | 当前状态 | 唯一就绪任务 | 是否不同 |
| --- | --- | --- | --- | --- |
| 相同目标 | 块 7，优先级 12 | 就绪 | 块 7，优先级 12 | 否 |
| 不同目标 | 块 7，优先级 4 | 时间等待 | 块 15，优先级 12 | 是 |

第二行说明：当前任务虽然优先级数字更小，但它已等待，不能参与“最高就绪”的选择。证明必须接受这个场景。

## 4. “知道它正确”还不够，还要交出资源

真正的任务切换规则不仅需要数学结论，还需要状态中的资源：

- `AHprio`：同一抽象任务表中的最高就绪目标。
- `GV target ... |-> ...`：保存该目标的全局指针，并且有完整写权限。
- 当前任务仍存在，且目标与当前任务不同。

新接口从已有前缀的实际后置提取这些资源，不是假设一份新的切换结果。用逻辑合取保留两种资源视图，不用分离合取复制同一份所有权。

## 5. 为什么还没有真的证明切换

现有当前指针只给半权限读取，切换需要完整写权限；中断标志、临界区栈和共享不变量也还没有连接。它们不能通过普通 frame 随便带过内部调用。

还有一个边界：合法自删除后，当前任务可能已不在任务表中，本轮“仍存活当前任务”的接口不覆盖它；框架有另一个 `switchdead_rule`，后续必须单独连接，不能禁止合法自删除来凑证明。

所以下一步是补调用契约和临界区资源，再使用框架真正的 `switch_rule`。最终目标仍是同一具体内核的 `GOOD_OS`，不是这些中间引理。

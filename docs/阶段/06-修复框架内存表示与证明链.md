# 第六阶段：修复框架内存表示与证明链

本章接续第五阶段，不要求你回答练习题。本阶段框架内存修复已通过完整验收，具体命令、证据和剩余假设见[阶段报告](../../audit/STAGE06_FRAMEWORK_REPAIR.md)。具体内核整体验证仍未完成。

## 1. 这次究竟修什么

第五阶段发现的是逻辑基础错误，不是 C 编译错误：

```text
原 mem 接受任意地址函数
        ↓
可以构造每个地址都有值的函数
        ↓
原 MemoryNotFull 又断言所有 mem 都不满
        ↓
两个结论合起来得到 False
```

Coq 检查证明是否遵守给定定义和假设，并不会替你保证随手声明的公理正确。如果假设本身矛盾，成功编译也不是可信的验证成果。

这次的直接目标是去掉这条矛盾路径，恢复真正使用分配的旧证明链，并检查整个活动工程。它与最终完成 94 个 C 函数和整核 `GOOD_OS` 的目标不是一回事。

## 2. 为什么不是只删除一行公理

原来的命题 `forall m, exists b, fresh m b` 对任意地址函数为假。删去公理后，原命题不会自动变真。

有两条正确路线：

- 保留任意函数类型，把“内存有块标识上界”作为额外前提，沿所有状态和规则传递。
- 让合法内存值自身就携带这个性质，所有构造内存的地方必须证明它。

第五阶段先建立第一种路线所需的显式接口。本阶段通过隔离实验选择第二种表示策略，原因和代价记录在 [ADR-0003](../adr/0003-以内存类型封装块上界.md)。这是一次显式决策变更，不把旧 ADR 改写成一开始就选了新方案。

## 3. 从函数变为“函数加证明”

核心结构可读成：

```coq
Record Map : Type := mkMap {
  contents : addr -> option (bool * memval);
  bounded : raw_bounded contents
}.
```

- `contents` 仍是原来的数据函数：输入地址，返回没有值或者带权限的值。
- `bounded` 是一个命题证明：存在正整数 `upper`，所有已占用地址的块标识都小于它。
- 只有数据而没有证明，不能构造合法的 `mem`。

`bounded` 不是另一个公理，也不是恒真的 `True`。它是构造器真正要求你交出的证明。

地址中的块标识和块内偏移不同。例如 `(3, 16)` 表示第 3 号块内偏移 16。这里限制的是块标识的上界，不是最大偏移、物理内存大小或系统最多能执行多少次分配。

## 4. 为什么现在一定能找出新块

设一个合法内存的所有已占用块标识都小于 `upper`。

那么 `upper` 自己不可能已经被占用，否则就得到 `upper < upper`。因此选择它作为新块即可。

这正是稳定接口 `memory_has_fresh_block` 的证明。原来两处 `fresh_exist` 现在都直接复用该接口，不再调用 `MemoryNotFull`。

注意：这个结论针对新的合法内存类型，不是偷偷重新断言任意地址函数都有上界。

## 5. 更新、合并、释放为什么不会丢掉性质

| 操作 | 数据处理 | 上界如何证明 |
| --- | --- | --- |
| 空内存 | 所有地址返回 `None` | 选 1 即可 |
| 设置地址 | 原来的地址相等判断和更新 | 原上界与新块号后继取最大值 |
| 删除地址 | 指定地址变为 `None` | 沿用原上界 |
| 合并内存 | 保留原半权限合并算法 | 两个上界取最大值 |
| 内存相减 | 保留原权限相减算法 | 沿用被减内存的上界 |
| 分配多个字节 | 原来的递归设置 | 每个结果仍是合法内存 |
| 写入／释放 | 原来的权限检查和递归 | 成功结果仍是合法内存 |

上界可以增长。我们没有用“空间永远不能增长”换取证明通过，也没有把初始化定义成假命题。

## 6. 怎么确认没有顺便改坏算法

仅证明新的类型有上界不够；可能同时把写入改成空操作。

因此 `memory_representation.v` 另外保留原始函数算法作为 raw 对照。权限合并和相减的数据算法也单独写出，不是两边都调用被测实现。

`erase` 表示只取出合法内存的数据函数，忽略证明字段。对应定理包括：

- 空内存、读取、设置、删除、单点内存、合并、相减的擦除等式。
- `join` 与 raw 权限兼容、数据合并之间的双向等价。
- 对任意长度分配、任意字节列表写入，以及任意长度释放，结果擦除后与原算法一致。
- 合法内存类型有实际值；一次分配后还可以继续找到新块。
- 具体地址上的成功分配、写入、释放，以及只读内存拒绝写入。

这些结论证明的是此次表示迁移，不是 C 到框架的完整语义对应。

迁移有一个明确的语义限制：只允许块标识有界的内存，不再覆盖任意旧 raw 函数。擦除定理证明的是这个子域内原语算法一致，不是两个状态全集完全等价。具体 V2.93.01 的初始化可满足性与真实程序连接，仍需在后续工作中给出。

## 7. 为什么还需要反向实验

检查器不只看“全部成功”：

| 对照 | 必须观察到的结果 |
| --- | --- |
| 用全满 raw 函数和证明 `I : True` 调用实际内存构造器 | 在边界证明类型检查处拒绝 |
| 构造器隔离夹具保持边界要求 | 同一个候选值和 `I` 被拒绝 |
| 夹具仅将边界谓词中和为 `True` | 同一个候选值和 `I` 被接受 |
| raw 设置算法单独将目标地址置空 | 在 `erase_set` 证明处拒绝 |
| raw 合并算法单独改错权限 | 在 `erase_merge` 证明处拒绝 |
| raw 释放算法单独改为允许另一种权限 | 在 `erase_freeb` 证明处拒绝 |

每个算法故障都必须走到自己的指定定理，不把较早的编译错误算作检验了后面的机制。构造器夹具的对照只检验边界门槛，不声称中和后的整个框架也经过 soundness 验证。

第五阶段完整原始失败报告仍保留。新的门禁还在隔离模块重放其最小逻辑路径，并只移除那条错误公理，确认同一矛盾证明失去依据。该最小重放不冒充完整旧框架的新构建。

## 8. 怎么运行完整检查

在仓库根目录执行：

```sh
export COQBIN=/data/home/lucentzhou/.opam/default/bin/
make build COQBIN="$COQBIN" JOBS=2
make check-memory-bound COQBIN="$COQBIN"
make check-framework-trust COQBIN="$COQBIN"
make check-build COQBIN="$COQBIN" JOBS=2
make test
make audit
make source-freeze-check
make check-c-evidence
make check-models COQBIN="$COQBIN"
```

`check-framework-trust` 会先构建当前源码，再打印分配调用链、`RuleSound`、`Soundness` 等真实根的假设，最后用 `coqchk` 检查依赖闭包。它不是只检查新增辅助文件。

`check-build` 另开一次性目录，只复制活动源码和构建入口，不复制旧 `.vo` 或参考资料，然后从头编译。只看本机增量构建不足以排除旧产物影响。

## 9. 怎样理解剩余假设

本次不宣称“没有任何公理”或“Coq 已证明自己的整体一致性”。依赖审计必须列出真实剩余假设。此次 13 个框架根的实际并集是经典排中律、标准依赖函数外延性和标准 `eq_rect_eq` 相等运输原则；11 个边界根和 20 个表示根的并集只有前两项。这些原则与已经存在反例的全局内存公理不能混为一谈，也不表示活动源码里其它抽象常量都已被消除。

审计还发现，公共库和通用映射模块各自又声明了一次函数外延性。这些重复声明现改为由标准库函数外延性证明的引理；不通过把新遇到的名字加入白名单来绕过门禁。

假设解析也不能只认 ASCII 名称。隔离 Coq 模块实际打印 `α : False` 时，旧解析器曾漏检；新增反向测试和解析修复后必须拒绝这个未知假设。这个故意含公理的测试模块不属于活动证明链。

完整实际列表、验收结果与局限见[信任基础](../../TRUSTED_BASE.md)和[本阶段报告](../../audit/STAGE06_FRAMEWORK_REPAIR.md)。检查器遇到未审查的假设会失败，不默默接受新名字。

框架修复并不增加 C 函数证明覆盖。固定配置仍有 94 个已定位函数，模型对应、规格、函数证明和整体连接要按顺序推进。

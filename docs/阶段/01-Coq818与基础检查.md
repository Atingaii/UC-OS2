# 第一阶段：让 Coq 8.18 基础工程可以被检查

## 1. 这一阶段在做什么

最终目标是证明固定配置的 uC/OS-II 内核源码正确。现在还不能直接开始逐函数证明：如果证明文件本身编译不了、检查工具又把参考论文当成程序依赖，后面的“验证成功”就没有可信起点。

因此，本阶段解决三个基础问题：

1. 把实际使用的 Coq 固定到 8.18.0。
2. 修复已有小模型证明的导入与参数引入问题，不改变模型、规格或内核行为。
3. 让项目审计检查活动构建输入，同时保留历史资料，并用反向测试证明它仍会拒绝不允许的依赖和证明洞。

这是一项完整的基础构建检查点，不是一个内核 API 已经证明完成的检查点。

## 2. 先认识四个工具

| 工具 | 在这里的作用 | 不负责什么 |
| --- | --- | --- |
| opam | 安装和选择 OCaml／Coq 软件包 | 不会替你证明内核 |
| Coq / `coqc` | 将 `.v` 源码编译成经过检查的 `.vo` | 编译通过不自动说明模型就是 C 源码 |
| GNU Make / `make` | 根据依赖关系调用编译器和检查脚本 | 不决定定理是不是项目真正需要的定理 |
| Git | 保存源文件、说明和每阶段变更 | 提交成功不等于验证成功 |

`.v` 是我们维护的源文件；`.vo` 是编译器生成的文件。只把前者提交。`.glob`、`.aux` 和自动生成的 `Makefile.coq` 也不作为源码提交。

Coq 中，`Definition` 定义对象，`Theorem` 陈述命题，`Proof ... Qed` 提交一个由内核检查的证明。`Admitted` 则会把未证明的命题当作假设，因此活动内核专用树禁止使用。

## 3. 为什么降级环境

交接要求的验收版本是 **Coq 8.18.0**，本机原来是 **8.20.1**。不能在另一个版本上运行几项检查，就把它写成指定环境的验收。

本次在已有 `default` opam switch 中降级四个包：

| 包 | 原版本 | 目标版本 |
| --- | --- | --- |
| `coq` | 8.20.1 | 8.18.0 |
| `coq-core` | 8.20.1 | 8.18.0 |
| `coq-stdlib` | 8.20.1 | 8.18.0 |
| `coqide-server` | 8.20.1 | 8.18.0 |

OCaml 编译器仍为 4.14.2，不为降级 Coq 另外重建一份 OCaml。变更前已导出本机软件包状态到忽略目录 `audit/logs/opam-before-8.18.export`，它用于本机恢复，不应成为证明依赖。

环境准备命令：

```sh
opam install coq.8.18.0 --yes --jobs=2
eval "$(opam env --switch=default)"
coqc --version
```

在自己的机器上，`default` 可能不是你的 switch 名称，应先用 `opam switch list` 确认。安装结果必须以最后的 `coqc --version` 为准，而不是以终端里曾出现过“安装中”为准。

## 4. 导入问题：定义存在，不等于当前可以直接用短名

阅读顺序：

1. `certiucos/v293/model/V293PendModel.v`
2. `certiucos/v293/model/V293TaskDeleteModel.v`
3. `certiucos/v293/spec/V293SafetySpec.v`
4. `certiucos/v293/proofs/V293SafetyProof.v`

原来的关系可以简化为：

```text
PendModel、TaskDeleteModel → SafetySpec → SafetyProof
```

`SafetySpec` 通过 `Require Import` 使用模型中的定义。`SafetyProof` 再导入 `SafetySpec`，不等于自动在当前命名空间中导入所有模型短名。原文件调用 `V293_timeout_suspend_resume_ready` 时因此报“找不到变量”。

这里的修复是让证明文件**显式导入它直接使用的模型模块**，而不是修改定理、不证明就结束、或把规格弱化成容易成立的命题。

修复前后保持不变的内容：

- 三个模型的定义。
- 三个 safety 规格的命题。
- 超时与自删除证明的证明步骤；互斥锁证明只把裸 `intros` 改为显式引入参数。
- C 源码、配置与两项授权修复的范围。

先只补导入，原来的名称错误消失，但编译继续暴露出互斥锁定理的 `Cannot find a relation to rewrite`。这说明第一个修复有效，但不意味着后续证明也已经通过。

第二次单因素修改把 `intros; reflexivity` 改为 `intros base remaining; reflexivity`：显式指定两个参数，迫使命题别名展开为全称量化。随后六个文件才全部编译通过。不能将第二处失败隐藏在第一次成功后面，也不需要为此改弱规格。

## 5. 审计为什么原来失败

仓库保留了前人关于旧版本的论文和记录。原审计在 Markdown 中搜到旧版本文字，就直接判失败。因此：

```text
参考资料谈论旧版本 ≠ 当前证明导入旧内核模型
```

但反过来，不能简单忽略所有文件或删除这些资料来得到绿色结果。

新检查的边界是：

- 活动源码：`framework/`、`tactics/`、`certiucos/`、`csrc/`。
- 构建脚本：`scripts/`、根目录代码文件与明确的构建入口。
- 特别纳入以前漏掉的 `Makefile` 和 `_CoqProject`，额外目录中的非归档 Coq 文件也检查。
- `references/`、两份历史提示词和测试中的故意非法输入不是活动构建输入。
- 获取的 `checkout/` 仍由独立源码哈希审计负责，不拿普通文本扫描代替源码身份校验。

活动输入中的旧目标标识会被拒绝；把归档路径字面量写入构建输入也会被拒绝，包括 `-R references CertiOS` 这种不带斜线的加载路径。检查还会拒绝缺少活动 Coq 文件或缺少上游锁文件的空工程。

**边界限制：**这是静态文本门禁，不是完整依赖分析器。通过变量拼接、运行时下载或间接命令构造的依赖，不能仅凭此脚本排除；因此还必须结合隔离构建、源码锁校验、根定理假设与 `coqchk`。活动代码注释中出现受禁路径也可能触发保守拒绝。

## 6. 证明洞扫描不能只截断每行第一个注释

旧代码把一行第一个 `(*` 后的内容全忽略，会漏掉：

```coq
(* 一段已经结束的注释 *) Admitted.
```

它也会把跨行注释中的词误判为真实命令。

新代码逐字符处理嵌套注释与字符串，保留行号，只在剩余代码中检查证明洞及新假设命令；同时覆盖 `Axioms`、`Parameters`、`Conjectures` 这类复数写法。

这仍不是 Coq 解析器，也不是最终公理审计。编译与 `Print Assumptions` 是独立检查，不能删掉。

## 7. 怎么复现检查

在仓库根目录运行：

```sh
make test
make audit
make check-models
make check-build JOBS=2
make build JOBS=2
```

如果你的 Coq 不在默认 `PATH`：

```sh
make check-models COQBIN=/你的/opam/switch/bin/
make build COQBIN=/你的/opam/switch/bin/ JOBS=2
```

`COQBIN` 是以 `/` 结尾的程序目录前缀，不是 `coqc` 文件名。`make build` 会先检查版本，不接受 8.20.1 或其他补丁版本代替指定的 8.18.0。

### `make test`

运行 `tests/` 下的两个测试文件，共 14 个测试；其中 12 个审计测试位于 `tests/test_project_audit.py`，另外两个检查版本选择。测试在一次性目录构造最小项目，通过真实审计命令检查退出码，不只调用某个内部字符串函数。

测试覆盖：合法项目通过、历史文字可保留、真实旧 Coq 导入被拒绝、旧构建清单被拒绝、构建不能直接引用归档、行内注释后证明洞被拒绝、多行嵌套注释不误判、复数假设命令被拒绝、空活动树被拒绝、缺锁文件被拒绝。

在修复审计前，这批测试实际运行失败；修复后才通过。保留非法输入测试，是为了防止未来通过删除规则“修好”测试。

### `make audit`

运行项目边界检查和覆盖清单格式检查。覆盖清单仍为空，六阶段均为 0。空清单的格式通过，不等于整核证明通过。

### `make check-models`

只把六个小模型／规格／证明源文件复制到一次性目录，按依赖顺序编译。随后：

- 对三个现有小模型根定理执行 `Print Assumptions`。
- 要求三者均为 `Closed under the global context`。
- 用 `coqchk` 检查该模块及其依赖。
- 退出时删除该次调用自己创建的临时目录。

因此检查不依赖项目目录中旧的 `.vo`，也不依赖参考目录。

### `make check-build` 与 `make build`

编译 `_CoqProject` 中的整个基础工程，包括复用的框架与证明工具。它比六个文件的小模型检查大得多；前者通过不能替代后者的全量构建结果。

`make check-build` 只复制活动 `.v` 源码及三个构建入口，在没有旧产物、没有参考资料的临时目录运行完整构建，并在退出时清理该次目录。这样无需破坏当前工作目录来验证“从零可构建”。

`coqc-wrapper.sh` 是已有的进程栈／GC 设置包装，不改变命题或证明。本次不启用包装的干净全量构建已经通过，因此默认构建及小模型检查均直接使用 `coqc`。包装器保留为可选诊断工具，不把它当作构建必需条件，也不从不同缓存／并发条件的运行推导性能收益。具体命令与结果见检查记录。

## 8. 当前小模型能说明什么

例如等待模型有 `waiting`、`suspended`、`ready` 和等待结果字段。`ready` 表示有运行资格，不表示此刻正在 CPU 上执行。

一个任务只被恢复挂起状态，但仍在等待消息时，不会立即变为 `ready=true`。这是 `V293_resume` 把 `ready` 设成 `negb waiting` 的直接结果。

另一个场景是“等待中已超时，同时仍被挂起”：超时清除等待但保留挂起；之后恢复挂起，才可就绪，并保留 Timeout 结果。这两条路径不要混淆。

互斥锁的小规格当前只是“恢复函数等于有效优先级函数”，而前者本来就是后者的别名；该性质很弱。编译和检查它，并不意味着真实互斥锁源码的优先级继承／恢复已经得到验证。后续必须建立与真实字段、链表、就绪表操作相连的规格。

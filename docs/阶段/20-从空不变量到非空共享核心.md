# 第二十课：从空不变量到非空共享核心

## 1. 这次解决什么问题

上一课有两份分离的资源：`SWINV I` 和调用方持有的抽象任务表。不能把任务表既算在调用方，又算在 `I` 内；也不能为了套用切换规则把它丢掉。

本课先实现一个**非空的共享核心**，让四类抽象状态和真实 `OSTCBCur` 指针有明确归属。它证明框架 `GoodI` 的接口条件，但还没有装入完整内核的物理数据结构。

## 2. 先填好资源归属表

| 资源 | 本课归属 | 作用／尚缺内容 |
| --- | --- | --- |
| 抽象当前任务 `curtid` | 共享核心，独占 | 与真实当前指针保持一致 |
| 抽象任务表 `abstcblsid` | 共享核心，独占 | 切换前后保持同一张表；不能再在外部重复持有 |
| 抽象事件表 `absecblsid` | 共享核心，独占 | 本课只保存，不证明与真实 ECB 对应 |
| 抽象时间 `ostmid` | 共享核心，独占 | 本课只保存，不是 tick 正确性 |
| `OSTCBCur` 第一半权限 | 共享核心 | 与抽象当前任务指向同一任务 |
| `OSTCBCur` 第二半权限 | `SWINVt` 外加的当前任务资源 | 合并两半后才可写，写完再拆回 |
| 真实就绪位图、优先级表、TCB／ECB | 尚待纳入和关联 | **不能因此宣称实际内核不变量已经完成** |
| 局部不变量 `LocalInv` | 本课明确选 `Aemp` | 只验证空局部资源场景，不代表任意任务私有资源 |

这里 `**` 是分离合取，表示资源能按框架的权限规则组合，不是普通逻辑的“同时成立”。两个半权限可以合并；独占的抽象表不能复制。

## 3. 打开、使用、关闭

本课证明两个方向：

```text
SWINV  →  中断状态标记 ** 共享核心
中断状态标记 ** 共享核心  →  SWINV
```

这不是额外赠送资源，而是同一资源的重新封装。

`SWINVt I current` 另外带当前指针的一半权限。打开共享核心后，先证明两半读到同一个任务，再复用上一课的 `V293_current_halves_write` 合成完整写权限。

## 4. 真正写入时，两个世界一起更新

切换涉及两个不同但必须一致的动作：

```text
实际内存：OSTCBCur := target
抽象状态：curtid := target
```

`V293_shared_store` 从框架实际 `store` 的结果出发，证明两项更新后仍满足 `SWINVt I target`。它没有假设“整个切换已经正确”，也没有用 `GoodI` 证明它自己。

任务表、事件表、时间槽位和其他分离资源在这一步不变。若只写物理指针而省略抽象更新，两个当前任务标记便可能不同，保持证明会失败。

## 5. `GoodI` 到底检查什么

| 条件 | 本课结果 |
| --- | --- |
| 共享部分拥有全部抽象槽位，外部不能再分走一份抽象状态 | 已证明；逐一检查四个槽位 |
| `SWINVt` 中的当前任务确实是实际指针读到的任务 | 已证明；使用同一全局环境和实际 `load` |
| 当前指针的实际写入和抽象标记更新保持共享不变量 | 已证明；不是把保持作为前提 |
| 当前任务已被删除时，局部资源合回仍成立 | 仅对本课明确选定的空 `LocalInv` 证明 |
| 调度器满足框架 `GoodSched` | 复用当前目标已证明的调度器 |
| 完整真实内核不变量、整个 `OS_Sched` 和最终 `GOOD_OS` | **尚未完成** |

`GoodI` 是框架对不变量的一组条件，不是“操作系统已经验证完成”的另一个名字。

## 6. 为什么不是空证明

不能只证明“如果某状态存在，那么切换保持它”，却让这个状态根本不存在。

本课先用真实编码的可写指针字节和四个抽象槽位构造状态，再证明一次实际 `store` 确实有结果。任务表、事件表、时间值和目标指针可任意给定。

另外把同一个目标任务放进两个具体场景：

| 场景 | 当前任务（优先级 4） | 目标任务（优先级 12） | 检查 |
| --- | --- | --- | --- |
| 当前仍存活 | 时间等待，不是就绪 | 就绪，确实最高就绪 | 同一状态满足 `SWINVt`、`AHprio` 并可执行实际写入 |
| 当前已删除 | 不在抽象任务表中 | 就绪，确实最高就绪 | 同样可写入并保持；不强加当前成员前提 |

这是具体可满足性，**不是**已经从真实启动过程走到这些状态，也不是已验证 `switchdead_rule` 调用链。

## 7. 怎样检查错误真的会被发现

本轮单独移除时间槽位、单独省略抽象当前任务更新、单独把见证指针改成只读，并给 `GoodI` 根单独增加 `False` 前提。前三种在预定证明义务拒绝；最后一种先编译核心与见证，再由无额外前提的固定接口拒绝。

删除时间槽位导致的早期失败只验证该槽位，不拿它冒充后续保持条件的测试。首次预检还暴露了被删除槽位的参数缺少显式类型，因此先补全正常定义的类型，再重测；类型推断错误不计作有效消融结果。

## 8. 接下来按什么顺序做

1. 把真实就绪位图、优先级表和任务／事件布局纳入共享资源，建立它们与同一张抽象任务表的关系。
2. 打开共享资源后，让已有内部调用与前缀使用它们，再关闭。不能把旧入口中的外部任务表原封不动重复加上。
3. 区分共享和局部资源，接实际抽象调度动作、`switch_rule` 和合法自删除的 `switchdead_rule`。
4. 再完成临界区入口／出口、完整函数环境与初始化，最终闭合源码级 `GOOD_OS` 和同程序 K1–K4。

无需回答练习。建议顺序：本课归属表 → `V293_shared_core` → `V293_shared_store` → `V293_shared_good` → 两种切换状态见证。验收事实见[第十九阶段报告](../../audit/STAGE19_SHARED_STATE.md)。第一阶段未完成前，不把 uC/OS-III 当作已经启动或已经交付。

# 第十二课：把调度器函数体交给内部函数框架

上一课证明：如果已经拿到两个可写字节和正确的读取资源，`OS_SchedNew` 的两次赋值及 void 返回满足规格。

这一课解决一个具体衔接问题：**调用者不应知道函数运行时新分配的局部地址，函数返回时又必须交还局部资源。** 不要求你回答问题，按下面顺序阅读即可。

## 1. 先分清三层

| 层次 | 描述什么 | 本次结果 |
| --- | --- | --- |
| 函数体 Hoare | 给定局部地址后，两次赋值如何改变内存 | 复用上一课证明 |
| 内部函数组件 | 局部变量构造器、函数规格表、函数体规则是否一致 | 新增参数化单函数 `WFFunEnv` 证明 |
| 整个内核 | 真正的全局布局、所有函数、任务状态和初始化能否一起连接 | 尚未完成 |

`WFFunEnv` 是框架的标准谓词，不是新造一个表示“成功”的标签。它检查程序表／规格表定义域一致、函数签名及局部声明有效，并要求框架生成的前后置确实支持函数体 Hoare。

## 2. 为什么不能直接把上一课的前置当函数规格？

上一课的函数体前置包含：

```text
Alvarenv y ... byblock
PV (byblock, 0) @ Tint8 |-> yold
```

它们说“局部变量 y 已绑定到块 byblock，并且我可以写这个字节”。但是调用者还没有进入被调用函数，不应事先指定这个新局部地址。

框架因此区分两种断言：

- `fpre`／`fpost` 的 `funasrt`：只描述函数对外要求／交还的资源，不含局部变量绑定。
- `BuildPreI`／`BuildRetI`：读取函数声明后，自动把局部变量资源与局部环境定义域加上。

新增文件 `V293OSSchedNewInternal.v` 证明对外断言符合 `GoodFunAsrt`，没有绕过这个限制。

## 3. 真正的输入有哪些？

调度器对外前置要求：

1. 四个真实全局变量的环境绑定。
2. 实际 256 字节查表、两个就绪行字节和计算出的组字节，都是只读资源。
3. `OSPrioHighRdy` 的一个可写字节，其旧值不作限制。
4. 调用方自己的 `CurLINV li tid`，以及关闭中断的 `Aie false`。
5. 两个行值均小于 256，并且至少有一个 0–12 范围内的就绪优先级。
6. 调用方的抽象操作 `aop`，执行后保持不变。

这里**不要求调用方提前证明表达式会读出什么、最终选择值就绪或最小**。那些结果由函数体和查表定理导出。

行值不是写死在函数规格表里的常量。框架逻辑参数 `lg` 携带两行快照和抽象操作；同一组 `lg` 关联调用前后置，因此同一个内部函数组件可以描述不同调用时的不同就绪位图。

格式不合法的 `lg` 对应 `Afalse`，表示不能用这份规格发起该种调用。合法格式并不全部为假：后面有实际可满足见证，并且独立探针逐项检查选择器的精确形状。

## 4. 入口资源怎样接上？

函数没有 C 参数，只有一个局部字节 `y`。框架构造出的局部部分是：

```text
(EX yold, LV y @ Tint8 |-> yold) ** Aemp
```

`LV` 内部再存在量化一个实际内存块。旧值是任意 `val`，不是人为规定成零或 `Vundef`。

完整入口还包含 `A_dom_lenv [(y, Tint8)]`：局部环境恰好只有这一个声明。结合四个全局标识都不等于 `y`，就能证明这些全局变量没有被局部变量遮蔽。

证明顺序是：

```text
BuildPreI 生成的资源
→ 展开局部值／地址的存在量词
→ 从准确局部定义域推出没有遮蔽
→ 得到上一课函数体需要的 bindings 与两个可写字节
→ 使用已证明的 body_hoare
```

局部定义域不是装饰项：删除它的消融必须在入口环境桥接失败，而不是提前以哈希不匹配结束。

## 5. 返回时必须交还什么？

函数体结束时，`y` 保存选中的行，最高就绪优先级字节保存选择结果。

对外后置要求：返回值为 `None`，所选优先级就绪且不大于任意其他合法就绪优先级，并保留输入、关闭中断状态、调用方不变量与抽象操作。

与此同时，还必须把 `Alvarenv y ...` 和 `y` 的可写字节重新合成：

```text
EX v, LV y @ Tint8 |-> v
```

它连同准确的局部定义域进入 `BuildRetI`。这让框架的释放规则有完整资源可用；不是把一个仍然分配着的局部字节悄悄丢掉。

**本课证明的是资源交接符合框架构造器，不是另外新增了一份具体 alloc/free 执行轨迹。** 分配／释放的通用语义与 soundness 仍使用已修复的框架证明。

## 6. 四个可以定位的接口

在 `certiucos/v293/proofs/` 中阅读：

| 接口 | 作用 |
| --- | --- |
| `V293_OSSchedNew_internal_contract` | 任意程序表中包含准确函数时，连接真正的 `BuildPreI`／`BuildRetI` |
| `V293_OSSchedNew_WFFunEnv` | 一个非空单函数程序表与规格表满足框架内部函数条件 |
| `V293_OSSchedNew_internal_builders` | 无 C 参数时，两个构造器确实返回 `Some` |
| `V293_OSSchedNew_internal_precondition_witness` | 某个实际状态满足构造出的整个入口，而不仅仅是构造器返回了 `Some` |

最后一个在 `V293OSSchedNewInternalWitness.v`：复用真实分离内存布局，就绪行为 `0 / 16`，组为 `2`，候选优先级为 `12`，中断关闭，局部环境恰好只有 `y`。

见证中的空局部不变量仅是可满足性夹具。主组件仍对任意满足 `GoodLInvAsrt` 的调用方 `li` 量化；未来真正的内核不变量必须另行构造并连接。

## 7. 怎样排除“看起来编译成功”？

独立探针重写资源、合法逻辑参数分支、返回结果、签名和非空函数表的期望类型，而不是只看有没有同名定理。

五项单因素控制分别删除局部定义域、删除程序入口、改变返回结果、添加 `False` 前提、把 `fpre` 改成全 `Afalse`。后两项先证明变异对象确实能编译，再要求独立类型检查拒绝；隔离后的原版也必须先通过。

因此，“只要有 False，就什么都能证明”不是绕过验收的办法。也不能让前面的模块先失败，再声称后面的返回或组件义务已经检查过。

## 8. 你现在应怎样继续读？

先看 `V293_OSSchedNew_internal_contract` 的声明，找到两行构造器等式；再看 `V293_OSSchedNew_WFFunEnv`，它把该接口用于函数表。最后看实际入口见证，理解“构造器成功”和“前置可满足”是不同要求。

# 第二十五课：不切换，也要完成抽象调度

上一课已经串起比较、计数器与真正普通切换。本课继续同一段程序，不另建小调度器，也不要求你回答练习。

## 第一步：把两个层次分开

实际程序做的是：选出最高就绪任务，比较它与当前任务；不同才执行切换。

抽象规格还要记录：这一次调度是否已经完成。`sched;;aop` 表示“先调度，再做后续动作”；`aop` 表示这一次调度已经完成。

**没有切换，不代表没有调度。** 如果检查后发现当前任务本来就是最高就绪者，调度可以完成，只是不需要换人。

## 第二步：沿着真实证据走，不添加假设

源码对应的查表与目标赋值已经给出最高就绪目标。已证明的任务表关系还保证：

```text
选出的优先级 = 当前优先级
                  ↓
选出的任务指针 = 当前任务指针
                  ↓
当前任务就是最高就绪任务
                  ↓
允许完成抽象的自调度
```

这里不是额外假设“当前任务已经最高”。结论来自同一份实际共享任务表、位图和优先级表的关系；没有复制一份独占任务表，也没有把后半段当作未知 oracle。

框架规则 `absinfer_sched'` 完成自调度，随后去掉抽象顺序中的 `END None`。这两个都是证明中的抽象步骤，不是给冻结 C 新增 CPU 指令，也不是偷偷执行一次物理任务切换。

## 第三步：补全本轮分支表

| 条件 | 本段实际执行 | 结束时抽象动作 | 本段计数器结果 |
| --- | --- | --- | --- |
| 中断嵌套或调度锁计数非零 | 跳过调度主体 | 保留 `sched;;aop` | 保持 `c` |
| 两计数皆零，选出当前任务 | 调用、查表、目标赋值；不切换 | 完成自调度，成为 `aop` | 保持 `c` |
| 两计数皆零，选出其他任务 | 调用、赋值、计数器递增、普通切换 | 原线程恢复时为 `aop` | `Int.add c Int.one` |

后两行现在具有相同的后置资源形状：`aop`、`SWINVt`、原线程的动态栈和完整剩余局部资源。计数器以条件表达式区分，不能在不切换的分支也加一。

相等分支没有经过其他线程执行；不同分支的后置则描述原线程将来恢复，不是“切换指令之后仍立即运行原线程”。

**计数器说明仍限于当前片段的资源契约。** 它和位图、数组等目前被作为片段独占的局部 frame 保留。真实内核中其他任务也会修改这些全局资源；纳入完整共享不变量之前，不能宣称跨其他任务执行后，全局计数器只增加了这一次。

## 第四步：为什么第一行不直接改成 `aop`

抽象 `V293_scheduler` 根据就绪任务选择，不读取调度锁。当前入口关系也允许当前任务处于等待态。

本轮构造了一个具有全部入口资源的状态：

| 项目 | 值 |
| --- | --- |
| 中断嵌套字节 | `0` |
| 调度锁字节 | `1` |
| 当前任务优先级 | `4`，但正在时间等待，不是 ready |
| 最高就绪任务 | 另一个优先级 `12` 的任务 |
| 抽象入口动作 | 真正的 `sched;;aop` |
| `sched_self` | 不成立 |

`4` 的数字更小也没有用：它不在就绪集合中。这份状态同时有真实片段内存、当前指针权限和唯一抽象任务表，不是分别构造几组互不相关的纯条件。

这说明**仅凭当前片段入口，不能把第一行套用“选回自己”的规则**。它不说明这种锁定等待状态可从真实初始化到达，也不是锁定状态下调度一定出错的报告。下一层必须根据调用方和可达不变量明确延期调度的规格；不能为了让证明通过，把调度器改成允许任意当前任务。

## 第五步：在仓库中按顺序看

1. `V293OSSchedDispatchFinish.v` 的 `V293_dispatch_equal_finish`：相等分支从同一任务表完成自调度。
2. `V293_dispatch_change_finish`：不改实际比较／递增／切换代码，合并两个 enabled 分支。
3. `V293_dispatch_prefix_finish`：接回原实际调用和目标赋值。
4. `V293_OSSched_guarded_dispatch_finish`：接回两个 guard；禁止调度仍保留入口。
5. `V293OSSchedDispatchFinishWitness.v`：完整锁定入口及 `~sched_self` 的同状态反例。

入口可满足性继续使用上一课的完整见证，允许两种目标模式、两个任意合法字节、任意计数器、事件表、时间和后续动作。它不是实际初始化证明。

## 这一课完成后，离最终目标还有什么

本轮推进的是同一规范化调度片段，不是完整 `OS_Sched` 的源码级证明。`OSCtxSw`／`OSPrioCur` 的源码级边界、临界区入口／出口、真实全局物理资源共享、合法自删除特殊切换、其他函数、完整环境与初始化仍需完成。

六门覆盖没有增加：仍为 `94 / 1 / 1 / 1 / 1 / 0`。第一阶段最终目标仍是固定 uC/OS-II 的真实源码级 `GOOD_OS` 和同程序 K1–K4；完成之后才进入 uC/OS-III。

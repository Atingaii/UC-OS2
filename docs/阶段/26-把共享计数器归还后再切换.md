# 第二十六课：把共享计数器归还后，再切换

前两课已经把调度片段串起来，但留下了一个不能直接推广到整核的问题：计数器等真实全局变量，仍被当作本线程独占的局部资源。本课先修正计数器在切换尾部的归属，不要求你回答问题。

## 第一步：分清“刚写完”和“将来恢复”

假设当前切换计数器为 `7`：

```text
线程 A 递增：7 → 8
线程 A 切换出去
其他线程可能继续调度：8 → 9 → ……
线程 A 将来恢复
```

递增刚结束时，计数器确实是 `8`；A 将来恢复时，却不能只凭这一次递增保证它仍是 `8`。

之前的局部片段定理在其资源契约下成立，但契约把计数器留在私有 frame 中。它不是“其他线程执行以后，真实全局计数器依然只增加一次”的证明。旧证据保留，新证明不继承这个不适合整核的保证。

## 第二步：把存储所有权放对位置

分离逻辑不只记录值，也记录访问资源的权限。

| 项目 | 实际存储内容 | 本轮放在哪里 |
| --- | --- | --- |
| 计数器单元 | 一个 `Tint32` 值，完整写权限 | 切换前归还共享不变量 |
| 额外物理单元列表 | 每项固定地址、类型和完整写权限 | 同一个共享不变量；当前具体见证取空列表 |
| `counter` 的环境绑定 | 变量名指向哪个地址／类型 | 可作为切换 frame 保留，不占有计数器单元 |
| 真正线程私有的 `px` | 由调用方明确提供的局部资源 | 满足框架条件后保留 |

`V293_storage` 对每个单元描述的是“存在一个类型正确的值”，不是“值永远等于进入时的值”。它没有用 `Atrue` 吞掉任意内存，也没有允许凭空丢掉资源。

## 第三步：按时间点看证明

| 时间点 | 能保证什么 | 不能额外声称什么 |
| --- | --- | --- |
| 递增前，资源已打开 | 完整计数器为 `c`，还有实际切换所需资源 | 尚未完成调度 |
| 真正递增后、切换前 | 完整计数器精确为 `Int.add c Int.one` | 不等于原线程已经恢复 |
| 关闭共享不变量 | 计数器和额外物理单元已经归还；值有类型、权限完整 | 不能再在私有 frame 另留同一份完整单元 |
| 真正切换并恢复后 | 后续动作 `aop`、`SWINVt`、原线程栈及合法私有 frame | 不固定原共享值，也不保证计数器仍为旧 `c+1` |

`Int.add` 是 32 位模运算：最大无符号值加一得到零。新接口没有排除最大值。

## 第四步：对应仓库里的三个文件

1. `certiucos/v293/proofs/V293DispatchStorage.v`
   - `V293_storage`：固定地址／类型的有类型完整存储。
   - `V293_storage_inv`：把这些存储接到现有共享核心和目标单元。
   - `V293_storage_invariant_good`：证明框架要求的 `GoodI`，包括实际当前指针写入后的保持。
2. `certiucos/v293/proofs/V293OSSchedStorageTail.v`
   - `V293_storage_tail_increment`：真正递增，得到切换前精确 `c+1`。
   - `V293_storage_tail_return`：把已借出的共享资源封回去。
   - `V293_storage_increment_switch`：顺序执行真正递增和框架普通切换，没有“假设后半段正确”的前提。
3. `certiucos/v293/proofs/V293OSSchedStorageWitness.v`
   - 同一个具体状态同时具有 pending 动作、两半当前指针、唯一抽象槽位、目标指针、任意计数器和必要环境绑定。
   - 覆盖同目标／当前 ready，以及不同目标／当前时间等待两种模式。
   - 这里只是完整**尾部入口**，额外单元列表为空，不是完整调度函数入口或全部全局布局。

建议先读本课的时间点表，再看第二个文件的最终定理，最后回头看 `GoodI` 的技术证明。

## 第五步：现在还缺哪一段

本轮新尾部使用含物理存储的 `V293_storage_inv`；上一课完整规范化前缀仍使用原来的 `V293_dispatch_inv`。**不能把两个不变量不同的定理直接拼接后宣称整段完成。**

下一步需要把实际位图、优先级数组、guard 字节、当前优先级和计数器的资源，在同一个新共享不变量下借给前缀／比较，再归还；同时补实际物理数据与抽象任务表之间的关系，而不只是它们的类型。`OSCtxSw`／`OSPrioCur` 的源码对应也仍然开放。

这不是新的内核功能，也没有修改冻结 C 或放宽 scheduler。完整 `OS_Sched`、临界区、合法自删除、其他函数、初始化和最终 `GOOD_OS` 仍需继续。六门覆盖仍为 `94 / 1 / 1 / 1 / 1 / 0`；先完成 uC/OS-II 整核证明，再进入 uC/OS-III。

本课的控制、验收和边界见[第二十五阶段报告](../../audit/STAGE25_SCHEDULER_STORAGE.md)。

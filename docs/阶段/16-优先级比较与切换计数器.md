# 第十六课：优先级变化后，先加计数器，再切换

## 1. 我们接着证明哪几行

前面已经连接了两个调度条件和下面两句：

```c
OS_SchedNew();
OSTCBHighRdy = OSTCBPrioTbl[OSPrioHighRdy];
```

现在沿同一个 V2.93.01 函数继续，不换内核、不改 C。配置后的下一段是：

```c
if (OSPrioHighRdy != OSPrioCur) {
    OSCtxSwCtr++;
    OSCtxSw();
}
```

`OSPrioHighRdy` 是刚从就绪位图选出的最高就绪优先级；`OSPrioCur` 是当前优先级；数字越小，优先级越高。`OSCtxSwCtr` 是 32 位无符号切换计数器。前面的任务表关系还保证选出的指针确实属于同一状态里的就绪任务。

**比较相同，就不进入这个分支；比较不同，先递增计数器，然后才到任务切换。** 这不等于“已经证明任务切换成功”：最后一项仍需真实切换规则。

## 2. 补全执行路径表

设 `p` 是此次计算出的最高就绪优先级，`c` 是进入调度器时的计数器。

| 中断嵌套 | 调度锁嵌套 | 当前优先级 | 此段行为 | 计数器 | 切换义务 |
| --- | --- | --- | --- | --- | --- |
| 非零 | 无需读取 | 无需读取 | 整个调度主体跳过 | 保持 `c` | 不需要 |
| 零 | 非零 | 无需读取 | 内层主体跳过 | 保持 `c` | 不需要 |
| 零 | 零 | 等于 `p` | 先更新最高就绪任务指针，再跳过切换分支 | 保持 `c` | 不需要 |
| 零 | 零 | 不等于 `p` | 更新指针、递增计数器、到达切换点 | `(c + 1) mod 2^32` | **仍须证明** |

注意第三行不是“所有东西都不变”：最高就绪任务指针的赋值已经发生了。新后置保留的是这个赋值后的状态，而不是整个函数最初的前置。

## 3. 为什么 Coq 中没有直接写 `!=` 和 `++`

当前 CoqImp 语言没有 `!=` 运算符，因此固定对应为：

```coq
eunop oppsite
  (ebinop oeq (ecast (evar high) Tint32) (ecast (evar current) Tint32))
```

这里 `oppsite` 是框架里的逻辑非，不是按位取反；两边原本都是字节，提升到 32 位后比较。求值证明从全局绑定、无局部遮蔽和实际字节资源推出结果，不把比较结果直接塞进前置。

C 的后缀 `++` 原本还会产生旧值，但这里它独立成句、旧值被丢弃，又不是 `volatile` 对象，因此只保留一次递增写入：

```coq
sassign (evar counter)
  (ebinop oplus (evar counter) (econst32 Int.one))
```

检查器先核对整个配置后 C AST，包括真正的声明、字节提升、后缀标志和语句位置，再逐字核对这个固定 Coq 发射。这里是受信任的受限源码对应检查，**不是已验证的 C 编译器**。

## 4. 不能偷偷加上“不溢出”条件

无符号计数器允许回绕：

```text
4294967294 → 4294967295 → 0 → 1
```

因此定理对所有 `Int.int` 值成立，更新使用 `Int.add c Int.one`，没有 `c < 4294967295` 的额外限制。独立探针也检查最大值加一为零。

本轮另做了一个反向实验：只给最外层组合定理增加“计数器不是最大值”的前提。这个变异自身及见证能编译，但不再符合原来覆盖所有计数器的接口，因而被拒绝。不能靠排除边界值把 C 的行为改成一个更容易证明的问题。

## 5. 新证明怎么接上旧证明

按下面顺序阅读即可，无需先读全部框架：

1. `certiucos/v293/code/V293OSSchedChange.v`：比较、递增和带开放切换后续的语句。
2. `V293_OSSched_priority_comparison`：从前两句得到的**同一个状态**读取最高就绪优先级和当前优先级。
3. `V293_OSSched_counter_increment`：使用真实 `assign_rule`，要求计数器有写权限，保留调用方资源。
4. `V293_OSSched_tail_increment`：把通用赋值接到已有最高就绪任务后置中，保留原任务表和指针。
5. `V293_OSSched_guarded_changed_prefix`：组合两层条件、内部调用、指针赋值、优先级比较和计数器。
6. `V293OSSchedChangeWitness.v`：在同一具体内存中放下全部表、当前任务、输出、三个合法字节值及任意计数器，证明前置不是空洞条件。

最后这个见证对任意中断嵌套字节、锁嵌套字节、当前优先级字节和计数器值成立。它包括禁用、同优先级、不同优先级以及回绕值，不只展示“全零”的顺利路径。

## 6. `suffix` 现在还欠什么

上一步的 `suffix` 同时包含比较、计数器和切换。现在比较和计数器已经接上，剩下的明确义务是：

```text
中断嵌套为零 ∧ 调度锁嵌套为零 ∧ 最高就绪优先级不同
    ⇒ 从递增后的状态证明真实切换 continuation
```

没有把普通函数调用 `scall OSCtxSw` 的假设当成已完成切换。下一步要对接框架 `switch_rule`，兑现目标任务、切换不变量和当前任务的局部不变量；还要处理真实临界区保存令牌、TCB 字段、共享不变量及完整程序环境。

最终目标仍是固定 uC/OS-II 程序的源码级 `GOOD_OS` 和同程序 K1–K4，然后才进入 uC/OS-III。本课不是整核证明完成声明，六门覆盖仍为 `94 / 1 / 1 / 1 / 1 / 0`。正式实测结果见[第十五阶段报告](../../audit/STAGE15_SCHEDULER_CHANGE.md)。

## 7. 下一步按什么顺序做

下一轮不从空白开始，也不另外造一个调度器模型。入口就是本轮递增后的 `V293_OSSched_tail_state`，对照 `framework/logic/inferules.v` 中的 `switch_rule`：

| 先核对的资源 | 现在已有 | 还要兑现 |
| --- | --- | --- |
| 最高就绪任务 | 同一抽象任务表里的最高就绪任务与已写入目标指针 | 与框架调度关系 `AHprio sd t` 对接 |
| 当前任务 | 当前任务指针的只读资源及调用方局部不变量 | 当前 TCB 成员关系、当前优先级关系，以及规则要求的可写权限 |
| 切换时共享状态 | 关闭中断的状态资源 | `isrclr`、中断栈与 `SWINV`，不能只用“中断已关”替代 |
| 抽象动作 | 原调用方抽象动作被保留 | 明确真实调度动作 `sched` 怎样接在该动作之前 |

先证明这些资源之间的连接，再使用真正的切换规则；随后处理临界区的保存与恢复。`OSCtxSw()` 到框架切换原语的对应也需要明确记录源码抽象边界，不是把硬件汇编正确性算作本轮成果。

最先检查“当前任务确实存在且优先级对应”的原因是：本轮见证只保证三个字节合法及内存不冲突，尚未保证任意当前优先级都与完整内核不变量兼容。补齐这一关系才能从局部可执行片段继续走向整核，而不是继续堆不相连的引理。

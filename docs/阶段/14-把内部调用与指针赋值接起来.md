# 第十四课：把内部调用与指针赋值接起来

上一课有两个独立结果：“调用能算优先级”和“给定优先级能读出任务指针”。本课把中间资源交接补上，不需要你回答练习题。

## 第一步：明确这次到底要证明哪两句

```c
OS_SchedNew();
OSTCBHighRdy = OSTCBPrioTbl[OSPrioHighRdy];
```

最终想得到：**执行这两句后，`OSTCBHighRdy` 指向最高优先级的就绪任务。** 数字越小，优先级越高。

前提不只是“数组存在”：位图必须和任务表对应，任务表必须和指针数组对应；还要有实际内存、正确全局绑定、可写输出和内部函数规格。完整系统以后必须建立和保持这些条件。

## 第二步：看懂最小资源表

| 对象 | 为什么需要 | 这两句后的状态 |
| --- | --- | --- |
| 查表、就绪组、两行就绪位图 | 第一条调用计算最高优先级 | 内容保留 |
| `OSPrioHighRdy` 可写字节 | 接收内部调用结果，再作为数组下标 | 保存计算出的优先级 |
| `OSTCBPrioTbl` 只读指针表 | 用优先级查对应任务 | 内容保留 |
| 抽象任务表及两类全称关系 | 说明查到的是哪个任务，以及为什么最高 | 同一张任务表保留 |
| `OSTCBHighRdy` 可写指针单元 | 接收第二句结果 | 改成最高就绪任务指针 |
| 调用方 frame、局部不变量 | 保护本次计算没有权利破坏的资源 | 保留 |

这里 `**` 表示可分离的资源，不是普通逻辑“并且”。两个可写单元不能占同一个地址；见证定理专门证明它们能一起存在。

## 第三步：理解连接处

调用前 `OSPrioHighRdy` 可以是旧值。内部调用返回后，它已持有算出的字节。

证明分三层：

1. 从调用后置的空间资源推出真实 `load` 返回这个字节；
2. 从同一状态中的指针表资源，实际计算 `OSTCBPrioTbl[OSPrioHighRdy]`；
3. 用赋值规则写入 `OSTCBHighRdy`，保留其余资源。

不能跳过第一层，直接把“下标已经正确”当成新前提；那样两个独立结果仍然没有连接。

## 第四步：顺序规则是什么

可以把 Hoare 三元组暂时读作：

```text
{执行前必须拥有的资源} 代码 {执行后保证拥有的资源}
```

顺序规则就是：

```text
{P} OS_SchedNew() {Q}
{Q} 指针赋值        {R}
────────────────────────
{P} 两句按顺序执行  {R}
```

关键不是画出这张图，而是两个 `Q` 必须真正接得上。本阶段使用框架的 `call_rule`、`assign_rule` 和 `seq_rule`，不另造一套“看起来执行过”的替代语义。

完整接口是 `V293_OSSched_unlocked_prefix_hoare`；指针赋值接口是 `V293_OSSched_target_assign`。

## 第五步：一个完整前置的例子

只有优先级 12 就绪时，两行位图为 `[0,16]`，组为 2，任务数组第 12 项存着该任务指针。

这次见证把以下内容放在同一个真实状态：查表、位图、当前任务、抽象任务表、指针数组，以及两个独立可写输出。优先级初值可以是 0，输出任务指针初值可以为空。

`V293_OSSched_prefix_precondition_witness` 证明整个前置确实成立；它不是完整操作系统启动过程，也不证明每个任务都能从启动到达。

## 第六步：怎样确认不是假通过

检查器分别改变一个因素，其余保持不变：

- 读取结论偏移 1：在桥接读取引理拒绝；
- 去掉指针写权限：在赋值证明拒绝；
- 颠倒两句：在组合证明拒绝；
- 增加 `False` 前提：定理和前置见证先编译，再由独立接口拒绝。

最后一项很关键：“Coq 编译通过”只说明该定理被证明，不说明定理的前提就是项目真正需要的前提。

验收结果见[第十三阶段报告](../../audit/STAGE13_SCHEDULER_PREFIX.md)。

# 第二十三课：把共享目标接回真实调用与条件分支

无需答题，直接顺着下面的状态表看。

## 1. 上一课为什么还不能直接拼起来

之前分别得到：

- stage20：真实 `OS_SchedNew()` 调用和目标指针赋值，任务表在共享不变量中，目标单元却在外面。
- stage21：真正使用框架切换规则，但要求目标单元也在共享不变量中。

两份结论使用不同的资源归属。就像两个接头形状不同，不能仅凭“分别证明过”就宣布整段程序证明成功。

本课把前面的调用与赋值也放到 stage21 的 `V293_dispatch_inv` 下。没有复制任务表或目标单元，没有修改 C。

## 2. 真实执行的两句代码

```c
OS_SchedNew();
OSTCBHighRdy = OSTCBPrioTbl[OSPrioHighRdy];
```

第一句从位图算出最高就绪优先级，第二句读取相同优先级表中的实际指针，并写入真正可写的目标单元。不是把数学答案直接放进后置条件。

| 检查点 | 任务表／事件表／时间 | 目标指针 | 所有权位置 |
| --- | --- | --- | --- |
| 调用前 | 指定的同一份值 | 任意类型正确的空指针或真实指针 | 都在 `V293_dispatch_inv` 内 |
| 打开共享资源 | 任务表暂时借给已证明的真实前缀 | 同一个完整可写单元借出 | 原资源重组，不复制 |
| 调用和赋值后 | 三份值不变 | 实际选出的最高就绪任务 | 与当前任务槽位一起归还同一个共享不变量 |

`entry` 是对共享状态的观察，不是另存一份任务表。赋值后 `snapshot` 还观察新写入的目标值。

入口并不要求目标已经正确，否则容易把要证明的结论偷放进前提。

## 3. 内部调用为什么使用较小的资源契约

外层规则始终使用新的完整共享不变量。打开资源后，内部 `OS_SchedNew` 契约只携带 `V293_opened_inv`，不再重复占有整份任务表和目标单元。实际位图、优先级表和可写输出由前缀证明显式使用，之后才归还外层。

这不是换成空内核证明：较小契约只用于已打开资源的内部调用点，整个前缀的环境仍是含真实共享资源的新 `Inv`。

## 4. 两层条件现在也接到这个入口

```c
if (OSIntNesting == 0u) {
    if (OSLockNesting == 0u) {
        /* 上述真实两句前缀 */
    }
}
```

| 中断嵌套字节 | 调度锁字节 | 新结论 |
| --- | --- | --- |
| 非零 | 任意合法字节 | 不执行前缀，保持完整入口，包括旧目标单元 |
| 零 | 非零 | 不执行前缀，仍保持完整入口 |
| 零 | 零 | 执行真实调用和赋值，目标更新为最高就绪任务 |

禁用分支不能谎称“目标已经更新”。本轮专门把它的后置错误改成执行后状态，检查 Coq 在这条分支义务拒绝。

## 5. 本轮三个最重要的接口

打开 `certiucos/v293/proofs/V293OSSchedDispatchShared.v`：

1. `V293_dispatch_entry_open`／`close`：观察与实际唯一资源之间的借还。
2. `V293_OSSched_dispatch_prefix`：没有后续语句 oracle 的真实两句前缀。
3. `V293_OSSched_guarded_dispatch_prefix`：用同一个共享核心包住两层条件。

`V293OSSchedDispatchSharedWitness.v` 复用已有完整状态，移动的是同一个目标单元。两个场景分别是当前任务就绪／选回自己，以及当前任务仍在时间等待／选中另一任务。事件表和时间可以任意指定。

这个完整前缀入口见证使用 `spec_done None` 和空栈；规则本身对任意动作、栈参数化。不要把它称作“完整 guard 入口见证”“待执行调度入口见证”或“实际初始化”。

## 6. 接下来做什么

现在前缀和实际切换使用相同的共享核心，但中间仍需连接优先级比较、计数器递增、第二半当前指针权限和局部资源保留；还要明确 `OSPrioCur` 同步及 `OSCtxSw` 到框架原语的源码对应。

这一步完成后也不是整核结束：合法自删除切换、物理 TCB／ECB 关系、临界区、完整函数环境与初始化，以及最终 `GOOD_OS` 和同程序 K1–K4 仍须完成。uC/OS-II 最终验收前不切换到 uC/OS-III。

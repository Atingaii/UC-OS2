# 第十三课：从内部调用走向真正的任务指针

前一课已经证明：`OS_SchedNew` 的内部规格能与框架的函数入口、返回构造器对接。本课继续同一条调度链，不换一个简单函数刷数量。

## 1. 先看准确的调用位置

冻结的 V2.93.01 `Source/os_core.c` 第 1702–1732 行，在当前配置下是：

```c
void OS_Sched(void) {
    OS_CPU_SR cpu_sr = 0u;
    V293_EnterCritical(&cpu_sr);
    if (OSIntNesting == 0u) {
        if (OSLockNesting == 0u) {
            OS_SchedNew();
            OSTCBHighRdy = OSTCBPrioTbl[OSPrioHighRdy];
            if (OSPrioHighRdy != OSPrioCur) {
                OSCtxSwCtr++;
                OSCtxSw();
            }
        }
    }
    V293_ExitCritical(&cpu_sr);
}
```

这里不是说原 C 文件把临界区写成了这两个名字，而是固定分析端口将宏展开为带保存令牌的边界调用。**有进入临界区的函数调用，不等于已经证明了中断关闭不变量。**

本课只翻译未锁定分支最前面的两句。检查器核对整个调用方的精确 AST，是为了确认这两句的位置、类型和上下文没有认错，不代表整个 `OS_Sched` 已经有 Hoare 证明。

## 2. 这两句分别在做什么

| 代码 | 输入 | 作用 | 本轮证据 | 仍然缺少 |
| --- | --- | --- | --- | --- |
| `OS_SchedNew();` | 就绪位图、查表资源、内部规格查找、局部不变量 | 算出最高就绪优先级并写入 `OSPrioHighRdy` | 框架真实 `call_rule` 的 `InfRules` 实例 | 在完整内部环境中实际兑现规格查找与调用方资源 |
| `OSTCBPrioTbl[OSPrioHighRdy]` | 已算出的优先级、13 项指针表、任务表关系 | 从内存读出对应 TCB 指针 | 实际 `evalval`／`evaltype`，返回同一抽象任务表中的最高就绪任务 | 从调用后置直接导出此处前置的资源连接 |
| `OSTCBHighRdy = ...` | 上述指针以及输出指针单元的可写资源 | 更新“下一任务”指针 | 这条赋值已准确翻译 | 指针写入的 Hoare 与前两步的顺序组合 |
| 后续切换与临界区退出 | 当前优先级、计数器、CPU 边界 | 决定是否切换并恢复中断状态 | 仅核对源码结构 | 分支、计数器、切换与临界区配对证明 |

因此，“有调用规则”和“会正确读表”不能拼成一句“整个调度函数已经证明”。中间的资源交接还要正式证明。

## 3. 为什么一个数字还不够

假设只有优先级 12 就绪：

```text
OSRdyTbl = [0, 16]
OSRdyGrp = 2
OSPrioHighRdy = 12
```

前几课证明了这个数字的计算，但数字本身还不是任务。还必须证明：

1. 位图第 12 位意味着抽象 TCB 表里确实有一个优先级 12 的就绪任务；
2. `OSTCBPrioTbl[12]` 确实存着这个任务的指针；
3. 当前物理内存实际能读出这个表项；
4. 所有其他就绪任务的优先级数字都不小于 12。

数值越小，uC/OS-II 的任务优先级越高。

`V293_bitmap_tasks` 对 **所有**合法优先级建立“位图就绪 ⇔ 存在就绪任务”的关系；`V293_priority_table` 对 **所有**抽象任务建立“优先级范围与表项指针”的关系。不是把“选中任务已经最高”当作前提。

这些关系将来要由真实共享不变量建立和维护。本课只证明：若关系成立，真实读取会得到怎样的结果；还没有证明所有任务创建、等待、唤醒、挂起和删除操作都保持它们。

## 4. 指针表与字节表的区别

前几课的查表每项 1 字节。本课固定分析目标中的指针每项是 4 字节：

```text
表项 0 地址 = base + 0
表项 1 地址 = base + 4
表项 12 地址 = base + 48
整个表 = 13 × 4 = 52 字节
```

`V293_read_pointers` 用分离断言逐项描述这 52 字节；`V293_read_pointers_load` 从这些资源推出真实 `load`。再用框架表达式语义计算 `earrayelem`，而不是直接假设整个表达式恰好返回期望指针。

这里不会解引用任何 TCB 字段，TCB 的指向类型暂为参数。不能据此声称真实 `OS_TCB` 的完整结构布局已经连接。

## 5. 为什么要求“同一个状态”

只说“某张任务表有最高任务”太弱：它可能根本不是当前程序状态里的那张表。

本课将 `Aabsdata abstcblsid (abstcblist tasks)` 与物理表资源放在**同一个分离状态**里，结论是 `V293_scheduler (getabst s) t`。实际任务成员关系、物理指针读取与调度谓词因此指向同一个任务。

另有一个实际可满足的前置见证：13 项指针表中前 12 项为空，第 12 项为一个就绪任务指针；优先级字节为 12；抽象任务表也只有该任务。其内存由有界内存构造器建立，不是互相可能矛盾的读取等式。

这个见证只覆盖目标读取的前置，不覆盖整个调用方、临界区或完整共享不变量。

## 6. `GoodSched` 不是什么意思

`V293_scheduler_good` 证明调度谓词满足框架要求，包括在分离扩展下稳定、确实对应任务表成员等。

它**不**证明每个任意状态里都有就绪任务，也不独立证明唯一性、实际 TCB 所有状态的编码对应或空闲任务永远存在。真实初始化及共享不变量仍要补上这些义务。

## 7. 怎样识别不可靠的“通过”

本轮预先固定五个单因素实验；原版必须先通过，其他输入不变：

| 单独改变什么 | 指定观察位置 |
| --- | --- |
| 删除位图与任务成员关系 | 选中任务定理失败 |
| 删除任务与指针表项的对应 | 选中任务定理失败 |
| 把指针资源步长从 4 改成 1 | 实际读取引理失败 |
| 给调用定理额外加 `False` 前提 | 变异先编译成功，再被独立类型探针拒绝 |
| 给目标读取定理额外加 `False` 前提 | 变异先编译成功，再被独立类型探针拒绝 |

最后两项说明：一个定理名字存在、甚至能编译，并不足以证明它提供了需要的接口。

## 8. 下一步从哪里继续

继续这两句，不另选简单函数：

1. 组织调用方的指针表、抽象任务表、全局绑定与无局部遮蔽资源，证明它们能作为 `GoodFrm` 保留；
2. 从 `OS_SchedNew` 的真实调用后置推出 `OSPrioHighRdy` 的实际字节读取；
3. 为 `OSTCBHighRdy` 提供可写的 4 字节指针资源，用赋值规则完成更新；
4. 用顺序规则把内部调用与指针赋值连接成这两句的一个 Hoare 接口；
5. 再处理外层分支、保存令牌的临界区、实际 TCB 状态与共享不变量。

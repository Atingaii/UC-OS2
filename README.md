# uC/OS-II V2.93.01 的 Coq 形式化验证

使用 CoqImp 通用框架，在 **Coq 8.18** 环境中验证一个固定配置的 uC/OS-II V2.93.01 程序的源码级功能正确性与 safety 性质。

**当前是验证基础工程，不是已完成的内核证明。** 修复后固定配置已冻结，清点出 94 个 C 定义与 16 个声明级边界，六阶段覆盖为 `94 / 1 / 1 / 1 / 1 / 0`。

- `OSVersion` 已获得源码翻译、规格、局部 Hoare 和单函数 API 组件证据，其余函数的六门覆盖仍仅定位。
- 调度链已有 `OS_SchedNew` 函数体 Hoare、内部构造器、参数化单函数 `WFFunEnv`、内部调用规则，以及调用方前两句的顺序 Hoare、两层条件、实际优先级比较和 32 位模递增的顺序组合、当前 TCB 成员／优先级和不同目标的空间资源连接、完整前置可满足见证、调用方预留第二半当前指针后的完整 `SWPRE_NDEAD`，以及显式开放的真实切换义务；完整 `OS_Sched` 仍未证明。
- 真实共享不变量及完整程序连接仍未闭合，最终 `GOOD_OS` 定理尚未完成。Git 工作区整洁只表示改动已归档，不表示构建或证明验收通过。

**框架内存修复已通过完整验收（保留列明的逻辑假设）。** 第五阶段发现原 `MemoryNotFull` 可推出 `False`；第六阶段以内存类型封装块上界，删除该公理并恢复分配及 soundness 证明链。109 文件干净构建、框架根假设检查和依赖闭包 `coqchk` 均通过；这不等于具体内核已验证。历史失败证据保留，完整验收结果见 [第六阶段报告](audit/STAGE06_FRAMEWORK_REPAIR.md) 与 [信任基础](TRUSTED_BASE.md)。

## 环境与常用命令

准备好 Coq 8.18.0、Git、Python 3、GNU Make、Bash、tar、Clang、GCC 与支持 JSON 的 Universal Ctags 后，在仓库根目录执行：

```sh
coqc --version
# 仅在 checkout 不存在时获取；已有修改时不要重建。
make fetch-source
make source-audit
make config-audit
make source-inventory-check
make source-freeze-check
make check-c
make check-c-evidence
make test
make audit
make check-models
make check-build
make build
# 新有界接口的正向检查：
make check-memory-bound
# 框架分配／soundness 根的实际依赖与 coqchk：
make check-framework-trust
# 真实函数的受限翻译、局部接口及反向检查：
make check-functions
```

本机已降为 Coq 8.18.0。第一阶段已修复小模型的导入与参数引入问题，审计回归测试、静态审计、六文件隔离编译、三个小模型根定理的假设与 `coqchk` 检查均已通过。完整构建结果与源码校验见第一阶段检查记录；这些检查不能替代最终整核证明。

第二阶段新增真实源码清单及 12 项集成测试，`make test` 合计 26 项且要求已获取锁定源码；具体前后对照和结果见第二阶段检查记录。`make source-inventory-check` 只核对，不改写已提交清单。

第三阶段将两项授权补丁应用到临时源码副本，23 个真实 C 场景在四种补丁组合、GCC／Clang、两种优化下共执行 368 次对照；另有 11 项逐机制／故障注入检查和 2 项输入边界检查。第三阶段 `make test` 合计 40 项。C 回归需要 Linux i386 可执行支持，不依赖 32 位 libc；模拟 CPU 边界及未完成义务见第三阶段教学。

第四阶段固定与第三阶段相同的修复后源码身份，清点 94 个定义并建立完整位置证据；新增 22 项正反测试，该阶段全套 62 项。`make source-freeze-check` 实际重放和清点，`make audit` 检查记录身份与覆盖。Coq 源码对应、所有函数证明和整体连接仍未完成。

第五阶段发现原全局内存公理与任意函数式内存表示相冲突；隔离诊断实际复现矛盾，当时信任门禁保持失败。新增 11 个有界内存接口和 3 项解析测试，该阶段全套 65 项，详见历史报告及 [ADR-0002](docs/adr/0002-内存新鲜块必须来自显式边界.md)。

第六阶段将块标识上界封装到内存类型，移除错误公理，迁移两处 `fresh_exist` 及其客户端；新增 20 个原语对应／可满足根，以及构造器和三个指定位置的故障对照。全套 73 项测试通过；109 文件干净构建通过，11 个边界根、20 个表示／操作对应根及 13 个框架根的假设审计与依赖闭包检查通过。实际假设和反向对照结果见[独立修复证据](audit/framework-memory-repair.json)及第六阶段记录。表示决策变更见 [ADR-0003](docs/adr/0003-以内存类型封装块上界.md)，不增加任何 C 函数证明覆盖。

第七阶段完成首个真实函数 `OSVersion` 的受限 AST 检查翻译和局部 Hoare 证明，另有返回执行／内存不变定理。新检查器隔离干净构建全部 112 个文件，独立检查接口类型、假设、`coqchk`，并拒绝错误返回常量与 `False` 前置条件。C 前端及小型生成器仍属于显式信任边界，不声称已证明完整 C 编译器。当时组件与整核连接均为 0。第八阶段进一步建立单函数 `APIRule`，113 文件干净构建和六个根通过，现仅 `OSVersion` 的组件连接为 1、整核连接仍为 0；见[第八阶段报告](audit/STAGE08_API_COMPONENT.md)。

`make build` 在当前目录增量构建；`make check-build` 仅复制活动 Coq 源码和构建入口，在没有参考资料与旧 `.vo` 的一次性目录中完整构建，结束后清理该目录。

`make fetch-source` 会获取锁定提交并验证哈希，也会重建目标 `checkout/` 目录；已有本地源码工作时，应先检查并保留现场。
